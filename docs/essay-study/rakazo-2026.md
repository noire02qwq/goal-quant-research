## 1. Bot 间委派与结果回传（重点问题①）

### 1.1 群内交接 `handoff_to_bot`：consume-once、一次一主

入口工具 `handoff_to_bot` → [`packages/adapters/src/run-tools-messaging.ts:178-191`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-tools-messaging.ts#L178)，实现 [`packages/adapters/src/group-handoff.ts:24`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/group-handoff.ts#L24) `handoffToGroupBot()`。核心语义：

1. **幂等键按"源 Run"收敛，群内一阶段一主**：`deliveryKey = group-handoff:${inGroup ? run.id : (input.deliveryKey ?? run.id)}`（[`group-handoff.ts:90`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/group-handoff.ts#L90)）。它作为 `messages.clientNonce`，命中唯一约束 `(threadId, clientNonce)`（[`group-handoff.ts:91-123`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/group-handoff.ts#L91)）——**同一源 Run 在同一个群里只会产生一条交接消息和一个后续 Run**；重放直接返回已记录的 `botId/runId/eventSeq`，不新建。源码注释写明理由："A group stage has one owner; an outside turn can send several independent tasks."（群外触发的 run 可带 `deliveryKey` 发多个独立任务）。
2. **consume-once 的前置校验**：源 Run 必须仍是 `status = running`（[`group-handoff.ts:65-80`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/group-handoff.ts#L65)，"source run is no longer active" 直接拒绝）；目标必须是当前群成员、源 Bot 也必须还在群里、不能交接给自己（[:132-134](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/group-handoff.ts#L132)）；跨群跳转被拒（"group handoffs must stay in the current group"，[:82-84](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/group-handoff.ts#L82)）。
3. **禁止回弹 + 链长上限**：如果源消息里已有 `handoff` block 且 `fromBotId === targetId`，拒绝（"do not hand this stage back to its sender; post the result in the shared thread instead"，[:144-152](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/group-handoff.ts#L144)）；hop 计数 `nextBotMessageHop` 从源消息读回，超过上限拒绝（[:153-159](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/group-handoff.ts#L153)），上限默认 **6**，可用 `BOT_MESSAGE_MAX_HOPS` 覆盖（[`packages/core/src/bot-messages.ts:13-20`](https://github.com/elie222/rakazo/blob/main/packages/core/src/bot-messages.ts#L13)）。hop 计数函数见 [`bot-messages.ts:39-45`](https://github.com/elie222/rakazo/blob/main/packages/core/src/bot-messages.ts#L39)。
4. **一个事务里原子完成"消息 + Task + Run + 事件"**：先按 id 排序对两个 thread `FOR UPDATE`（锁序与 `message_bot` 对齐，[:62-64](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/group-handoff.ts#L62)），再写 `handoff` block 消息、`task`（`status: queued`）、`run`（`trigger: "follow_up"`、`sourceMessageId` = 交接消息）、`group.handoff` 事件（[:161-213](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/group-handoff.ts#L161)）。事务提交后才做实时通知与 `runContinueJob` 入队；入队失败只记日志，注释："The queued run is durable and the job reconciler will repair a missed immediate wake."（[:225-231](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/group-handoff.ts#L225)）。
5. **交接后源 turn 被强制收口**：成功后给源 Bot 的 note 是 "Handoff recorded. End this turn without narrating it; the next bot owns the next stage."（[:238-240](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/group-handoff.ts#L238)）。落到执行层是硬约束：`ctx.state.handedOff = true`（[`run-tools-messaging.ts:189`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-tools-messaging.ts#L189)），此后**任何工具调用都被拒**——"This stage was handed off. End the turn without more tool calls."（[`run-tools.ts:85-89`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-tools.ts#L85)），最终回复块与文本被置空（[`run-turn.ts:774-788`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-turn.ts#L774) `blocks = []`、`text = ""`；[:725-755](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-turn.ts#L725) 也不再把 working notes 兜底成回复）。**即：交接是"本 turn 立即结束 + 所有权转移"，不是并行协作。**

### 1.2 上下文归属：会话共享、记忆/电脑私有、上下文不随交接搬运

- 群只共享会话：「Each bot keeps its own memory, computer and instructions; the group only shares the conversation.」[`docs/groups.md:11`](https://github.com/elie222/rakazo/blob/main/docs/groups.md#L11)。
- 交接时**只搬 `text` 这一段任务描述**：`handoffBlock = { kind: "handoff", fromBotId, toBotId, text, hop }`（[`group-handoff.ts:161-167`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/group-handoff.ts#L161)），新 Task 的 `prompt` 就是这段 text（[:177-186](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/group-handoff.ts#L177)）。**源 Bot 的对话上下文、内存、工具结果都不迁移**；目标 Bot 从自己视角读群线程（它能看到群里已有消息），并拿到自己那份记忆。
- 身份与所有权靠 prompt 约束（不是靠 schema）：群成员 roster 注入 "You are … This is your identity for the entire turn." + "**A handoff transfers ownership.** … Never bounce a stage between members. One bot owns each stage."（[`packages/core/src/bot-messages.ts:145-166`](https://github.com/elie222/rakazo/blob/main/packages/core/src/bot-messages.ts#L145)，第 162 行）；同时注入 `BOT_DELIBERATION_GUIDANCE` 要求"权衡队友消息而不是照单全收"（[:138-143](https://github.com/elie222/rakazo/blob/main/packages/core/src/bot-messages.ts#L138)）。⚠️ 这些只是提示词层约束，**没有服务端强制的"阶段所有权"字段**；唯一硬约束是 1.1 的 `handedOff` 收口与 hop/回弹检查。

### 1.3 点对点 `message_bot`：可重放投递 + 自动回传 + 失败归属

[`packages/adapters/src/bot-messages.ts:66`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/bot-messages.ts#L66) `messageBot()`：

1. **投递可重放（consume-once）**：注释直说"tool call 可在租约过期后被重新执行，投递必须可重放，否则收件人会被发两次、被唤醒两次"（[:128-130](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/bot-messages.ts#L128)）。`deliveryKey` → `bot-message:<key>` 作为 `clientNonce`，事务内先查 `(threadId, clientNonce)`，查到即返回 `replayed: true`（[:171-179](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/bot-messages.ts#L171)）；并发两个都漏查时输家撞唯一约束，被捕获后按成功重放处理（[:293-305](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/bot-messages.ts#L293)）。重放返回的 note："Already sent to … it was not sent again."（[:131-139](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/bot-messages.ts#L131)）。
2. **同一事务双写 + 唤醒**：发件侧 echo（`bot_message_sent`）、收件侧入站（`bot_message_received`，`role: user`）、Task、Run（`trigger: "bot_message"`、`sourceMessageId` = 入站消息）、双向 `thread.message.created` 事件，全部在一个事务里（[:213-291](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/bot-messages.ts#L213)）；投递是**异步**的，note 明说 "Delivery is async; a reply wakes you later as a new message."（[:318-324](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/bot-messages.ts#L318)）。
3. **结果回传（委派的"收件回执"）**：`returnBotMessageOutcome()`（[:328-400](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/bot-messages.ts#L328)）——被委派 Run 结束时，**除非它已经显式发过 `intent: "result"` 的消息**（只认 `result`，中间的 `status` 不算，[:358-367](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/bot-messages.ts#L358)），否则自动把最终文本回传给发起方；`deliveryKey = auto-outcome:${run.id}`（"每个 Run 一个键，executor 与 reconciler 的 status/result 不会双投"，[:390-392](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/bot-messages.ts#L390)）；成功后写 `runs.botOutcomeReturnedAt`（[:402-411](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/bot-messages.ts#L402)，条件含 `status ∈ {completed,failed,cancelled}` 且该字段为 null，天然幂等）。
4. **失败归属**：委派 Run 失败时回传的是 `Could not complete the delegated request: <error>`，`intent: "status"`（[`run-turn.ts:978-987`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-turn.ts#L978)）；成功走 [:838-846](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-turn.ts#L838)（先回传再发完成通知，注释明确"标 `botOutcomeReturnedAt` 必须在成功回传之后，崩溃或投递失败要留给 reconciler 看见"）；另有"卡死兜底"路径按 result 回传（[:603-614](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-turn.ts#L603)）。
5. **reconciler 兜底（消息丢失不掉单）**：[`job-reconciler.ts:241-306`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/job-reconciler.ts#L241) 扫 `trigger = bot_message AND botOutcomeReturnedAt IS NULL` 且已终态的 Run，重新组装文本（failed → "Could not complete the delegated request: …"；completed 但无文本 → "…completed its turn without a written summary."；只有中期进度 → 按 `status` 回传），用**同一个** `auto-outcome:<runId>` 键投递；未成功只 bump `updatedAt` 让下轮再扫（[:298-304](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/job-reconciler.ts#L298)）。⚠️ 因此"结果回传"是**至少一次投递 + 幂等去重**，不是严格 exactly-once。
6. **链路上限与回执豁免**：bot-to-bot hop 同样上限 6（[`bot-messages.ts:118-124`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/bot-messages.ts#L118)），但"回给最初请求者的 result/status"例外（`returnsToSender`，[:111-117](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/bot-messages.ts#L111)），保证委派链能闭环。收件侧唤醒 prompt 按 `intent` 给不同动作指令，`request` 时明确"你的最终回复会自动回传给对方"（[`core/bot-messages.ts:180-210`](https://github.com/elie222/rakazo/blob/main/packages/core/src/bot-messages.ts#L180)）。

### 1.4 短命子代理 `run_subagent`：turn 内、不可嵌套、共享预算、失败不打断父 turn

实现 [`packages/adapters/src/pi-runtime-subagent.ts:47`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/pi-runtime-subagent.ts#L47) `executeSubagent()`：

- **不落库、不建线程**：直接在父 turn 内 `new Agent(...)`，`history: []`、`messages: []`（[:147-157、256-271](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/pi-runtime-subagent.ts#L147)）；系统提示写明"You run inside the parent bot's turn — you are not a separate bot chat… you cannot talk to the user: report your result back to the parent bot."（[:256-266](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/pi-runtime-subagent.ts#L256)）。产品文档同口径：「Subagents finish with the task; they have no chat or memory of their own.」[`docs/groups.md:35-39`](https://github.com/elie222/rakazo/blob/main/docs/groups.md#L35)。
- **不可嵌套 + 并发闸**：`if (host.depth > 0) return "Subagents cannot nest further."`（[:52](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/pi-runtime-subagent.ts#L52)）；`MAX_PARALLEL_SUBAGENTS = 4`，经 `host.subagentGate` 信号量获取/释放（[:31、53、409](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/pi-runtime-subagent.ts#L31)）。
- **剥离委派类工具**：`childDefs = tools.filter(t => !DELEGATION_TOOL_NAMES.has(t.name))`（[:121](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/pi-runtime-subagent.ts#L121)），即子代理不能再 `message_bot`/`handoff_to_bot`/`spawn_bot`/`run_subagent`。
- **共享父级 tool-call 预算**：`nestedHost.abortTurn` 只在 `pausePending` 或 `toolCallBudget.exceeded` 时中止父 turn（[:141-146](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/pi-runtime-subagent.ts#L141)）；预算耗尽时结果里带预算提示文案（[:375-385](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/pi-runtime-subagent.ts#L375)）。
- **结果 = 一次 tool result，12k 字符截断**：`helperResultText(...)` 截到 `12_000 - label.length`，返回 `Result from your helper "<name>" (not a message from the user):\n…`（[:378-395](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/pi-runtime-subagent.ts#L378)）。
- **失败归属**：模型错误、未知模型、abort、异常统一返回字符串 `Subagent failed: <msg>` 作为 tool result（[:95、117、373、406](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/pi-runtime-subagent.ts#L95)），**不抛异常、不终止父 turn**；UI 上以 `subagent` 卡片状态 `running/completed/failed` 呈现（事件经 `host.queue` 推送，[:61-68、386-393](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/pi-runtime-subagent.ts#L61)）。⚠️ 子代理**没有持久化回执**——父 turn 崩了，子代理的中间产物只剩 UI 卡片事件，这条与本项目"产物/回执"的差距要注意。
- 一个实现细节：`run_subagent` 在 `messagingTools` 里还有一个**空壳 handler**（直接回 `{ ok: true, result: task }`，[`run-tools-messaging.ts:66-72`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-tools-messaging.ts#L66)），真实执行走 pi-runtime 分发——⚠️ 未逐条追踪 `builtin-tool-bridge` 的路由，未验证两条路径何时各走哪条。

### 1.5 `spawn_bot`（创建持久 Bot）与生命周期

## 2. Routines 触发与持久化（重点问题②）

### 2.1 数据模型与触发类型

`Routine` 表 [`packages/db/prisma/schema.prisma:1148-1184`](https://github.com/elie222/rakazo/blob/main/packages/db/prisma/schema.prisma#L1148)：`crons: String[]` + `timezone` + `active` + `lastRunAt`/`nextRunAt`（索引 `[active, nextRunAt]`）+ `watch`/`watchState`（变更触发的规则与上次状态，JSON）+ `accountFailures`（模型账号连续被拒次数，用于拉开排程）+ `modelProvider/modelId/thinkingLevel`（routine 级模型钉住）+ 可选 `threadId`（可以挂在群线程上）。

触发类型（[`docs/routines.md:28-57`](https://github.com/elie222/rakazo/blob/main/docs/routines.md#L28)）：定时（小时/天/工作日/周/月/自定义，**Advanced 接受 cron 表达式**，按 Settings 时区）、变更 watch（5 分钟~1 天轮询文件夹/命令输出/连接器工具，只在有变化时才产生 Run，可选每次都发 "No changes"）、Webhook、Git event、Slack 消息。**watch 与 schedule 互斥**（文档同段）。Webhook/外部消息触发的 Run 走更严的审批（[:55-57](https://github.com/elie222/rakazo/blob/main/docs/routines.md#L55)）。

### 2.2 触发链路：行级认领 + 单例 job + 幂等 nonce

排队唤醒 job [`packages/adapter-kit/src/background-jobs.ts:92-99`](https://github.com/elie222/rakazo/blob/main/packages/adapter-kit/src/background-jobs.ts#L92)：`routineWakeupJob(routineId, scheduledFor)` → `availableAt = scheduledFor`、**`replaceKey = routine:${routineId}`**（同 Routine 同时只有一个 pending 唤醒，重排即覆盖）。

执行 [`packages/adapters/src/run-routines.ts:115`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L115) `wakeRoutine()`，关键顺序：

1. **过期/错位唤醒直接丢**：`routine.nextRunAt?.getTime() !== scheduledAt.getTime()` 就 return（[:121](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L121)）——`scheduledFor` 就是这次 occurrence 的幂等凭据。
2. **未到期的先推后**：`deferFutureRoutine`（[:32-40](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L32)）。
3. **change watch 先跑、不花模型**：`tickRoutineWatch` 只有"有变化"才产生 Run（[:155-165](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L155)）。
4. **行级认领（CAS）**：`tx.routine.updateMany({ where: { id, active: true, nextRunAt: scheduledAt, bot: { archivedAt: null } }, data: { lastRunAt, nextRunAt: nextRunAt, … } })`，`count !== 1` 即没认领到（[:187-202](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L187)）。**认领与推进 `nextRunAt` 在同一事务**，所以"一次 occurrence 只会开一个 Run"是数据库约束出来的，不是靠分布式锁。
5. **Run 的幂等键**：`clientNonce = routine-timer:${routineId}:${scheduledFor}`（`routineTimerNonce`，[`routine-coalescing.ts:5-7`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/routine-coalescing.ts#L5)），配合 `Run @@unique([spaceId, clientNonce])`——重复触发撞唯一键（[:209-252](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L209)）。注释特别说明这是"周期 timer tick 的保留 provenance，手工/事件/retry Run 不用它"。
6. **认领后先入队再发事件**：enqueue 失败只 warn（"committed run and advanced schedule are the durable source of truth"，[:265-280](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L265)）；一次性 cron 触发后 `jobs.cancel(routineJobKey)` 并 `active = false`（[:300-308](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L300)）。

### 2.3 断点恢复 / 漏触发：三层兜底

1. **Run 层**：`Run` 带 `leaseOwner/leaseFence/leaseExpiresAt/checkpoint`（[`schema.prisma:949-953`](https://github.com/elie222/rakazo/blob/main/packages/db/prisma/schema.prisma#L949)），可恢复状态 `RESUMABLE = [queued, waiting_input, waiting_takeover]`（[`run-wakeup.ts:19`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-wakeup.ts#L19)）。⚠️ 我只读了状态集合与调用点，**未逐行读 checkpoint 的具体恢复实现**（`packages/adapters/src/run-wakeup.ts`、`executor.ts` 未精读）。
2. **队列层**：`job-reconciler.ts` 定期把到期 Run 重新 `enqueue(runContinueJob)`，并用 `keepExisting`/`replaceLockedBefore` 避免把正在退避的 job 立即拉起（[`job-reconciler.ts:316-330`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/job-reconciler.ts#L316) 及其注释）。
3. **排程层**：reconciler 分页扫描 `active: true AND nextRunAt <= now + ROUTINE_LOOKAHEAD_MS` 的 Routine，逐个补 `routineWakeupJob`（[`job-reconciler.ts:381-425`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/job-reconciler.ts#L381)），带 `(nextRunAt, id)` 游标跨页续扫。**因此进程重启/队列丢失不会永久漏掉一次定时**——只要 `nextRunAt` 还在且已到期，reconciler 会重新点火。
4. **漏掉的 occurrence 会被折叠**：`findPendingRoutineTick()`（[`routine-coalescing.ts:24-128`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/routine-coalescing.ts#L24)）在持有 Routine 行锁的前提下，找出"完全未开始"的同款 timer Run（判定条件非常严格：`queued`、无 attempt、无 effect、无 steering、无 checkpoint、无 lease、`task.status = queued` 且 prompt 相同……），**保留最早一个、把其余标 `cancelled` + 事件 `reason: "routine_coalesced", supersededByRunId`**；注释强调"绝不折叠事件触发、手工 test、retry 或真正尝试过的 Run"（[:20-23](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/routine-coalescing.ts#L20)），折叠前还按 `leaseFence` 复查（[:93-106](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/routine-coalescing.ts#L93)）。**即：漏触发恢复的语义是"补跑一次、多余的排队 occurrence 合并"，不是逐个补跑。**
5. **迟到会被告知**：`LATE_ROUTINE_RUN_MS = 15 分钟`，超期启动的 timer Run 会在 prompt 里注入"due … / started …"并要求模型按实际时间调整（[`routine-lateness.ts:10-56`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/routine-lateness.ts#L10)），"最近一次到期 occurrence"用二分找（[:34-46](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/routine-lateness.ts#L34)）。

### 2.4 失败退避、重试与脏 cron

- **瞬时模型错误只补一次**：`scheduleRoutineRetry` 12 分钟后重试，且**只有当这个 Run 还没发过消息、没调过工具**才补（防重复副作用，[:46-90](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L46)）；若 30 分钟内就有下一次正常 occurrence，跳过重试（`ROUTINE_RETRY_NEXT_RUN_WINDOW_MS`，[:29-44](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L29)）。
- **重试最多一次且全局唯一**：`Run.retryOfRunId @unique`（[`schema.prisma:958-959`](https://github.com/elie222/rakazo/blob/main/packages/db/prisma/schema.prisma#L958)，注释"The failed routine run this run retries. Unique, so a run is retried at most once."）；`retryRoutineRun`（[:334-478](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L334)）在事务里二次确认"没有更新的同 Routine Run"才建重试，撞唯一键视为"已被别的投递做了"（[:449-453](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L449)）；入队失败会把刚建的 retry Run 删掉，好让队列自己的重试再来一次（[:463-477](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L463)）。
- **账号级失败退避**：`accountFailures` 字段（schema 注释）+ `routine-backoff.ts`（⚠️ 未逐行读，仅看到 `clearRoutineBackoff`/`nextRunAt` 重排的调用点）。
- **脏 cron 兜底**：crons 里没有一个可解析的 cron 时，把已到期那次跑完就 `nextRunAt = null` 并 `active = false`，注释明说"否则 wakeup job 会 crash-loop"（[:166-179](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L166)）。
- **归档 Bot 自动停表**：`wakeRoutine` 发现 Bot 已归档就把 routine 重新置 `active = false`（[:127-134](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-routines.ts#L127)）。

> **小结（②）**：Rakazo 的定时 = `Routine.nextRunAt`（权威）+ graphile 单例 job（加速）+ `(routineId, scheduledFor)`/`clientNonce`（幂等）+ reconciler（补漏）+ 行级 CAS（并发唯一）。**没有"日历类型"**（只有 cron + 时区 + watch），也没有 DAG 依赖。

## 3. Team vs Private Computer：容器暂停/重建后的状态保留（重点问题③）

### 3.1 两层状态：`computers` 行 + AgentHome（home store）

- `Computer` 表 [`schema.prisma:1399-1447`](https://github.com/elie222/rakazo/blob/main/packages/db/prisma/schema.prisma#L1399)：`scope`（`team` / `dedicated`）+ `scopeKey @unique` + `homeKey @unique` + `homeRevision` / `homeRevisionAt` + `restorePending` + `providerRef` + `state`（stopped/booting/running/suspending/suspended/quarantined/error）+ 控制/执行两套租约（`controlLeaseId/ExpiresAt/BotId/RunId/Fence`、`executionRunId/BotId/LeaseExpiresAt/Fence`）+ `runningSince`。
- `restorePending` 的注释是整套机制的钥匙：「The machine at `providerRef` came from a start whose restore never finished, so it holds no full copy of the saved home: **nothing is saved from it, and the next start restores it.**」（[:1414-1416](https://github.com/elie222/rakazo/blob/main/packages/db/prisma/schema.prisma#L1414)）
- **home 是独立于沙箱的持久层**：`AgentHomeStore` 有 `LocalAgentHomeStore`（`DATA_DIR/homes/<botId>`，[`home.ts:29-58`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/home.ts#L29)）和对象存储实现（`homeStorageId/homeStorageKey/homeStorageRevision` + 本地 hydration 缓存）。整体架构图见 [`docs/computer-runtime.md:3-11`](https://github.com/elie222/rakazo/blob/main/docs/computer-runtime.md#L3)：`SandboxProvider workspace <-> AgentHomeStore <-> Rakazo-owned DATA_DIR`。

### 3.2 重建/暂停后怎么恢复：`restoreComputerWorkspace` + `replaces(ref)`

- 启动路径 [`computer-lifecycle.ts:366-481`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-lifecycle.ts#L366)：
  - `replaces(ref) = reclaimStamp !== null || existing.restorePending || ref.fresh === true || !existing.providerRef || providerRef 变了 || kind 变了`（[:366-372](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-lifecycle.ts#L366)）——**只有"这是一台新机器/换过机器/上次恢复没做完"才需要从 home 灌数据**；纯 reconnect（同一 providerRef 还活着）不灌。
  - `markReplacement()` 一旦 provider 返回替换机就立刻把 `restorePending = true` 写库（CAS on `state: booting + updatedAt + previousRef`，[:413-432](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-lifecycle.ts#L413)），**即使后续失败，标记也先落地**——注释："a start that fails or dies after that point leaves the row marked"。
  - `if (replacement) await restoreComputerWorkspace(...)`（[:476-481](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-lifecycle.ts#L476)），恢复成功、目录布局就绪、活跃控制租约核对之后，才在同一个 CAS 里 `state: running` + `restorePending: false`（[:500-527](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-lifecycle.ts#L500)）。
  - 失败回滚：新建的机器 rollback 销毁，安全 stop 无法完成则进 `quarantined`，否则 `error`；`restorePending` 按 `replaces()` 重新写回（[:563-590](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-lifecycle.ts#L563)）。
- `restoreComputerWorkspace` 本体 [`computer-workspace.ts:51-66`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-workspace.ts#L51)：
  - **Docker 直接挂载服务器 home，无需拷贝**：`mountsServerHome(kind) { return kind === "docker" }`（[:31-33](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-workspace.ts#L31)）+ `homeIsMounted()` 短路（[:37-49](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-workspace.ts#L37)）——**容器重建后状态天然还在，因为文件根本不在容器里**。
  - 其余 provider：`await sandbox.importWorkspace(computer, home.exportHome(homeKey, …))`（[:65](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-workspace.ts#L65)），即从服务端 home 灌回新容器。
  - 对象存储型 home 在 provision 前先 `hydrate`（把存储里的修订拉到本地缓存），并 `forgetMissingCache` 防止"缓存目录被删后被当成空目录"（[`computer-lifecycle.ts:387-401`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-lifecycle.ts#L387)）；宿主机中途变化会抛 "Computer host changed while it was starting"（[:475-477](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-lifecycle.ts#L475)）。

### 3.3 保存（checkpoint）的触发点与策略

- **保存 = 导出到 home 并记 revision**：`checkpointAndRecordComputerWorkspace` 写 `homeRevision/homeRevisionAt`（[`computer-workspace.ts:447-470`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-workspace.ts#L447)）。
- **触发点 1 — Run 结束**：`checkpointRunComputerWorkspace`（[:403-445](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-workspace.ts#L403)）。**Team + 远程 provider 必须先抢 `state: "running" → "suspending"` 的 CAS**，条件里要求"没有任何别人未过期的 execution lease、且控制权不是别人的"——注释："Remote exports quiesce browsers, so a run must not checkpoint while peers are driving them."（远程导出要静默浏览器，不能在别人操作时导出）；抢不到就交给"最后一个收尾的 Run 或已排定的 idle job"。Docker 或非 team 直接保存（挂载/独占，无需 quiesce）。
- **触发点 2 — 空闲休眠**：`computer-idle.ts` 先 CAS 到 `suspending` 再 checkpoint、再 `computer.sleep` job（[:520-560](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-idle.ts#L520)）；对"provider 已经停了且自上次保存没变过"的机器走 `suspendStoppedComputer` 免启动保存（[:700-730](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-idle.ts#L700)），理由写在注释里：为了省一次启动，而**启动正是 restore 可能失败的地方**。
- **触发点 3 — 显式停机**：`checkpointAndStopComputer`（[:476-501](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-workspace.ts#L476)）——先保存再 stop；**损坏的机器不保存直接 stop 并 `discardUnsaved`**，保留 provider 上一份好副本（注释："Nothing on a damaged computer can be read"）；其他保存失败会先抛错、不 stop。
- **保存策略**：上限 5 GiB / 100 万文件，超限"继续运行但不保存"（[`workspace-save-policy.ts:4-7`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/workspace-save-policy.ts#L4)）；跳过 `.cache/.npm/node_modules/.venv/__pycache__/.next/.turbo`、core dump、日志，以及浏览器 profile 下的 Cache/组件缓存/锁文件（[:9-68](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/workspace-save-policy.ts#L9)）。⚠️ 我没读 `exportHome` 的并发/原子提交细节（`home.ts` 只看了前 60 行）。

### 3.4 损坏与自愈

- `prepare()` 抛 `isSandboxDamagedError` 且抢到 `autoRecoveredAt` 一次性额度 → stop（`discardUnsaved: true`）→ 再 provision → 再 prepare；日志 `computer.auto_recover`（step: stop/recovered/failed），注释："Stopping keeps the provider's last good copy … starting again resumes it, **or replaces it from the saved workspace when that is newer**"（[`computer-lifecycle.ts:424-456`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-lifecycle.ts#L424)）。
- 用户侧四个动作见 [`docs/computer.md:45-51`](https://github.com/elie222/rakazo/blob/main/docs/computer.md#L45)：Stop / Update（保存 workspace 并装新软件）/ Recover（重建一台坏掉的）/ Reset（回到上次保存的 workspace，**未保存的丢失**）。

### 3.5 Team vs Private 的实际差异

- 产品语义 [`docs/computer.md:31-38`](https://github.com/elie222/rakazo/blob/main/docs/computer.md#L31)：**Team（默认）**= space 内 Bot 共享一台机器、共享文件与已装工具，但**每 Bot 独立屏幕与浏览器 profile**，"sites you sign in to are carried over to the other bots"（登录态跨 Bot 共享）；**Private**= 独占整机，用于文件/登录不能共享的场景。
- 实现差异：`scope = "team"` 时 `scopeKey` 按 space+user、多个 Bot 共用一台 `Computer`（`bot.computerId` 指向它）；`scope = "dedicated"` 时 `scopeKey` 含 `botId`（`computerScopeKey({mode:"dedicated", spaceId, userId, botId})`，[`child-bots.ts:299-307`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/child-bots.ts#L299)）。**两者的 home/restore 机制是同一套**（都走 `homeKey` + `restoreComputerWorkspace`）。
- Team 的隔离边界是**目录约定不是安全边界**：「These folders organize work but are not security boundaries: every Team bot can access the full Team workspace.」[`docs/computer-runtime.md:13`](https://github.com/elie222/rakazo/blob/main/docs/computer-runtime.md#L13)；每 Bot 在 `bots/<bot-id>/`，共享工作放 `shared/`；每 Bot 的浏览器 profile 是 `.browser-profiles/chromium-bot-<32hex>`，**永不从别的 Bot 克隆、合并，释放桌面也不删**（同文档；profile 名校验见 [`computer-workspace.ts:75-80`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-workspace.ts#L75)、删除的 symlink 防护见 [`child-bots.ts:846-875`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/child-bots.ts#L846)）。
- 删除 Bot 时：Team 上的目录/profile 若机器没在跑，就**留到下次开机再清**（`removeTeamBotWorkspace` 注释 "A Team Computer that is not running removes the folder when it next boots."，[:785-815](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/child-bots.ts#L785)）；正在跑则给 10 秒预算清理（`LIVE_CLEANUP_BUDGET_MS`，[:704-705](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/child-bots.ts#L704)）。

> ⚠️ **未验证**：以上全部来自静态阅读。没有实际起容器、没有复现"暂停→重建→状态还在"、没有验证 E2B/Daytona 等远程 provider 的 export/import 实际耗时与失败率；`docs/computer-runtime.md` 中"整机空闲关机保留 workspace""成功 Run 结束保留屏幕与浏览器"等运行期行为我只读了文档、未核对到每一处实现。

## 4. 角色分工与人工接管的权限边界（重点问题④）

### 4.1 没有 `assigned_role`：分工靠 roster + mention + prompt + handoff

- **全仓库 grep `assigned_role` 零命中**（含 docs、schema、tests）——⚠️ **Rakazo 不存在 schema 化的角色字段**；本项目 §12.2 W3 设想的 `goal_plan_task.assigned_role` 在 Rakazo 没有直接对应物，只能类比到"Bot 的 description + 群 roster 注入"。
- 谁应答：无 mention → **第一个成员**回答；`@Name`/`@everyone` 点名（[`docs/groups.md:13-17`](https://github.com/elie222/rakazo/blob/main/docs/groups.md#L13)）。实现 `resolveGroupTargetBotIds`：`everyone` 全选，否则按被 @ 的成员名匹配，**一个都没匹配到就回落到 `members[0]`**（[`packages/core/src/group-mentions.ts:44-77`](https://github.com/elie222/rakazo/blob/main/packages/core/src/group-mentions.ts#L44)）；另外还有从用户自然语言里猜交接对象的 `inferHandoffTargetBotId`（"hand it to @X" / "X take"，[:79-101](https://github.com/elie222/rakazo/blob/main/packages/core/src/group-mentions.ts#L79)）。
- 选人依据 = 成员 `description`（"How other bots see it"，[`docs/groups.md:28-33`](https://github.com/elie222/rakazo/blob/main/docs/groups.md#L28)）注入 roster；跨 space 私聊默认关闭，需在 Bot 的 Permissions 里打开 "Allow cross-space bot communication"。
- 交接本身仍受审批门约束：`create_group`/`update_group` 在**必须审批**集合里（[`core/action-approval.ts:30-45`](https://github.com/elie222/rakazo/blob/main/packages/core/src/action-approval.ts#L30)），而 `handoff_to_bot`/`message_bot` **不在豁免集合**（豁免集合见 [:5-27](https://github.com/elie222/rakazo/blob/main/packages/core/src/action-approval.ts#L5)，⚠️ 我未读 `run-tool-gate.ts`，具体按模式（Ask/Auto/Never）如何落到这两个工具**未验证**）。

### 4.2 Take control：独占控制租约（不是"暂停 agent"这么简单）

- 模型侧 `request_takeover` 工具是**无操作**的 `{ ok: true }`（[`run-tools-messaging.ts:63-65`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-tools-messaging.ts#L63)），真正语义由 run 状态机与 computer 租约承担。
- **控制租约字段**在 `Computer` 行：`controlHolder`（`none`/`user`/…）、`controlLeaseId`、`controlLeaseExpiresAt`、`controlBotId`、`controlRunId`、`controlFence`（[`schema.prisma:1425-1430`](https://github.com/elie222/rakazo/blob/main/packages/db/prisma/schema.prisma#L1425)）。
- **TTL 默认 15 分钟**，`COMPUTER_TAKEOVER_TTL_MS` 可改（[`computer-control.ts:9-14`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-control.ts#L9)）；到期由 `computer.control-expire:<computerId>:<leaseId>` job 触发 `expireComputerControl()`（[:178-285](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-control.ts#L178)）：先 CAS `controlHolder → none` **再**撤 provider 屏幕控制（注释："Deny API input before touching the provider"），撤失败保留 lease id 交给 job 重试或 reconciler（reconciler 也扫到期控制租约，[`job-reconciler.ts:386-424`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/job-reconciler.ts#L386)），最后 `finalizeComputerControlRelease` 并给挂着的 Run 排 `runContinueJob`（[:274-284](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-control.ts#L274)）。孤儿控制（无 `controlBotId`）单独清理（[:205-242](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/computer-control.ts#L205)）。
- **接管期间 agent 还能做什么**：屏幕类工具被门禁，文件与 shell 仍可用——`DESKTOP_HELD_FOR_TAKEOVER_MESSAGE = "The user has the screen. File and shell tools still work."`（[`takeover-resume.ts:8-10`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/takeover-resume.ts#L8)）。文档侧的拒绝条件：Team Bot 在**持有活跃执行租约或活跃 Run**时取控制会被 HTTP 409 拒（"Stop the bot first"），除非该 Run 已是 `waiting_takeover`（[`docs/computer-runtime.md` "Take control" 段](https://github.com/elie222/rakazo/blob/main/docs/computer-runtime.md)）。
- **释放后的续跑**：`takeoverResumeFromRelease()` 给两种 checkpoint 提示——`takeover`（"用户把屏幕交回来了，用当前屏幕状态继续，别为这一步再申请接管"）与 `takeover-skipped`（"接管没完成就结束了，**不要假设那步做过了**，除非仍然过不去才再申请"）（[`takeover-resume.ts:18-34`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/takeover-resume.ts#L18)）；并发释放靠 `continueRunClaimFence` 的 `(status, checkpoint)` 复查，防止被别人抢走（[:57-73](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/takeover-resume.ts#L57)）。**这是"挂起 Run → 人工介入 → 同一 Run 继续"的完整样板。**

### 4.3 `waiting_takeover` 的等待、提醒与过期

- 状态机：`running → waiting_takeover`，`waiting_takeover → [queued, cancelled]`（[`packages/core/src/run-state.ts:53-55`](https://github.com/elie222/rakazo/blob/main/packages/core/src/run-state.ts#L53)）。
- **无人理会 30 分钟自动取消**：`TAKEOVER_WAIT_EXPIRE_AFTER_MS = 30 * 60_000`，注释理由是"它占着这台 Bot 的电脑，后面这个 Bot 的工作会排在它后面"（[`stuck-work.ts:11-13`](https://github.com/elie222/rakazo/blob/main/packages/core/src/stuck-work.ts#L11)）；普通 queued/waiting_input 则 4 小时提醒、24 小时取消（[:6-9](https://github.com/elie222/rakazo/blob/main/packages/core/src/stuck-work.ts#L6)）。取消会在线程里留状态行 "Stopped. This was still waiting for you on the screen."（[:68-73](https://github.com/elie222/rakazo/blob/main/packages/core/src/stuck-work.ts#L68)）。
- 非计费 provider 上，请求接管后**保持整机清醒 30 分钟**，之后机器挂起、Run 继续等（[`docs/computer-runtime.md` "Take control" 段](https://github.com/elie222/rakazo/blob/main/docs/computer-runtime.md)）。
- 卡死 Run 的兜底回传见 §1.3 第 5 点与 [`stuck-work.ts:96-124`](https://github.com/elie222/rakazo/blob/main/packages/core/src/stuck-work.ts#L96)。

### 4.4 用户本机（"use your own computer"）的可达性边界

`userComputerOwner()`（[`run-tools-user-computer.ts:44-56`](https://github.com/elie222/rakazo/blob/main/packages/adapters/src/run-tools-user-computer.ts#L44)）——**只有 `trigger ∈ {user, follow_up}`、来源角色是 user、且 run 的 userId 等于 bot 的 userId 时**，这个 Run 才拿得到用户的桌面；注释逐条点名：**routines、webhooks、消息渠道、别的 Bot、别人发的消息，一律拿不到任何人的本机**。产品侧还要 Settings 打开 "Let bots use this computer"，且**每个 space 首次命令、首次用每个 app 都要问一次**，Block 规则可直接拒绝（[`docs/computer.md:57-65`](https://github.com/elie222/rakazo/blob/main/docs/computer.md#L57)）。

### 4.5 审批模式与工具分级（Take control 之外的"人工门"）

- 三模式 Ask / Auto / Never ask + Allow/Block 名单 + per-space 覆盖（[`docs/approvals.md`](https://github.com/elie222/rakazo/blob/main/docs/approvals.md)）。Auto 模式由一个独立的 **approval model** 判定"是否在任务内、是否不可逆且用户没要求"。
- **"Always ask" 集合**（Auto/Ask 下不因 Always allow 而跳过）：改 Bot 指令/模型、建 space、"外部文本可能 steering"的 webhook Run、watch 命令的 routine、外部内容点名的站点（同文档 "What always asks" 段）。⚠️ 这条我只读了文档，未在代码里逐条定位。
- 代码里的三档集合（[`core/action-approval.ts:5-70`](https://github.com/elie222/rakazo/blob/main/packages/core/src/action-approval.ts#L5)）：豁免（读类 + `shell/write_file/computer_act/run_subagent/spawn_bot/schedule_*` 等）、必审批（`delete_bot/archive_bot/user_computer_*`/`create_group/update_group/create_child_routine/feedback` 等）、显式审批（`set_child_instructions/set_child_bot_model/create_space/respond_agent_connection`）。连接器工具用**名字启发式**判定：`get/list/search/find/read` 视为读、`send/post/delete/…` 视为写，`readOnly` 声明为 false 一律要审批，"declared read never relaxes the name check"（[:74-88](https://github.com/elie222/rakazo/blob/main/packages/core/src/action-approval.ts#L74)）。
- 无人值守（routine 等）另有一份 `UNATTENDED_SAFE_BUILTIN_TOOLS` 白名单（[:46-62](https://github.com/elie222/rakazo/blob/main/packages/core/src/action-approval.ts#L46)），包含 `run_subagent`、`request_takeover`、只读工具。
- 最近一次提交本身就是一条边界演进："Ask before a click that pays on a website"（`ade7100`），即**付款类点击**也被拉进必须问的范畴。
