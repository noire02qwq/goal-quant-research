## 摘要

大语言模型（LLM）正越来越多地以团队形式部署，然而现有协调方法往往处于两个极端。高度结构化的方法依赖于先验指定的固定角色、流水线或任务分解；与之相对，完全非结构化的团队虽具备适应性与探索能力，却饱受低效之苦，例如错误传播、智能体间冲突，以及以时间、Token 或文件操作衡量的资源浪费。

我们提出面向任务演化的语言智能体团队（Language Agent Teams for Task Evolution，LATTE）——一个受分布式系统启发、用于协调 LLM 团队的框架；在分布式系统中，处理器必须在部分可观测与通信受限的条件下运行。在 LATTE 中，一组智能体协同构建并维护一张共享的、不断演化的协调图，其中编码了子任务依赖关系、各智能体的分配情况以及子任务进展的当前状态。该协议在保持一致性的同时，赋予智能体动态分配工作、调整协调方式并发现新任务的能力。在多个协作任务与多种基础模型上，我们展示了 LATTE 如何降低 Token 消耗、墙钟时间、通信量与协调失败（例如文件冲突和冗余输出），同时达到或超越包括 MetaGPT、去中心化团队、自上而下的 Leader-Worker 层级与静态分解在内的标准设计的准确率。

## 1 引言

协作能够帮助群体成就非凡的事业 [50, 20]，但也伴随着可观的协调成本。在软件开发等复杂领域，把工作分摊给一个团队甚至可能胜过最出色的程序员 [9, 54]，但同样要付出大量额外开销 [6]。当一位协作者修改了其他人所依赖的核心函数时会发生什么？相互依赖的任务应按什么顺序执行？当团队成员在速度或可靠性上存在差异时，工作该如何分配？团队又该如何防止单点错误在整个系统中层层扩散？在实践中，这些问题屡见不鲜，包括并发编辑冲突 [15]、超线性通信开销 [6]、依赖错位 [7, 32]、分布式带来的延迟 [21]、生产力差异 [45]，以及拖尾者（stragglers）[10]。协作可以显著放大能力，但前提是协调被有效管理。

近期工作表明，通过把任务、角色与上下文分布到多个智能体上，LLM 团队能够提升准确率与问题求解能力 [2, 5, 29, 49, 56, 61]，并展现出涌现式协调 [38]。尽管取得了这些成功，LLM 团队的设计仍从根本上受限。现代 LLM 的强大很大程度上源于其灵活适应新上下文与新任务的能力 [13]。相比之下，大多数现有 LLM 团队架构施加了僵化的协调结构，在执行前指定固定角色或预先规定任务分解 [22, 40]。我们认为，以这种方式约束 LLM 团队会限制其动态适应能力 [42]，并引入脆弱性——Lead 的失败或幻觉会向下游传播 [24]。

图1：LATTE。大多数现有 LLM 团队设计要么高度结构化（a. 流水线系统；b. Leader-Worker 层级），要么是非结构化的（c. 去中心化团队）。(d) LATTE 为团队提供了一张由它们共同维护和调整的动态协调图。例如，在一项数据分析任务中，Lead 初始化 G0 并把 Worker 1 分配去执行预处理。随着 Worker 1 了解数据，它在前沿（DISCOVER）上派生出并行子任务，Lead 随后将这些子任务 ASSIGN 给 Worker 2 和 Worker 3。随着这一过程继续，Lead 可以 RELEASE 拖尾者并 CLOSE 已完成的子任务，而 Worker 则主动 CLAIM 前沿任务以避免空闲。这张共享的图在保留并行性的同时，将协调决策串行化。（原文第2页）

非结构化或去中心化的 LLM 团队更加灵活 [31]，但也面临自身的挑战。在缺乏协调脚手架的情况下，智能体经常互相覆盖彼此的产出、产生不一致或错误的输出，并错误地报告任务完成 [35, 46]。当任务必须顺序执行时，这些问题会恶化：此时向团队增加智能体会导致过度沟通与性能下降 [26, 35]。自我协调的团队往往无法胜过单个专家模型 [37]，也无法克服个别智能体传播的失败 [3]。这表明 LLM 团队的设计中存在一种根本张力：需要结构来改善协调与智能体间的一致性，但过度规定又会抑制让 LLM 强大的适应性。

为化解这一张力，我们提出 LATTE（Language Agent Teams for Task Evolution，面向任务演化的语言智能体团队），一个正式的编排框架，使 LLM 团队能够在执行过程中显式地表示并调整自身的协调方式（图1）。我们从分布式系统中汲取灵感——在那里，协议使任务得以在信息不完整与动态条件下被可靠调度 [1, 34, 55]——在 LATTE 框架内运作的智能体共同构建并维护一张共享的、不断演化的协调任务图。图中，节点表示被分配给智能体的子任务，边编码子任务之间的完成依赖关系，一组图变更算子则允许团队随着执行推进重构协调方式。这张图作为任务分解、进展、角色与活跃投入的演化记录。每个智能体基于局部上下文对图提出更新，由单一智能体进行审核与合并。这种分工减少了层级设计中出现的瓶颈与单点故障，提供了监控拖尾者的显式机制，并通过自然的串行化防止局部视角分歧或不一致。由此得到的框架在不牺牲涌现式、上下文敏感的适应能力的前提下，保持了连贯性与效率。我们的贡献如下：

1. 面向 LLM 团队的正式编排框架（基于动态任务图）：我们定义了一组图变更算子（Discover、Assign、Claim、Complete、Release、Close 与 Verify），并给出显式的前置条件、后置条件与不变式保持保证，最终形成一个严格的多智能体 LLM 协调执行协议。我们证明图结构能够诱导出理想的运行时性质，例如通过前沿节点（frontier nodes）实现最大并行度。

2. 混合式中心化–去中心化模型：我们引入一个两层协调模型，其中工作智能体（Worker）对图提出结构性修改建议，由 Lead 编排者接受或拒绝，在保持全局一致性的同时实现局部适应性。这一分工建立在对任务分解的概率化解释之上。

3. LLM 团队可解释性：LATTE 把任务执行过程中的协调外化，提供了解读与审计团队行为的途径。我们的评估给出了一套协调指标（覆盖次数、并发冲突、浪费的字符数、空闲轮次与拖尾尾延迟），弥补了多智能体 LLM 系统基准测评中的一个系统性缺口。

4. 实证验证：LATTE 持续降低 Token 消耗、墙钟时间、智能体间消息数、文件覆盖次数、一致性冲突与总输出量，同时取得比其他结构以及广泛使用的 LLM 团队实现更高的准确率。

这些结果共同表明，由智能体自身维护的显式协调结构，是通往同时更高效、更可解释、更具适应性的 LLM 团队的一条可行路径。

## 2 相关工作

关于 LLM 团队协调的已有工作集中在三种模式上。MetaGPT 和 ChatDev 等静态系统在执行开始前分配固定的功能角色与任务结构 [22, 40]。虽然这简化了调度，但当新的依赖关系出现或工作负载在执行中途变化时，静态分配可能难以应对。HuggingGPT 及近期元智能体（meta-agent）方法等层级式或中心化框架使用一个 Lead 智能体来规划、分派并综合下属的工作 [47, 28]。中心化能够强制一致性，但会产生瓶颈与单点故障，这在 LLM 团队中尤为严重，因为 Lead 可能产生幻觉、崩溃或未能汇总分布式的进展 [46]。

去中心化团队让智能体自主运作，从而避免瓶颈，提升多样性，并把长上下文分布到多个智能体 [14, 29]。然而，只依据任务状态局部视图运作的智能体可能产生冲突或冗余的输出，而且扩大智能体数量可能降低性能，尤其在需要顺序推理、专家智能体分配或一致性的任务中 [26, 37, 35]。

来自分布式计算的任务图（task graphs）为任务分解与分配提供了自然的改进：节点表示任务，边编码先后约束，调度器高效地把工作分配到各个处理器 [51, 36]。HEFT 等经典调度器在执行前计算全局优化的分配；动态变体与 NABBIT 等工作窃取（work-stealing）方法在任务可用时在线分配 [25, 1]。然而，这些系统假设任务定义明确且具备显式的控制机制。把任务图扩展到 LLM 团队，需要支持能够以自然语言自主发现、修改并认领任务的智能体。据我们所知，LATTE 是首个弥合这一鸿沟的框架：LLM 团队在执行过程中共同构建、维护并修订一张共享任务图，作为在线的、动态的协调结构。我们在附录 A1 中给出相关工作的扩展讨论。

## 3 LATTE：面向任务演化的语言智能体团队

针对既有架构的局限，我们为结构化的 LLM 团队执行框架确立四项关键设计要求（desiderata）。

D1. 混合协调：为避免完全中心化系统的瓶颈与完全去中心化系统的不一致，协调应当是混合的。影响共享状态的决策（例如图更新或工件）必须由中心居中调节，而任务执行应当见机行事，以允许并行推进。

D2. 自适应伸缩：框架应高效部署智能体，依据当前工作负载动态激活智能体，并在依赖关系允许时最大化并行度。

D3. 容错与监控：由于智能体可能停滞、产生幻觉或输出空值，系统必须支持主动监控与动态再分配，以便检测并重新分配来自无响应智能体的任务。系统还应支持审计，使智能体能够主动识别并标记出需要额外质量控制的高不确定性输出。

D4. 上下文作用域限定：为防止记忆过载与混淆，每个智能体应获得作用域受限的上下文。Worker 只应看到自己的局部子任务，而 Lead 的视野应限于协调图而非完整的执行历史。

### 3.1 动态协调图

LATTE 团队中的智能体集合 A = {ℓ} ∪ W 属于两种类型之一：负责维护协调结构的 Lead ℓ，以及负责执行所分配子任务的一组 Worker W。协调通过一张共享的动态协调图进行，该图在执行过程中显式跟踪任务进展、智能体分配与共享状态。

定义 1（动态协调图）。第 t ∈ {1, …, T} 轮的动态协调图 Gt 是一个有向无环图 Gt = (Vt, Et, λt)。其中 Vt 是有限的节点集合，每个节点对应一个子任务；Et ⊆ Vt × Vt 是子任务之间的依赖边集合，满足 (u, v) ∈ Et 意味着子任务 v 必须等到 u 完成之后才能开始；λt : Vt → (A ∪ {⊥}) × S 为每个节点分配一个智能体和一个状态，其中 ⊥ 表示未分配，S := {pending, assigned, in_progress, done, verified}。

协调图的一项优势在于它编码了任务执行过程中的并行机会。

定义 2（前沿）。第 t 轮的前沿 Ft ⊆ Vt 是依赖均已满足的待处理节点集合：Ft := {v ∈ Vt | status(v) = pending 且 ∀(u, v) ∈ Et, status(u) = done}。

Ft 决定了哪些子任务可以立即执行，因此对应于在 t 时刻能够并行推进的 Worker 数量。

### 3.2 图变更算子

Lead 与 Worker 之间信息的不对称直接决定了算子权限。Worker wi 基于其子任务 v 的局部轨迹 dt(i) 进行推理，拥有足够的信息提出局部更改，例如发现执行过程中遇到的新子任务（DISCOVER）以及认证其子任务的完成（COMPLETE）。它缺乏 v 之外的视野，因而无法安全、全面地评估那些对整图有影响的提案，例如强制完成其无法观察到下游影响的节点（CLOSE）。Lead ℓ 保持对 Gt 的全局可见性，并独占控制对整图有影响的算子，例如重新分配停滞工作的 RELEASE 与拦截错误的 VERIFY。

与其他算子不同，任务获取无需中心化。与其要求 ℓ 为每个子任务执行 ASSIGN，空闲的 Worker 可以通过 CLAIM(v) 直接从 v ∈ Ft 主动认领可用工作。这呼应了分布式计算中的工作窃取（work-stealing）或自调度原则 [39, 1]：快速处理器从共享队列认领就绪任务，而不是等待中央调度器，从而减少开销、改善墙钟时间。对同一 v ∈ Ft 的并发认领由编排者裁决，在不中心化获取过程的同时保持串行化。

因此，LATTE 提供一组图变更算子，具有显式的前置条件、后置条件与不变式保持保证（表1，附录 A3）。与既往多智能体 LLM 框架中协调契约隐含在角色提示里不同，LATTE 让这些契约对每个算子都显式且可验证。

| 算子 | 调用者 | 输出 |
| --- | --- | --- |
| DISCOVER(v, deps) | ℓ, w | 添加带有依赖 deps 的待处理节点 v |
| ASSIGN(v, w) | ℓ | 把待处理的 v 分配给 Worker w |
| CLAIM(v) | w | Worker w 认领节点 v |
| COMPLETE(v) | w | 把 v 标记为其 w 已完成 |
| RELEASE(v) | ℓ | 把 v 退回为 pending |
| CLOSE(v) | ℓ | 强制完成 v |
| VERIFY(v) | ℓ | 为 v 发起验证 |

表1：图变更算子。

DAG 不变式。所有算子都保持 Gt 上的 DAG 不变式。DISCOVER 是唯一向 Gt 添加边的算子，其前置条件 v ∉ Vt 保证不会产生自环。此外，要求 deps ⊆ Vt 且所得图保持无环，确保不会引入环。其余所有算子只修改 λt，保持 (Vt, Et) 不变。

概率化动机。这种 Leader-Worker 分工还可以通过概率视角来解读：把任务图的动态演化看作一个近似后验推断问题。为实现上下文作用域限定，LATTE 把图更新过程解耦为提议（由 Worker 执行）与评估（由 Lead 执行），这在概念上植根于 Metropolis-Hastings 等采样过程。该动机的更多细节见附录 A2。

### 3.3 LATTE 执行

完整执行协议见 A4.5 节的算法 1。LATTE 分两个阶段进行：先是一个初步规划阶段，随后是围绕动态演化协调图的迭代执行循环。在规划阶段，ℓ 获得任务描述，并通过 DISCOVER 操作提出问题的初始分解来初始化 G0。在执行阶段，每一轮 t = 1, …, T，智能体被有选择地派发到当前图 Gt 上运作。每轮包含五个步骤：（1）心跳监控（即周期性存活检查），向 ℓ 标记拖尾者或停滞的 Worker；（2）前沿识别，计算可用任务队列 Ft；（3）派发，对象包括仍在进行中的智能体、被分配到新前沿任务的智能体，以及必要时的 ℓ；（4）所有被选中智能体的并行执行；（5）终止，返回所有任务输出与 Gt。

### 3.4 协调性质

LATTE 协议为 LLM 团队配备了满足第 3.1 节引入的四项设计要求（D1–D4）的结构性工具。

D1. 混合协调：为在一致性与适应性之间取得平衡，Lead ℓ 独占控制对整图有影响的算子（ASSIGN、VERIFY、CLOSE），而 Worker w 在其局部作用域内自主运作。关键的是，LATTE 实现了自调度：空闲 Worker 可以对任意 v ∈ Ft 调用 CLAIM(v)，实现机会式执行，从而降低 Lead 开销、改善墙钟时间 [39]。对 Gt 的所有结构性更新都被串行化，防止竞态条件与共享状态的不一致。

D2. 自适应伸缩：在每一轮 t，LATTE 派发的 Worker 数量等于 min(|Ft|, |W|)。这确保了在给定 Gt 下的最大并行度：任何合法协议都无法在 t 时刻派发更多 Worker 而不违反依赖约束。只有存在可用工作时才激活智能体，消除了空闲计算。

D3. 容错与监控：心跳机制会标记那些已被分配但连续 H 轮保持不活跃的 Worker，在其阻塞进展之前把潜在停滞暴露给 ℓ。检测到拖尾者之后，ℓ 可以调用 RELEASE(v) 把任务退回待处理状态，使其可以被立即重新分配或自我认领。此外，LATTE 并不强制对每个子任务进行昂贵的审查，而是支持涌现式验证：VERIFY 算子由 ℓ 有选择地在被判定为高风险或高不确定性的节点上调用，这使得质量控制的严格程度能够随任务图的复杂度动态伸缩。

D4. 上下文作用域限定：为缓解上下文累积与 Token 耗尽，Worker 只接收其所分配子任务及其直接前驱的描述。Lead 接收 Gt 与智能体消息，但不摄入各个 Worker 的完整执行轨迹。这些约束限定了每个智能体需要关注的上下文范围，减少由无关信息引起的推理错误。

## 4 实验

我们在三个新设计的协作领域中评估 LATTE 与若干现有多智能体框架的表现：探索性数据分析、调试与代码生成。选择这些领域是为了对不同的协调性质（并行性、一致性与适应性）进行压力测试。实验设置与提示设计见附录 A4 与 A5，完整的任务规格与评估标准见附录 A6。每个任务奖励上述协调性质的不同组合：

图2：效率–准确率权衡。A) LATTE 比其他框架更高效。我们度量期望成本（按试验完成率加权的总 Token 数或墙钟时间），以纳入团队未能终止的运行。B) 在准确率对 Token 成本的 Pareto 前沿上，LATTE 以更低的 Token 消耗（跨任务归一化）取得更高的任务成功率。（原文第6页）

任务1：探索性数据分析。智能体在一个不透明的数据集上进行探索性分析，需要预处理、分析、可视化与对发现的综合。正确性由一套私有测试套件评估，检查智能体是否正确识别了植入的数据属性。

任务2：调试。智能体针对一个测试套件调试既有的代码仓库，需要迭代地运行测试并修改代码。该任务同时奖励并行性（相互独立的缺陷可以同时诊断）与一致性（某些函数只有在依赖被修复之后才能验证）。我们在一个信号处理库中植入了多个缺陷，成功要求团队通过给定套件中的全部测试。

任务3：库扩展。智能体扩展一个 Python 文本处理库：补全两个既有类，并基于桩（stub）构建六个新模块。该任务具有天然的顺序依赖、可并行的模块以及一个最终的集成步骤。正确性在完成之后由一套私有测试套件评估。与任务1和任务2不同，所需函数是事先完全已知的。

我们将 LATTE 的性能与四种基线团队结构进行比较。我们测试 Leader-Worker 层级（由单个 Lead 综合并把任务分派给四个 Worker）、MetaGPT [22]（基于流水线的 LLM 团队的代表，包含不同角色：Product Manager、Architect、Project Manager、Engineer、QA Engineer）、由 5 个对等智能体组成的去中心化团队，以及静态任务图消融（Lead 基于其先验 G0 初始化分配，规划之后智能体不能更新图）。我们将团队规模保持为 N = 5，以便与 MetaGPT 对标。对每种团队结构，我们测试两个前沿基础模型：Claude Sonnet 4-6（Anthropic；claude-sonnet-4-6）与 GPT-5.2（OpenAI；gpt-5.2）。每个条件运行 10 次试验，共 300 次试验（5 条件 × 2 模型 × 3 任务 × 10 重复）。完整实现细节见附录 A4 与 A5。

### 5.2 LLM 团队通过 LATTE 成功利用动态协调图

图3表明，LLM 团队成功利用了 LATTE 协议的全部表达力来管理任务复杂性。DISCOVER 是使用最频繁的算子，这证实团队会随着新需求出现而主动扩展其协调图。Lead 通过 ASSIGN 有效地进行委派，而 Worker 发起的 CLAIM 操作的高成功率表明，去中心化自调度显著减少了协调瓶颈。值得注意的是，LATTE 团队通过对恢复算子的选择性使用展现出涌现式容错。Lead 在 36% 的试验中调用 RELEASE 来重新分配拖尾任务；同样，VERIFY 在 19% 的试验中被调用，表明 Lead 会在认为必要时触发验证。具体而言，Lead 在高不确定性、高难度的试验中更频繁地触发 VERIFY——这些试验中团队平均需要 18.1 轮才能通过测试；相比之下，平均 8.1 轮即成功完成的试验中不含任何验证事件。这些行为尤为令人鼓舞，因为它们表明 LATTE 具备自主容错、监控与战略性资源分配的能力。

关键的是，这些模式之所以可观测，正是因为 LATTE 把涌现式协调外化，提供了具体的方式来解读与审计团队行为。不断演化的任务图让原本隐藏的决策变得直接可观测。例如，图3C 展示了团队结构与进展如何随时间演化。在 Leader-Worker 或去中心化团队中，选择性验证这类机制将不可见，或者埋没在消息日志之中，而不会被记录为显式且结构化的协调决策。

图3：LLM 团队成功利用 LATTE。A) LATTE 团队在各轮中涌现式地调用了所有图算子，表明协调工具箱得到充分利用。B) 动态协调图随时间增长得比静态图更大，这反映出对哪些子任务需要执行的更丰富、更细粒度的理解，为部署 Worker 提供了更多机会。相比之下，较小的静态图代表一种固定的、欠指定的协调结构，无法适应任务需求。C) 使用 GPT-5.2 的一个代表性示例，展示协调图如何跨轮演化。随着智能体添加边与依赖，图编码了涌现式的分配与进展。由于协调被显式表示，团队行为可以随时间被追踪、解读和诊断，这是相对于黑箱多智能体系统的关键优势。（原文第8页）

### 5.3 LATTE 诱导更好的协调

除了总体性能，我们还报告更细粒度的协调指标，以弥补团队评估中的一个根本缺口：覆盖（overwrites）、并发写入、通信开销与浪费的输出在既有工作中很少被度量，而它们直接刻画了智能体浪费资源与相互干扰的频率。

LATTE 减少智能体间冲突。在具有共享状态的协作任务中，智能体可能覆盖已完成的工作、同时编辑同一份文本，或冗余地重复劳动。每种冲突都会在浪费的 Token、损坏的状态与下游调试上付出不同的代价。LATTE 通过显式的任务分配与依赖跟踪缓解这些失败模式，确保智能体按照明确的顺序在互不相交的子任务上运作（图4A–C）。这些削减相当可观。LATTE 智能体平均每试验互相覆盖 4.3 次，而 Leader-Worker 团队为 22.8 次（p < 0.01）、去中心化团队为 35.4 次（p < 0.01），分别降低了 5.3 倍与 8.2 倍。对同一函数的并发写入遵循同样的模式：每试验 1.0 次，对比 Leader-Worker 的 8.5 次（p < 0.01）与去中心化的 11.5 次（p < 0.01）。这些冲突累积为浪费的输出。LATTE 平均每试验产生 5,236 个被丢弃的字符，而 Leader-Worker 为 45,436 个（p < 0.01）、去中心化为 78,062 个（p < 0.01），分别相当于多出超过 40,000 与 70,000 个从未出现在最终产物中的输出字符。

LATTE 降低高昂的通信成本。通信开销也是 LLM 团队中一项实实在在的成本。智能体倾向于发送过多消息，消耗不必要的 Token、引入延迟，并用无关信息打扰队友 [35, 59, 8]。LATTE 通过让通信有的放矢来约束这一点（图4D）：Worker 只有在被阻塞、需要澄清或为另一个智能体标示依赖时才向 Lead 发送消息。这一结构带来了可度量的更少通信。LATTE 智能体每个任务发送 20.4 条智能体间消息，对比 Leader-Worker 团队的 31.4 条（p = 0.04）与去中心化团队的 34.8 条（p < 0.01）。LATTE 智能体交换的消息也更精简：发送 42,484 个字符，对比 Leader-Worker 团队的 50,073 个（p < 0.01）与去中心化团队的 60,394 个（p < 0.01）。这些结果表明，LATTE 减少了不必要的通信，并限制了每个智能体的上下文累积。

LATTE 选择性激活智能体，减少空闲计算。LATTE 把参与限制在 Ft，只有存在待处理工作时才激活智能体。平均而言，智能体仅有 48.7% 的轮次处于活跃状态，同时保持了高水平的任务表现（图4E）。相比之下，去中心化团队无论需求如何，每一轮都激活所有智能体，抬高了计算与通信成本。Leader-Worker 团队介于两者之间，在 80% 的轮次中部署智能体。

图4：LATTE 改善协调。(A) 覆盖：智能体在后续轮次覆盖先前智能体的工作。(B) 并发写入：两个智能体同时写入同一函数。(C) 浪费的输出：写出但未出现在最终输出中的字符。(D) 通信开销：交换消息的数量与体量。(E) 不活跃：智能体被抑制的轮次比例。LATTE 降低 A–D 并提高 E。（原文第9页）

LATTE 缓解拖尾者。最后，静态系统中的一个关键挑战是拖尾者（stragglers）：完成所分配任务耗时明显偏长的智能体 [11, 35]。LATTE 通过监控节点执行时间、在超过阈值时向 Lead 发送心跳来应对，Lead 可以选择 RELEASE 并重新分配任务，Worker 也可以选择自我认领。RELEASE 在 36% 的运行中被调用，证实拖尾者缓解在实践中涌现。其对完成时间的影响相当可观。LATTE 团队平均 39.2 秒完成所分配节点，而静态团队为 75.6 秒（p < 0.01）；尾部差距更大：第 95 百分位为 130 秒，对比静态团队的 294 秒（降低 2.3 倍），表明该机制有效阻止拖尾者阻塞任务完成。

## 6 结论

受分布式系统中的任务图与调度协议启发，LATTE 使 LLM 团队能够在保持一致性与效率的同时动态探索并解决问题。在各种设置下，LATTE 在 Token 与时间效率、冲突解决与协调质量上表现出持续的增益，同时保留了智能体随任务演化探索并完善方案的灵活性。更广泛地说，LATTE 挑战了既有框架中的一个核心假设：协调结构必须由系统架构师强加。相反，允许智能体在线维护并修订自己的协调结构，使团队能够适应执行过程中积累的证据。这些结果确立了显式的、由智能体维护的协调，作为构建同时更高效、更可靠、更具适应性的 LLM 团队的原则。通过降低 Token 消耗与墙钟时间，LATTE 直接削减了 LLM 团队相关的计算（进而包括财务）成本，把原本会花在冗余通信与未解决冲突上的资源节省下来。

局限。若干局限指出了未来工作的有前景方向。首先，LATTE 引入了图初始化的规划开销，在单个智能体即已足够的短小或简单任务上，这可能超过其收益。对该开销的更深入分析见附录 A6.3。其次，我们的评估聚焦于具有天然子任务边界的领域，例如编码。当前算子集可以扩展，以支持较不结构化的任务发现与分解形式，使 LATTE 能在未来工作中处理更广泛的开放式推理任务。第三，我们将团队规模固定，以便与 MetaGPT 等基线公平对标，LATTE 如何伸缩的问题留待未来工作。

第四，LATTE 团队展现出识别何处需要验证的涌现能力，有选择地调用 VERIFY，而不是对所有智能体输出施加一刀切的审查机制 [23]。理解并强化这些涌现式验证机制是一个特别有前景的方向，因为有针对性的质量控制可能是大规模可靠 LLM 团队表现的关键。最后，未来工作应探索在协调结果上进行微调或强化学习，使团队能够随时间学会更好的图构造、任务分配与通信协议。

### A1 相关工作

#### A1.1 LLM 团队

LLM 越来越多地以多智能体团队形式部署。在某些设置中，这些团队通过提升多样性并把长上下文分布到多个智能体而胜过单个模型 [61, 29, 5, 14]。得益于这些涌现的协作能力，LLM 团队在科学发现 [49, 60] 与软件工程 [22, 40] 等领域取得了理想的结果。尽管取得了这些成功，协调仍是一项关键挑战。随着多个智能体互动并共同贡献于一项共享任务，确保一致、非冗余且结构良好的协作变得极其困难。

近期工作表明，扩大智能体数量并不能可靠地提升性能，事实上还可能依据任务结构与智能体异质性而恶化结果 [26, 37, 57, 43]。特别是在需要顺序推理或一致共享状态（如软件仓库）的设置中，性能会退化 [35]。非结构化的互动还可能进一步导致诸如职责幻觉、错误信息以及智能体间对抗行为等失败 [46]。

为克服这些挑战，各种框架力图通过显式结构化的任务分配与互动来提升团队表现。一种常见做法是施加基于角色的层级式分解。MetaGPT 等系统为执行协作式软件任务的智能体分配固定的功能角色（例如 Product Manager、Engineer）[22]，而 ChatDev 同样采用固定层级与基于角色的专门化 [40]。HuggingGPT [47] 等框架同样使用一个 LLM 控制器，针对固定的任务分类体系来规划并分派异构专家模型，但不会在执行过程中调整底层分解。更近期的方法引入了反馈驱动的重规划，由一个元智能体迭代更新计划 [28]。

在单智能体设置中，推理与规划可以被组织为围绕中间步骤的链、图或树，也可以被分解为更简单的子问题、其解向前馈送，从而在被提示的示例之外提升组合性与泛化能力 [53, 58, 4, 62]。

#### A1.2 任务图与协调协议

近期工作指出了 LLM 团队与分布式计算系统之间的相似性。拥有有限局部信息的智能体争夺共享资源、毫无预警地失败、重试、竞争，并且必须产出连贯的共享输出；值得注意的是，这正是分布式计算工程师们花费数十年建模的场景 [11, 33, 36]。在这两种设置中，不同的协调结构之间都会出现关键的权衡 [52]。

首先，完全中心化的架构可以通过指定一个 Lead 来分配任务并串行化更新，从而避免一致性冲突，但会造成瓶颈与单点故障。完全去中心化的方法更具可扩展性与鲁棒性，但在任务状态局部视图上独立运作的智能体可能产生冲突或冗余的输出。其次，静态方法事先确定固定的任务分配，简化了全局调度，但需要事先具备完整的任务可见性。因此，静态分配在任务失败、新依赖出现或工作负载变化时无法适应。相比之下，动态方法在任务可用时在线分配，但需要机制来在任务演化时维持一致性。

任务图被用于分布式系统（以及强化学习与规划 [12, 16]）中，将这一协调问题形式化：节点表示任务，边编码先后依赖，目标是高效地把任务调度到处理器 [55, 51]。HEFT 等经典调度算法位于两条轴的中心化、静态一端，在执行开始前计算全局优化的分配 [51]。动态变体沿第二条轴前进，在任务与依赖逐渐已知时在线做出分配 [25]。NABBIT 等方法使用共享任务池与工作窃取，兼顾一定的去中心化与动态分配，使处理器无需中央 Leader 即可自主认领就绪任务 [1]。Decima 等基于学习的调度器进一步在运行时依据工作负载结构调整策略 [34]，把动态分配与学习式协调结合起来。Ray 通过分片控制存储与自下而上的分布式调度器，同样把在线任务图调度规模化落地，支持结构事先未知的动态任务图 [36]。

然而 Ray 的动态性在于执行调度，而非任务规格：节点是事先注册的、类型良好的远程函数与 actor 方法，图只在这些原语于运行时被调用时才演化。这些方法假设任务定义明确且控制机制显式，而不是能够灵活、自主地以自然语言发现和修改任务的智能体。即便把任务图的概念移植到层级式决策智能体 [12, 16]，这些假设依然存在。

### A2 概率化动机

为论证 Lead 与 Worker 之间的分工，我们把团队协调发展为一个关于任务图上后验推断的概率化解释。由于 Lead 与 Worker 智能体具有不同程度的可见性，这一后验推断的单步或单轮成本在不同智能体之间有所不同。（近似的）贝叶斯推断与思考相称，而在平衡推断成本的同时进行思考，则引出一个更高层的问题——思考如何思考，即元推理（meta-reasoning）[44, 19, 17]。我们将 LATTE 论证为封装了一种元推理方法，用于高效地把全团队的计算资源投向如下贝叶斯推断问题：在给定所有观测数据的条件下识别最佳任务分解 [41, 48, 27]。

推断问题。令 Gt 表示团队在第 t 轮的当前任务分解，或是关于全局任务应如何分解与分配的一个假设。我们将合法 DAG 的空间视为假设空间，并把团队的目标建模为后验推断：找到最大化 P(Gt | Dt) 的 Gt，其中 Dt 表示第 t 轮累积的全部证据（例如执行日志、已完成输出、消息与环境反馈）。由贝叶斯定理我们有

```
                            P (Dt | Gt )P (Gt )
             P (Gt | Dt ) =                      .                 (1)
                                      P (Dt )
```

边际似然 P(Dt) = ΣG P(Dt|G)P(G) 需要对所有合法任务图的空间求和，在组合意义上不可行。此外，似然 P(Dt|G) 没有闭式解，因为 Dt 由自然语言输出或执行轨迹构成，其概率无法直接评估。

MCMC 作为可行的替代。马尔可夫链蒙特卡洛（MCMC）为后验推断提供了一条绕开 P(Dt) 计算的标准路径。我们并不直接评估后验，而是构造一条以 P(Gt|Dt) 为平稳分布的任务图上的马尔可夫链。在每一步，生成一个提案 G′t 并以如下概率接受：

```
                               P (Dt | G′t ) P (G′t ) Q(Gt | G′t , Dt )
  A(Gt → G′t | Dt ) = min 1,                                          (2)
                               P (Dt | Gt ) P (Gt ) Q(G′t | Gt , Dt )
```

其中 Q(G′t | Gt, Dt) 是提议分布。由于 P(Dt) 同时出现在分子与分母中，它精确抵消，使得无需计算边际似然即可评估接受比。

Leader-Worker 分解作为元推理。剩下的挑战是构造一个既可行又富有表达力的提议分布 Q。一种做法是让对所有 Worker 智能体的过往交互 Dt 拥有完整可见性的 Lead ℓ 负责识别新的提案 G′t；如果不考虑推断成本，这一做法看似颇有前途。然而，该策略把重任压在单个智能体（本工作中即单个 LLM）身上，要求其先处理完整历史 Dt 中的大量信息，再在一个指数级庞大的假设空间上进行推理，而这两者都会降低 LLM 响应的可靠性 [30]。

与其把推断的所有负担都压在 Lead 肩上，一种替代且更具成本效益的做法是赋能各个 Worker 智能体 wi。具体而言，可以从每个 Worker wi 获得一个新的任务分解 G′t,i。接下来，获得新任务分解的一个快捷方式是简单合并所有 Worker 的提案：G′t = merge(G′t,1, G′t,2, …)。或者，把每个新提案视为粒子滤波中的一个点估计，并均匀随机地选取其中之一。值得注意的是，这类方法位于前述以 Leader 为中心的方法的对立极端——在那里，推断成本被降低到处理每个 Worker 各自的局部历史 dt(i) ⊂ Dt。遗憾的是，由于每个 Worker 都缺乏全局视野，没有任何 Worker 智能体能够很好地判断其提案是否真的提升了整个团队的全局任务表现。

前述方法要么最大化、要么牺牲推断质量，并相应地大幅增加或降低成本；而 LATTE 可以通过利用 Gt 的结构，为元推理问题获得更高效的解，并更好地平衡推断的质量–成本权衡。具体而言，我们将每个 Worker wi 分配到一个局部子任务 gt(i) ⊂ Gt，并积累局部执行轨迹 dt(i) ⊂ Dt。Worker wi 通过采样提出局部更新：

```
                          (i)′             (i)   (i)
                         gt      ∼ Q(· | gt , dt )                       (3)
```

把提案限制在 gt(i) 之内使每个 Worker 的任务保持可行，因为 wi 关注的是其局部轨迹 dt(i) 而非完整历史 Dt。第 t 轮的候选全局分解随后是所有 Worker 局部更新的并集 G′t = ∪i gt(i)′。

Lead ℓ 保持对 Gt 的全局可见性并评估接受比，或者提交 Gt+1 = G′t，或者保留 Gt+1 = Gt。因此，Worker 拥有充分的局部信息在其自身作用域内提出结构性更改，而 Lead 拥有评估提案是否改善整体分解所需的全局视图。关键的是，这呼应了 Metropolis-Hastings 的接受步骤 [18]，其中评估者只需近似未归一化似然之比 P(Dt|G′t)P(G′t)/P(Dt|Gt)P(Gt)（例如在两张特定图之间比较），而无需在整个假设空间上积分；但关键在于，我们并不主张 LATTE 智能体必然显式计算这一比值。此外，与上述纯局部 Worker 更新方法相比，LATTE 额外产生一笔边际成本——由 Lead 评估所提局部更新的收益——同时利用 Lead 的全局可见性来维持高质量推断。总体而言，这一框架提供了规范性说明，解释了 LATTE 中的分工为何有据可依，以及相关 LLM 在近似什么行为。我们在下一节把这一分工形式化为一组图变更算子。

### A3 图变更算子

我们定义七个变更任务图的算子；每个算子由 Lead ℓ、Worker w 或两者调用。Ft 表示在时刻 t 依赖已被完全满足的节点集合。

**DISCOVER(v, deps)**（ℓ, w）：要求 v ∉ Vt、deps ⊆ Vt，且添加 v 保持无环性。把 v 加入 Vt，在 Et 中插入从每个依赖指向 v 的边，并初始化 λt(v) ← (⊥, pending)。

**ASSIGN(v, w)**（ℓ）：要求 status(v) = pending 且 w ∈ W。置 λt(v) ← (w, assigned)。

**CLAIM(v)**（w）：要求 v ∈ Ft 且 agent(v) ∈ {⊥, w}。置 λt(v) ← (w, in_progress)。

**COMPLETE(v)**（w）：要求 status(v) = in_progress 且 agent(v) = w。置 λt(v) ← (w, done)。

**RELEASE(v)**（ℓ）：要求 status(v) ∈ {assigned, in_progress}。重置 λt(v) ← (⊥, pending)。

**CLOSE(v)**（ℓ）：要求 status(v) ∈ {assigned, in_progress}。置 λt(v) ← (agent(v), done)，无需 Worker 发出完成信号。

**VERIFY(v)**（ℓ）：要求 status(v) = done 且 vver ∉ Vt。把一个验证节点 vver 加入 Vt，在 Et 中插入边 (v, vver)，并初始化 λt(vver) ← (⊥, pending)。

### A4 LATTE 实现

#### A4.1 团队组成

每次运行包含一个 Lead（Lead）与 N 个 Worker 智能体（命名为 Dev1 至 DevN；所有实验中 N = 4）。所有智能体运行相同的基础模型与相同的采样参数。

Lead 智能体。Lead 在执行开始之前运行一个隔离的规划阶段。给定自然语言任务描述，它最多有 5 个回合，通过 <discover_task> 动作产出初始任务图（节点 + 依赖边）。执行期间，Lead 监控进展、发布 <assign_task> 与 <release_task> 指令，并可以变更图（添加节点、关闭过期节点）。其上下文窗口被限制为最近 10 条消息。

Worker 智能体。Worker 从 Lead 接收任务分配并实现它们。它们可以发出 <claim_task>、<complete_task> 与 <discover_task>，来提议向图中添加新的子任务。其上下文窗口被限制为最近 20 条消息。

并发。同一轮内所有智能体并发运行——编排者先让 Lead 步进，然后并行派发 Worker，并在推进到下一轮之前收集它们的响应。

#### A4.2 Lead 提示

你是一名资深软件工程师，带领一个开发团队协作完成编码任务。

职责：

1. 理解项目的整体目标与需求
2. 拆分工作并有策略地向团队成员分配任务
3. 监控进展并协调团队
4. 在队友遇到问题时帮助其解除阻塞
5. 审查工作的质量与一致性
6. 综合结果并确保项目成功完成

高效工作并适当授权。信任你的队友完成他们分配到的任务，但在需要时提供指导。保持沟通清晰且可执行。

并行性：

队友可以从就绪队列中自我分配——他们不需要等待你。你的职责是保持图的正确并处理失败，而不是手动分派每一个任务。

话虽如此，当你知道某个特定智能体是合适人选时，应主动分配任务（例如在解除某个拖尾者的阻塞之后、在一次验证完成之后）。当多个任务就绪时，一次性把它们全部分配，每个可用智能体一个。

不过，要审慎决定什么可以并行运行。避免把两个智能体分配到同时写入同一函数的任务上。一个好的规则：处理不同函数或不同文件的任务可以并行运行；都修改同一份共享数据的任务应当串行。

在可能的情况下，构建宽的图，而不是深的图。只用 dependencies 表达真实的实现顺序（即「在 A 的输出存在之前我无法开始 B」）。不要仅仅为了安全而把任务串成链——如果两个任务涉及不同的函数或文件，它们之间没有 dependencies，就可以并行运行。

有了这种结构，task-analyze 一完成，三个实现任务就会同时就绪。

可用动作：

不要自己编辑文件——专注于指导团队并验证他们的工作。

1. 向队友分配任务：

```
<assign_task id="task-1" to="AgentName" />
```

2. 向所有队友广播消息（用它来协调工作）：

```
<broadcast>Your message here</broadcast>
```

3. 运行 Python 脚本并查看其输出：

```
<run_script path="script.py" />
```

4. 向智能体请求状态：

```
<request_status />
```

5. 运行测试：

```
<run_tests />
```

6. 图更新。任务图是一份活的文档。在以下情形使用 <discover_task> 添加新任务：(a) 队友报告完成任务后测试仍然失败；(b) 你注意到遗漏了依赖，或先前任务产生了错误输出；(c) 项目需要事先未计划的验证或集成环节。

示例：如果 Dev2 完成了某个函数的实现却广播说测试仍然是红的，应立即添加一个修复任务，而不是等待：

```
<discover_task id="fix-index" title="Fix index() API bug"
    dependencies="task-2">
    Run <run_tests /> to see failures, fix search_lib.py,
    confirm all tests pass.
</discover_task>
```

index 函数是按 dict 输入实现的，但测试传入的是 list。

7. 如果一个任务利害关系重大——它位于许多其他任务的上游，或其输出事后难以验证——你可以请求由第二个智能体进行验证：

```
<verify_task id="task-X" />
```

这会向图中插入一个轻量级审查任务，必须在其下游任务继续之前完成。执行验证的智能体将检查正确性并修复任何问题。

8. 拖尾者缓解。如果队友被分配任务已经数轮仍未完成，他们可能卡住了。使用该动作把任务释放回 pending，使其可以被重新分配：

```
<release_task id="task-X" />
```

这会清除当前所有者并把任务重置为 pending。然后用以下方式重新分配：

```
<assign_task id="task-X" to="DevY" />
```

可以分配给不同的智能体，也可以分配给同一智能体但给出更清晰的指令。在重新分配之前，广播一条消息说明该智能体应如何做得不同。

9. 如果测试套件已经通过，但任务仍被标记为 "assigned" 或 "in_progress"（例如队友完成了工作却忘记发出 <complete_task>），你可以直接关闭它们：

```
<close_task id="task-X" />
```

只有在用 <run_tests /> 确认测试通过之后才使用此动作。当满足以下条件时这是正确的动作：所有测试都是绿的，该任务的工作在代码库中显然已经完成，且负责的智能体不再取得进展。

#### A4.3 Worker 提示

你是一名作为开发团队一员工作的资深软件工程师。

职责：

1. 完成 Lead 分配给你的任务。
2. 编写干净、有良好文档的代码。
3. 要直接读取既有文件的内容，使用：

```
<read_file path="math_utils.py" />
```

这会立即返回文件内容——不需要脚本。始终优先使用它，而不是编写辅助脚本来打印文件。

要执行脚本并查看其输出，使用：

```
<run_script path="script.py" />
```

这会运行文件并把 stdout/stderr 返回给你。在标记任务完成之前，用它验证你的代码可用。

重要：<run_script> 只接受 .py 文件名——它不是 shell。不要传入 ls、head 或 python3 script.py 这样的 shell 命令。要列出文件，先用 <edit_file> 写一个简短的 Python 脚本，再用 <run_script> 运行它。示例：

```
<edit_file path="check_files.py">
import os; print(os.listdir('.'))
</edit_file>
<run_script path="check_files.py" />
```

4. 使用 <run_tests /> 运行测试套件并检查你的工作。

重要：如果 <run_tests /> 仍在失败，不要把任务标记为完成。如果你完成了实现而测试仍是红的，用 <discover_task> 添加一个后续修复任务，而不是标记为完成后继续前进。这会让问题对整个团队保持可见。

5. 在被阻塞或需要澄清时与团队 Lead 沟通。
6. 在进入下一个任务之前，彻底完成当前任务。

积极主动、注重协作、关注细节。专注于产出高质量的工作。

发现新任务：

每当你发现尚未出现在任务列表中的工作，就使用 <discover_task>。在可能的情况下，构建宽的图，而不是深的图。只用 dependencies 表达真实的实现顺序（即「在 A 的输出存在之前我无法开始 B」）。

```
<discover_task id="new-task-id" title="Short title"
dependencies="only-if-truly-required">
  Clear description of what needs to be done and why.
</discover_task>
```

#### A4.4 参数

采样。所有智能体使用 temperature 0.7，每次调用的最大输出长度为 4,096 Token。

轮次上限。LATTE 团队（与基线团队）总共有 40 轮来完成每个任务。它们可以通过标记任务完成（由 Lead 或去中心化团队中的 Worker）更快地完成任务。随后根据其实现是否通过给定任务的测试套件来评估成功。

心跳监控。我们在所有 LATTE 实验中设置 H = 4。如果某个 Worker 在其子任务实现上卡住超过 4 轮且没有发出任何动作，Lead 会收到通知并被提示介入。

认领的冲突裁决。空闲的 Worker 智能体被允许从 Ft 自我认领任务。并发认领按处理顺序以 FIFO 方式处理；当多个 Worker 在同一轮认领同一个任务时，编排者按顺序逐个处理智能体，被处理的第一个认领获胜，其后的认领者收到一条错误消息并必须重新轮询。

API 重试。Anthropic 与 OpenAI 的请求依赖各自 SDK 的重试逻辑。未设置单次调用的墙钟超时。

#### A4.5 LATTE 执行协议

```
Algorithm 1 LATTE Execution
Require: Task description τ , agents A = {ℓ} ∪ W, max rounds T , heartbeat threshold H
Ensure: Final task graph GT
  Phase 0: Planning
  G0 ← ℓ.DISCOVER(τ )                                        ▷ Leader initializes coordination graph
  Phase 1: Execution
  for t = 1 to T do
    // 1. Heartbeat monitoring
      Flag to ℓ any w ∈ W with no actions in H consecutive rounds
    // 2. Frontier identification
      Ft ← {v ∈ Gt : S TATUS(v) = pending, ∀u ∈ D EPS(v) : S TATUS(u) = done}
    // 3. Agent dispatching
      Re-engage busy Workers that have received new context since last round
      Assign idle Workers to tasks in Ft , at most one Worker per task
      Invoke ℓ if Gt has changed, a heartbeat was flagged, or ℓ has been idle for H rounds
    // 4. Parallel execution
      All selected agents act in parallel:
         ℓ receives full graph Gt ; Workers receive assigned task or Ft
         Each agent emits actions ⊆ {D ISCOVER, C LAIM, C OMPLETE}
      Gt ← A PPLY(Gt−1 , all emitted actions)
    // 5. Termination check
      if ∀v ∈ Gt : S TATUS(v) = done then
          return Gt
      end if
  end for
  return GT
```

### A5 基线实现

#### A5.1 MetaGPT

我们使用 MetaGPT [22] 论文发布时的原始代码库，对应 ICLR 2024 投稿时公开可得的版本（commit tag v0.1，创作于 2023 年 4–8 月），因为它忠实地实例化了论文中描述的固定标准操作流程（Standard Operating Procedure，SOP）。

流水线。MetaGPT 把协作组织为围绕五个基于角色的智能体的固定、顺序 SOP：

1. ProductManager（Alice）把任务描述转化为产品需求文档（PRD）、用户故事与竞品分析。
2. Architect（Bob）接收 PRD 并产出系统设计文档，包括 Python 包名、文件结构与 API 规格。
3. ProjectManager（Eve）读取系统设计，并向 Engineer 发布任务列表。
4. Engineer（Alex，n_borg = 1）按顺序实现所分配的文件，每个动作处理一个文件，向共享内存发出代码块。
5. QaEngineer（Edward，test_round_allowed = 5）监视 Engineer 的输出，在允许的轮数内迭代「写测试 → 运行代码 → 调试错误」循环。

智能体完全通过一条共享的发布-订阅消息总线通信：每个角色监视一组固定的上游动作类型，只有在匹配的消息到达时才行动。任务分解、要写哪些文件、每个文件包含什么以及以什么顺序写，完全在规划阶段（步骤 1–3）决定，执行期间无法修改。

参数。所有智能体使用与附录 A4 中所述 LATTE 与基线运行相同的模型与采样参数。每次 MetaGPT 运行被分配 n_round = 40 个团队总轮次，以与其他团队条件匹配。QaEngineer 以 test_round_allowed = 5 初始化，与原论文中调试-修复循环的上限一致。

SOP 输出与任务评估之间的错配。由于顺序流水线中的每个角色都在前一个角色的输出上运作，而不是在共享任务环境上运作，工件会累积在由 Architect 事先设计决定的位置，而不是任务期望的位置。更广泛地说，由于任务分解在任何代码执行之前就已确定，Engineer 无法发现潜在的任务结构，例如哪些函数共享内部辅助函数、给定文件中实际存在哪些缺陷，或哪些数据列承载了关注的信号。在非平稳任务上——正确的分解只有在执行过程中才会显现——事先的计划会被系统性地错误指定，而 SOP 没有提供修订它的机制。

#### A5.4 静态图消融

静态条件使用与动态条件相同的基于图的编排者，但在规划阶段之后禁用任务发现与重新分配。规划期间，Lead 收到一条提示，要求其事先输出完整的任务图，在执行开始之前指定每个任务及其依赖。规划一旦结束，图即被冻结：运行中的任务发现（discover_task）、拖尾者释放（release_task）、验证插入（verify_task）以及测试失败时的自动修复任务注入，都在编排者层面被禁用。队友不能自我分配；Lead 负责在执行开始时通过 assign_task 分配每个任务。无论任务是否可用，所有 N 个队友每轮都被派发。如果队友未能完成所分配的任务，没有任何恢复机制可用。

### A6 实验

#### A6.1 设置

任务1：探索性数据分析。在数据集中识别有意义的模式本质上是耗时且开放式的。该过程从预处理与过滤开始，可以由单个智能体处理。随后，多个智能体可以沿不同方向并行探索数据（例如刻画分布、识别异常值、生成可视化）。最后一个智能体随后汇总并综合这些发现。重要的是，纯静态的任务分解很可能是次优的，因为数据的底层结构与有前景的方向只有在分析过程中才会显现。

我们首先模拟了一个表格化的 HR 数据集，包含 400 条员工记录、八个刻意不透明的列名，且没有数据字典。数据中植入了三个真值属性：（1）员工满意度分数是主导的流失预测因子；（2）薪资呈双峰分布，反映两个劳动力层级；（3）流失率因部门而显著不同。智能体的任务是产出三个相互依赖的工件：一个建立共享列名映射与特征 schema 的 config.py（所有下游脚本都必须导入的基础）；一个结构化的 findings.json，包含横跨五个分析类别（分布、关系、子群效应、异常值与缺失数据）的量化佐证；以及一份至少 100 词的 summary.txt 书面叙述。正确性由一套私有测试套件评估，检查是否识别出真正的流失列、列-特征分类是否与数据类型匹配，以及三个植入的属性是否以正确的方向性论断出现在发现之中。

任务2：调试。调试是另一项本质上非平稳的任务；智能体必须运行测试、读取输出、修改代码以解决可能的多个错误，并重复该过程直到问题解决。它同样奖励并行性与一致性，因为多个智能体可以同时诊断相互独立的错误，而某些错误需要修改复合函数，这些函数只有在依赖被修复之后才能验证。在任务2中，我们在一个 Python 信号处理库中植入了 8 个缺陷（每个函数 1 个），覆盖一系列常见的数值错误，例如归一化分母中的 +1 或不等式错误。与任务1（性能在智能体标记任务完成之后评估）不同，团队可以访问完整的测试套件。成功要求公共测试套件中的所有测试通过。

任务3：库扩展。最后，代码生成是一项本质上耗时的任务；智能体团队可以通过并行工作、生成代码库中相互独立的部分来提升表现。在该任务中，智能体获得一个部分实现的 Python 文本处理库，其中三个文件可用：Document 类、Tokenizer 类与 utils 模块。他们必须扩展现有类，并基于桩文件构建六个新模块：sentiment.py、keywords.py、summarizer.py、similarity.py、formatter.py 与 pipeline.py。生成的每个阶段需要不同数量的智能体：首先必须扩展两个既有类，这只需要两个智能体来修改；然后新模块可以独立并行生成；最后只需一个智能体把一切集成到最终的 pipeline 中。鼓励智能体编写自己的测试，正确性在他们标记测试完成之后由一套私有测试套件判定，测试常见输出与边界情况。

#### A6.2 试验

对每个基础模型，我们共运行 150 次试验（3 个任务、5 种团队结构、10 次重复）。对 Claude Sonnet 4-6，这相当于 2,136 次 API cells、40.7M 输入 Token 与 8.5M 输出 Token（约 250 美元）。对 GPT 5.2，这相当于 4,582 次 API 调用、83.1M 输入 Token 与 14M 输出 Token（约 260 美元）。

#### A6.3 规划开销分析

LATTE 的适应性引入了两部分编排成本。第一，Lead 播种任务图的初始规划阶段：动态条件平均播种 3.8（±2.0）个节点、耗时 14.5 秒，而静态条件为 8.3（±1.8）个节点、耗时 16.7 秒——静态条件把完整分解前置。第二，执行中的编排：动态条件下 Lead 平均在 30.8% 的执行轮次中保持活跃，而静态条件为 14.8%，每次运行平均增加 0.9 个额外的 Lead 活跃轮次。

虽然这些是真实成本，但它们并不超过 LATTE 为动态与复杂任务带来的收益。在所有任务与模型上，动态条件平均以 9.8 轮、148K Token 完成，而静态条件为 15.9 轮、297K Token。因此，动态开销中每一个额外的 Lead 活跃轮次，换来大约少 6 轮的 Worker 执行总轮次。
