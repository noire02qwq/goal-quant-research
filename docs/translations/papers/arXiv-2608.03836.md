## 摘要

一个持久化执行状态、使运行可以被中断、挺过崩溃并继续的框架，必须回答一个问题：对于已经发生过的 effect，一次 resume 意味着什么。五个广泛部署的 agent 工作流框架给出的答案各不相同，没有一个公开可机器校验的契约，而实测行为甚至违反它们自己写下的片段。RESUME CONTRACT（resume 契约）在持久化 API 上陈述六条性质——前缀续跑（prefix continuation，PC）、effect 恰好一次（effect exactly-once，EO）、fork 确定性（fork determinism，FD）、checkpoint 有效性（checkpoint validity，CV）、仅消费一次（consume-once，CO）、恢复确定性（recovery determinism，RD）——外加 fork 意图（fork-intent）与活性（liveness）义务。

一个 TLA+ 模型对参考语义做穷尽校验，扩大界后判定不变（7.4×10⁶ 个不同状态），参考合取式另经 TLAPS 无界证明（196 条义务）；一个 39 格故障矩阵与两个伴随模块给出独立性论证所需的分离模型（五条性质各自独立于其余性质的合取；CO 可拆分，其消费子句独立于全部六条）。一套确定性、不调用 LLM 的 harness 在固定版本上测量五个框架。

LangGraph 1.2.9 会持久记录第二个 resume 值却从不读取它，静默持久化 schema 非法状态，并在真实 SIGKILL 之后重新执行已持久记录的工作——同一个 API 上，跨 interrupt 是 exactly-once，跨崩溃是 at-least-once。CrewAI 1.15.2 违背其书面声明，重新执行已完成的带 effect 方法；pydantic-graph 1.x 在节点中途崩溃后无法 resume；被测框架中没有两个共享同一一致性画像。consume-once 在顺序场景成立、在并发投递下失败：k 个进程 resume 同一个已挂起的 interrupt 会触发受门控 effect k 次，40 格中 36 格饱和度为 1.0，两个持久后端上都不低于 0.933。准入窗口跟随受门控节点自身的执行时长，由剂量—响应测得。该失败可跨主机：两台机器上的两个竞争者在 10/10 次重复中全部重复触发。真实模型的格子按模型 40/40 复现 fork 违反。

REMIT 是一个参考定序器，其经 Verus 验证的恢复核心在 CI 门禁下与已发布可执行文件逐行相同（不主张端到端精化），它修复了 fork 与有效性两格。跨进程那一格在读路径上被修复，且修复已经发布：一个默认关闭的门在共享存储中认领消费，服务一个竞争者、在任何节点执行前拒绝其余（两个持久后端上均为 {1:10}，竞争者分处两台主机时同样如此）。

**关键词**：一致性测试、形式化规约、checkpointing、崩溃恢复、exactly-once 语义、幂等、模型检查、TLA+、interrupt、human-in-the-loop、工作流框架、LLM agent。

## 1 引言

持久化平面（persistence plane）许下一个简单的承诺：一次运行可以停下来——为了人工审批、为了崩溃、为了被抢占——然后继续。这个承诺很古老，其失效模式也很经典；新颖之处在于承诺如今被许在了哪里。新一代面向 LLM agent 的工作流框架已把这套机制交付给那些把支付、消息和文件写入置于其后的开发者：LangGraph 按 superstep 对图状态做 checkpoint，并暴露 `interrupt()` 与 `Command(resume=...)`；LlamaIndex Workflows 在运行中途序列化工作流 `Context` 再恢复它；CrewAI 持久化 flow 状态、并从 checkpoint 文件恢复运行。

当 agent 被授予对非幂等 effect 的权力时，「继续」就变成一个正确性问题：哪些已完成的 effect 可以再次触发、同一个 interrupt 被两次回答成不同值时会发生什么、什么可以被持久化、恢复决策是否是持久状态的函数。本文测量这套机制是否成立。

这里的差距不只是缺少规约，而是不自洽。被评估的框架没有一个就这些义务提供可机器校验的契约；在确有片段陈述的地方，框架之间互相矛盾：CrewAI 的 checkpointing 文档声称恢复「resume[s] without re-running completed work」[1]；LlamaIndex Workflows 指示用户把 `wait_for_event` 放在前面并「make any preceding work safe to re-execute」[2]；LangGraph 则跨 resume 记忆化已完成的 `@task` 结果。三个框架，三种互不相容的答案——而且正如我们所示，其中两个连自己陈述或暗示的语义都不满足。

从分歧到危害的链条是具体的：一个把带副作用的工作流在框架间迁移的开发者，无法在本地判断哪种纪律在生效——没有类型、没有签名、没有可查阅的已记录性质——而本文复现的那些 GitHub issue 正是这个缺口的现实形态。我们把 issue 当作动机，从不当作测量；每一条行为论断都由第 5 节的确定性 harness 重新建立。持久化平面缺少网络协议和文件系统几十年来就有的东西：一份显式契约、一个机器校验的模型、一套一致性测试套件。

一份契约之所以能横跨不同的执行模型，是因为它们共享一个边界——checkpoint、interrupt、resume 命令、一个状态检查 API——下面每条性质都只在这个面上陈述；一个记录了更弱纪律的框架被记为分歧（divergent，D），而不是缺陷。我们用四步把这一点落实。

**(1) RESUME CONTRACT（第 3 节）。** 抽象 resume 平面上的六条性质：前缀续跑 PC、effect 恰好一次 EO、fork 确定性 FD、checkpoint 有效性 CV、仅消费一次 CO、恢复确定性 RD。PC/EO 管什么可以重新执行；FD/CO 管 interrupt 生命周期；CV 管什么可以被持久化；RD——动机来自我们在 LangGraph 同步持久化模式下报告的一个排序缺陷（issue #8039）——要求恢复决策是持久状态的函数。这组性质早于测量而存在（第 3.4 节）。

**(2) 一个机器校验的模型（第 4 节）。** 一个带六个故障开关的 TLA+ 模块，每个开关建模一类在已部署框架中观察到的违反。TLC 对参考配置校验全部六条性质（生成 87 个状态、59 个不同、无错误），并对每个单故障配置给出深度 4–6 的反例。一个逐不变量矩阵——每条故障对每条性质、共 39 次运行——绘出每条故障的完整违反足迹；这些足迹是被发现的、不是被规定的，而那些全状态空间保持干净的运行，正是第 3.4 节所需的分离模型。

**(3) 一个确定性一致性 harness 与跨框架研究（第 5–6 节）。** 每个探针都是跑在框架持久化 API 之上的纯 Python 协议序列——不调用 LLM、不依赖时间窗口；矩阵中的崩溃基于异常，另在栅栏同步的 SIGKILL 下复现（探针 133）——配有进程内 effect 计数器，持久后端探针上再用磁盘外部账本交叉核对。

在当前版本（LangGraph 1.2.9、LlamaIndex Workflows 2.22.2、CrewAI 1.15.2、pydantic-graph 1.107.1、AutoGen AgentChat 0.7.5）上，研究发现：LangGraph 在全部三种 checkpointer 后端（含真实 PostgreSQL）上有一个现存的 fork 违反和一个现已静默的合法性违反；CrewAI 在 checkpoint 恢复下重新执行已完成的带 effect 方法，与其功能的书面声明相反；LlamaIndex Workflows 有文档写明的 at-least-once 前缀重放；一次击穿 pydantic-graph 自身 resume 入口的崩溃；AutoGen AgentChat 是被测框架中唯一对被篡改状态大声拒绝的；每一个不完整的持久化边界都允许重新执行已完成的工作（探针 160）；consume-once 顺序成立、跨进程投递下失败（探针 159）；被测框架中没有两个共享同一一致性画像。

两个被测 LangGraph 行为（#7361、#6792）作为 1.1.x 回归发布、已在 1.2.9 修复——没有已陈述的契约，语义甚至会在同一个框架内部漂移。

**(4) 一条带已验证模型的修复路径，且已发布（第 7 节）。** REMIT 是一个参考 resume 定序器与只追加的 effect 账本，位于现有 checkpointer 接口之下（首先是 LangGraph 的 `BaseCheckpointSaver`），按标注的成熟度分级交付：不变量以 Verus [3] 陈述并由机器 discharge、已发布的恢复决策核心是一个已验证的可执行函数（不主张端到端精化）；PyO3 绑定之后的 Rust 核心，与 TLA+ 转移关系做可执行一致性检查；一个把静默的非法持久化变成运行时大声拒绝的合法性门；以及由一对配对实验了结的 fork 确定性——写路径键控失败、读路径 fork 意图过滤器在同一协议上修复 #6663——由打包的无决策 shim 用原厂 saver 作差分对照重新建立。这补全了第 4.3 节的机制说明。

**定位。** 两个近期系统从两侧夹住本文、但都不占据其中：框架 API 之下，Crab [4] 对 OS 级沙箱状态做 checkpoint；之上，DART [5] 决定机械上可行的回滚在语义上何时可接受。两者都不问原语本身是否信守承诺。同意完整性（consent-integrity）工作 [6] 把审批绑定到动作内容；FD/CO 管的是审批的生命周期。并发的框架测试工作 [7] 负责找 bug；我们定义这些 bug 所违反的契约、测量一致性，并给出带机器验证模型的参考实现。据我们所知，此前没有工作同时结合显式的 resume 契约、机器校验的模型与跨框架一致性测量。

**主张了什么、没主张什么。** 由于下面各节在提出论断处就地限定，范围在此集中说明。**已证明**：无判别器时 FD–CO 的不可能性（引理 1）；EO、PC、FD、CV、RD 相互独立于其余性质的合取，以及 CO 对 EO 的结构依赖（命题 1），每一条都由在给定界下穷尽检查的模型作证；参考合取式本身由 TLAPS 对满足模块假设的每个常量赋值无界 discharge（第 9 节）。

**已机器校验**：参考模型全部可达空间上的六条性质，在表 2 的扩大界下复检；两个界集下的逐不变量故障矩阵；独立性见证。**已测量**：五个固定版本框架被探路径上的一致性，effect 判定依据是一个持久的跨进程账本。**已验证**：REMIT 的恢复决策核心，一个在 CI 门禁下与已发布者逐行相同的可执行函数；EO 准入与 PC/CV 提交核心作为已验证的可执行孪生、由穷尽差分套件桥接到已发布实现（第 7.3 节）——不是那个复合包，也不主张到编译二进制的精化。

**未主张**：性质集的最小性或完备性；任何违反的流行率；被测框架代表整个生态；任何框架在未被测量的性质上失败。

## 2 resume 平面及其碎片化

### 2.1 基本原语

我们用 **resume plane（resume 平面）** 指 agent 框架中的这样一个子系统：(i) 持久记录执行进度（checkpoint），(ii) 让一次运行挂起等待外部输入（interrupt），(iii) 从持久状态继续运行（resume）——无论是在 interrupt 之后、崩溃之后，还是显式恢复之后。

在 LangGraph 中，这个平面就是 checkpointer（`InMemorySaver`、`SqliteSaver`、`PostgresSaver`）加上 `interrupt()` 与 `Command(resume=...)`，以 `(thread_id, checkpoint_id)` 寻址；持久化文档给「带先前 checkpoint_id 的调用」两种读法——创建分支的时间旅行（「在任意 checkpoint 处 fork 图状态」）以及重新触发 interrupt 的重放 [8]。在 LlamaIndex Workflows 中，该平面是 `Context.to_dict()`/`from_dict()`，加上配合 `InputRequiredEvent`/`HumanResponseEvent` 的 `wait_for_event` 惯用法。在 CrewAI 中，它是 `@persist` 的 flow 状态持久化，以及自 checkpointing 功能出现后的 `CheckpointConfig` 与 `Flow.from_checkpoint`。

**表 1　各框架对已完成工作的 resume 纪律文档记载**（实践者会用于持久 human-in-the-loop 或崩溃 resume 的机制）。「陈述」引用或转述框架自己的文档；第 6 节检验行为是否相符。

| 框架（机制） | 恢复时对已完成工作的陈述纪律 |
|---|---|
| CrewAI 1.15.2（CheckpointConfig） | exactly-once：恢复「resume[s] without re-running completed work」[1]。 |
| LlamaIndex Workflows 2.22.2（wait_for_event + Context 序列化） | 对步骤前缀是 at-least-once：事件到达时运行时会重放该步骤；用户必须「make any preceding work safe to re-execute」[2]；进行中的步骤在恢复时重启 [9]。 |
| LangGraph 1.2.9（@task + checkpointer） | 对任务体是 exactly-once，靠跨 resume 记忆化已完成任务的结果；图节点语义以 checkpoint 为粒度 [8]。 |

### 2.2 三个框架，三份书面语义

表 1 汇总了各框架自己的文档对那个核心问题——已完成的工作在 resume 时会不会重新执行？——就实践者会去用的那个机制所说的话，而这些陈述彼此不相容：CrewAI 的 checkpointing 声称已完成的工作会被跳过；LlamaIndex Workflows 文档写明，持久等待之前的步骤代码会重放、进行中的步骤在恢复时重启 [9]；LangGraph 则记忆化已完成的 `@task` 结果。于是一个在框架之间迁移带副作用工作流的开发者，会毫无提示地从 exactly-once 制度跨入 at-least-once 制度：没有类型错误、没有警告、也没有可查阅的已命名性质。

### 2.3 违反的版本稳定性

LangGraph 探针横跨五个版本执行——1.0.5、1.1.0、1.1.3、1.1.10、1.2.9——以区分稳定的违反与短暂的回归。fork 违反（#6663）与静默持久化违反（#6491 类）在每个被测版本上都复现：它们是 resume 平面横跨一年版本的稳定性质，而不是等待补丁的回归。至于 #7361 和 #6792——问题跟踪器把它们报告为狭窄窗口内的回归——版本扫描发现当前及相邻版本都是干净的；这两者只被当作有据可查的历史来引用，从不作为我们自己的测量。证据文件 `results/regression/` 记录了每一个格子。

**图 1　分层定位。** 相邻系统假定框架 resume 原语是可靠的；本文规约并检验这一假定。图中自上而下为：DART [5]：原语之上的回滚可接受性（已提交的下游消费者、effect 策略）；本文：RESUME CONTRACT——在框架 resume API（checkpointer、interrupt、resume 命令）之上的 PC / EO / FD / CV / CO / RD；Crab [4]：OS 级沙箱 checkpoint/restore（文件系统、进程、microVM）。

### 2.4 分层定位

图 1 把本契约放在恢复领域中两个近期强系统之间。Crab [4] 工作在框架 API 之下：一个 eBPF 插桩的主机运行时，对 OS 可见的沙箱状态做 checkpoint，其部署机制会合成缓存的 LLM 响应，使恢复后的 agent 不重放已完成的动作——这是在另一个层面上对本文所称 EO 性质的默认承认。DART [5] 工作在 API 之上，证明在已提交的下游消费者之下回滚何时可接受。两者都把原语自身的语义当作给定；契约层则先问那个更早的问题：原语本身可靠吗？成熟的恢复纪律环绕这一层，其定位见第 8 节；但没有一个规约或测量 agent 框架 resume API 本身。

**可比性与阅读指引。** 对每个框架，我们探测其官方文档记载的、用于持久 human-in-the-loop 或崩溃恢复的机制（工件的选择清单记录采用数字与抓取日期），并在每个平面上实例化同一个抽象工作流——把一个非幂等 effect 门控在人工决策上、在持久步骤之后崩溃——因此矩阵各行之间的分歧，正是迁移开发者所继承的那个隐患。文档语义（本节）与实测行为（第 6 节）按表 5 注 b 的分类规则严格分开。纵向深度随行为丰富度而定：LangGraph 横扫五个版本；其余头条格子在工件中做版本扫描（`results/sweep/`，附发布日期凭据）：六个 CrewAI 版本覆盖 2026-04-08 至 2026-07-24，CheckpointConfig 分歧在每一个存在恢复路径的版本上都在——与该功能同岁；三个 LlamaIndex Workflows 版本与三个 pydantic-graph 1.x 版本，并行的 2.x 线已不再暴露被探模块。快速版本迭代之下违反依然稳定：没有任何东西收敛到某个隐含规范。

## 3 RESUME CONTRACT（resume 契约）

**设计原则。** 这组性质不是事后排出来的 bug 分类；它们依次回答这样一个问题序列——任何需要确定性 resume 语义的调用方，也就是任何把非幂等 effect 门控在这个平面上的调用方，在跨过 interrupt / 崩溃 / resume 边界时必须能够回答：执行从哪里继续（PC）？effect 会重复吗（EO）？一次 fork 是什么意思（FD）？什么可以被持久化（CV）？什么消耗了授权（CO）？恢复是否仅仅是持久状态的函数（RD）？——再往下一层：fork 是怎样被请求的（FI，一条协议义务）。第 6 节观察到的失败实例化了这些问题；它们并没有产生这些问题。

### 3.1 抽象模型

**定义 1（Resume 平面）。** 一次运行按顺序执行任务 1..N；任务 t 携带一个非幂等的外部 effect e_t。其中一个任务 IP 是 interrupt 门控的：它的 effect 只有在某个 resume 值 v ∈ V 被消费之后才触发。完成任务 t 会把一条 checkpoint 记录 ⟨t, valid⟩ 追加到持久日志，并把持久前沿 F 推进到 max(F, t)。崩溃抹掉易失状态；恢复把继续点选为持久日志的函数。一次寻址到该 interrupt checkpoint 的 resume 携带值 v_k，并产生分支结果 o_k。

模型刻意抽象掉框架的细节——图的 superstep、事件队列、flow 监听器——只保留调用方编程所依赖的那个可观察接口：effect、checkpoint、interrupt、resume 值、结果、恢复决策。一个受门控的任务是最小的非平凡实例；跨多个门与并行分支的组合在本节末的 Scope 中处理，并在第 6 节探测。

下面每条性质都在这个接口上陈述，因此判定仅由表面上的可观察物决定；那些深入其下做插桩的探针（对抗性 saver、执行器轨迹、源码审计）只负责定位机制，从不决定格子。PC 的日志推导子句在任何有限探针集合上都是通过其可观察后果来认证的——状态相等且 effect 记录完好——而不是通过观察来源。

### 3.2 性质

**性质 1（PC：前缀续跑）。** 恢复从持久记录的前沿状态继续：恢复之后的执行或者从记录在前沿 F 的状态 S_F 开始，或者从一个仅由持久日志确定性推导出、且等于 S_F 的状态开始。记忆化的重放是符合的：前缀代码可以在恢复期间重新运行，只要每个前缀 effect 都从持久记录中取出（从而 EO 得到保持），并且重新推导出的状态是日志的纯函数。从初始值重新推导状态、或者带着活跃的 effect 去遍历前缀，都违反 PC。这里的相等是可观察状态的相等，而可观察状态在全文中恰好就是调用方与后续任务通过框架公开状态检查 API 能够取回的东西；内部表示不受约束。

**性质 2（EO：effect 恰好一次）。** 对每个任务 t，effect e_t 在一条分支上跨任意 interrupt、崩溃与 resume 的序列至多触发一次（作为安全不变量，EO 是 at-most-once；「恰好」由与第 4 节活性义务配对而来）。EO 只约束可观察的外部 effect，从不约束消息投递：一个已提交、但确认丢失的 effect 计为已触发，而针对丢失确认的重试纪律是注 4 中的幂等键组合。

**性质 3（FD：fork 确定性）。** 如果携带 fork 意图（定义 2）、取值 v1,…,vm 的 resume 被寻址到同一个 interrupt checkpoint，那么每个分支结果都满足 o_k = f(v_k)，其中 f 是分支语义；特别地，当 f 是单射时，v_j ≠ v₁ ⇒ o_j ≠ o₁。这里的 f 是决策函数：框架把所给值路由进受门控分支决策的方式，其确定性由门的构造保证；决策下游的模型或工具非确定性位于 f 之外，因此 FD 对非确定性 agent 也是良定义的。

**性质 4（CV：checkpoint 有效性）。** 每条被持久化的 checkpoint 记录都满足状态 schema：一个本会持久化 schema 非法状态的写入，以错误被拒绝，而不是被存储。

**性质 5（CO：仅消费一次）。** 共两个子句，这里先给出名字，因为后文会分别对它们量化。（CO-c，消费计数）一个 interrupt 至多被一次 resume 消费。（CO-e，effect 无作用）一次不带 fork 意图、寻址到已完成运行或已被消费 interrupt 的 resume——包括对先前 resume 的逐字节相同重投——对 effect 而言是惰性的。

这两个子句不可互换，而这一区别在下文有两处承重。当一次误投递触发了什么，CO-e 被违反；当授权被取走两次，无论其后是否有第二个 effect 跟着出现，CO-c 就被违反——一个从持久记录幂等地供给自己 effect 的门，可以在 effect 计数仍为 1 的情况下把同一次人工审批消费两次，结果是审批轨迹错了而 effect 账本是对的。本文测量到的跨进程失败（探针 159）正是一次 CO-c 失败，而且恰好也破坏了 CO-e；第 4 节的模型只形式化 CO-e，第 3.4 节则报告每个子句各自独立于什么。

**性质 6（RD：恢复确定性）。** 恢复决策（哪些任务跳过、哪些重新执行）是持久状态的函数：从相同的持久日志出发的两次恢复做出相同的决策。

**注 1。** CO 是 EO 在受门控任务上、限制在 effect 范围内的推论，单独命名是因为 interrupt 生命周期正是已部署系统集中行使人工权力的地方、审批轨迹是审计对象，而且一个框架可以在别处满足 CO 却违反 EO，一致性矩阵所示即为此。（依赖分析在第 3.4 节，该节同时声明这组性质并不完备、并给出候选的第七条性质；我们在此先标出这一关系，以免读者带着独立性假设读三页。）

RD 的动机来自我们在 LangGraph 同步持久化模式（#8039）中报告的一个排序隐患：一个已完成任务的待写入与取代它的 checkpoint 被送往同一个执行器，中间没有排序栅栏，因此两者之间的崩溃可能留下两种持久状态之一。RD 名下带着两项义务。按陈述，性质 6 是真正的确定性——相同的持久日志、相同的决策——模型校验它（清单 1），探针 118 与 128 直接测试它：两者都从同一份已提交的崩溃日志恢复两次（持久后端上经 sha256 校验的逐字节相同副本），每一对中决策都相同。

而 #8039 隐患还额外要求序不变性：无栅栏窗口内的崩溃与不止一种合法日志相容，而在每一种内部都确定、却在两者之间分歧的恢复，会让崩溃后的行为无法复现。探针 118、128、136 在已实现的崩溃对上测试这项更强的义务；Verus 恢复核心（第 7 节）只覆盖已完成的窗口，不覆盖被崩溃截断的那一对——这正是 LangGraph 实测的不变性与其崩溃路径 EO 违反能够自洽的原因。RD 的纳入早于任何观察到的失败。

### 3.3 fork 意图：让 FD 与 CO 可以同时满足

FD 与 CO 在同一个线上点约束行为——一次寻址到已被消费 interrupt 的第二次 resume——但方向相反：FD 要求新值在新分支上被采纳，CO 要求一次误重投是惰性的。没有判别器，两者在相同的流量上无法同时满足，因此契约不把「显式 fork」留在未定义状态：

**定义 2（显式 fork）。** 一个 resume 携带 fork 意图，当且仅当它带有一个分支判别器，把它与先前 resume 的重投区分开：一个不同的 resume 序号、一个显式 fork 标志，或者一个被框架自己的文档指定为可创建分支的地址。

**性质 7（FI：fork 意图可表达性）。** resume API 必须让定义 2 的判别器能够在线上表达。FI 是接口上的一条协议义务，而不是某条轨迹的行为性质；一个无法表达 fork 意图的 API，会迫使实现靠猜测来解决「重试还是 fork」，因而无法同时满足 FD 与 CO。FI 与各性质一起编号，是因为一致性报告需要为它留一列；它又被刻意排除在模型检查之外：它约束 API 能说什么，不约束轨迹做什么。

**定义 3（按意图索引的 FD 与 CO）。** 设一个意图标注给每个 resume w 分配一个外生标签 ι(w) ∈ {FORK, RETRY}——这是调用方的意图，不是 w 的字段。若每个标 FORK 的 w 都在一条新分支上被采纳、其受门控 effect 恰好触发一次，则称一个响应者满足 FD^ι；若每个标 RETRY 的 w 都对 effect 惰性，则称其满足 CO^ι。当线上带有判别器时，ι 可恢复，二者与 FD、CO 重合；当线上没有时，二者严格更强。第 6 节的矩阵只报告 FD 与 CO：没有任何探针能提供 ι。

**引理 1（无判别器时 FD–CO 不相容）。** 在一个 resume 不携带分支判别器的线上协议上——被接受的流量中没有，传输元数据在内；注 2 划定范围——没有任何响应者（确定性的也好、随机化的也好）能在该协议所允许的一切流量上同时满足 FD^ι 与 CO^ι（定义 3），只要在这种意图标注下两个标签都得到实现。

**证明。** 设 interrupt c 已被消费、记录值为 v₁，分支结果 o₁ = f(v₁)，该分支的 effect 已触发过一次。构造两次执行，它们在持久状态、线上轨迹、本地调度与环境输入（含时钟）上完全相同，直到并包括寻址到 c 的 w = resume(v₁) 到达为止：在 (a) 中，w 是传输重复，CO 要求其 effect 惰性；在 (b) 中，w 是调用方请求的 fork、再次回答 v₁，FD 连同逐分支 EO 要求一条新分支、其受门控 effect 恰好触发一次。响应者所能依据的每一个输入在 (a) 与 (b) 中都相同；唯一不同的是调用方的意图，而按假设线上无法承载它。确定性响应者对两者只产生一种行为，必然违反其中一条要求。随机化响应者对两者只诱导出一个分布；两种必需行为是互斥事件，因此其成功概率之和至多为 1，于是至少在意图之一上以 ≥ 1/2 的概率出错。矛盾。（这个构造是一个不可区分性论证：两次执行对响应者而言观察等价，只差一个线上无法承载的外生标签。）

**注 2（范围）。** 传输元数据在构造之内：被接受流量暴露的任何 request id、重试令牌或幂等键，都是定义 2 意义上的判别器，从而使 FI 成立、引理不适用；该不可能性针对的是被接受流量不携带此类比特的协议——也就是被探的 LangGraph 面。此外，这个构造预设两种意图都可允许：一个排除重复、或禁止同值 fork 的环境，可以让一侧为空来脱身——那是关于环境的事实，而不是关于响应者的事实；在被探的本地 API 上，两者都以调用方调用的形式到达。

引理 1 刻意不是对 LangGraph 缺陷的解释。它的作用更为前置：它是 FI 必要性的定理形式——只要求 FD 而不要求 FI 是不自洽的。LangGraph 是更棘手的第二个案例：它的文档给「显式 checkpoint 地址」两种读法——创建分支的时间旅行与重放（第 2 节）——于是在第一种读法下该地址满足定义 2 第 3 款、在第二种读法下却起不到判别作用；FI 至多在一种有文档的读法下成立，这种双重文档本身就是 FI 所指缺口的一个实例，而且无论哪种读法该循环都供给所记录的值（FD 失败）——这个分解仍然把缺陷定位到供给逻辑，正是探针 134 的修复所利用的那条接缝。充分性只以构造方式主张：只要判别器存在，一个按它做分支键控的响应者就能让 FD 与同值重放幂等性同时成立——已在模型层面机器校验（LGF-B，表 2）；LGF 是一个只供给结果、没有 effect 状态的模型，因此 CO 中与 effect 相关的那一半改由 REMIT 的逐分支账本来行使（第 7.3 节）。

FI 正是 REMIT 的 ⟨checkpointId, resumeIndex⟩ 键控所提供的东西，也是被探的 LangGraph 协议所缺少的：`Command(resume=v)` 与 resume-map 形式都不携带重试/fork 比特，而探针使用的地址——一个先前的 `checkpoint_id`——恰恰是持久化文档作为可创建分支的时间旅行原语呈现给用户的那个 [8]。因此第 6 节的 ✗ 判定在两种有文档的读法下都成立，而 FI 命名的正是使这种歧义成为可能的协议缺口。

### 3.4 部分独立性（接口相对）与经验必要性

「六个是不是正确的数量」由一个逐不变量故障矩阵来回答——每个 ResumeContract 故障模型对每条性质各检查一次，外加状态重建模块；共 39 次 TLC 运行，见表 3——其中干净的行恰好就是逻辑独立性论证所需的分离模型，并由一个伴随模块补足，该模块提供那些部署机制开关所纠缠住的三个见证（再加 21 次运行，`R10_Separations.tla`，每个判定、状态数与反例深度在两种环境下都相同）。

这个 39 格矩阵在 R8 常量下重新推导、每格判定相同（凭据在 `results/tla/independence_r8/`），因此这些分离不是小配置的产物：反例随空间增长而加深——fork 故障从深度 5 加深到 8、双重消费从 6 加深到 13（单 worker 的最小深度，凭据在 `results/tla/singleworker_20260806/`；矩阵文件记录的是 16 worker 的中止时轨迹，可能更深）——而每一个干净的格在大四个数量级的状态空间上依然干净。

标题由三个范围词限定：这些分离是**接口相对的**——在定义 1 的词汇表上建立，契约本身就在这个域上陈述，这也是每条独立性主张对其签名的相对性；是**见证完备的**——每个见证在两个界集下都被完全探索，R8 下每个成立的格都穷尽 1.0–1.4×10⁶ 个不同状态，而参考运行只有 59–396；也是**部分的**，因为有一条依赖（CO 对 EO）是结构性的。

有一个区别承担了证明论上的分量，在此只说一次。分离主张是不可蕴涵 S ⊬ P，而不可蕴涵在任何逻辑中都通过展示 S∧¬P 的一个模型来证明：一个契约接口上的结构，其中合取成立而目标失败。一个完全检查过的有限见证就是这样一个模型，可以一劳永逸地了结该主张。TLC 对见证可达空间的穷尽广度优先枚举，就是对该见证的完整验证——对其常量所定义的结构并不存在「界之外」——因此命题 1 的不可蕴涵是通过展示建立的、从不采样，而 R8 的重新推导是「见证并非退化配置」的佐证，不是其有效性的来源。

真正界相对的是全称那一侧：参考语义满足合取式（R0/R8）、以及每条故障被发现的足迹是完备的，这些都是对所有行为的主张，在给定常量下穷尽、在常量之外沉默。TLAPS 现在把前者无界 discharge（第 9 节）；足迹完备性恰好保持这种界相对地位，而要把已经展示的见证变成证明并不需要任何 TLAPS 步骤。

**命题 1（部分独立，机器校验）。** 在定义 1 的接口上（形式化于第 4 节）：

**(i)** FD 逻辑独立于其余五条性质的合取：ForkIgnore 模型在参考界下、于其全部可达状态空间满足 EO、PC、CV、CO 与 RD（TLC 完成、无错误），同时违反 FD。

**(ii)** CV 同样独立，由 InvalidPersist 见证——一个结构上很容易的分离，而且是有意如此：没有别的不变量读取有效性位，因为契约把 CV 陈述在写入上，所以它在模型内的独立性是定义性的；而部署中真正重要的耦合——非法状态被下游消费——是一个经验问题，由下游后果探针回答（探针 150，第 6 节）。

**(iii)** 在非空洞的见证上，集合中没有任何单条性质蕴涵 PC：EO 不蕴涵 PC——状态重建模型（R7）在其全部状态空间上满足 EO 而违反 PC——FD、CV、CO、RD 也都不蕴涵 PC：(iv) 的 PrefixReplay 模型违反 PC，而那四条在其全部状态空间上非空洞地成立。R7 其余的格是空洞的（机制不存在）；空洞的格分离不了任何东西，表 3 如实标注。

**(iv)** CO 可以拆分，且只有一个子句是依赖的。CO-e 不独立于 EO：在 `ResumeContract.tla` 的形式化中，该不变量是 `effects[IP] <= 1`，也就是限制在受门控任务上的 EO，因此 EO ⇒ CO-e，且每个 CO-e 违反都是 EO 违反——矩阵证实了这一点，而且我们直说：这条蕴涵是关于两个公式的事实，而不是一个发现——无论转移关系如何它都成立。CO-c 则独立于其余全部六条的合取，包括 CO-e。

CO-c 的见证是一个丢失更新模型（`R11_ConsumeCount.tla`，凭据在 `formal/tla/consumecount/`），它带一个消费计数器，并允许第二个竞争者在第一个竞争者的清除写落地之前就读到已挂起 interrupt 的等待标志。其参考格精确复现 R0（87 生成 / 59 不同）；保守性由构造保证——竞争者禁用、计数器是既有轨迹的函数、动作字母表与 R0 相同——而 87/59 的恒等就是该构造的可执行检查。打开竞争、且门从持久记录幂等地供给 effect 之后，TLC 在 127 生成 / 95 不同状态上完成，TypeOK、EO、PC、FD、CV、CO-e 与 RD 成立，CO-c 在深度 5 被违反；同一判定模式在更宽的界下重新推导（8,191 个不同状态，反例深度 6）。

这不只是记账问题：CO-c 正是实测跨进程失败所破坏的那个子句，而在它被当作不变量携带之前，模型无法表达本文自己的头条组合结果。CO-e 的蕴涵是单向的，其逆向在模型内有一个分离见证：PrefixReplay 模型——恢复从任务 1 重启、而受门控任务的 effect 从持久记录中取出，这正是 LangGraph 实测崩溃路径的记忆化门纪律——违反 EO（在一个非受门控任务上）与 PC，而 FD、CV、CO 与 RD 在其全部可达状态空间上成立（TLC 完成，287 生成 / 183 不同状态）；真正行使到门的那条崩溃路径轨迹本身，由已发布的 R9W 配置见证（消费；在前沿 IP 处崩溃；重放；门从记录中供给）。

**(v)** RD、PC 与 EO 各自独立于其余五条的合取，由一个伴随模块（`R10_Separations.tla`）见证，其三个开关是本研究观察到的机制的 effect 安全或控制安全变体，每个都构造为恰好一条性质失败、其余五条在其全部可达状态空间上成立（TLC 完成、无错误、参考界下）：**Regate**——在持久状态相同时，一次恢复越过已消费的门继续、另一次把门重新武装，重新消费从持久记录中供给，于是恢复决策不同（RD ✗），而没有 effect 被触发两次、也没有已完成任务被重新执行；**Rebuild**——确定性重启，工作状态取自初始值而非从日志重新推导，每个前缀 effect 都从记录中取出（PC ✗）；以及 **Redeliver**——持久前沿任务的 effect 被 at-least-once 地重新发出，而控制流越过它继续、受门控任务被排除在外（EO ✗）。

在原有的开关集合内，这三者没有一个能分离，因为非确定性恢复的足迹是 {EO, PC, CO, RD}——它的重放分支会重新执行前缀——而这种纠缠本身就是下面记录的发现。总之：对 EO、PC、FD、CV、RD 与 CO-c，已建立对「其余性质合取」的独立性；只有 CO-e 按 (iv) 是定义性依赖的。

**两条评注。** 尽管有 (iv)，CO 仍作为具名性质保留，因为它隔离出一个性质不同的生产机制——误投的重复投递与崩溃重放之别——而且框架数据呈现出同样的单向结构：LangGraph 1.2.9 在崩溃路径上违反 EO，而在同一配置上 CO 成立（表 5）。而 (v) 记录的纠缠本身就是一项发现：分支中含重放的恢复不确定性会把重放的破坏一并拖来——这正是 CrewAI 恢复凭据在实况中展示的——这也是为什么那些见证是 effect 安全的变体：它们展示的是逻辑独立性，而不是「任何框架一次只违反一条性质」。

经验一侧自有其分量。对 EO、FD、CV、CO 以及活性义务中的每一条，都存在一条观察到的框架路径，在其上该性质失败、而其余性质在该路径上成立；每一条观察到的 PC 违反（CrewAI 从初值重建的恢复）都与一次 EO 违反同时发生，因此在框架层面，PC 的必要性是与命题 1(iii) 的模型层面分离**一起**被主张的。三个主张，严格分开：(i) 经验必要性，按上述观察到的路径；(ii) 形式化的部分独立——命题 1；(iii) 不主张任何关于最小性、完备性或充分性的定理。

这组性质不是从失败清单反向工程出来的：RD 是从恢复问题进入的，当时和现在都没有观察到的失败。CO 的陈述同样与测量前的集合一致；测量所锐化的是**哪条路径**为它作证：激发该性质的那个顺序误 resume，被被探平面拒绝了，而来自第二个进程的同一投递却被接受（探针 159），于是该性质是在并发路径上挣得其经验必要性的。

**为什么是六个——会不会有第七条？** 每个问题一条性质，对应调用方跨过边界时必须能够回答的问题，而 FI 是 fork 那个问题所需的协议前提。合并被上面的分离挡住；再拆分则没有任何观察到的机制支持。候选的第七条以范围排除的形式列出：跨版本 checkpoint 迁移有效性、一个 effect 可见性排序义务、以及被丢弃 resume 的大声与静默处置（第 6 节把最后一条标为规格级缺口）。

**范围与组合。** 定义 1 是线性化的：性质按因果链陈述，而一个 DAG 的并行分支各自就是这样一条链；跨门的顺序组合与同一 superstep 上的并发扇出都已被探测（第 6 节，探针 138、141），更深的嵌套与多 checkpointer 的扇入仍是未来工作。从未通过公开状态 API 浮出的不可见投机执行，位于契约之外。CV 按 schema 版本成立，而 checkpoint 迁移是一个具名排除：在 schema v 下有效的记录，在 v+1 下不是 CV 的对象，因此演进需要在任何 resume 之前有一个显式的迁移步骤——一个静默自动迁移的平面会恰好把 CV 所指的隐患重新引入（REMIT 的门相对于加载时所提供的 validator 作答）。CO 的 resume 身份是 checkpoint 地址加负载；传输元数据被排除。这些性质不主张彼此正交——一次 CV 失败会动摇 CO 所依赖的可寻址性——因此一致性按性质分别报告，从不合并成一个比特。

**注 3（合取式买到了什么，非正式）。** 在定义 1 之下：EO 与 CO 固定 effect 的重数，PC 固定继续状态，RD 固定恢复选择，CV 固定日志完整性，FD 连同 FI 固定分支结果——合起来，调用方可见的结果是输入、持久日志与所给决策的函数。这是定位，不是定理；R0/R8 在模型上机器校验这个合取式。

**注 4（fork 与恰好一次）。** EO 按设计是逐分支的：fork 是用户请求的下游执行复制，所以受门控 effect 对每个被请求的分支合法地触发一次。契约禁止的是没人要求的复制——分支内部跨崩溃或 resume 的重新执行（EO），以及由什么都没请求的 resume 所触发的 effect（CO）。如果某个部署连被请求的分支 effect 也不可接受，那就在 effect 本身上把 FD 与幂等键组合起来；契约管的是这个平面，不是支付处理器。

**注 5（与经典语义的关系）。** 限制在崩溃恢复上的 EO，是 exactly-once 处理在工作流中的类比（是状态管理，不是投递 [10]；全书中 EO 都是 effect 保证，从不是消息投递）；EO/CO 重述了 Helland 论证为不可避免的应用层幂等纪律 [11]、[12]；PC 的记忆化重放子句刻意就是为 Durable Functions [13] 形式化、并被事件溯源 actor [14] 实践的那套纪律，因此基于重放的恢复符合 PC，而 CrewAI 从初值重建的恢复不符合；RD 是回滚恢复 [15] 意义上恢复函数的确定性。贡献不在于这些概念本身，而在于把它们组装成一组可校验的义务，用于一个今天对它们未作陈述、互相分歧、而且正被违反的 API。

## 4 机器校验模型

本节的验证对象始终是**规格**，而不是任何框架：TLC 穷尽参考语义及其故障变体，而第 4.3 节那个源自框架的模块是一个单独标注的、由专家建立的抽象。模型继承契约的范围排除（第 3 节）。

### 4.1 TLA+ 模块

我们把定义 1 与性质 1–6 形式化为一个 TLA+ 模块 `ResumeContract.tla`（251 行，在工件中），并配一个消费计数的伴随模块 `R11_ConsumeCount.tla`，后者携带基础模块的原子 `Consume` 无法表达的 CO-c 不变量（这一配对的动机在下面陈述该缺口处给出）。状态由程序计数器、逐任务 effect 计数器、checkpoint 日志、持久前沿、interrupt 标志、已消费值、fork 值与 fork 结果的序列、崩溃计数、恢复历史（持久前沿与决策的配对）以及一个前缀回退标志组成。动作是 `ExecTask`、`EmitInterrupt`、`Consume(v)`、`ForkResume(v)`、`CrashRecover` 与 `ExtraResume`。六条性质是状态不变量；清单 1 原样给出其中四条。

```tla
EffectExactlyOnce ==
\A t \in Tasks : effects[t] <= 1
ForkDeterminism ==
\A k \in 1..Len(forkOuts) :
  forkOuts[k] = f(forkVals[k])
CheckpointValidity ==
\A k \in 1..Len(ckpts) : ckpts[k].valid
RecoveryDeterminism ==
\A i, j \in 1..Len(recHist) :
  recHist[i].dur = recHist[j].dur
  => recHist[i].dec = recHist[j].dec
```

**清单 1　`ResumeContract.tla` 中的契约不变量（摘录）。**

六个布尔故障开关选择参考语义或某一类观察到的违反——每个开关转写的都是一个已部署的机制，而不是对目标性质的否定，表 3 随后测量每个机制实际上破坏了什么：`FaultReplay`（恢复在恢复后的状态上从任务 1 重启——CrewAI 的恢复纪律，以及 #7361 回归类）、`FaultForkIgnore`（同一 checkpoint 上的第二次 resume 被回答成第一个分支的结果——#6663）、`FaultInvalidPersist`（一条 schema 非法的完成记录被静默持久化——#6491 类）、`FaultNondetRecovery`（在持久状态相同时跳过还是重新执行不受约束——#8039）、`FaultDoubleConsume`（一次误 resume 在已完成的运行上重新触发受门控 effect——#2315 类 [16]），以及 `FaultPrefixReplay`（恢复从任务 1 重启、而受门控任务的 effect 从持久记录中取出——记忆化的门前缀重放，LangGraph 1.2.9 的崩溃路径类，见探针 118/133；在那些测量之后才加入）。

一个已发布的见证配置（R9W）校验「行使到门的状态」的否定，其 `recHist` 合取式强制崩溃之前发生过消费；TLC 深度 7 的反例就是端到端实现的记忆化门崩溃路径——interrupt 被消费（前沿到达 IP），崩溃从 dur = IP 恢复，前缀重放重新执行任务 1（这就是 EO 违反），而重放的那一遍跨过门、受门控 effect 从持久记录中取出，`effects[IP]` 在整条轨迹上保持不变。

活性那一行补上了一个空洞性漏洞：一个拒绝一切 resume 的框架会满足全部六条安全不变量，所以契约把它们与 `EventuallyCompletes` 在弱公平性下配对，这一点在参考配置上得到验证（而一个崩溃后持久状态无法恢复的已部署框架，在精神上违反它，见第 6.4 节）。

R1 的反例值得对着实况数据读：执行任务 1（⟨1,0,0⟩，前沿 1、已持久）；崩溃并重放；再次执行任务 1（⟨2,0,0⟩）——EO 在四个状态上被违反。第 6 节在 CrewAI 中实测了同样的算术：任务 1 已持久化，任务 2 崩溃，resume，已完成的任务再次触发，把计数器顶到 12，而 exactly-once 预测的是 11。

**建模假设，以及这些校验意味着什么。** 调度器状态与消息管道被抽象掉了——这正是性质本身所量化其上的那层抽象。故障开关注入的是在已部署框架中观察到的机制，表 3 发现每个机制破坏了什么；这些都不说明规格刻画了任何一个框架，那份负担落在第 4.3 节与那些测量上。配置是一个旋钮，不是天花板：参考空间是让每条性质都可被证伪的最小空间，而 R8（10 个任务、interrupt 在 5、4 个值、5 次 resume、4 次崩溃、4 次额外 resume）在 1.47×10⁷ 生成 / 7.4×10⁶ 不同状态、深度 24 上通过六条不变量加 TypeOK——这是在这些常量下对完整可达空间的穷尽广度优先检查——而 fork 故障在单 worker 搜索下仍在深度 8 给出反例。（在扩大的故障运行上，多个 worker 会竞相撞出反例，因此那里只有「哪条不变量被违反」是稳定的凭据；此处报告的每个深度都是单 worker 深度。）

模型有三处范围边界是被陈述的、而不是被发现的。**第一**，被建模的崩溃是一次恢复决策事件：`CrashRecover` 带有「没有 pending interrupt」的前置条件，因此当运行正挂起等待人工时发生的崩溃，不在本模块的转移关系之内。该情形由探针 158/158b/158c 在全部三个会挂起的平面上做经验覆盖，并由伴随模块 `ResumeContractParked.tla` 做形式覆盖：在持久挂起之下——这是每个会挂起的平面的实测行为——六条不变量与活性义务在两个界集下都成立，故障矩阵重新推导、判定与深度与表 3 一致；在易失挂起之下，六条安全不变量成立而 `EventuallyCompletes` 被违反——靠「死掉」换来的安全，pydantic-graph 的处置方式（第 6.4 节），现在是一个模型级反例而不只是一个实测格（凭据在 `formal/tla/parked/`，两种环境）。

**第二**，fork 分支是结果层面的：`ForkResume` 记录值与结果、不触发任何 effect，因此注 4 的逐分支记账是 REMIT 账本（第 7.3 节）的性质，而不是本模块的。**第三**，也是最要紧的一条：CO-c 在这里根本不可表示：`Consume(v)` 原子地清除 waiting，因此对一个活着的挂起 interrupt 的第二次消费，不是这个转移关系所允许的行为，而且模块不带消费计数器。这是一个真实的缺口，不是抽象选择，因为第 6 节的跨进程失败正是那第二次消费；而且 `FaultDoubleConsume` 不是它的影子，它由 `pc = NTasks + 1` 守卫——一次已完成的运行，也就是被探平面所拒绝的那个顺序机制。

伴随模块 `R11_ConsumeCount.tla` 补上这个缺口：一个消费计数器，CO-c 与 CO-e 作为两条独立不变量，外加一个额外的竞争者在第一个竞争者的清除写落地之前读到等待标志——正是探针 159 的双竞争者形态，竞争者被供给自己的值（FD 完好，如实测）且不追加 checkpoint（重复对框架状态不可见，如实测）。其参考格精确复现 R0（87 生成 / 59 不同），这是「由构造保证的保守性」的可执行检查（竞争者禁用；计数器是 R0 轨迹的函数）。打开竞争、且门幂等之后，TLC 在 127 / 95 个状态上完成，EO、PC、FD、CV、CO-e、RD 与 TypeOK 成立，CO-c 在深度 5 被违反——这正是命题 1(iv) 的分离见证。若竞争连 effect 也触发，被发现的足迹是 {EO, CO-e, CO-c}，PC、FD、CV、RD 干净，与探针 159 逐格吻合。两种模式在更宽的界下都重新推导（8,191 个不同状态，深度 6）。该模块的 32 格矩阵在两套独立配置的环境之间、以及跨一个 JDK 大版本复现，因此这些计数是模块与检查器的性质，而不是工具链的性质。

活性只使用弱公平性——没有动作会在竞争中被反复禁用又重新启用，因此强公平性只会增加假设而不带来定理——而且它是一次进展检查，不是可用性声明。分工如下：TLC 校验协议；Verus（第 7 节）校验 REMIT 的不变量——从不校验那些框架。

### 4.3 一个源自框架的模型：fork 违反是重放幂等的影子

故障开关运行证明的是契约足够精确、可以校验；它们对框架什么也没说。第二个模块 `LangGraphFork.tla` 在 fork 这一轴上补上这个缺口。它把 LangGraph 的 resume 路径建模为一个与持久化文档、以及 #6663 复现行为相一致的操作抽象：投递到某个 (thread, checkpoint) 的 resume 值被记录为一次 pending 写，而一次寻址到「已带有 resume 写的 checkpoint」的调用，会重放所记录的写而不是记录新的写。模块中不存在故障开关。TLC 发现了违反：两次调用提供 ⟨va, vb⟩ 时，被供给的结果是 ⟨va, va⟩——FD 在深度 3 被违反（LGF-A）——而 `ReplayIdempotence` 始终成立。合起来这就是发现：那条「记录写」的规则正是让同值重复调用幂等的东西（一个设计出来的性质），也正是破坏 fork 的东西——#6663 不是疏忽，而是一个设计选择的影子。修复后的算法——pending 写按 (checkpoint, resume 序号) 键控，正是 REMIT 的分支键控——同时验证幂等性与 fork 确定性（LGF-B）。

被建模的规则在源码中有出处。`InMemorySaver.put_writes` 中的去重守卫只跳过非负的写索引，而写索引表把 resume 通道映射到一个负槽位（`__resume__7 → −4`），从而把它豁免掉；持久 saver 则对这些通道做 upsert。因此第二个 resume 值被持久地记录下来——记在 null task id 之下——却从不被读取：绑定点在任务准备处，`pregel/_algo.py` 中的 scratchpad 构造器按优先级解析一个任务的 resume（先用任务记录的；null 任务只经 `get_null_resume`；resume-map 的值追加在已记录列表之后），于是寻址到某个「任务已带着被消费的 resume」的 checkpoint 的调用，无论它提供什么、无论哪种调用形式，都被供给所记录的值。

探针数据证实每一条：该违反在裸形式与 resume-map 形式下、在全部三个后端上都相同（探针 126、127、130）；存储转储显示两个值都持久存在、而第一个被供给了两次；fork 键控的 saver shim 无法修复它（探针 125）——saver 层面的任何键控都无法推翻一个 saver 从不做出的决策。模块中的「记录写」规则就是这个优先级在规格粒度上的表述，相关责任行在工件中被引用：

## 5 一致性方法学

### 5.1 设计原则

harness 遵守三条约束，使每个判定都确定且可移植。

- **不用 LLM。** 所有探针都用纯 Python 任务与确定性值驱动持久化 API；没有任何判定依赖采样、供应商状态或提示行为。
- **无时间窗口的崩溃注入。** 每个崩溃判定都在不依赖时间窗口的情况下决定：矩阵中的崩溃基于异常；探针 133 用文件系统栅栏同步的 SIGKILL 杀死进程；探针 137 把杀死点扩成三点矩阵；探针 160 则穷尽该接口——每个持久化操作跑一次，由一个串行化包装器把持久前缀恰好冻结在那么多已完成操作上，每个点的冻结都自审计。没有 sleep 窗口竞争、没有杀死时刻分布：一个崩溃一致性判定是协议性质，在固定依赖解析与运行时下与主机无关，而工件钉住的正是这两项。三个并发格（探针 159、168、174）是具名的例外，因为它们的对象是一场竞争：其判定是存在性主张，由外部账本决定、以观察到的频率报告——在测量范围内饱和到 1.0——从不作为无时间窗口的协议事实。置信区间只出现在真实（live）格上，那些重复是真正的样本。
- **effect 账本 oracle。** 每个带副作用的任务递增一个进程内计数器；EO/CO 读计数器，PC 读执行顺序与状态血缘，FD 把分支结果与所给值比较，CV 在一次违反 schema 的写入之后检查持久日志，RD 跨构造出的持久状态比较恢复决策（探针 118、128）。在持久后端探针上，计数器由一个磁盘上的 SQLite effect 账本交叉核对，独立于 checkpointer 数据库与进程内存；两个 oracle 在每个报告的格上都一致（探针 126）。

两个 oracle 都位于框架状态之外：正如 CrewAI 恢复凭据所示，框架可见的状态可以看起来正确，而账本记录到一次重复。账本不需要与 effect 做两阶段提交：在持久后端与杀死探针上，effect 就是账本的那次追加——一条自动提交的 INSERT，在任务返回之前就已持久，每一次杀死都由该 INSERT 之后的一个持久事件把关——因此按顺序账本就等于触发了的 effect，而唯一可能的错误接线（一条丢失的记录）只会少计，从而使每个报告的重复都是一个下界。探针 163 机械地检查这个顺序：在 INSERT 之前、之后、以及框架的持久写之后杀死，崩溃后的计数分别是 0/1/1，而且只有 INSERT 之后的窗口会在 resume 时重复（1 → 2，每次重复、两种环境）。

RD 需要的不只是直线协议：它关心持久化操作的顺序，所以其探针构造的是「在两个无序操作之间崩溃会留下的那两种合法持久状态」——通过一个丢弃型 checkpointer 做穷尽探索——而不是去和杀死赛跑。两种交错、两次确定性 resume、一次比较。

每个探针都把原始 JSON 与稳定视图 JSON 写进 `results/` 下按活动划分的证据目录（每个活动一个子目录），并生成清单；论文中的数字只从已提交的证据主张，工件的审计会重新推导它们。以真实密钥为门的生态检查按 API key 把关、没有密钥就跳过，其稳定字段只有 effect 计数器（第 6.5 节）。

## 6 一致性结果

表 5 是一致性矩阵。我们逐条凭据走一遍。

### 6.1 LangGraph 1.2.9：fork 违反与静默的合法性违反

**FD（✗，issue #6663；全部三个后端；两种调用形式）。** 一个单节点图发生 interrupt；探针记录该 interrupt checkpoint 的 `checkpoint_id`，并向同一个 `(thread_id, checkpoint_id)` 发出两次 resume：先是 `Command(resume=True)`，再是 `Command(resume=False)`——也就是持久化文档作为「可创建分支的时间旅行原语」呈现给用户的那个地址 [8]。实测：第一次 resume 返回值 1，第二次也返回 1——所给的 False 被静默忽略，第一个分支的结果被重新供给——而且对后端与调用形式都不敏感：在 SqliteSaver 与真实 PostgresSaver 上相同（探针 126、130），在以 interrupt 为键的 resume-map 形式下也相同（探针 127、130）。按第 4.3 节，第二个值被持久记录、却从不被读取——一个对同一次审批给出不同回答的人工，被给予了第一个答案的后果；第 7 节修复这一格（探针 134）。

**CV（✗，#6491 类——现已静默；全部三个后端）。** 一个基于 pydantic 类型状态（`items: List[str]`）的图运行一个追加 `None` 的节点。如最初报告的那样，非法输出被持久化、随后的 `get_state_history` 抛错、线程变得不可读；在 1.2.9 上，调用与历史读取都不抛错，而 schema 非法的值持久存在，在全部三个后端上相同（探针 126、130）——一次严格的 CV 违反，而且更糟，因为没有任何东西向调用方发出信号。下游后果探针（探针 150；双主机复现）把「静默」的含义按制度分开：终端写入完全静默——`get_state` 返回损坏的值，对它做 `model_validate` 抛错，而且这种静默在新进程的 SQLite 反序列化下依然存在——而图中途的写入是「延迟大声」的：损坏记录在 ValidationError 浮出（晚一个 superstep）之前就已持久，此后该线程自己的读 API 会抛错（这就是最初 #6491 的症状）。后续一次干净的运行只有靠完全覆盖输入才能逃脱，损坏的历史被保留在其下。

**RD（✓，在 checkpointer 粒度上；两种持久状态顺序；两个后端；执行器层已插桩）。** 探针 118（内存）与 128（SqliteSaver）以构造的方式了结 checkpointer API 层面的问题：一个丢弃型 checkpointer 在那对有争议的持久化操作周围构造出两种合法持久状态，而在每个后端上两者都恢复到相同的决策与 effect 计数。探针 124 记录了 #8039 所指那一层的真实提交顺序：在同步持久化下是 ⟨put, put_writes, put⟩，任务结果写入与 superstep checkpoint 相邻且无栅栏——这就是被直接观察到的 #8039 前置条件。探针 136 消除了与执行池赛跑的任何必要：一个对抗但合法的 saver 把每个 `put_writes` 都推迟到随后的 `put` 之后——这就是失败调度的持久顺序，且是确定的——注入的崩溃留下真正分歧的持久状态，而从两者恢复在结果与重新执行计数上都相同：针对已实现的隐患，RD 在 1.2.9 上成立（注 1）。

**EO 按路径分裂（✓ interrupt / ✗ crash；分类已定）。** 在每一次持久化操作都完好的情况下——任务的结果经 `put_writes` 持久记录——崩溃后的 resume 会重新执行那个已完成的任务（崩溃时 effect 计数 1，恢复后 2），在 SqliteSaver 与 PostgresSaver 上复现，持久账本一致（探针 126、130）。文档审计了结了分类问题：pending writes 一节说明，已完成节点的写入被存储，正是为了让恢复时「you don't re-run the successful nodes」[8]；而实测行为重新运行了那个写入已持久的成功任务，因此这一格相对框架自己陈述的语义是 ✗。机制上，interrupt-resume 记忆化已完成的任务结果（#6792，已修复），而崩溃-resume 不记忆：同一个 API 上，跨 interrupt 是 exactly-once，跨崩溃是 at-least-once。

探针 133 回应「那只是基于异常的崩溃」这一反对：SIGKILL 在持久写之后栅栏同步地杀死，在新解释器中恢复，已完成任务同样重新执行（账本 1→2）；探针 137 扩到三个杀死点、每点三次重复，逐字节稳定。同进程重试的对照（探针 141）：异常在重试时保留已完成的兄弟任务，而进程死亡后的恢复不保留。

**interrupt 路径上的 PC/EO（✓，带回归历史）。** 从 interrupt checkpoint 恢复不会重新执行 interrupt 之前的节点（相对 1.1.x 的回归，#7361 已修复），函数式 API 的管线在 sync 与 async 变体下恢复时都不重新执行任何东西（#6792 已修复）。**CO（✓，全部三个后端）。** 完成之后的一次误 `Command(resume=...)` 被吞掉：interrupt 之后的 effect 计数保持 1、最终状态不变，在全部三个 saver 上相同（探针 126、130）。这种吞掉是静默的——契约得到了满足，但调用方没有收到任何「一次 resume 被丢弃」的信号，这是完整研究将要跟踪的一个规格级缺口。

**注 c**　pydantic-graph 的 ✓ 格受一个可恢复性失败限定：崩溃之后 `iter_from_persistence` 抛出（`GraphRuntimeError`，无法恢复）——因为没有任何东西恢复，所以 effect 不重复，安全成立而进展失败（第 6.4 节）；v2.x 完全移除了持久化机制。

**注 d**　AutoGen：对同一份已保存状态的二次恢复没有增加任何 effect（探针 140）；这个平面上不存在 interrupt 授权轴，因此 CO 按「恢复惰性」报告。AutoGen 的平面在框架侧什么也不持久化——`save_state` 把状态交给调用方，由调用方负责持久性——所以性质 4 的写入子句在框架侧没有实例；被探的 CV 类比是加载时对调用方所给状态的校验，✓ 证明的正是这一点（被篡改的是调用方持有的副本，从不是框架持久化的任何东西）。

**注 e**　持久后端上的 CO 按并发分裂：顺序重投是惰性的（探针 126、130），而来自两个并发 OS 进程的同一投递会触发受门控 effect 两次，在开发机的两个持久后端上都是 10/10（探针 159；容器复现次数较少、且每次都重复）——默认打包的 REMIT shim 不修复这一格（shim 启用时仍 10/10；它的定序器是每进程的），而 shim 的可选跨进程门（v0.1.2）修复了它：两个持久后端上均为 {1:10}，输家在任何节点执行前被大声拒绝（第 7.2 节）。

### 6.2 LlamaIndex Workflows 2.22.2：分歧而非违反——以及一个干净的 fork

两步 HITL 模式（一个步骤返回 `InputRequiredEvent`，第二个步骤消费 `HumanResponseEvent`）各方面都干净：在 interrupt 处快照、恢复，interrupt 之前的步骤计数器保持 1（PC/EO）；对同一份快照恢复两次、分别回答 YES 与 NO，得到各自的结果（FD——LangGraph 失败的性质，LlamaIndex Workflows 通过）；向一个活着的运行再投一次响应被吞掉、后续步骤只触发一次（CO）；序列化一个含有不可序列化对象的 context 会以 `ValueError` 快速失败（CV）。

`wait_for_event` 惯用法——文档记载的持久 HITL 模式——按设计表现不同：恢复一个已序列化的 context 会重新执行步骤前缀（计数器 1→2），正如文档所警告的那样（「make any preceding work safe to re-execute」[2]）；是 D，不是 ✗。更锐化的主张是：这个生态的问题在于，同一个 API 形状之下同时存在 exactly-once 的声称、at-least-once 的文档、以及静默的重放，而没有任何东西告诉调用方自己正处在哪种制度里。

### 6.3 CrewAI 1.15.2：状态中不可见的重放

**@persist（U）。** 用已持久化的 id 重新 kick 一个已完成的 `@persist` flow，会恢复状态并重新执行两个方法：状态计数器从 11 变成 22，两个 effect 计数器都读到 2。标签按表 5 注 b 得出：该功能的文档在两个方向上都没有陈述恢复纪律，因此这些格是 U——重复被测得并完整报告，只等一条可引用的陈述来定标签。崩溃 resume 变体是无可争议的那一例：方法 s1 完成并持久化（计数器 1），s2 抛错；用同一个 id 重新 kickoff 会重新执行 s1，运行结束时计数器为 12，而 exactly-once 预测的是 11——一份状态和一个外部 effect 被复制了。这正是 R1 反例的算术，实况呈现——而且不是异常语义的产物：在 SIGKILL 下，每一次重复都复现该复制，第二个 effect 由一个在第一个触发时尚不存在的进程触发（探针 164，两种环境）。

**CheckpointConfig（✗）。** checkpointing 功能的文档陈述恢复「resume[s] without re-running completed work」[1]。在 1.15.2 上实测：启用 checkpointing 后，s1 完成、其 checkpoint 被写入（状态计数器 1、已持久），s2 抛错；对最新 checkpoint 调用 `Flow.from_checkpoint` 再 `kickoff()`，会重新执行那个已完成的方法——s1 的 effect 计数器读到 2。最终状态计数器读到 11——数值上正是 exactly-once 的答案——因为状态是从初始值重建的而不是被恢复的，所以这次复制在框架状态里不可见、只在外部 effect 账本中可见。如果 s1 是刷一张卡，那么卡被刷了两次而 flow 的状态看起来是对的——正是这条凭据让 harness 的 oracle 必须放在外部。若维护者声明采用「只含状态」的语义，按注 b 的规则该格会重新归类为 D，改变的只是标签、从不改变测量。

**一项撤回的观察。** 一次在临时虚拟环境中的探索性运行曾提示，文档中的 Flow 事件配置（`on_events=["method_execution_finished"]`）不写任何 checkpoint 文件。在钉住的、由 lockfile 解析的环境中，同一配置会写 checkpoint；「零文件」的观察被撤回，探针 115b 保留为回归守卫。一个探针、两种环境、两个答案：一个一致性判定只有相对一次钉住的解析才有意义，而 `reproduce.sh` 会对照已提交的 lockfile 审计这一点。

### 6.4 pydantic-graph 1.x：靠不可恢复换来的安全

纳入依据是选择规则，不是图方便：pydantic-graph 文档用 `FileStatePersistence` 来中断与恢复运行，因此它声称自己属于这个平面——而活性义务的存在，正是为了让「从不 resume」不能靠空洞性通过。这项发现是相对框架自己文档化恢复声称的一个缺陷：所有被探的安全性质都通过，而这个平面的意义失败了。

在第二个节点处崩溃之后——第一个节点的 effect 已触发并被快照——框架自己的 resume 入口拒绝恢复它自己写下的持久化文件（`GraphRuntimeError: Unable to restore snapshot from state persistence`）；没有任何已完成的 effect 重复，因为没有任何执行恢复。该失败专属于「节点中途崩溃」这一状态：在节点之间挂起时被 SIGKILL，会恢复并恰好完成一次（探针 158c，双主机），而在第二个节点内部 SIGKILL 则复现该拒绝（探针 164，两种环境）——这条边界在真实进程死亡下从两侧被夹住，而一次长耗时 agent 步骤中的崩溃多半会落在里面。对已完成运行的一次误 resume 被大声拒绝（一个分歧对照：LangGraph 会静默吞掉同一事件），结构损坏的快照则快速失败。

安全空洞、进展死掉——这就是活性义务在已部署系统中的见证，现在也有了它的派生见证：易失挂起之下的挂起崩溃伴随模块违反 `EventuallyCompletes`，而每条安全不变量都成立（第 4 节）。这是版本轴上一个尖锐的碎片化数据点：2.x 直接删除了持久化机制，而被钉住的版本在同一个「判定正是从它读出」的接口上，用一条 deprecation 警告在运行时宣布这件事。

### 6.5 真实生态格子

「抽象化」这条告诫——纯 Python 节点不是 agent——由带真实模型的、按密钥把关的探针从两个方向回答，这些探针唯一被审计的字段是工具 effect 计数器。在 OpenAI Agents SDK 0.18.2（基于文件的 session [18]）上，一个被指示用带副作用的工具只扣一次费的 agent 确实只扣了一次（计数器 1），而一个恢复同一基于文件 session 的新 runner 没有再次调用该工具：跨 session 恢复的 EO 在实况中成立（一次实况观察——其无 LLM 的 harness 探针在完整矩阵计划中）。在 LangGraph 1.2.9 上、由 claude-haiku-4-5 驱动一个 ReAct agent、`interrupt_before=["tools"]`，计数器在 interrupt 时读 0、审批 resume 之后读 1、注入一次误 resume 之后仍是 1——与同一路径上无 LLM 探针观察到的静默惰性相同。

失败方向也在实况中跑过（探针 131）：门处 effect 账本为空，审批 resume 触发受门控工具一次（账本 [10]），第二次携带被修改决策的 resume 被供给第一个决策的分支——agent 逐字重复第一个答案、工具带着过期的值再次触发（账本 [10,10]）。fork 违反在实况中复现，形状与无 LLM 持久账本探针所记录的完全一致。

复现矩阵（探针 148，只审计计数器）覆盖每个供应商两个模型、两台主机——每个供应商在自己的框架格上被探，因此每格内的跨模型复现是同供应商的——每 (探针, 模型, 主机) N=20：240 次实况运行、零 harness 错误、两台主机上钉住的版本完全相同（session 恢复格跑的是 openai-agents 0.18.3，比上面试点的 0.18.2 高一个补丁版本）。

按模型合并（N=40）：interrupt-approve 格的违反字段在 claude-haiku-4-5 与 claude-sonnet-4-6 上 0/40 次运行触发（95% Wilson 上界 0.09）；session 恢复格在 gpt-4o-mini 与 gpt-4.1-mini 上显示 0/40 违反、40/40 完成；而 fork 违反在每个 Claude 模型上 40/40 次运行复现（95% Wilson [0.91,1.0]）——总体 80/80，在每个 (模型, 主机) 组合上，正如机制说明对「任何模型选择都无法掩盖的读路径缺陷」所预测的那样（逐 (模型, 主机) 行：`results/live/148_matrix.json`）。这些是存在性与稳定性复现——在 N=40 时，0.09 的真实率与观察到零次是相容的——它们证明的是存在性与跨模型、跨主机的稳定性，从不是罕见度或流行率。

真实的 PC 与 CV 分支补全图景（探针 152，跨两个 Claude 模型 N=40）：门之前的 checkpoint 血缘在 approve-resume 之前 40/40 次运行保持前缀稳定，而一个经 saver API 提交的 schema 损坏 checkpoint 在 40/40 中被静默持久化（损坏写入由 harness 提交；真实流量证明的是周围的那次运行与检测面）——它只在下一次 `get_tuple` 或 `get_state` 处以一个 `KeyError` 起爆，离出错的写入很远，这正是 CV 所指的延迟失败。

### 6.6 读懂矩阵

**跨门的顺序组合（探针 138）。** 一个双门工作流的组合方式与契约预测一致：EO 在两次门之间的 session 重启后成立，CO 每个门都成立，fork 违反在第二个门处、原厂 saver 下复发，而读路径 shim 在同一协议上修复该格。

**在门处挂起时崩溃（探针 158、158b、158c）。** 模型以前置条件排除掉的那个崩溃位置——挂起等待人工时的进程死亡——在全部三个会挂起的平面上都一致，并在两台主机上复现：pending interrupt 存活，前缀 effect 保持为 1，门带着所给的值触发一次，完成后的误投保持惰性。持久挂起是这个平面中管用的那一部分。

**穷尽杀死点扫描（探针 160）。** 双任务协议执行五次持久化操作（put、三次 put_writes、put）；在每次之后 SIGKILL——每次运行只杀一次——在全部四个不完整边界上都重新执行了已完成的带 effect 工作，并在五个点中的每一个上都恢复（第五个是已完成的运行，不计入重复核算）。在这个协议上，每一个「尚未完成」的持久前缀都允许重新执行：崩溃路径的 EO 类不是「我们选在哪里杀」的产物。

**跨进程重复投递（探针 159）。** 唯一一个「一致的判定无法在自己的组合下存活」的格。两个 OS 进程共享同一个磁盘上的 SqliteSaver，各自从自旋栅栏出发、向同一个挂起的 interrupt 发出 `Command(resume=...)`：受门控 effect 在开发机上 10/10 次重复中触发两次、容器中 3/3，两边都没有错误，门之前的 effect 全程恰好触发一次——重复只在受门控节点本身，不是被重放的前缀。逐字节相同的重投——顺序探针测为惰性的那一支（探针 126）——正是会重复的那一支；当两个竞争者携带不同的值时，两个值都触发、每个竞争者都被供给自己的值，因此这个并发失败是双重消费，而不是 #6663 那种「供给先记录值」的 fork 失败。事后的持久状态只记录了一个分支，所以——与 CrewAI 的恢复一样——重复在框架状态中不可见、只在外部 effect 账本中可见。同一竞争下的不同线程不受影响（k=4 个 worker、一个数据库、逐线程 exactly-once），这把竞争定位到同线程 resume，而不是后端的写路径。

模型中的影子不是 `FaultDoubleConsume`（由运行完成守卫，是平面所拒绝的那个顺序情形），而是 `R11_ConsumeCount.tla` 的丢失更新开关（第 4 节），其被发现的足迹 {EO, CO-e, CO-c}、PC/FD/CV/RD 干净，恰好与这一格吻合：CO 顺序成立、并发失败，与 EO 按路径分裂平行。它也不是某个存储或某台机器的性质：在 PostgresSaver 3.1.0 上对真实服务器跑同一协议，两台主机上都和 SQLite 那一支一样 10/10 次重复中重复、无错误——两个后端、两套独立配置的环境。行级锁与 MVCC 并不能关上这个窗口：resume 路径上对 interrupt 消费的「读—决策—写」，在两个后端上都没有 compare-and-swap 守卫——这正是隔离异常分类学 [19] 中经典的丢失更新形态；它之所以到达 resume 平面，是因为 interrupt 消费是一次没人做成原子的「读—改—写」。

**窗口的形状（探针 168）。** 探针 159 只测一个点——两个竞争者、零到达偏移。探针 168 扫描该点留下的两个参数：竞争者数 k ∈ {2,3,4,8,16}、到达抖动 ∈ {0,1,5,25}ms，在两个持久后端上、每格十次重复。四十个格、400 次协议执行、零竞争者错误。受门控 effect 触发 2,628 次，而 exactly-once 预测 400 次。饱和度——平均触发次数除以 k，即赢得竞争的那部分竞争者——在 40 格中的 36 格是 1.0，且从不低于 0.933；40 格中的 39 格每次重复都重复。在 k = 16、零抖动下，SqliteSaver 与真实 PostgresSaver 上的分布都是 {16:10}：一次审批触发十六次，十次里十次，两个后端都是。因此这个失败不是「两个进程会重复」，而是「窗口内到达的每个竞争者都会消费」，在 k = 16 以下没有观察到任何上限。

抖动加到 25ms 也关不上它：在全部十个 (后端, k) 组合上响应都是平的，因此这个窗口大于探针 139 整个原厂 interrupt 协议。于是它的宽度被直接测量而不是被界定：给受门控节点一个受控时长 D、把抖动扫过它——D 代表一个已部署的门在触发 effect 之前所做的模型调用或支付请求。在 k = 4、两个后端每格十次重复下，边缘在三个剂量上跟随 D（表 6）。窗口跟随受门控节点的执行时长——也就是已部署量级：一个节点要等模型响应的门，会把授权保持未消费那么长的时间，期间到达的每次 resume 都会触发。

这也是对探针 165 机制说明的独立佐证——`__resume__` 日志写入与受门控执行在执行器上并发，因此消费在 superstep 汇合之前并不持久。有两条限制是被陈述的、不是被抹平的：D 扫描的后端两列共享同一个抖动种子，因此它们是配对比较、不是对后端不变性的独立证据（该主张靠零抖动格与探针 129 的源码审计）；剂量—响应那一支只在开发机上跑过。

**跨主机竞争者（探针 174）。** 剩下的分布轴被直接测量：两台机器上的两个竞争者——一台与联网的 PostgreSQL 服务器同址，一台隔着 WAN 链路、每次查询约 450ms——协调表、effect 账本与逐竞争者到达时间戳全在服务器侧，因此凭据本身就带着服务器时钟的到达偏移，能证明竞争确实发生。在一个插桩为 5s 的门下，0.38–1.89s 的到达偏移在每一轮里都把两个竞争者塞进窗口：原厂平面在 10/10 次重复中触发受门控 effect 两次，账本把每次触发分别记到一台主机名下。已发布的门在同一协议上供给一个竞争者、以 `RemitConsumeConflict` 拒绝另一个，10/10——而且是在受门控节点执行之前：输家没有账本行，其 invoke 在 1.8–3.8s 内返回，而赢家是 5.04s，所以拒绝发生在节点自身耗时之前。同址的竞争者赢下了每一轮带门的较量；门做的是串行化，不做公平仲裁，而契约也不要求公平。

同一链路上的第一次活动被保留为差分：远程竞争者在计时窗口内支付了连接建立成本，落在赢家的 superstep 汇合之后，在 2s 门下 10/10 走了惰性路径——这就是跨主机观察到的剂量—响应边缘。仍有一处不对称是设计使然：默认打包的 REMIT shim 不修复这一格（shim 启用时仍 10/10 重复），因为它的定序器是每进程状态，两个进程带两个定序器。它给出的设计含义——消费记录应放在共享存储中、用 compare-and-swap 保护，而不是放在插值层——在第 7.2 节实现，现已作为 shim 的可选跨进程门（v0.1.2）发布，把该格翻转为两个后端上的 {1:10}（不带门的那一支保留为永久差分）；该节还在第二条性质上复现了 125/134 对为 FD 建立的「写路径 / 读路径」不对称。

**同一 superstep 上的并发扇出（探针 141）。** 两条并行分支，各有自己的门与 effect：两个 interrupt 在一遍中都浮出，一个 resume map 把每个值路由到自己的分支、每个 effect 恰好触发一次，一个误 resume map 是惰性的，崩溃那一格给出上面所述的「重试保留」对照。更深的嵌套与竞争多个 checkpointer 的扇入仍是未来工作。

**四条观察。**

**(i)** 没有两个被测框架共享同一一致性画像——这是连同活性义务一起、在六条性质上说的（单看六列会把 pydantic-graph 与全 ✓ 的安全行混为一谈）。画像是按框架定义的——它在共同被探格上的被探路径行，外加活性——而 LangGraph 的三个后端折叠成一行（后端不变性，(iv)），所以这个主张不是在数配置。表 7 逐对了结它：十对中有九对在双方都被探过的格上行为分离；第十对——AutoGen 对 LlamaIndex Workflows——是结构性的，在每个共同被探格上一致、只在路径集归属上不同（D 惯用法只在 LI 上）。没有任何分离只靠一个 U 格支撑。在一个共同被探格上见证到的分离，不会因为再探一个格而被撤销，因此填满网格只会细化这些画像、从不反转它们。

harness 也不是被设计成会失败的：RD 在所有被探处通过，CO 在 LangGraph 上顺序通过，真实的一致格每个模型 0/40 通过，而 LGF-B、修复格以及多门 EO/CO 格全部通过。分歧坐在 interrupt 相邻的轴上：LangGraph 在 FD 上失败而 LlamaIndex Workflows 通过；LlamaIndex Workflows 用文档把 EO 说没了、而 LangGraph 记忆化；CrewAI 声称最强的纪律、交付最弱的。

**(iii)** 那对回归（#7361、#6792——1.1.x 弄坏、1.2.9 修好）显示这个平面在维护压力下漂移，而用户 issue 是它唯一的规格；CI 里的一致性测试套件是长期解法，版本扫描（第 2.3 节）是这幅漂移图景的另一半——违反在每个被探版本上都稳定，而表面翻搅到 pydantic-graph 的 2.x 线已经不再暴露被探模块。

**(iv)** LangGraph 的判定跨三个被测后端都不变：每个被探格在 InMemorySaver、SqliteSaver 与真实 PostgresSaver 上完全相同。这是架构定位，不是对所有 saver 的归纳：跨 saver 的源码审计（探针 129）把那些违反性决策放在执行循环里、位于 `BaseCheckpointSaver` 接口之上，因此经该接口到达的任何后端都会继承它们；实测的不变性正是这个定位的预测，并得到确认。

### 6.7 同一负载上的内嵌持久执行引擎

与「延后引擎」正面对比（第 8 节）的语义那一半，不需要大规模迁移；探针 147 测量它。该探针把本文的抽象负载——一个非幂等 effect、一个等待人工决策的门、一个持久步骤之后的崩溃——跑在 DBOS 2.27.0 上、作为内嵌 worker（SQLite 系统数据库，无服务器），用与所有其他探针相同的外部账本 oracle。所有被探格都一致。

**跨进程死亡的 exactly-once：** 第一步的结果持久记录之后，在门处 SIGKILL 该 worker；一个新进程恢复 pending 的工作流，带着已记录的步骤结果重新执行——这就是 PC 的记忆化重放纪律——账本显示该步骤的 effect 恰好一次。

**fork 意图：** 在已记录的 receive 步上调用 `fork_workflow(id, start_step)`，是该引擎显式、有文档的可创建分支地址——是 fork 意图义务（定义 2）的一个已部署实例——分叉出的分支供给了自己那个不同的决策，每个分支一个受门控 effect，前缀未被重新执行。

**仅消费一次：** 向已完成运行投递一次误重复决策，账本保持不变（静默惰性，LangGraph 所展示的那种处置；send API 的幂等键参数就是传输层的去重判别器）。延迟代价见补充材料表 S3(b)，同一协议、两种环境，其中每次运行约 0.5s 的引擎启动开销会被长生命周期的 worker 摊薄。容器中 +39% 的 shim 差值在那里是被陈述的、不是被抹平的：该探针计的是一个短的单操作窗口，shim 额外的 `get_tuple` 步骤在其中无法摊薄，因此它并不与探针 139 在完整协议上「5% 以内」的数字矛盾；开发机显示同样的窗口落在噪声之内，这也是两者都报告的原因。

绝对延迟受环境约束；在两种环境中，引擎都比它要替代的 checkpointer 路径慢，门回答延迟上慢 2.9–5.0×。方向很重要：一个更快且一致的引擎会终结本文「在 checkpointer 接口处修复」的论证。这是一个引擎基线，不是矩阵中的一行。论点很窄：第 8 节给出的那个替代方案——整体采用持久执行模型——按构造交付了框架失败的每一个被探格，代价是它自己声明的采用成本与延迟成本。

## 7 REMIT：带已验证模型与一致性测试核心的参考定序器

契约的修复工件是 REMIT，一个参考 resume 定序器与只追加的 effect 账本，按四个明确标注的成熟度级别交付：一个由机器 discharge 的 Verus 模型，其决策核心另外在已发布 crate 中被验证为可执行文件；一个在 PyO3 绑定之后镜像该模型的 Rust 核心，带对 TLA+ 转移关系的可执行一致性检查（第 7.3 节）；一个运行时 CV 强制 shim；以及一个双侧 FD 强制结果、以一个可用的修复收尾（探针 125、134），并由打包的无决策 shim 在钉住的版本上重新建立。工件在 PyPI 分发（`pip install remit-contract`：预编译 manylinux wheel 与源码分发）；release v0.1.2——发布第 7.2 节那个可选跨进程门的版本——正是此处评估的构建。全文的验证对象始终是 REMIT 的模型及其抽取出来的可执行核心，从不是那个复合包。表 9 逐层说明证明走到了多远、并指出缺失的那一级；正文其他地方不再重审此事。

### 7.1 架构

REMIT 插在 checkpointer 接口处——每个被探框架都已经把持久性路由经过的那个窄腰。它的状态是：(i) 一本只追加的 effect 账本，记录 ⟨branch, task, effectId⟩，与完成的 checkpoint 事务性地一起写入；(ii) 一个定序器，按线程对那些「排序未被强制」的持久化操作做全序——正是它们产生了 #8039。六条性质映射为局部不变量：EO/CO 映射到账本唯一性；PC 映射到前沿单调性；FD 映射到按 ⟨checkpointId, resumeIndex⟩ 的分支键控与逐分支账本；CV 映射到写入时的 schema 校验；RD 映射到定序器的全序，使恢复成为持久日志的纯函数。第一个集成目标是实现 LangGraph `BaseCheckpointSaver` 的一个 shim；下面依次报告三条强制支线。

**(i)** 核心不变量在采用之后由机器 discharge，形式是一组独立的 Verus target、带逐文件的新计数。`proof/remit_verus.rs` 陈述 effect 账本与持久前沿——EO/CO（准入一个新 effect 使计数恰好为 1、并保持账本唯一性）、PC（提交把前沿恰好推进一格、从不重新进入持久前缀），以及 FD 的键控那一半：10 项验证、0 错误。FD 与 RD 的行为那一半是带归纳内容的定理，各配一个机器校验的反例证书：`remit_verus_fd_machine.rs` 通过对 record/serve 步骤的归纳不变量证明「每个分支都被供给它自己那次调用所记录的值」（5 项验证、0 错误），而 `negative/fd_stock_certificate.rs`——同一条义务在原厂 #6663「先供给后记录」规则下——被拒绝（1 个错误），从而证明该证明是有内容的。

`remit_verus_rd_interp.rs` 用性质 6 自己的话解释恢复决策（当且仅当任务被持久记录才跳过），并对已完成的 #8039 窗口证明序无关性——`put_writes`/`put` 这一对无论先后都持久存在（相邻换位）——以及跨相等写集数量的序无关性（6 项验证、0 错误；其中一项是定义性的基例，相同记录到相同决策——内容在换位与写集引理里）；被崩溃截断、内容分歧的那一对按设计位于这些假设之外——定序器消除了那个窗口，而两种顺序的构造（探针 118、128、136）正是它的证据——而顺序敏感的规则在同一义务上失败（`negative/rd_ordersensitive_certificate.rs`，1 个错误）。在 Verus 0.2026.05.03.8b81855 上，每个正面 target 都以 0 错误 discharge。更早时，FD 与 RD 曾被陈述为「定义使其重言式化」的引理——证明体为空即可验证；这些引理已被删除、其计数已退役，这次修正连同完整的 discharge 历史与日期记录在 `crates/remit/VERIFICATION.md` 中。

**(ii)** CV 支线以实况演示：一个强制 `commit_checkpoint` 有效性子句的校验型 saver，在 1.2.9 上重跑那个完全相同的静默持久化协议，把该违反变成大声拒绝——没有任何非法内容被持久化、历史可读——同一输入下从基线 ✗ 变成 ✓（探针 123）。拒绝在持久化之前触发，因此线程的持久状态仍是它最后一个有效 checkpoint，调用方可以修复后继续——而原厂路径会让损坏记录持久存在，并在图中途破坏线程自己的读 API（探针 150）。大声的代价是调用方得到一个异常；静默的代价是线程本身。

**(iii)** FD 支线由一对配对实验了结，它精确定位了强制点所在。写路径无能为力：一个 fork 键控的 saver 把每次 resume 写存在不同键下，并不能恢复 FD（探针 125），因为循环从不就「供给哪次 resume」询问 saver——第 4.3 节的优先级决策发生在它之上。读路径成功：一个只重写 `get_tuple` 的子类——当 config 携带显式 `checkpoint_id`（定义 2 第 3 款的可创建分支地址）时，它剥掉已记录的 `__resume__` pending 写，从而让调用方自己的值被读取——在同一协议上修复了 #6663（探针 134）：原厂对照违反；在 shim 之下，裸形式与 resume-map 的 fork 格先产出 1、再产出 0，每个分支一个取值正确的 effect；同值再 fork 是确定的；普通地址上的一次误 resume 保持惰性。Verus 证明说的是「序号键控在抽象层面恢复 FD」；探针 125/134 说的是它在 LangGraph 里能绑在哪里：不在持久化处，而在循环所加载的持久状态视图处。

演示器的判别器是那个有文档的可创建分支地址；生产则携带一个显式 fork 标志——FI（性质 7）被具体化——探针 155 在地址启发式到不了的地方评估该标志：在一个被 checkpoint 的子图之下，键控标志的配置（`fork_on_explicit_checkpoint=False` 加一个显式的 `remit_fork` 键）让子图的 interrupt–resume 与原厂一致，仍在父门处修复 #6663 那一格、每个分支恰好触发一次，并让普通地址上的误 resume 保持惰性，在 InMemorySaver 与 SqliteSaver、两种环境上都是如此。这些配对实验就是审稿人会要求的消融：只加合法性门就翻转 CV（探针 123），只加 fork 过滤器就翻转 FD（探针 134 对探针 125）。

相对其他修复家族：幂等包装器把负担移进用户任务代码；重放抑制会在合法 fork 上破坏逐分支 EO；完整的事件溯源历史就是第 8 节讨论的持久执行采用。REMIT 是最小插值点。

**插值开销（探针 139）。** 每个配置 N=200 次全新数据库的完整 interrupt 协议迭代，在两台绝对存储延迟相差 3–5× 的主机上（补充材料表 S3(a)）：容器中在原厂 5% 以内，开发机上两次 200 迭代运行中在 ±1.7% 以内（已提交的逐格差值 −0.34% 到 +0.38%）。该判定在两种延迟制度下都成立：在单线程协议上，强制点不增加可测量的延迟——这个微基准是没有模型延迟可藏身的对抗性分母。并发是探针 157（第 7.3 节）；第 6.7 节测量引擎对比的语义格与一次初步的单负载延迟对比。

### 7.2 修复跨进程那一格，以及修复绑定在哪里

探针 159 测量的是默认发布的 shim 未能修复的那一格。它陈述的设计含义——把消费记录用 compare-and-swap 放进共享存储、而不是放进插值层——在探针 165 中作为一个 saver 层面的门实现，此后被提升为已发布 shim 的可选跨进程门（v0.1.2），而它的开发过程在第二条性质上复现了 125/134 对为 FD 建立的那个结构性发现。

**写路径（被证伪）。** 第一个设计主张：在任何 `__resume__` pending 写被接受之前，先在共享的持久认领表中记下 ⟨thread, checkpoint⟩。在钉住的版本上实测，门启用时竞争仍在每次重复中重复，而输家被大声拒绝——在它的 effect 已经触发之后。一条插桩轨迹给出原因：null task 的 `__resume__` 日志写被提交给一个后台执行器，与受门控执行并发、而不是排在它之前，因此在那里提出的否决只有到 superstep 汇合时才浮出。

**读路径（修复该格）。** 重新绑定到循环在受门控执行之前所做的那次持久状态读取上——在 `get_tuple` 内部，当返回的 checkpoint 携带一个 pending interrupt 时——门用一条带唯一性约束的 INSERT（SQLite 主键；Postgres `ON CONFLICT`）取得认领。两个竞争者在那里加载的显然是同一个 checkpoint，因此恰好只有一个能赢。受门控 effect 随后在 SqliteSaver 上 10/10 次重复中触发一次、在真实 PostgresSaver 上 10/10，输家在任何节点执行之前被拒绝；同值与不同值的竞争两支都给出 {1:10} 的分布；顺序的单 resume 对照原样通过，因此门不会对合法的首次消费误报；完成后的误投保持惰性；而原厂对照在同一轮里复现该重复（5/5，两个后端），作为差分。

由此得到的发现不是门本身，而是**门的位置**。这已是第二次，在两条不同性质上，放在持久写路径上的修复无能为力，而同一修复放在持久状态读取路径上就成功：fork 确定性（探针 125 失败、探针 134 成功）与跨进程 consume-once（v1 门失败、v2 门成功）。共同原因在两条轨迹中都可见——循环的决策取自 `get_tuple` 的返回值，saver 只在事后才被告知该决策，因此位于决策之下的插值无法否决它。

这是关于「在 checkpointer 形状的架构中，一致性修复能绑在哪里」的一句话，其条件是两条轨迹都呈现的那种循环形状：任何「读持久状态 → 决策 → 再报告给 saver」的平面，其唯一 saver 层面的强制接缝就在读取处。一个在决策之前先咨询 saver 的平面不在该主张之内，而这两对配对实验为这个架构建立该接缝，而不是为每一种可能的写路径设计。

**两处昔日的限制现在是接口问题，而不是缺陷。** `get_tuple` 不携带读意图判别器，因此挂起期间的一次裸状态检查会取走认领——实况确认：对一个挂起线程调用 `get_state` 在我们自己的回归 harness 中就消费了它——已发布的门把它转换成一个显式的选择退出（调用配置中的 `remit_inspect`），也就是写路径上 FI 缺口在读路径上的 CO 类比。

那个缺口也正是门以「可选」而非「默认开启」发布的原因：`get_tuple` 用同一次调用既服务状态检查、又服务执行前加载，没有任何比特区分两者，因此默认开启的门会把对挂起线程的每一次裸检查都变成一次消费，除非每个调用方都先采用 `remit_inspect`。这个默认是接口强加的，不是修复选择的；一个增加了读意图判别器的平面，会让默认开启变得安全。

而且这个门已不再是一个 saver 层面的演示器：v0.1.2 把它提升进已发布 shim、作为可选配置（`cross_process_gate=True`），在 saver 自己的数据库中取 (thread, checkpoint) 认领，并在任何节点执行之前以类型化的 `RemitConsumeConflict` 拒绝输家——两个持久后端上均为 {1:10}，不带门的默认保留、且仍测得 10/10，作为永久差分。仍然受限的是范围，明说：该门为共享同一存储的同步 saver 串行化普通地址的投递；分布在两台主机上、对一台联网 PostgreSQL 服务器的竞争者复现了两侧（探针 174）：原厂路径在 5s 门内 10/10 次重复中重复，已发布的门在 10/10 中于任何节点执行之前以 `RemitConsumeConflict` 拒绝输掉的竞争者；网络分区与更广的拓扑仍未测量。

### 7.3 从已验证模型到已发布包

REMIT 以可安装包发布（`remit-contract`；MIT），带一个刻意的分工：每个契约决策都在 Rust 中计算；Python 负责转换类型与施加判定。Rust 是 Verus 所验证的基底，一个 abi3 wheel 把核心带给用户、用户机器上不需要工具链；所主张的新颖之处从来不是语言，只是核心所强制的契约。

**三层。** (i) `remit-core`，一个 Rust crate（`#![forbid(unsafe_code)]`，零依赖测试套件），逐项重新实现已验证的抽象模型：带 exactly-once 准入的只追加 effect 账本、有效性排在任何追加之前的前缀单调提交门、⟨checkpointId, resumeIndex⟩ 分支键控、作为纯函数的「探针-134 视图规则」、逐平面的定序器/日志，以及作为持久日志的纯函数、序无关的恢复；`VERIFICATION.md` 以表格给出引理到函数的对应。(ii) `remit-py`，一个 PyO3 层，把契约违反暴露为类型化异常（`RemitDuplicateEffect`、`RemitPrefixViolation`、`RemitValidityError`、`RemitOrderViolation`，以及来自 v0.1.2 跨进程门的 `RemitConsumeConflict`）。(iii) `remit.langgraph_shim`，一层覆盖任意 `BaseCheckpointSaver` 的无决策外壳：`get_tuple` 把寻址方式描述给核心并施加其「剥 / 留」判定；`put` 把用户 validator 的答案报告给合法性门，该门在委派任何东西之前抛错；`put_writes` 在定序器中记日志。外壳中的每个条件分支要么路由一条核心判定、要么抽取一个配置字段——这是一条可审计的主张。

表 9 第 4–6 级背后是三组可执行证据。**模型一致性**（第 5 级）把 `ResumeContract.tla` 的动作字母表（含使能条件）转写到 Rust 核心上，独立地影子跟踪 TLA+ 的变量、从而使「一致」成为关于两个实现的主张，并在每个动作之后重新校验全部六条不变量；一个带种子的随机化分支跑 2×10⁴ 条、每条至多 48 个动作的序列，穷尽分支则彻底去掉采样 caveat。其状态数超过 TLC 的 87/59，这是设计使然——实现层面的状态更细、合并的历史更少；穷尽性主张不变。

**并发**（第 6 级）从至多 64 个线程驱动准入、fork 与定序，校验 exactly-once 准入、无空洞的连续 fork 序号、无空洞的逐平面日志、以及竞争误 resume 的惰性；探针 157 随后在共享同一个 saver 上测量端到端问题，k ∈ {1,4,16,64}，每格 N=200 次协议，四支，两种环境。两个结构性发现顺带而来：两个后端、两种环境下的吞吐对 k 都是平坦的，而中位延迟大致线性增长——串行化天花板是进程（受 GIL 约束），不是后端，一个无持久化的 InMemorySaver 对照佐证了这一点；而写者锁在尾部浮现（开发机上 k=64 时 SQLite p95 为 2.7s、Postgres 为 1.3s，这个次序在容器的 overlay 文件系统 Postgres 上不复现）。这就是为什么只有正确性判定与环境内相对开销被外推（凭据：`results/matrix/157_*.json`）。

在论文钉住的版本上做集成，是在 LangGraph 1.2.9 上对 Rust 核心 shim 重放探针-134 协议——八个格，全部通过：裸形式与 resume-map 的 fork 各自供给自己的值、两个后端上逐分支账本都是 [1,0]；同值再 fork 是确定的；进程内误 resume 惰性；validator 抛错以 `RemitValidityError` 浮出、无任何东西被持久化；核心日志严格有序；而原厂 saver 作为差分对照复现 #6663——容器与主机双向复现，CI 每次 push 都重新执行。

一项早先的「单项、十五条复合 discharge」主张，随被删除的定义性引理一起退役；完整的 discharge 日志——包括一个撤回的 CV/RD 文件，它带着占位的 `assume(false)` 体——连同日期记录在 `VERIFICATION.md` 中。CV 另有实况演示（探针 123），RD 带有执行器层与对抗顺序的证据（探针 124、136）。位于 `BaseCheckpointSaver` 之后的生产定序器已发布（第 7.3 节），契约决策在 Rust 中，而 FI 义务所要求的显式 fork 标志作为部署判别器可用（`fork_on_explicit_checkpoint=False` 加一个可配置的标志键）。

未验证的面被收窄并点名：没有机械化精化把 Verus 模型连到编译后的 `remit-core`（一致性 harness 与并发套件是桥接证据，不是证明）；PyO3 边界与无决策外壳是未验证的 Python 侧代码，靠构造与审计缓解；这里的每一条证明始终是关于 REMIT 模型的证明，从不是对任何框架的验证。这份清单此前推迟的唯一一项——把第 7.2 节的读路径消费主张提升进已发布 shim——已完成（v0.1.2，可选），这使门本身像外壳其余部分一样落在边界未验证的 Python 一侧，其接受/拒绝决策经由核心的纯判定函数路由。生产规模的引擎正面对比是被划定在范围之外的，而不是欠着的，理由见第 8 节。

## 8 相关工作

**契约周围的恢复层。** Crab [4] 为 agent 沙箱提供语义感知的 OS 级 checkpoint/restore；其恢复机制会合成缓存的响应，正是为了让恢复后的 agent 不重放已完成的动作。DART [5] 在持久化原语之上证明回滚的可接受性。两者按层互补（图 1）；没有一个规约或测量原语自身的语义。

**语义回滚攻击与审批完整性。** 离 EO/CO 轴最近的是 ACRFence [21]：它把 Action Replay 与 Authority Resurrection 识别为 agent checkpoint–restore 中的攻击类，并通过「记录不可逆的工具 effect、恢复时采用 replay-or-fork 语义」来缓解——这是 EO 与 CO 的对抗面，也是 REMIT 所实例化的那个缓解家族。ACRFence 用概念验证与 issue 调查确立该威胁；本文把契约规约为一个机器校验模型、跨五个框架与三个后端确定性地测量一致性、并在 checkpointer 接口处发布一个修复——FI 就是其 replay-or-fork 判别在协议层面的形式。同意完整性中介 [6] 把审批绑定到动作的真实内容；FD/CO 处理与之正交的生命周期轴——一个回答是否只被消费一次、以及不同的回答是否产生不同的分支——#6663 与 #2315 类 [16] 正是其观察到的失败。

**测试与验证 agent 框架。** 一项 998 份报告的实证研究把主要的 bug 质量定位在执行语义机制上 [22]；LogicHunter [7] 用 agentic oracle 生成框架测试；鲁棒性基准 [23] 测量扰动下的任务成功率。这些是横向的；本文是纵向的：一份具名契约、一个被校验的模型、一致性判定、一个参考实现。同一生命周期的控制面那一半——stop 是否抑制对外可见的 effect——由 SoundGate [17] 测量并修复：它从运行时之外的一个强制点确立一个原语的一条性质，在那里「完全中介」由门所处的位置推出。REMIT 继承了更难的位置：checkpoint 与 resume 就是这个平面，所以它插在运行时内部，必须测量自己的中介而不是假设它（第 7.2 节）——两篇论文是同一个问题在这条线两侧的提问，而且在一点上血缘是字面的：此处形式化为 RD 的排序隐患（#8039，第 2 节）正是在那项测量中作为未解残留浮出、并因此在上游提交。AgentConform——AgentRFC 框架 [24] 的一致性检查器——用 TLA+ 模型测试 agent 通信协议：这是方法上最近的表亲，只是对象不同。运行时强制系统 [25]、[26] 按策略把关动作；本契约管的是这些门在做 checkpoint 与 resume 时所依赖的那个基底。失效模式分类学 [27] 说明了部署层面的利害；SagaLLM [28] 在本文所规约的平面之上添加补偿语义。

**这个平面没有继承的持久化传统。** Akka Persistence [14] 与 Orleans [29] 为有状态实体提供带已陈述持久化语义的事件溯源状态；Erlang/OTP 监督 [30] 把「从干净状态重启」写成规范；而持久化语言这一支——Argus 的 guardian 与原子动作 [31]、正交持久化 [32]——几十年前就把持久性变成了一条带已陈述语义的语言义务。agent 框架重新实现了这个平面、却没有继承那套纪律：事件溯源重放要求确定性的 handler，而 agent 循环内嵌非确定性的模型调用，于是框架转而采用快照式 checkpointing——恰恰是本契约所管辖的那个平面。FD 不是 linearizability [33]（那约束的是单个对象的并发历史），而是「从一个持久点创建分支」的确定性义务。直接移植 Orleans 风格的 grain 持久化或 Akka 的 journal，是 REMIT 一个合理的替代修复。

**为什么不直接用 Temporal 或 DBOS。** 持久执行引擎强制确定性与 exactly-once，但强加它们的执行模型：Temporal（及其 Cadence 血统）把非确定性隔离在 activity、副作用 API 与版本控制之后 [34]；DBOS 把步骤绑到数据库事务 [35]；托管编排器则把工作流定义完全外置 [36]。agent 框架选择更轻、更贴合模型的持久化，正是为了避开这些约束；契约让它们保留这个选择，同时陈述它们仍必须满足的保证。整体采用持久执行模型是一条正当路径，本文不反对；契约管辖的是那些选择了退出的框架。第 6.7 节在内嵌引擎上跑本文的负载，测得每个被探格都一致，代价是门回答延迟为 checkpointer 路径的 2.9–5.0×：引擎测量为那个替代方案定价，而 REMIT 自己的基线就是它所插值的原厂 checkpointer（补充材料表 S3）。

**持久执行的形式语义。** 实现 exactly-once 外部 effect 是离 EO 最近的既有义务：Olive 通过把意图日志与幂等、可恢复的操作配对，为云存储做到这一点 [37]，而本契约的 EO 就是那套纪律被陈述为「调用方可见的义务」，用在一个既没有该日志、也没有该幂等性的平面上。方法上最近的是 Flux [38]，它自动验证有状态 serverless 应用的幂等一致性——正是 CO-e 的形状在上一层。这一层就是全部差别：Flux 验证的是应用的函数能否容忍平台的重试，而 RESUME CONTRACT 问的是这个平面自己的原语是否信守承诺——任何逐节点的幂等证明都抓不到 #6663，那里第二个值在任务准备阶段、任何节点运行之前就被丢弃了。最近的「把 resume 写下来」的先行工作，是 Durable Functions 的已发表语义 [13]；Beldi [39]、Netherite [40]、共享日志后继（Boki [41]、Halfmoon [42]）与 AMBROSIA [43] 构建基于日志或重放的 exactly-once serverless 执行，Restate 则发布面向 agent 循环的持久 promise [44]——每一个都给某一个引擎一套由构造强制的语义，而且是引擎内部的，理由见表 10 所记；而本文为一个框架生态规约一份契约，据我们所知其中没有一个陈述过，新颖性主张限定在 agent 框架，不在形式化 resume 语义。

**表 10　本契约对成熟持久执行引擎就同类问题所陈述义务的对比。** 重要的是最后一列：引擎陈述了该义务的地方，契约只是在另一个接口上的重述、不主张新颖性；引擎把它委托给应用、或从不暴露该义务所约束的那个写入的地方，它无法转移到一个「采用了快照却没有采用周围模型」的框架。

PC 与 RD 是那些引擎已陈述义务的重述，除了把它们带到一个原本没有的接口，本文不为它们主张任何东西。承重的是另外四行。EO 最尖锐：Temporal 的 activity 是 at-least-once，其对外部 effect 的 exactly-once 故事是调用方提供的幂等键，因此契约的 EO 强于经典持久执行引擎所承诺的——「直接用 Temporal」不会消解这个问题，它只是把问题搬进用户代码，这正是注 4 的组合从另一侧看到的样子。

CV 完全没有对应物，因为一个拥有自己序列化的引擎从不暴露 CV 所约束的那个写入——agent 框架确实暴露它，而且其中一个还静默损坏它。FD 与 CO 只部分可转移，DBOS 是最有教益的案例：它在被探格上同时满足两者，恰恰因为它发布了 FI 义务所要求的两个判别器——一个有文档的可创建分支地址，以及投递 API 上的一个幂等键——这是一个未参考本契约构建的系统对 FI 必要性的佐证。

**已验证系统、崩溃恢复与 API 之下的 checkpointing。** IronFleet [45]、Verdi [46] 与 Perennial [47] 定义了「从 REMIT 的 Verus 模型到其编译核心的机械化精化」所能达到的保证门槛，FSCQ [48] 与 GoJournal [49] 则把崩溃安全性证明到对运行代码的精化——这正是第 9 节此处称为缺失的那道门槛。除 Verus 本身 [3] 之外，Anvil [20] 用 Rust 验证集群管理控制器——是 REMIT 形态最接近的现存实例，其范围在第 7.4 节划定。RD 的「相同日志、相同决策」纪律在状态机复制中是基础性的（Viewstamped Replication [50]、Raft [51]）；本文不为这条原则主张新颖性，只主张在一个缺少它的接口上陈述它。在 API 之下，record-and-replay（rr [52]）、进程级 checkpoint/restore（CRIU、DMTCP [53]）与多级 HPC checkpointing（BLCR [54]、SCR [55]、VeloC [56]）提供确定性与状态捕获，其关注点是 I/O 成本与保真度、而不是 API 级的 effect 语义；RD 与 PC 把这些义务在 API 层重述，用于一个采用了快照却没采用那套纪律的平面。在可观察接口上陈述义务自有其血缘——契约式设计 [57]、接口自动机 [58]、会话类型 [59]、Alloy 中的轻量建模 [60]——RESUME CONTRACT 是其中 resume 平面的实例。

**工作流恢复、effect 纪律与语言级挂起。** 「resume 时什么可以重新执行」有一支二十年的文献，agent 框架没有继承：ConTract 模型 [61]（本文标题无意中呼应了它的名字）、工作流恢复 [62]、工作流模式目录 [63]、异常模式 [64]，以及自 Sagas [65] 起的补偿；Petri 网工作流健全性 [66] 与 BPMN 语义 [67] 早二十年就确立了可机器校验的流程模型，TCC 式原子交互 [68] 是 REST 时代的补偿纪律。Helland 的幂等一支 [11]、[12] 是「exactly-once effect 需要应用层幂等键」的经典论证——注 4 的「FD 加键」组合就是该论证在 fork 处的形态——而 Ramalingam 与 Vaswani 为被中断的工作流程序按构造导出幂等 [69]，那是 EO/CO 此处置于框架之上的这条纪律在语言层面的祖先。在 RPC 层，血缘从 at-most-once 调用语义 [70] 走到 RIFL 的持久完成记录（重新执行前先查阅）[71]——那套 exactly-once 纪律在 checkpointer 平面上的类比正是 REMIT 的账本。用编程语言的术语说，这个平面是一个持久化定界 continuation [72]、[73]，在操作层面是一个被持久化的 effect handler [74]；web continuation 那一支遇到的是同一个「后退按钮 fork」，也用同样的方式解决——显式的分支身份 [75]。Ray [76] 在若干 agent 框架所运行的基底内部、从血缘重建 actor 状态；Airflow [77] 与 Prefect [78] 把 EO/CO 此处置于框架的幂等纪律推进用户任务代码；Kafka 的事务性双写 [79] 在下一层解决了「提交并触发」；crash-only 设计 [80] 预示了「恢复路径是首要的」这一立场。

**经典基础与方法学。** 这些性质把经典概念——回滚恢复的确定性 [15]、分布式快照 [81]、流处理中的 exactly-once 状态管理（Flink [10]、MillWheel [82]）、ARIES 的重做历史 [83]——实例化在一个它们本不存在的接口上。方法上，harness 源自崩溃一致性测试（ALICE [84]、CrashMonkey/B3 [85]）、Jepsen [86]「对照已陈述契约检查实现」的立场，以及 ioco 式基于模型的测试 [87]，并置于工业界的 TLA+ 实践 [88]、[89] 之上——移植到这样一层：其第一项任务是把契约写下来；故障开关实例化规约变异 [90]，基于血缘的故障注入 [91] 是其系统化的对照面。激发 RD 的 #8039 排序缺陷在 LangGraph 的跟踪器中 [92]。

**隔离异常与黑盒异常推断。** 跨进程的 consume-once 失败是一次丢失更新，发生在没人做成原子的「读—改—写」上，其自然词汇来自隔离文献：除 ANSI 批判 [19] 之外，Adya 等人与实现无关的定义 [93] 是该异常的可移植形式，而 Elle [94] 是从客户端可观察历史推断此类异常的最新水平——恰好是探针 159 的 oracle 所处的认识论位置，也是对该格做多竞争者刻画时应采用的纪律。我们点名它们而不主张它们：本文在一个并发形态下展示了该异常，不对平面的隔离级别做分类。

## 9 效度威胁

**构念：文档记载的弱点算违反吗？** 分类规则（表 5，注 b）是全覆盖且对称的，它移动的是标签而不是测量：在该规则下，LlamaIndex Workflows 的前缀重放是 D，LangGraph 的 fork 行为与 CrewAI 的 checkpointing 行为是 ✗，CrewAI 的 @persist 恢复是 U。CrewAI 最强的那条声称（任务跳过）是针对 crew 陈述的，其探针需要真实 agent，已排入完整矩阵。

**构念：机制可比性与模型落地。** 矩阵各格比较的是性质、不是机制：LlamaIndex Workflows 的 fork ✓ 依赖客户端快照副本，而 LangGraph 的 ✗ 关系到服务端线程 fork，因此跨框架的 FD 格是在各自框架自己的惯用法上证明该性质。EO 崩溃路径的分类由文档审计了结（第 6 节）；维护者的一句澄清会把该格重新归类为有文档的分歧，而不改变测量。`LangGraphFork.tla` 是一个操作抽象，落地于复现行为与钉住版本上的源码阅读（第 4.3 节）；它仍是专家建立的、不是机械抽取的，这正是「模型落地」与「行为判定」被分开可审计的原因。

**构念：effect oracle。** 主 oracle 是一个进程内计数器，它精确捕捉非幂等的重新执行，但不捕捉生产延迟或失效模式。持久后端探针增加一个磁盘上的外部账本作为第二 oracle，在每个报告的格上都一致（探针 126）；探针 142 把状态持有者完全移出被测进程——一个位于独立 OS 进程的外部服务，其 SQLite 状态在工作流的 SIGKILL 下存活、并记录下重复的重新执行（⟨s1, s1, s2⟩）。一个带有生产失效模式的远程第三方仍在范围之外；它与契约的接口是注 4 的幂等键组合。真实格（第 6.5 节）在每格 N=20 下审计计数器（探针 148；240 次运行、零 harness 错误），而探针 131 在 80/80 次运行中经外部账本抓到真实的 fork 违反——该 oracle 的实况验证既不是只测通过、也不是单模型、也不是单主机。探针 152 通过血缘与 schema 可观察物在实况中关闭 PC 与 CV；RD 的实况验证需要语义稳定的模型输出，按设计不在范围之内。复现数字以观察频率加 Wilson 区间报告；确定性论证靠的是机制说明，从不是样本。

**内部效度：探针保真度。** 每个 LangGraph 探针都由对应公开 issue 中的最小复现构建、再加 effect 计数器扩展；版本扫描（第 2.3 节）防止单版本产物；原始 JSON 输出随工件发布。每个试点判定都在第二台、独立配置的开发机上按位相同地复现——这是同一团队做的跨主机确定性检查、不是独立复现——（约定沿用我们此前的测量工作 [95]）；一个真实探针（131）的模型构造 import 在活动之后被修正、以匹配已提交环境的钉住版本——被测的框架路径未被触碰、重跑复现已提交的判定字段——这是一次「没有隐藏的主机依赖泄漏进判定」的确定性检查，不是独立的方法学验证。

一项源码级变异研究（探针 156）检验判定是否与定位到的机制因果耦合：八个一阶突变体，手工推导自机制说明所指的 resume 供给处、每个锚定到被 vendored 源码的唯一一行，逐个施加、探针套件逐字节不变；八个在两台主机上全部被杀死，包括位于 #6663 机制所指那条优先级行上的突变体（一次因果耦合检查；不主张变异充分性分数，而且手工放在被注视位置的突变体无法回应「调参迎合已知 bug」的指控）。

互补的检查变异的是 harness（探针 169、170、172；完整的算子表与逐算子分析在补充材料 S1）：探针 169 从已提交的稳定视图凭据重新推导十五条承重判定，15 条全部在场、无一相左；四个算子恰好杀死它们预测的格——fork 值失明杀死 #6663 而不杀别的，一个只看状态的 oracle 与一个少计的账本各自杀死跨进程 consume-once 格，而移除栅栏什么都不杀——无时间窗口的主张在证据中得到 discharge——两个算子需要文档化的修正才能说出话，而 crash no-op 与 pin 漂移按设计在范围之外。

标签规则反转根本没有机械位置可言：表 5 注 b 的 U/X 规则在读者赋判定时才应用，不由任何探针存储。因此注 b 的敏感性主张是靠重新贴标而不是靠变异来 discharge；重新计算（补充材料 S4）显示最严格的替代规则恰好触及那两个 U 格，观察 (i) 的全部十个分离都成立，而规则选择移动的只是标签、从不是碎片化结果。

**跨环境主张自带一条机械守卫**，是在一次险情之后加上的：一个容器凭据曾靠复制其开发机孪生并改写主机字段而产生——而且因为每个格都一致（这正是复现所断言的），任何读格子的检查看不见这次替换。格子一致是主张本身，因此它不能同时充当检查；于是审计断言「带不同主机标识的两个凭据不共享时间戳」，这样复制的凭据无法冒充复现。持久后端探针（126–130）在第三个、独立配置的环境中执行（第 5 节），与每条 InMemorySaver 路径的判定一致；其余每个探针家族、扩大的 TLC 配置、39 格矩阵、打包的 Rust/PyO3 套件以及引擎基线格，都在容器与主机之间复现、稳定字段零分歧。harness 不含时间、不含随机性、不含模型调用，因此判定只能随包版本变化，而包版本是钉住的。

**外部效度：广度与漂移。** 研究覆盖五个框架——三个深入，外加范围更窄的 AutoGen AgentChat 恢复平面与 pydantic-graph 持久化——在有文档的路径上；AG2、OpenAI Agents SDK、Claude Agent SDK 与 Agno 在建的完整矩阵中。单个违反可能在上游被打补丁——#7361 与 #6792 已经是（在作为回归发布之后）——这就是为什么主张依赖契约、模型与版本钉住的凭据，而不是依赖某个单一 bug 的存活期。

**生态效度：effect 与崩溃的抽象。** 两个 oracle 都不是真实的支付式 API；oracle 审计的是框架的调用纪律，而分区或重复之下的端到端投递属于 effect 层的幂等键组合（注 4）。跨进程 CO 格（探针 159）确立的是「顺序惰性保证跨进程不组合」，不是一个比率；探针 168 把形态扩到 k=16、25ms 抖动、两个后端上 40 个格，并用剂量—响应测量窗口（第 6 节）。点名三条残留限制：剂量—响应那一支只在开发机上跑过；其后端两列共享同一抖动种子，因此是配对的、对后端不变性不承担分量；k>16 与更宽的抖动仍未测量，而跨主机分布只在一个双主机拓扑上测量（探针 174），网络分区被排除——所确立的是「窗口接纳其中到达的每个竞争者、在 16 以下未观察到上限」，而不是「不存在上限」。在这个 API 上，传输层的客户端重试归约为已探过的重复投递情形（126 顺序惰性、159 并发重复）。

崩溃模型是进程粒度的 fail-stop：矩阵中基于异常，探针 133/137/158/160 基于 SIGKILL，探针 164 把真实进程死亡扩展到剩下两个带崩溃的格——CrewAI 的 checkpoint 恢复重复与 pydantic-graph 的节点中途不可恢复性都同样复现（3/3 与 3/3，两种环境）——因此没有任何矩阵崩溃判定仅靠异常语义。断电、fsync 重排与撕裂写属于崩溃一致性文献 [84]、[85]，位于该平面之下。

关于不用 LLM 的反对：这些性质是在持久化 API 上陈述的、按构造与模型无关，因此环中的模型只能增加性质本就放在 f 之外的非确定性，而真实格从两个方向检查真实模型流量既不掩盖也不制造那些确定性判定（第 6.5 节）。真实流量仍可能改变的——达到探针所不及路径的工作负载形态——正是本文不回答的流行率问题。

最后，形式结果按第 3.4 节所说的量词形状分野：已展示的分离由完全枚举的有限见证了结、无需升级，而在两条全称主张中，其中一条现已 discharge。TLAPS 证明了参考合取式无界成立：`Reference ⇒ (Spec ⇒ □ContractConjunction)`，用的正是 `IndCheck.tla` 中展示的那条归纳不变量——在三组常量下经 TLC 检查为归纳（8,610 / 450,926 / 97,800 个不变量状态，TLC 找到两个合取项、拒绝了更弱的候选）——其类型从模型检查的界推广到无界序列，因此该定理对满足模块假设的每个常量赋值都成立（`ResumeContractProofs.tla`：196 条义务、零省略，Zenon/SMT 后端、Isabelle 从未被调用，在两台主机上、两套 tlapm 构建下复现；运行器与凭据在 `formal/tla/tlaps/`，凭据带规范的 SHA-256，证明被审计的模块逐字节未变）。前沿单调性与 CO–EO 包含关系在同一文件中作为引理 discharge。

**两处披露让该主张保持诚实。** 证明的负担在「后继」而不在「充分」：该不变量承重的合取项是「持久前沿恰好落后程序计数器一格」——`ExecTask` 是前缀回退标志的唯一写者，其写入被一个该合取项所禁止的条件守卫——因此对那些不变量结构性承载的性质而言，蕴涵步骤近乎是定义性的，定理的内容在于「在每个动作下保持」。而且证明模块逐字命名了规格自己的未命名 ASSUME（这是 tlapm 跨 EXTENDS 的引用限制）；信任基不变。故障足迹完备性保持其界相对地位——在陈述的常量下穷尽、在一个数量级更宽处重新推导、之外沉默——而活性、挂起伴随模块与消费计数矩阵仍是 TLC 校验的结果；一致性级别格的 TLAPS 义务在相邻工作 [96] 中 discharge。

## 10 结论

LLM-agent 框架的 resume 平面把人工审批与非幂等 effect 带过 interrupt、崩溃与恢复，而今天它在没有任何已陈述语义的情况下做这件事：三个主流框架文档化了三种互不相容的纪律，其中两个连自己陈述或暗示的语义都违反，而这个平面在一次次补丁版本中回归、用户 issue 是它唯一的规格。RESUME CONTRACT 命名了那些让「resume」有含义的性质；一个 TLA+ 模型校验参考语义、把每项观察到的失败展示为一个短反例、并绘出每条注入故障的完整违反足迹；一套确定性、不用 LLM 的 harness 把这些性质变成逐版本的一致性判定。

它交付：带 fork 意图义务的契约；带部分独立性结果、以及经 TLAPS 无界证明的参考合取式的机器校验模型；一份落地于源码、经样本外检验的 fork 违反机制说明；一个后端不变、版本稳定的测量；跨进程的刻画——窗口内的每个竞争者都消费、在 k=16 以下未观察到上限、窗口由剂量—响应跟随受门控节点自身的时长；已 discharge 的 Verus 证明、其恢复核心被验证为已发布可执行文件；以及 REMIT 本身，在 6,400 次并发协议下保持 exactly-once 完好的同时修复 fork 与有效性两格。

跨进程那一格在读路径上、而且只在读路径上被修复，位于已发布 shim 的可选门之后（第 7.2 节），在竞争者分处两台主机时依然成立（探针 174：原厂 {2:10}，门 {1:10}）——两对配对实验证明，位于决策之下的插值无法否决它。它推迟、且不据此主张任何东西的：从已验证模型到编译核心的机械化精化、更深的并发嵌套、以及语料规模的流行率研究。

对实践者的直接含义是：「这个框架有 checkpointing」对已完成的 effect 不构成任何许可；对框架作者的含义是：这份契约是可校验的，测试套件是一个 CI 作业，而 resume 可以被做成名副其实的 resume。
