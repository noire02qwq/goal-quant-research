## 摘要

人类审批通常被视为 agent 执行有重大后果的操作之前的最后一道安全边界。这道边界只有在提交审查的操作就是随后被授权或放行的操作时才有意义。我们把这种绑定失败称为 Loopjacking：人批准了自己理解为操作 A 的东西，而实现却把这个决定用于一个实质上完全不同的操作 B。我们区分两种变体。在基于表示（representation-based）的攻击中，B 已经被编码，只是在审批时刻被省略或歪曲呈现；在审批后状态替换（post-approval state-substitution）攻击中，人看到的是正确的 A，随后可变的工作流状态把它换成了 B。

我们对一组特意选取的已发布 agent 产品进行了评估。我们复现了审批后状态替换：在七个受测的 Agno AgentOS 发布版本（最高到 3.0.9），以及十二个受测的条件式内存内 LangGraph Agent Server 组合版本（最高到 0.14.0）中都能重现。我们还在 OpenClaw 2026.2.23 中复现了表示不匹配，并在 2026.2.24 中观察到它被拒绝。OpenAI Agents SDK 0.22.0 与 0.22.2 提供了阴性对照：序列化的 continuation 保留了逐次调用的精确绑定，并拒绝被篡改的 B。这些结果并不估计整个生态的普遍程度。它们表明，完整的规范化审批渲染加使用时（use-time）的精确比对，或者阻止未授权的挂起状态篡改，能够在保留合法执行的前提下阻断所测的攻击。我们把这一贡献与既有的关于误导性对话、会话走私（session smuggling）、动作绑定（action binding）和授权连续性（authorization continuity）的工作区分开来。

## 1 引言

一个 human-in-the-loop 提示看上去可以像一个决定性的安全控制：agent 提出一个操作，人检查它，只有在作出明确决定之后才继续执行。实际上，被审查的操作可能要经过多个表示层。一个产品可以渲染一个字符串、持久化一个结构化的 tool call、接受一条 continuation 消息、重建一个当前动作，最后向 sink 派发不同的参数。只有当这些阶段在实际效果上达成一致时，审批才是可靠的。

这种一致性并不因为存在一个审批按钮就自动成立。考虑一个低权限用户：他可以请求工作，但无权授权一笔受保护的转账。管理员审查一笔向已批准供应商转账 20 单位的请求，并批准了它。如果该用户随后能把挂起的参数替换成向攻击者控制的目的地转账 2,000 单位，而产品在管理员仍然有效的决定之下执行了这次替换，那么人参与了，控制却失败了。第二种形式不需要任何事后篡改：完整请求本身已经编码了有害命令，而审批视图只显示一个不完整的 shell 片段。

我们用 Loopjacking 来称呼这种由产品负责的「审批—效果」不匹配。一条合格的轨迹需要同时具备：一个真实的、被理解为 A 的人作出的决定；实质不同的 B；攻击者可触达的影响；由产品负责地把该决定用于 B；一个有重大后果的 sink；以及证据表明攻击者没有等价的直达 B 的路径。表示不匹配与审批后状态替换是同一个绑定失败的两种不同变体。这个定义刻意排除了那些人明知而批准可见 B 的普通说服、泛泛的可变状态、没有人作出决定的确认伪造，以及从不复用任何审批的 prompt injection。

这一区分对测试和修复都很重要。只寻找可变任务，会漏掉在审批之前就被歪曲呈现的命令；只盯着对话看，会漏掉一次正确审查之后底层操作被改掉的情形。反过来，把每一条 continuation 或策略绕过都当成 Loopjacking，又会让这个术语宽泛到无法标识那个失效的安全边界。

本文有四点贡献：

1. 给出一个可检验的「人的决定 → 授权」链路模型，并把基于表示的轨迹与审批后状态替换的轨迹区分开来。
2. 报告对三条已发布产品路径的受控原生评估：一个 Agno AgentOS 配置、一个条件式 LangGraph Agent Server 组合，以及 OpenClaw 的 shell-wrapper 审批路径。
3. 把 OpenAI Agents SDK 的普通逐次调用审批作为阴性对照纳入，表明可恢复性与序列化本身并不意味着过期审批被复用。
4. 在所测轨迹上验证了两种互补防御：完整的规范化呈现加精确的使用时绑定，以及阻止不可信行为者修改已批准挂起状态的授权策略。

本研究是比较性的，而非代表性的。其样本选取是为了检验机制上不同的审批路径和一个可证伪的对照。我们报告精确的版本、配置、试验分母和边界；我们不推断全市场比率、普遍影响范围或单一严重性评分。证据截止日期为 2026 年 9 月 10 日。

## 2 操作、审批与攻击者模型

### 2.1 审批中介的操作

审批中介的执行有两个与安全相关的时刻。在审批时刻，产品向人呈现一个关于所提操作的可见视图。完整操作包括动作、参数、目标资源、主体与任务范围，以及任何能实质改变效果的执行上下文。人把显示的操作理解为 A，并记录决定 D。在使用时刻（use time），后续组件把 D 应用于当前操作，而当前操作可能已经不再是 A。

**审批绑定不变式（Approval-binding invariant）**：只有当在使用时刻评估的完整操作与人所审查并批准的操作实质等价，且该决定对当前的主体、任务和范围仍然有效时，一个决定才授权某个操作。强制点必须在所有受攻击者影响的变换之后重建该操作。如果操作存在实质差异，产品必须拒绝它，或取得新的审批。人可以有意批准整个可变任务，但前提是这种广度被清晰地呈现，且由此作出的决定仍然约束每一个后续效果。

图 1：审批绑定模型。当产品把针对人可见的 A 的决定用于放行实质不同的 B 时，就发生了 Loopjacking；安全分支会重建完整的当前操作，要么原样执行 A，要么拒绝 B 或为 B 重新授权。（原文第 3 页）

### 2.2 定义与变体

Loopjacking 是一种实现层面的失败：人批准了他们理解为 A 的操作或表示，但由产品负责的逻辑用这个决定去授权或放行实质不同的 B。攻击者劫持的是「人的决定」与「继承其权威的操作」之间的那条链路，而不一定是周围的对话或人的账户。

这个定义产生两个主要变体，如图 2 所示：

**基于表示的 Loopjacking（Representation-based Loopjacking）**：完整请求或执行上下文在决定作出之前就包含 B，但产品显示、规范化或检查的是一个实质上不完整的 A。审批只对这个不完整的表示是准确的。

**审批后状态替换（Post-approval state substitution）**：人看到并批准了确切的 A。在审批被消费之前，某个行为者把挂起的任务、线程、会话或 continuation 状态改成 B。执行时评估的是当前的 B，同时保留为 A 作出的决定。

重放（replay）、范围漂移（scope drift）和不一致的使用时解释，在「为 A 作出的真实决定正是授权 B 的东西」这一情形下也可以套用同一定义。它们并不会仅仅因为一条审批记录过期或一个工作流可变，就自动成为 Loopjacking。

### 2.3 必要条件

只有在以下六个条件全部成立时，我们才接纳一条轨迹。它们合起来防止这个标签坍缩成泛泛的「agent 被攻陷」。

1. **人的审批。** 一个人或一个独立的审批角色，针对一个被理解为 A 的视图作出一个产品记录的决定。
2. **实质不匹配。** B 改变的是与授权相关的效果，而不只是格式或无关紧要的字段。
3. **可触达的影响。** 攻击者能够通过一个受支持的、或现实可达的产品路径诱发这种不匹配。
4. **由产品负责的消费。** 产品代码以某种方式呈现、存储、转换或消费该决定，从而放行 B。
5. **有重大后果的 sink。** 到达 sink 的确切操作被记录下来；中间状态或模型的陈述不够格。
6. **无等价的直接权威。** 攻击者不劫持这次审批，就无法获得同样的实质效果。

这个操作性定义及其两变体分组是一种研究分类学，并不声称审批完整性或动作绑定是什么新东西。已有工作已经要求同意与执行之间的可信呈现与绑定 [25, 26, 6]。

图 2：两个主要变体及其安全分支。在表示变体中，B 在审查之前就已存在，但视图显示的是 A；在状态替换变体中，正确的 A 在审查之后变成 B。完整的渲染与使用时绑定可以同时解决两者；阻止未授权篡改则是针对状态变体的额外控制。（原文第 4 页）

### 2.4 攻击者与信任边界

攻击者可以是一个低权限的任务发起者、一个仓库写入者、一个远程 agent，或另一个具有狭窄状态更新能力的行为者。攻击者不必控制模型，也不必与审批者竞速。关键的是不对称的权威：攻击者能影响请求或挂起状态，却无法授权 B；审批者能授权有重大后果的执行，却并不打算要 B。

我们排除全能的数据库写入者——他能伪造每一个可信的审批字段，因为这样的主体已经控制了授权底座。我们也排除这些情形：B 在任何决定之前就执行、审批提示被完全跳过，或者唯一的事件只是普通用户输入或校验。prompt injection、memory poisoning 或会话走私可以提供 B，但一条 Loopjacking 轨迹只有在产品把为 A 作出的决定绑定到 B 时才开始。

我们的实验评估的是系统绑定，而不是人的易感性。审批角色只有在测试已经断言并记录了产品对 A 的确切视图之后才推进。这造就了一个确定性的审批决定，同时刻意回避了关于界面理解、欺骗率或用户行为的任何主张。

### 2.5 A2A 作为条件式载体

在 7.6.4 节之前，A2A 做出了三个与延迟审批路径相关的协同选择。TASK_STATE_AUTH_REQUIRED 是一个中断的、非终态的状态；在授权仍处于挂起状态时，建议 agent 接受发往同一 Task 的消息；而一个带外收到凭据的 agent 可以在没有客户端后续消息的情况下继续处理。周围文本以破坏性操作前的人类审批作为一个例子，但没有定义审批者、规范化操作、动作范围的审批对象，或应用侧的 sink [2]。

这些机制本身并不构成漏洞。不妨看图 3 中的条件式组合。一个无法批准、也无法直接执行 B 的 Task 写入者提出 A。产品把确切的 A 呈现给一个独立的审批者，并记录决定 DA。在该决定被消费之前，写入者在同一个非终态 Task 上发送 B。如果由实现负责的逻辑在收到凭据后从当前 Task 状态中选出 B，并且在没有使用时范围比对的情况下消费 DA，那么产品就在对 A 的审批之下放行了 B。这种组合就是审批后 Loopjacking。A2A 提供 Task、消息、中断与恢复的协同机制；审批视图与决定范围由实现或凭据签发方负责；操作选择、使用时比对与有重大后果的 sink 则由实现负责。

图 3：A2A 作为条件式载体。蓝色方框是协议协同，灰色方框是实现或签发方负责的语义。只有红色分支才是 Loopjacking：实现代码为 B 消费决定 DA；绿色分支使用同样的 A2A 机制，但把当前操作与决定相比对，拒绝或重新授权不匹配。（原文第 5 页）

Issue 2080 把缺失的责任归属框定为实现者歧义，而不是扩展核心协议范围的请求 [4]。合并的 pull request 2081 增加了 7.6.4 节：中断状态是一个协同信号，而不是授权授予；实现、签发方或扩展必须定义被授权的操作，并检查后续的使用 [5]。在我们 2026 年 9 月 10 日的截止点上，v1.0.1 仍是最近的打标签发布 [3]。这段历史支持的是一条规范清晰性的教训，而不是 A2A 或通用 SDK 的内在漏洞。下文的原生案例各自独立地确立了它们的审批语义与不安全的消费方式。

## 3 Loopjacking 案例

我们选择这些产品，是为了在不同的所有权与状态边界之下检验该定义。这组样本包含两条审批后路径、一条表示路径，以及一个预期能保持绑定的实现。选择是有目的的（purposive）：之所以选这些案例，是因为它们暴露了由产品负责的审批和一条可测量的「授权 → 效果」路径，而不是为了估计这种弱点出现的频率。

在所有实验中，动作都是无害的，但实质上各不相同。对于状态替换案例，A 是向已批准供应商转账 20 单位的模拟转账，B 是向攻击者指定的 sink 转账 2,000 单位的模拟转账。工具把它们实际收到的参数原样追加进一本账。对于 shell 案例，B 通过一个 A 中不可见的命令创建一个临时标记。这些 sink 确立了产品派发的操作，而无需联系生产服务或转移真实资产。

表 1：三条阳性产品路径的接纳情况。「直接 B 被拒绝」意味着攻击者要获得所测效果，这种不匹配是必需的。LangGraph 的结果以所述授权策略为条件。（原文第 6 页）

| 产品路径 | 审批与不匹配 | 攻击者边界 | 产品消费与控制 |
|---|---|---|---|
| Agno AgentOS 常规 Agent | 审批后状态替换。视图：transfer(20, vendor)。管理员批准之后，maker 提交 transfer(2000, sink) | maker 有 run/continue 权限，但没有审批 token，也没有直达 B 的路径 | AgentOS 安装并派发 B。错误行为者与直接 B 被拒绝；未改动的 A 与 exact-action 对照通过 |

### 3.1 Agno AgentOS：审批之后被改掉的 continuation

**边界。** 所测部署在 AgentOS 的 HTTP API 之后使用一个常规 Agno Agent。JSON Web Token 表示三个相关角色：具有 agents:run 的 maker、单独的具有 agent_os:admin 的审批管理员，以及没有相关任务权限的行为者。maker 可以启动并继续自己的 run，但无法解决审批；管理员可以解决产品的审批记录，但并不提供 continuation。这种分离很重要：攻击并不假设 maker 持有管理员 token。

**轨迹。** maker 先启动了 A，导致 AgentOS 为确切的工具名与参数持久化一条必需的审批。该审批记录把这次 run 与 maker 关联起来，并且只显示向已批准供应商转账 20 单位。挂起状态对照与直接 B 对照都没有产生任何 B 账本事件。随后审批管理员解决了 A；存储的记录把管理员记为解决者，并且仍然只包含 A。在挂起的审批清除之后，maker 继续同一个 run，并提交了一次工具执行：调用标识（call identity）沿用原来那个，但参数是 B 的，状态为 confirmed。AgentOS 接受了这次 continuation，并以 B 调用了注册的工具。审批列表中没有出现对 B 的审批。

所测的源码路径解释了这一结果。continuation 路由先检查是否仍有必需的审批处于挂起状态。一旦该 run 级状态被清除，它就反序列化调用方提供的工具执行，把提供的对象安装进 run，并派发一次 confirmed 的工具执行。在主测试路径中，调用标识是匹配的，但当前工具参数没有与已批准记录中的描述符（descriptor）比对。因此缺失的绑定位于已批准的 (tool, args) 对与派发时实际使用的对之间。

在完全相同的常规 Agent 配置下，已发布的 Agno 2.5.6、2.9.0、3.0.1、3.0.2、3.0.3、3.0.6 与 3.0.9 产生了这条轨迹。相邻的 2.5.5 对照允许直接 B，因此它不算合格的 Loopjacking 结果；2.5.6 是已确立的下边界——在这个版本上，审批门既能阻断直接 B，又可被替换后的 B 复用。包发布元数据确认了这里使用的证据冻结端点 [10]。我们不推断每个中间补丁都受影响，也没有确立任何已修复的 Agno 发布版本。

**对照。** 该矩阵拒绝了 maker 试图自行审批的尝试，拒绝了错误用户、外部人、挂起状态与错误会话的操作，并放行未改动的已批准 A。一个研究性对照在存储已批准的规范化描述符、并在使用时比对，它在保留 A 的同时拒绝了 B。该对照演示了修复不变式，但它不是 Agno 的产品修复。

### 3.2 LangGraph Agent Server：条件式共享线程替换

**边界。** LangGraph 实验使用已发布的 Agent Server 及其内存内运行时，LangChain 1.3.18、LangGraph 1.2.11，以及一个受支持的自定义授权策略。该策略允许 maker 更新一个共享的挂起线程，但不允许恢复它，也不允许调用受保护的转账。一个独立的审批者可以检查并恢复该线程，并持有模拟的 wire:execute 权限，但无法执行 maker 的更新。外部人被拒绝。这是文档化扩展点的一种合理组合，但我们不主张它是默认部署。

**轨迹。** maker 创建了一个线程，其 interrupt 显示确切的 A。审批者读取了该 interrupt。在审批者行动之前，maker 使用 Agent Server 自带的 A2A message-command 界面提交了 message.command.update；该更新把挂起的同 ID 工具调用替换成 B。maker 仍然无法恢复线程，也无法直接执行 B。随后审批者只提交了从早先视图得出的、已经过期的 approve 决定。Agent Server 从当前线程状态恢复，工具在审批者的身份与权限之下收到了确切的 B。攻击账本里是 B 而不是 A；一个独立的未改动对照执行了 A。

这条产品路径跨越四个组件：Agent Server 接收并转发该消息命令；message reducer 替换一条同 ID 的挂起消息；HITL 处理在恢复时重建当前调用；执行继承已认证的 resume 主体。没有任何比对把先前显示的动作与当前同 ID 的动作绑定起来。自定义授权策略制造了职责分离，但替换与恢复行为是由已发布的产品组合提供的。

这条严格轨迹在 12 个已发布的 Agent Server 版本上执行：0.7.5、0.7.103、0.8.7、0.9.1、0.10.3、0.11.4、0.12.4、0.12.6、0.12.9、0.13.2、0.13.4 与 0.14.0。版本 0.7.4 缺少必需的 command-update 路径。对 130 个稳定 wheel 的哈希校验扫描发现，从 0.7.5 到 0.13.4 的每一个发布都包含所需的转发路径；只有列出的抽样版本被实际执行，而 0.14.0 是单独的当前发布执行点。因此，当授权允许非审批者替换挂起的共享线程动作时，已发布的 LangGraph Agent Server 会在所测的内存内组合中执行 B。一个拒绝该更新的受支持策略能阻止 B 并保留 A，所以这一结果是有条件的，而非普遍的。截止点处的当前发布点由包元数据独立识别 [11]。

**对照与范围。** 直接 B、maker 恢复与外部人访问都没有产生受保护的效果。未改动的路径产生了确切的 A。在安全策略对照中，同一个 Auth 扩展拒绝了 maker 的更新，状态保持为 A，审批者执行了 A。生产环境的 Postgres 未被评估：官方镜像在服务客户端之前就要求 license key。因此我们不对 Postgres 作任何主张，也不指认任何厂商已修复的发布版本。

### 3.3 OpenClaw：不完整的 shell 表示

OpenClaw 暴露一条经由网关的审批路径，用于派发到节点主机的命令。在受影响的 shell-wrapper 路径中，请求携带一个位置参数向量，其内联负载（inline payload）为 $0 "$1"；额外的位置参数则选择了创建 B 标记的命令与目的地。完整向量在审批之前就已准备好。然而产品的审批事件只表示了内联负载 A。在通过产品审批解决路径记录一次 allow-once 决定之后，版本 2026.2.23 把完整向量放行给节点主机，并创建了标记。未经审批的直接 B 被拒绝，未改动的已批准命令则成功。

OpenClaw 2026.2.24 增加了对完整参数向量的一致性检查。在相同输入之下，它在节点执行之前就拒绝了不完整的原始命令表示，没有产生 B 标记，继续拒绝直接 B，并保留了未改动的 A。于是，已发布的 2026.2.23 消费了对不完整的 A 的审批并执行了完整的 B，而 2026.2.24 拒绝了这种不匹配。这个原生边界与厂商公告及补丁一致 [18, 7]。

后来的一则公告在实质上描述了同一种 shell-wrapper 不匹配，但列出的是 5 月的边界 [17]。注册表与提交祖先检查没有找到稳定的 2026.5.16 产物，而所检查的 5 月发布已经包含 2 月的修复。因此我们采用原始公告以及复现出的 2026.2.23 / 2026.2.24 边界。把后来的记录当作重复项，是我们基于证据的调和，而不是厂商或 GitHub 的正式合并决定。

这些实验中的审批决定，只在产品的确切事件被断言并记录之后才以脚本方式作出。该实验确立的是产品的表示与放行行为，它不确立一个人会多频繁地理解或批准同一个对话。

## 4 评估

### 4.1 方法

对每条产品路径，我们记录完整请求、人可见的审批表示、决定、相关的任务或调用血缘、使用时刻的操作，以及最终的账本或标记效果。试验使用锁定在隔离环境中的已发布包。联网产品经由其文档化的服务器路径跨越 loopback HTTP。模型是确定性的本地 fixture，因为模型选择并不是所主张的原因。凭据是合成的，所有外部效果都被替换成仅追加的账本或临时文件。

一个攻击结果除了观察到 B 之外，还必须满足五项对照：为审批呈现了确切的 A；未改动的已批准 A 成功；以攻击者身份直接执行 B 失败；在产品暴露该范围时，声明范围之外的行为者失败；已修复的发布或安全配置在保留 A 的同时阻断了不匹配。我们检查的是 sink 参数，而不只是一个 HTTP 状态、一个挂起状态或一个模型响应。

保留的证据包括包清单、依赖版本、原始请求与响应、授权决定、审批记录、最终效果与文件哈希。Agno 当前发布矩阵在 macOS 上使用 Python 3.12.11 并跨越其 AgentOS HTTP 路径；早期的代表性运行还使用了干净的 Linux 容器。LangGraph 的 0.13.2 点在 Linux 上重复执行；发布矩阵与其他当前点在 macOS 上运行。OpenClaw 跨越其 loopback 网关与节点主机路径。OpenAI Agents 使用原生 RunState 序列化与自带的确定性测试模型。

**Agno。** 每个列出的严格阳性 Agno 发布，都在五次攻击试验中执行了被替换的动作，在五次对照中执行了未改动的 A，三次直接 B 尝试全部被拒，通过了行为者边界检查，也通过了 exact-action 研究对照。证据冻结的当前 3.0.9 bundle 完成了全部 23 个声明单元。版本 2.5.5 说明了为什么直接路径对照是必需的：它同样执行了 continuation，但由于直接 B 成功，审批劫持并不需要。这些结果确立的是确切的所测发布点以及相邻的 2.5.5 / 2.5.6 边界，而不是一段不间断的影响范围。

**OpenClaw。** 2026.2.23 上全部 3/3 次试验都捕获了不完整的审批视图、完整的既有向量、产品的一次性允许决定，以及 B 的效果。每次试验也都拒绝了直接 B，并执行了未改动的 A。2026.2.24 上对应的全部 3/3 次试验都在节点执行之前拒绝了不匹配，同时保留了两个对照。这一配对发布测试定位了表示失败，并验证了产品修复。

**OpenAI Agents 阴性对照。** 对 0.22.0 与 0.22.2 两个版本，每一个已批准的确切 A 状态都被序列化、恢复并继续执行，全部执行了 A。在每次攻击试验中，挂起调用的原始序列化副本被改成 B，同时保留调用 ID 与原始的规范化审批/调用记录。恢复成功，但 resume 抛出 ModelBehaviorError，账本保持为空。未经批准的直接 B 处于暂停（paused）状态。因此在这些版本中，普通的逐次调用审批仍然绑定在规范化调用上，这表明仅凭 continuation 与序列化本身是不够的。审批与 resume 模型由 SDK 文档化 [21]，包元数据指认了发布端点 [12]。

### 4.3 比较性解读

三条阳性路径在不同阶段失败。OpenClaw 在决定之前就丢失了信息：面向人的那个字符串并不是节点将要执行的完整操作。Agno 呈现了正确的动作，但随后把「没有挂起的 run 级审批」当作足以接受调用方提供的当前参数。LangGraph 组合同样呈现了正确的动作，然后允许一个独立的状态写入者在审批者从当前状态恢复之前把它替换掉。OpenAI 对照在同样宽泛的暂停/序列化/恢复生命周期中保留了规范化调用记录，并拒绝被改动的原始调用。

这一比较在所测样本之内支持两个结论。第一，可恢复性（resumability）是审批后替换的载体，但既不是这个伞形概念的必要条件，也不是失败的充分原因。第二，安全的对象必须是完整的当前操作，而不只是一个调用标识、一个 run 的审批状态或一个渲染出来的子串。在所有被测轨迹中，完整的规范化渲染加使用时比对，或者阻止未授权的挂起状态篡改，都能在不破坏 A 的前提下阻断 B。

## 5 区分 Loopjacking

底层的安全规则是确立的：人批准的动作应当就是执行的动作。Consent Integrity 为黑盒 agent 审批定义了可信呈现与绑定到执行 [25]。SUDP 把一次新鲜的授权授予绑定到规范化操作，并把替换与重放视为协议威胁 [26]。微软的动作绑定审批设计同样规定了持久的动作摘要、经认证的审批者链、过期、消费与执行时再校验 [6]。因此 Loopjacking 的贡献是一个操作性定义、一个两变体比较，以及来自具名已发布产品路径的证据；它并不是审批完整性、exact-action 授予或再校验的发明。

表 3：近邻区分。Loopjacking 的决定性条件是：由产品负责地消费一个为 A 作出的真实人决定，去授权或放行实质不同的 B。（原文第 11 页）

| 近邻 | 核心机制 | 关系 | 缺失或区分条件 |
|---|---|---|---|
| Lies in the Loop [9] | 审批对话的内容或呈现被操纵 | 与基于表示的 Loopjacking 直接重叠 | Loopjacking 还涵盖正确审查之后由产品负责的状态替换 |
| Consent Integrity [25] | 可信呈现与绑定到执行 | 直接陈述了该安全性质，并涵盖替换威胁 | 本文贡献的是产品比对与变体分类，而不是该性质本身 |
| Agent Session Smuggling [1] | 远程 agent 向一个活跃的跨 agent 会话注入隐蔽指令 | 能把 B 送进有状态的工作流 | 不需要针对 A 的动作特定的人决定，也不需要为 B 消费该决定 |
| Authorization Continuity [27] | 判断一个存活的授予在 agent 状态、委托或任务阶段变化后是否仍然有效 | 最接近的通用过期授予模型 | Loopjacking 需要具体的「人审批 → 效果」轨迹与可触达的不匹配行为者 |
| AID-Guard [23] | 在 commit、重试与恢复时对请求与 provider 状态再校验 | 与接纳后的篡改及修复直接重叠 | 本身并不是产品审批劫持实例 |
| Memory poisoning [8] | 不可信数据持久化并引导后续行为 | 能提供或影响 B | 既不需要对 A 的审批，也不需要复用其权威 |

### 5.1 表示与审批欺骗

OWASP 的 Lies in the Loop 命名了那些操纵审批对话内容、让有害操作看起来无害的攻击 [9]。该工作是一个直接近邻：当产品的审批视图省略或歪曲了操作的实质部分时，其中一些案例满足我们的表示变体。范围并不相同：Loopjacking 要求由此产生的「A → B」授权轨迹，也包括「正确的审批视图之后发生状态替换」。普通社会工程——人明知而批准完全可见的 B——不在我们的定义之内。

OpenClaw 的公告是一个具体的表示案例。其他公开记录显示了不同的审批到效果的不匹配。Cursor 的 MCPoison 公告描述了一个良性的 MCP 配置被批准、随后被仓库写入者改动而未经重新审批 [15]。我们把它当作有来源支撑的类比，而不是本地复现的案例或普遍性的证据。

### 5.2 变化中的状态与授权连续性

近期的 agent 安全工作直接处理变化状态之下的授权问题。Authorization Continuity 追问：当 agent 的状态、工具、委托、执行或任务阶段发生变化时，一个授予是否仍然有效 [27]。Stateful Governance 要求效果相对于当前策略与资源状态串行化 [22]。AID-Guard 把再校验扩展到篡改、重试、模糊结果与恢复 [23]。更早的以及非 agent 的状态分歧示例同样表明，检查一个表示却使用另一个表示，会授予非预期的权威 [20]。这些工作排除了关于过期授权或 commit 时检查的新颖性主张。我们更窄的问题是：在已发布的 agent 产品中，人的审批如何附着到一个不同的具体效果之上，以及究竟是哪一个阶段产生了这种不匹配。

动作治理系统提供了互补的预防手段。AgentBound 把策略与治理回执绑定到具体动作 [13]，而确定性的 pre-action 授权在执行之前检查每一次结构化工具调用 [24]。当这种检查重建完整的当前操作、评估正确的策略，并对任何未经批准的改动失败关闭（fail closed）时，它就能阻止所测的攻击。

### 5.3 会话、prompt 与记忆攻击

Agent Session Smuggling 通过一个活跃的跨 agent 会话注入隐蔽的多轮指令 [1]。它能改变 agent 打算做什么，但它不需要人的审批，也不复用早先的决定。因此会话走私可能为易受 Loopjacking 影响的工作流提供 B；这两种分类是组合关系，而不是彼此包含。Memory poisoning 在这一点上类似：持久的不可信数据能影响后续操作，但只有当产品对 A 的审批随后被用于那个被改动的操作时，攻击才变成 Loopjacking [8]。

Prompt injection 与不安全的 allowlist 也能在不劫持某个具体人决定的情况下绕过确认。已发表的 agent 命令执行工作中，包括一些即便注入参数使其变得有害、仍被归类为安全或预批准的路径 [19]。Google ADK Python 公开的 confirmation-continuation issue 同样接受伪造的确认状态，而不是消费一个为 A 作出的真实人决定 [16]。两者都与安全相关，并促使了精确的当前操作检查，但在我们的定义之下都不计为 Loopjacking 结果。

## 6 检测与预防

图 1 所示的审批绑定不变式给出了防御方案：保留人所批准的操作，重建将要执行的操作，并在最后一个授权点上比对二者的完整规范化描述符。比对必须发生在所有受攻击者影响的解析、模板化、状态归约、continuation、默认值插入、包装器展开与参数解析之后。

### 6.1 规范化审批记录

一条审批记录至少应当绑定：

- 规范化的动作或工具标识，以及每一个实质参数；
- 目标资源、目的地与相关的副作用类别；
- 发起主体与任务、线程或会话范围；
- 批准主体，以及解释了该请求的策略或签发方；
- 一个 nonce、创建时间、过期时间与消费状态；以及
- 对向人展示的那个同一完整描述符计算出的摘要。

展示必须由这个描述符生成，而不是从一个有损的便捷字符串生成，同时执行却使用更丰富的对象。Shell wrapper 值得特别小心：内联负载、位置参数、环境变更、工作目录、解释器标志与重定向都可能改变效果。折叠视图仍然可能有用，但审批必须暴露任何实质的隐藏字段，否则就拒绝授权它们。

### 6.2 使用时决定

在放行效果之前，强制点应当重建完整的已解析操作，并把它与绑定到审批的描述符或摘要相比对。一个紧凑的决策过程是：

1. 若决定缺失、过期、已撤销、已消费，或超出其主体与任务范围，则拒绝；
2. 若当前操作与已批准的描述符存在实质差异，则拒绝或请求新的审批；
3. 对已解析的效果重新评估当前策略，包括资源与目的地约束；
4. 原子地消费该决定并放行效果，或记录一个防止重放的幂等 commit token；以及
5. 把已批准描述符、当前描述符、决定与效果追加进一条审计记录。

当 reducer 能替换与该标识关联的参数时，只绑定调用标识是不够的。当 continuation 能安装不同的工具执行时，只绑定 run 级的「approved」标志是不够的。当状态能在派发之前改变时，只在呈现时刻检查是不够的。

### 6.3 控制放置

有两种控制策略阻断了所研究的路径。

**绑定并再校验。** OpenClaw 2026.2.24 重建并检查完整的 shell 参数向量，在节点执行之前拒绝表示不匹配，同时仍然执行未改动的 A。OpenAI Agents 的普通逐次调用审批在序列化过程中保留规范化调用指纹，并拒绝同调用 ID 的原始调用改动。围绕 Agno 轨迹的一个研究性 exact-action 包装器同样拒绝了 B 并保留了 A。这是更通用的策略，因为它能经受住经授权的或良性的状态变化——只要实质效果一变，就要求一个新鲜的决定。

**阻止未授权篡改。** LangGraph 的安全策略拒绝了非审批者对挂起线程的更新。动作保持为确切的 A，审批者执行了 A。当业务角色能够禁止此类更新时，这是有效的。然而它特定于组合，而且当合法的更新、重试或迁移可能改变操作状态时，它不能替代 exact-action 绑定。

对所测轨迹而言，完整的规范化审批渲染加精确的当前效果检查，或者阻止未授权挂起状态改变的策略，都能在保留合法 A 的同时阻断 B。这份证据是有界的：OpenClaw 提供了已发布的产品修复；LangGraph 策略是受支持的安全配置；Agno 包装器是研究性对照，而非已发布修复。该设计与先前的 consent-integrity、操作绑定与动作绑定审批提案一致 [25, 26, 6]。

### 6.4 测试指引

一个回归测试应当保留的不只是最终状态码。它应当捕获审批视图与完整请求，通过每一个受支持的审查后界面改动一个实质字段，并在 sink 处断言确切的操作。最小测试套件是：未改动的 A 成功；拒绝不产生任何效果；攻击者无法直接执行 B；A 到 B 的表示或状态替换被拒绝或重新授权；错误的范围失败；已消费或过期的审批不能被重放。同时测试两个变体，可以避免只修可见的那个症状。

## 7 局限、伦理与可复现性

### 7.1 研究局限

这四条产品路径构成一个有目的的集合，而不是随机或代表性的样本。它们确立了机制上不同的案例和一个阴性对照，但无法测量生态的普遍程度，也不能表明大多数 agent 框架受影响。结果是特定于配置与版本的。由这个伞形定义推不出通用的 CWE、CVSS 分数、严重性或影响估计。

Agno 在七个合格发布点、加上不合格的 2.5.5 边界对照上被执行。中间补丁并非全部被执行或源码扫描，因此我们不主张一段不间断的影响范围。截止点处没有已知的已修复 Agno 发布，本研究中的 exact-action 对照是研究者自行编写的。

LangGraph 的结果依赖内存内运行时、LangChain 1.3.18、LangGraph 1.2.11，以及一个允许非审批者更新共享挂起线程的 Auth 策略。受支持的 deny-update 策略是安全的，所以该结果并不刻画所有部署。wheel 扫描验证了到 0.13.4 为止所需的转发路径，而 0.14.0 是单独的原生点。生产环境的 Postgres 行为未被测试，因为官方设置要求部署或企业 license key，且没有确立任何厂商修复。

OpenClaw 是所研究的唯一一条带有原生「受影响 / 已修复」发布对的阳性路径。其审批角色在检查了确切的产品审批事件之后被自动化。这隔离了绑定行为，但不测量用户理解、欺骗率或界面质量。后来那则公告的重复状态是基于证据的调和，而不是厂商的正式认定。

OpenAI 的结果仅限于 0.22.0 与 0.22.2 中普通的 function-tool 逐次调用审批。它不涵盖有意的 sticky always_approve 策略，也不涵盖能够伪造序列化状态中每一个可信规范化字段的攻击者。它是一个阴性对照，而不是「SDK 周围所有由应用自行编写的审批都安全」这一主张。

所有实验由一名研究者操作。选定的点在干净的 macOS 环境中重复执行，具有代表性的 Agno 与 LangGraph 版本还在 Linux 容器中执行，但没有独立复现。我们的文献与公开来源审查截至 2026 年 9 月 10 日；我们不主张穷尽覆盖，也不主张优先权。

### 7.2 伦理与披露

测试仅限于本地隔离环境中已发布的软件。所有网络流量使用 loopback 传输。token 与身份是合成的；秘密没有保留在留存流量中。有重大后果的工具只写入模拟账本或临时标记。我们没有联系生产系统、转移资金、访问第三方数据，也没有执行破坏性操作。

本研究在协同披露的约束之下进行。本手稿使用公开公告、公开的规范变更与本文所述的产品证据；它排除私人协同消息、个人联系信息、未经核实的时间线与无关的漏洞跟踪。产品发现被分开处理：A2A 规范历史、Agno 配置、条件式 LangGraph 组合、OpenClaw 公告与 OpenAI 阴性对照并不共享同一个被主张的根本原因。

### 7.3 可复现性

随附的证据归档 [14] 为每一个被接纳的点记录了已发布包版本、依赖锁定、平台、测试命令、确切的行为者与范围、请求、审批表示、规范化的 A 与 B、决定、原始传输或序列化状态、最终账本或标记，以及校验和。在仓库根目录运行 `python3 verify_archive.py` 会重新计算留存 bundle 的哈希与所声明的结果预言机（result oracle）。手稿中生成的数值读自冻结的结果对象，而不是手工敲进结果表。

复现不需要外部副作用。Agno 与 LangGraph 测试启动本地服务器并使用确定性模型；OpenClaw 测试连接本地网关与节点主机；OpenAI 对照序列化并恢复原生 run 状态。复现者应当同时验证攻击与其配对对照，并把缺少带许可的 Postgres 环境视为 LangGraph 主张之外的情形，而不是一个阴性结果。

## 8 结论

人的审批并不是一道安全边界，除非它仍然附着在继承其权威的完整操作之上。Loopjacking 命名的是这样一种由产品负责的失败：被理解为 A 的审批，授权或放行了实质不同的 B。这种不匹配可能在审批之前就以不完整的表示存在，也可能在之后通过可变的工作流状态产生。

被评估的产品展示了两种变体及其边界条件。所测的 Agno 配置与条件式 LangGraph 组合演示了审批后替换；OpenClaw 演示了审批前的表示不匹配；OpenAI Agents 则提供了一个反例，其中可恢复的序列化状态保持了动作绑定。这些是确切的产品与配置结果，而不是普遍性估计，也不是「审批完整性是新的」这一主张。

这条实用规则说起来简单、做起来容易漏掉：渲染完整的规范化操作，把决定绑定到该描述符及其范围，在使用时重建实际的当前效果，并拒绝或重新授权任何实质改动。阻止未授权的挂起状态篡改增加了有用的纵深防御，但精确的使用时绑定仍然是可移植的不变式。这些控制在不破坏合法 A 的前提下阻断了所研究的攻击。
