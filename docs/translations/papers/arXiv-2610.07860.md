## 摘要

多智能体系统正被越来越多地用于复杂的知识型工作，但它们的编排层在很大程度上仍然是无记忆的：每个新任务都要从零开始分解、分配与执行，无法从以往成功的执行中获得任何收益。我们提出 WorkflowOps，一个多智能体工作流编排框架，它从历史工作流中学习智能体协作先验，并按需扩展自身的智能体池以覆盖新的能力需求。本方法引入三个相互耦合的机制。其一，转移概率矩阵从历史工作流中统计智能体两两之间的协作频率，并在 DAG 工作流构建过程中将其用作软性引导，具体手段包括层内排序优化、基于概率阈值的边建议，以及为最大化并行度而做的传递归约。其二，充分性驱动的智能体创建闭环通过语义匹配分数检测能力缺口，借助 LLM 生成专门化的智能体，并同时把它们注入协作矩阵，使新建的智能体一经创建即可使用，并自带被预测出的协作先验。其三，分层语义匹配策略先用预训练的句向量进行快速、确定性的能力匹配作为第一轮筛选，仅对低置信度样本调用 LLM 核验，从而相比纯 LLM 方法减少了 80% 以上的 LLM 路由调用。

我们将工作流构建问题形式化为一个在依赖合法的 DAG 上、由马尔可夫协作先验引导的约束优化问题，并证明即便是完全不经训练的、轻量的基于频率的统计量，也能提供有效的编排引导。在混合了代码、数学与问答的任务集上的实验表明，WorkflowOps 相比近期的工作流构建基线提升了端到端通过率，且在结构化、可分解、过去的智能体交接模式可以迁移的任务上提升最大。

## 1 引言

基于大语言模型（LLM）的多智能体系统已迅速从研究原型演变为面向复杂知识工作的实用框架。AutoGen（Wu et al. 2024）、CrewAI（CrewAI 2024）、LangGraph（LangChain 2024）等系统允许开发者把专门化的智能体组合成协作工作流，用于研究综合、软件工程、合规分析、商业规划等任务。随着这些系统被应用于日益复杂且反复出现的任务，编排层——一个任务如何被分解、子任务如何分配给智能体、依赖关系如何组织、以及最终工作流如何执行——已经成为核心瓶颈。即使相似的工作流此前已经成功过，每次查询都从零重建工作流也会推高 API 成本、延迟以及误差累积的风险。

当前许多编排流水线的核心局限在于缺少持久的编排状态：工作流级别的协作先验、不断演化的能力覆盖、以及低成本的能力匹配，很少能在不同任务之间延续使用。历史工作流轨迹暴露出反复出现的交接、能力缺口和匹配模式，它们可以作为软性引导而非硬性约束被复用。近期工作通过拓扑选择、动态协调、学习式优化、路由以及子智能体创建来提升编排的适应性（authors 2026a,c,d；Yue et al. 2025；Zhang et al. 2026a；authors 2026b）。然而，这些方向通常是被分开研究的：有些方法在任务执行时重新计算决策，有些需要针对具体任务的训练，还有些创建了智能体却没有把它们整合进一个持久的协作模型。

我们提出 WorkflowOps，一个以历史为条件的编排框架，它通过协作先验矩阵、持续演化的智能体池和语义能力索引来维持持久状态。该系统把历史的或自举得到的成功工作流轨迹作为软性引导，在依赖合法的 DAG 上进行近似的约束优化，同时权衡与历史协作模式的一致性、子任务与智能体分配的充分性、以及结构并行性。具体而言，WorkflowOps 构建一个行随机的智能体转移矩阵，用于层内排序、软边建议，并通过传递归约（Aho, Garey, and Ullman 1972）剪除冗余边；它只在语义充分性检查暴露出能力缺口时才扩展智能体池；并以 Sentence-BERT 风格的嵌入（Reimers and Gurevych 2019）作为主要路由机制，对低置信度样本可选地进行 LLM 核验。

图1：WorkflowOps 总览。给定智能体池 A、转移矩阵 P 和任务 T，该流水线先分解 T，再把子任务匹配给智能体（当 ϕ < τ 时创建 a*），随后以 P 为软引导构建 DAG，并按层并行执行。输出为工作流 W、扩展后的 A′ 以及更新后的 P′；珊瑚色标记的是新建的智能体。（原文第2页）

我们在两个异构任务集上评估 WorkflowOps：一个混合了代码、数学与问答的 Mixed 基准，以及更难的、包含竞赛级与前沿难度问题的 Mixed_Hard 任务集。在 Mixed 测试划分上，DAG 模式的 WorkflowOps 达到 0.890 的总体通过率（Linear 模式为 0.870），比最强的查询级基线 MetaAgent（Zhang, Liu, and Xiao 2025）高出 13.9 个绝对百分点，比最强的任务级基线 ADAS（Hu, Lu, and Clune 2025）高出 19.6 个百分点。在更难的 Mixed_Hard 任务集上，WorkflowOps 达到 0.770，超过每一个已完成的基线至少 15 个百分点。消融实验显示，移除转移矩阵、关闭智能体池演化、以及用 TF-IDF 替换语义嵌入，分别使准确率下降 4.5、1.7 和 8.5 个百分点，从而验证了三个耦合机制各自的作用。增益在代码和数学任务上最强；相对 Linear 模式，DAG 执行通过矩阵建议的边带来适度的额外准确率提升。

我们的贡献如下：

1. 我们把以历史为条件的多智能体工作流构建形式化为在依赖合法的 DAG 上的近似约束优化问题，由从成功工作流轨迹中提取的持久马尔可夫协作先验引导。
2. 我们用一个转移先验的工作流构建算法实例化这一形式化：使用经验性的智能体间转移概率进行层内排序、软边建议和冗余剪除，同时保留硬性任务依赖。
3. 我们提出一个充分性驱动的智能体池扩展闭环，它通过语义匹配检测能力缺口，只在必要时创建专门化智能体，并把新智能体立即整合进协作先验矩阵。
4. 我们在 Mixed 和 Mixed_Hard 基准上给出了端到端的实证研究与消融分析：在 Mixed 上相比最强查询级基线总体提升 13.9 个百分点，在 Mixed_Hard 上领先已完成基线 15 个百分点以上，同时分离出转移先验、智能体演化与语义匹配各自的影响。

这些结果共同把 WorkflowOps 定位为一个轻量且可解释的框架，用于免训练、以历史为条件的多智能体编排。它不依赖昂贵的策略学习，也不从零重建工作流，而是证明：简单的基于频率的协作统计，只要与持久的智能体池演化和语义能力匹配相耦合，就能作为未来工作流构建的有效操作性先验。

## 2 相关工作

近期的多智能体编排方法主要通过拓扑选择、动态协调、学习式工作流优化、路由或智能体创建来提升适应性。AdaptOrch（authors 2026a）在预定义的编排模式之间做选择，CORAL（authors 2026c）研究基于信息流的动态协调，FlowSteer（authors 2026d）则通过强化学习学习工作流编辑策略。其他工作直接优化工作流结构或交互策略，包括 HeGFlow（Guan, Wang, and Shen 2025）、AgentPO（Sun et al. 2026），以及 ADAS（Hu, Lu, and Clune 2025）、MaAS（Zhang et al. 2025b）这类智能体架构搜索方法。这些方法表明编排结构确实重要，但其中许多要么在任务执行时重新计算决策，要么需要针对每个目标场景进行训练或搜索。

我们的基线正是这条工作流搜索路线的实例：AFlow（Zhang et al. 2025c）用 MCTS 搜索工作流代码，ADAS（Hu, Lu, and Clune 2025）执行自动化的智能体系统搜索，MaAS（Zhang et al. 2025b）在架构超网络上搜索，MetaAgent（Zhang, Liu, and Xiao 2025）则为每个查询构造一个有限状态机工作流。另一条路线复用工作流经验：Agent Workflow Memory（Wang et al. 2024）归纳并存储可复用的工作流技能，EvoFlow（Zhang et al. 2025a）演化出一个多样的工作流种群，TopoPrior（Zhang et al. 2026b）学习可跨领域迁移的拓扑先验。WorkflowOps 与这两条路线互补：它既不存储可执行工作流，也不学习拓扑生成器，而是积累可解释的智能体间转移统计，并在硬性任务依赖之下把它们用作免训练的软性引导。

另一条互补的研究线关注智能体路由与自演化智能体系统。MasRouter（Yue et al. 2025）和 EvoRoute（Zhang et al. 2026a）为多智能体系统学习路由策略，而 AOrchestra（authors 2026b）、SEAA（SEAA authors 2026）、SEVerA（Banerjee, Xu, and Singh 2026）与 AgentOrchestra（authors 2025a）则探索动态子智能体创建、自我扩展、验证或分层编排。WorkflowOps 的不同之处在于把这些线索整合进同一个免训练、以历史为条件的编排层：经验性转移先验引导 DAG 构建，语义匹配负责把子任务分配给智能体，需求驱动的智能体创建在扩展池的同时立即更新持久的协作先验。扩展的相关工作见附录 A。

## 3 问题形式化

一般性问题。给定一个任务 T 和一个智能体池 A，工作流编排必须产出一个依赖合法的工作流 DAG W 和一个智能体分配 π，使下游任务成功率最大化。这一表述不依赖任何具体机制。除此之外，WorkflowOps 还假设可以访问一份成功工作流的历史记录，并从中导出转移矩阵 P；P 是我们方法的输入，而不是问题本身的一部分。我们先定义核心对象。

定义 1（智能体池）智能体池 A = {a1, …, aN} 由 N 个专门化智能体组成。每个智能体 ai 由一段自然语言能力描述 di 和稠密嵌入 ei = fenc(di) ∈ Rh 刻画，其中 fenc 是一个预训练的句子编码器。

定义 2（任务分解）给定自然语言任务 T，分解函数 DLLM 产出子任务 S = {s1, …, sK} 和依赖 DAG Gdep = (S, Edep)，其中每条有向边 (si, sj) ∈ Edep 表示 si 必须在 sj 开始之前完成。每个子任务 sj 携带一个所需能力描述 cj。

定义 3（能力匹配）对于需求为 cj 的子任务 sj，它与智能体 ai 的匹配分数为：

```
ϕ(sj, ai) = cos(fenc(cj), ei)    (1)
```

（原文此行含无法解析的控制字符，已略去。）

分配 π : S → A 把每个子任务映射到匹配度最高的智能体：π(sj) = arg max_{ai∈A} ϕ(sj, ai)。

定义 4（充分性）当且仅当对所有 sj ∈ S 都有 ϕ(sj, π(sj)) ≥ τ 时，称分配 π 是 τ-充分的，其中 τ ∈ [0, 1] 是充分性阈值。缺口集合为 G = {sj | ϕ(sj, π(sj)) < τ}。

定义 5（转移矩阵）给定成功工作流的历史 H = {W1, …, WM}，其中每个工作流都包含一个有序的智能体调用序列，则转移矩阵 P ∈ R^{N×N} 为：

```
Pij = count(ai → aj in H) / Σ_{k=1}^{N} count(ai → ak in H)    (2)
```

其中 count(ai → aj in H) 表示在 H 的各个工作流中，智能体 aj 紧跟在 ai 之后出现的次数。P 是行随机的，编码了经验性的一阶马尔可夫协作先验。

定义 6（工作流）工作流 W = (V, E, π) 由节点 V = S、边 E = Edep ∪ Emat 以及智能体分配 π 组成，其中边集包含硬性依赖边与软性的矩阵建议边。

WorkflowOps 的设计目标。由于下游任务成功率在构建时刻无法直接度量，我们的方法优化一个以历史为条件的代理目标，它平衡三项：与历史协作先验的一致性、子任务—智能体分配的语义充分性、以及结构并行性：

```
Q(W, π, A′) = α · Align(W, P) + β · Suff(π) + γ · Par(W),    (3)

Align(W, P) = (1 / |E|) · Σ_{(si,sj)∈E} P_{π(si),π(sj)}    (4)

Suff(π) = (1 / |S|) · Σ_{j=1}^{K} ϕ(sj, π(sj))    (5)

Par(W) = |S| / depth(W)    (6)
```

约束为：保留硬性任务依赖、保持无环性、且只允许对智能体池做单调扩展 A′ ⊇ A。其中 depth(W) 是 DAG 中最长路径的长度。Align 度量与历史协作模式的吻合程度，Suff 度量能力覆盖，Par 度量可用的并行度。我们把这一目标当作设计原则而非全局求解的对象；WorkflowOps 通过分阶段分解、语义匹配、智能体池扩展、转移引导的 DAG 构建和分层执行来近似它。

## 4 方法

WorkflowOps 以四个阶段的流水线方式运行：(1) 任务分解与分层语义匹配；(2) 充分性驱动的智能体池扩展；(3) 转移先验引导的工作流构建；(4) 分层并行执行。下面逐阶段说明，并在需要处给出详细算法。WorkflowOps 的整体流程见图1。

### 4.1 任务分解与分层语义匹配

任务分解。给定自然语言任务 T，由一个 LLM 把它分解为 K 个子任务 S = {s1, …, sK}（3 ≤ K ≤ 7），每个子任务带有一个所需能力描述 cj，以及构成 DAG Gdep 的依赖连接。分解提示词会强制合法的 DAG 结构；如果 LLM 输出错误导致出现环，后处理步骤会通过 DFS 检测并打断环。因此，所有依赖连接都是在受模式约束的提示词下由 LLM 提出的：结构合法性由程序化手段保证，而分解的语义正确性则交给 LLM 负责。

分层语义匹配。我们采用兼顾质量与效率的两层匹配策略：

- 第一层：句向量匹配。我们使用预训练句子编码器 fenc（Sentence-BERT（Reimers and Gurevych 2019），具体为 all-MiniLM-L6-v2 变体），把智能体能力描述与子任务需求都编码为 384 维稠密向量。匹配分数计算如下：

```
ϕ(sj, ai) = cos(fenc(cj), fenc(di))    (7)
```

（原文此行含无法解析的控制字符，已略去。）

- 这里 ai 表示一个智能体，di 是它的能力描述，cj 是子任务需求（见定义 3）。智能体嵌入是预先计算并缓存的；子任务嵌入在分解时计算。这一层是确定性的，LLM 成本为零，通过批量矩阵乘法，每个子任务—智能体对的处理时间在亚毫秒量级。
- 第二层：LLM 按需核验。对于最佳匹配分数低于充分性阈值 τ 的子任务，可以启用一个可选的 LLM 核验阶段，判断现有智能体是否真的足够，还是确实存在能力缺口。该阶段只在嵌入相似度模棱两可的低置信度样本上调用。

复杂度对比。纯 LLM 路由需要用 LLM 调用来评估 K × N 个子任务—智能体对。我们的方法需要 K × N 次向量运算（第一层，成本可忽略），外加至多 K′ × 1 次 LLM 调用（第二层，其中 K′ ≪ K）。在 K=5 个子任务、N=35 个智能体的典型设置下，这把 175 次 LLM 调用缩减为约 5 次向量相似度计算外加约 1 次 LLM 核验调用。

### 4.2 转移先验引导的工作流构建

矩阵构建。转移矩阵 P（定义 5）在离线状态下由一批历史（或合成）工作流语料构建而成，做法是统计两两智能体转移并做行归一化。在我们的部署中，我们从约 65 条横跨八个任务领域的合成工作流自举，得到一个 35 × 35 的矩阵，其中约 20% 的元素非零。构建 P 只需对历史交接做一遍计数，查询是 O(1) 的，内存按 O(N²) 增长；在 N = 35 时矩阵只占几千字节，因此其构建与查询成本相对一次 LLM 调用可以忽略不计。

三重角色机制。转移矩阵在工作流构建期间扮演三个不同角色：

- (a) 层内排序优化。在每个拓扑层内部（共享同一深度、可以自由重排的子任务），智能体按照来自上一层智能体的转移概率排序。若上一层的智能体是 ap，而当前层含有分配给 ax 和 ay 的子任务，系统会偏好满足 Pp,x > Pp,y 的顺序，把 ax 放在 ay 之前。这依据历史上成功的模式优化了信息流的先后次序。
- (b) 基于概率阈值的边建议。对于不存在显式依赖边的每一对子任务 (si, sj)，如果 Pπ(si),π(sj) ≥ θ（边阈值），且加入该边仍保持拓扑序（即 depth(si) < depth(sj)），就添加一条软边。这些由矩阵建议的边编码了系统基于历史数据的信念：智能体 π(si) 的输出可以作为智能体 π(sj) 的有价值输入。
- (c) 传递归约。在硬性依赖边与软性矩阵建议边都被纳入之后，系统执行一次传递归约（Aho, Garey, and Ullman 1972）：若存在边 (u, v) 与 (v, w)，且直接边 (u, w) 也存在，则移除直接边 (u, w)，因为该依赖已经通过传递方式得到满足。这样可以移除冗余的顺序约束、最大化并行度，使同一拓扑层内有更多子任务得以并发执行。

算法 1 形式化了这一过程。

```
Algorithm 1 Transition-guided DAG workflow construction
Require: Subtasks S, dependency graph Gdep = (S, Edep), assignment π, transition matrix P, edge threshold θ
Ensure: Workflow W = (V, E, π)
 1: V ← S; E ← Edep
 2: Compute topological depths: depth(s) ← longest path from any source to s in Gdep
 3: for each pair (si, sj) ∈ S × S with si ≠ sj and (si, sj) ∉ E do
 4:    if Pπ(si),π(sj) ≥ θ and depth(si) < depth(sj) then
 5:       E ← E ∪ {(si, sj)} ▷ Add matrix-suggested soft edge
 6:    end if
 7: end for
 8: E ← TransitiveReduction(V, E) ▷ Remove redundant edges
 9: Compute parallel groups via layered topological sort of (V, E)
10: Sort agents within each layer by Pprev,π(s) descending ▷ Intra-layer ordering
11: return W = (V, E, π)
```

动态矩阵更新。当创建了新智能体（见 §4.3）时，必须把它们整合进 P。系统使用 LLM 为新智能体 anew 预测可能的前驱与后继智能体；该预测以新智能体的能力卡片和现有池中各智能体的能力描述为条件（见算法 2），预测出的转移概率被注入 P 中对应的行与列。所有受影响的行都会重新归一化以保持行随机性。这保证矩阵随智能体池一同增长，使工作流构建可以立即利用新智能体被预测出的协作模式。

为什么用软性引导。矩阵被用作软性引导而非硬性约束，原因有三：(i) 在约 20% 的矩阵密度下，硬性约束会挡掉合法但历史上未出现过的工作流；(ii) 依赖结构始终是不可商量的基础——矩阵不能推翻任务逻辑；(iii) 即使新颖的任务模式偏离历史先验，也仍应可以被表达出来。

### 4.3 充分性驱动的智能体池扩展

当现有智能体池无法 τ-充分地覆盖某个任务的需求时，WorkflowOps 进入一个闭环的智能体创建过程。这是一项定义性的能力：系统不会止步于勉强的分配，而是主动扩展自身的能力边界。

算法 2 形式化了这一充分性闭环。

```
Algorithm 2 Sufficiency-driven agent pool expansion
Require: Subtasks S, agent pool A, threshold τ, max rounds R, matrix P
Ensure: Expanded pool A′, updated matrix P′, sufficient assignment π′
 1: A′ ← A; P′ ← P
 2: for r = 1, . . . , R do
 3:    Build matching index from A′ using fenc
 4:    Compute π′ ← arg maxa∈A′ ϕ(sj, a) for all sj ∈ S
 5:    G ← {sj | ϕ(sj, π′(sj)) < τ} ▷ Identify capability gaps
 6:    if G = ∅ then
 7:       break ▷ All subtasks sufficiently covered
 8:    end if
 9:    for each sj ∈ G do
10:       if optional adequacy check indicates existing agents are insufficient then
11:          anew ← LLMGenerate(sj.capability) ▷ Generate agent definition
12:          Persist anew to agent pool on disk
13:          A′ ← A′ ∪ {anew}
14:          (pred, succ) ← LLMPredict(anew, A′) ▷ Predict collaborators
15:          P′ ← InjectAndNormalize(P′, anew, pred, succ)
16:    end for
17: end for
18: return A′, P′, π′
```

关键设计决策。需求驱动的创建。与不考虑池覆盖情况、为每个任务都创建智能体的 AOrchestra（authors 2026b）不同，WorkflowOps 只在检测到可度量的能力缺口（ϕ < τ）时才创建智能体。这避免了智能体池的无谓膨胀。

整合的协作知识。每个新智能体不仅会被加入池中，还会以 LLM 预测出的前驱与后继关系被注入转移矩阵 P。这意味着下一个用到该新智能体的工作流可以立即受益于协作先验，而不必靠多次执行去自然积累转移统计。

安全机制。该闭环受三重机制约束：(i) 最大轮数 R（默认 3）；(ii) 面向每个子任务的去重保护；(iii) 单次运行的最大智能体创建数量。

持久化与生命周期。创建出的智能体会被持久化到磁盘，并成为后续运行可用池的一部分。系统支持三种环境模式——探索式（自由演化）、受控式（周期性整理）与冻结式（面向生产锁版本），从而提供一条从实验走向企业级部署的治理路径。

### 4.4 分层并行执行

工作流构建完成后，WorkflowOps 按拓扑层执行 DAG。同一层中的所有节点彼此无依赖，因此可以并发运行；下游节点要么接收单个前驱的输出，要么接收包含全部上游结果的合并消息。这种执行模式在保留硬性依赖的同时，充分利用了转移引导的 DAG 构建所暴露出来的并行性。

我们把该 DAG 模式与 Linear 模式做对比：后者使用相同的分解与智能体分配，但顺序执行子任务。两种模式使用相同的消息抽象与日志接口，从而可以在顺序执行与转移引导的 DAG 执行之间做受控比较。详细的消息模式、扇入合并、错误传播、审计日志以及端到端流水线算法（算法 3）见附录 B。

## 5 实验

### 5.1 实验设置

任务集。我们使用两个异构的基准任务集，它们共用同一套推理流水线与评分框架。Mixed 结合了代码生成（HumanEval（Chen et al. 2021）、MBPP（Austin et al. 2021））、数学推理（GSM8K（Cobbe et al. 2021）、MATH（Hendrycks et al. 2021））与问答（DROP（Dua et al. 2019）、HotpotQA（Yang et al. 2018））；它包含 120 道验证题与 300 道测试题，各来源等量抽样。Mixed_Hard 包含难度更高的竞赛级与前沿难度问题，取自 AIME 2025（Balunović et al. 2026）、LiveCodeBench（Jain et al. 2024）、CodeContests（Li et al. 2022）与 GPQA Diamond（Rein et al. 2023），包含 180 道验证题与 694 道测试题。编排器看不到基准的身份，因此它必须在不做来源特定路由的前提下，同时应对宽泛的类别覆盖与更难的题目分布。

基线。我们与四个近期的多智能体编排系统做对比：AFlow（Zhang et al. 2025c），基于 MCTS 的工作流生成器；ADAS（Hu, Lu, and Clune 2025），自动化的智能体系统搜索方法；MaAS（Zhang et al. 2025b），在智能体超网络上的架构搜索；以及 MetaAgent（Zhang, Liu, and Xiao 2025），基于有限状态机的多智能体构造器。MetaAgent 为每个查询构造一个全新工作流，而 AFlow、ADAS 和 MaAS 则为每个基准搜索出一个工作流并在各查询间复用。

骨干模型与配置。所有系统都以 gpt-5 作为底层语言模型。WorkflowOps 使用充分性阈值 τ=0.45、边阈值 θ=0.3、all-MiniLM-L6-v2 句向量匹配器（Reimers and Gurevych 2019）、MAX_AGENTS_PER_RUN=4、MAX_CREATION_ROUNDS=3 以及 MAX_DAG_BRANCHING=3。每次分解产生 3−7 个子任务，每个配置以 16 个工作进程执行工作流，每条查询有 900 秒的墙钟超时。

指标。主要指标是通过率：抽出的最终答案与真值一致的测试行占比，其中代码任务通过在沙箱中对照规范测试执行来评分。我们还记录矩阵对齐度、充分性、动态智能体创建、缺口闭合、LLM 调用次数、token 数、延迟，以及 DAG 与 Linear 的墙钟耗时；详细的运行统计见附录 E。

### 5.4 效率分析

WorkflowOps 呈现出清晰的成本—准确率权衡。附录 E 以表格形式给出了 Mixed 测试划分上 Reference 配置的完整运行画像。系统平均每条查询使用 14.8 次 LLM 调用与 43.6k token，墙钟时间中位数为 605 秒。大部分调用来自两处：充分性驱动的智能体创建闭环（平均为每条查询创建 3.5 个智能体）与智能体执行（每个工作流节点调用一个智能体）。嵌入匹配器本身基本不产生 LLM 调用，这支持了把语义嵌入用作路由快速路径的设计选择。

以最便宜的消融单元 No-Evolve（7.8 次调用、15.9k token）为基准归一化，Reference 用 1.9 倍的调用与 2.7 倍的 token 换来 +1.7 个百分点的准确率。这使智能体池扩展成为一个显式的部署开关：当静态池已覆盖任务分布时，关闭扩展更具吸引力；而当任务可能暴露新的能力缺口时，Reference 设置更可取。在 Mixed 上，DAG 执行带来适度的准确率提升，且墙钟时间中位数与 Linear 模式几乎相同，因为多数工作流都很浅；DAG 与 Linear 的详细耗时对比及更多运行统计见附录 E。

## 6 讨论与局限

轻量先验作为编排记忆。一个关键发现是：简单的、基于频率的转移先验无需梯度训练，也能提供有用的工作流引导。与学习式工作流优化器不同，转移矩阵只需要执行历史、可解释、随新工作流完成而增量更新，并且在未观察到相关转移时能平缓退化。这使它成为静态模板与昂贵的针对性工作流搜索之间一个实用的折中。

局限。WorkflowOps 表明轻量的协作先验可以在不经梯度训练的情况下改善多智能体编排，但仍存在若干局限。其一，转移矩阵只捕捉一阶的两两交接；诸如重复智能体序列这类高阶协作模式并未被建模。其二，动态智能体创建依赖于 LLM 的生成质量，因此定义不佳的智能体可能会一直留存，除非对池进行整理；与此相关，我们的评估没有度量池扩展的长期影响——被创建的智能体是否被后续任务复用、被进一步完善或被剪除——所以我们主张的是需求驱动的扩展，而非持续的自我演化。

其三，当前系统只使用一个共享的转移矩阵，而领域专用的矩阵可能提供更有针对性的引导；由于 P 索引的是智能体角色而非骨干模型的输出，底层 LLM 更换时无需重建 P，尽管转移质量可能发生变化、应当重新验证。最后，我们的评估聚焦于代码、数学与问答类知识工作；向差异显著的其他领域推广仍需进一步研究。关于矩阵稀疏性、匹配设计与未来扩展的更多讨论见附录 F。

## 7 结论

我们提出了 WorkflowOps，一个多智能体工作流编排框架，用以应对当前多智能体系统中的无记忆编排问题。我们的三个耦合机制——转移概率矩阵引导、充分性驱动的智能体池扩展与分层语义匹配——使系统能够从执行历史中学习、按需扩展自身能力，并把子任务高效地路由给智能体，而这一切都不需要基于梯度的训练。收益在结构化、可分解、过去的智能体交接模式可以迁移的任务上最大。

转移矩阵表明，即便是一阶马尔可夫协作统计这样简单的量，在 DAG 工作流构建期间作为软性引导使用时，也能在工作流质量与并行度上带来有意义的提升。充分性闭环表明，配合整合式协作知识更新的需求驱动智能体创建，可以让智能体池及其协作先验按需共同成长。分层匹配策略则表明，预训练句向量可以作为能力匹配的有效快速路径，而 LLM 核验只留给真正模棱两可的情形。

未来工作。几个方向值得探索：(i) 把矩阵升级为学习式补全方法（矩阵分解、神经补全），以更好地覆盖稀疏转移；(ii) 从执行反馈中在线学习矩阵，形成类似强化学习的闭环；(iii) 捕捉领域特定协作模式的专用矩阵；(iv) 与 A2A（Google 2026）、MCP 等新兴智能体间协议集成，实现标准化的智能体通信。

### A 扩展相关工作

#### A.1 自适应与动态编排

近期的编排方法主要通过拓扑路由或学习式控制策略来提升适应性。AdaptOrch（authors 2026a）在预定义的编排模式之间做任务自适应的拓扑选择，并报告了相对静态模板的收益。CORAL（authors 2026c）从固定工作流转向基于信息流的、通过智能体间通信实现的动态协调。FlowSteer（authors 2026d）用端到端强化学习优化工作流编辑决策。这些方法与我们高度相关，但着眼点不同：WorkflowOps 强调的是从工作流历史中积累的、持久且免训练的协作先验，并在 DAG 构建期间将其用作软约束。

#### A.2 工作流结构学习与优化

HeGFlow（Guan, Wang, and Shen 2025）把工作流设计形式化为带训练流水线的异构图邻接优化，AgentPO（Sun et al. 2026）则在固定拓扑假设下优化协作交互策略。ProMAS（authors 2026e）用马尔可夫转移动力学做错误预测，而非工作流合成。与之相对，WorkflowOps 直接把历史转移统计当作可解释、可增量更新的结构构建先验来使用。

更宏观的综述视角（authors 2026f, 2025b；survey authors 2026）指出了静态模板编排与昂贵的重训练式优化之间的一个开放空档。我们的方法正定位在这一空档中：轻量的、由历史驱动的图构建，无需重新训练。

#### A.3 智能体路由与选择

MasRouter（Yue et al. 2025）与 EvoRoute（Zhang et al. 2026a）研究多智能体系统中的学习式路由，主要面向模型分配与成本—性能权衡。我们的场景与之互补：我们关注的是子任务与角色专门化智能体之间的能力匹配。WorkflowOps 的分层语义匹配策略可以解释为一种面向智能体能力的路由策略，它使用嵌入快速路径并可选地回退到 LLM，而不是在模型骨干之间路由。

#### A.4 自演化智能体架构

AOrchestra（authors 2026b）通过组合式智能体规格演示了动态子智能体创建，但它把创建出的子智能体视为一次性的：既不持久化，也不积累关于它们的协作知识。SEAA（SEAA authors 2026）与 SEVerA（Banerjee, Xu, and Singh 2026）主要在工具层或合成控制层给出了关于自我扩展与验证的形式化视角。AgentOrchestra（authors 2025a）研究带有动态工具路径的分层编排。WorkflowOps 的不同之处在于把需求驱动的智能体创建与立即整合进持久协作先验矩阵相耦合，使新建的角色能够影响未来的工作流构建。

#### A.5 工作流记忆与经验复用

Agent Workflow Memory（Wang et al. 2024）从经验中归纳可复用的工作流技能并存储起来供后续任务使用，EvoFlow（Zhang et al. 2025a）演化出一个多样的智能体工作流种群，TopoPrior（Zhang et al. 2026b）学习可跨领域迁移的拓扑先验。这些系统持久化的是可执行工作流或已学习的拓扑生成器。WorkflowOps 则持久化两两协作统计，使其在构建期间充当免训练的软性引导：硬性任务依赖始终被保留，先验可解释、可在不重训练的情况下增量更新，且此前未见过的工作流形态依然可以被表达出来。

### B 流水线与执行引擎细节

#### B.1 端到端流水线

算法 3 给出完整的 WorkflowOps 流水线；各个阶段在第 4 节中描述。

```
Algorithm 3 WorkflowOps end-to-end pipeline
Require: Task T, agent pool A, transition matrix P, threshold τ, edge threshold θ, max rounds R, workflow type ∈ {linear, dag}
Ensure: Final result mfinal, workflow W, logs L
 1: // Stage 1: Decomposition
 2: S, Gdep ← DLLM(T) ▷ LLM decomposes task into subtasks with dependencies
 3: Validate DAG: if HasCycle(Gdep), linearize dependencies
 4: // Stage 2: Matching + Sufficiency Loop
 5: A′, P′, π ← SufficiencyLoop(S, A, τ, R, P) ▷ Algorithm 2
 6: // Stage 3: Workflow Construction
 7: if workflow type = dag then
 8:     W ← TransitionGuidedDAG(S, Gdep, π, P′, θ) ▷ Algorithm 1
 9: else
10:     W ← BuildLinear(S, π, P′) ▷ Linear with intra-layer ordering
11: end if
12: // Stage 4: Execution
13: mfinal, L ← ExecuteDAG(W, T) ▷ Algorithm 4
14: // Stage 5: Persistence
15: Save (W, mfinal, L) to results directory with timestamps and metadata
16: return mfinal, W, L
```

#### B.2 分层 DAG 执行

工作流构建完成后，执行引擎通过分层拓扑遍历来处理 DAG。同一层的节点没有未解析的依赖，因而并行执行；当下游节点只有一个父节点时，它接收该前驱的输出，有多个父节点时则接收合并后的消息。

#### B.3 统一消息协议

所有智能体间通信都使用同一个 AgentMessage 模式，其中携带自然语言内容、可选的结构化数据、带类型的产物以及追踪元数据，包括源智能体、目标智能体、父消息 ID、工作流 ID 与步骤索引。这一可组合的协议避免了智能体使用异构消息格式时出现的两两适配器问题。

#### B.4 扇入合并

当并行分支汇合时，上游消息会被合并为下游智能体的单个输入。合并过程会拼接带标签的内容区块、保留来源归属，并对产物集合取并集，从而在各分支之间维持溯源信息。

#### B.5 错误传播

如果某个智能体步骤失败，系统会创建一条错误类型的消息并将其向下游传播。后续智能体收到错误上下文后，仍可能产出部分结果。这优先保证了运行的连续性与可追溯性，而不是立即中止工作流。

#### B.6 审计日志

每个执行步骤都会记录时间戳、输入/输出预览、成功或错误状态以及智能体元数据。再结合工作流定义——包括节点、边、分配、矩阵对齐分数与充分性报告——就构成了一条从任务接收到最终输出的完整决策链。

```
Algorithm 4 DAG execution engine
Require: Workflow W = (V, E, π), original task T
Ensure: Final result message mfinal, execution logs L
 1: Compute topological layers L0, L1, . . . , LD from (V, E)
 2: results ← {}; L ← []
 3: minit ← CreateMessage(T)
 4: for l = 0, 1, . . . , D do
 5:    parallel for each node v ∈ Ll : ▷ Thread pool within layer
 6:       preds ← {u | (u, v) ∈ E}
 7:       if preds = ∅: min ← minit
 8:       else if |preds| = 1: min ← results[preds[0]]
 9:       else: min ← MergeMessages({results[u] | u ∈ preds})
10:       mout ← ExecuteAgent(π(v), min)
11:       results[v] ← mout; append log to L
12: end for
13: terminals ← {v ∈ V | ∄ (v, w) ∈ E}
14: mfinal ← MergeMessages({results[v] | v ∈ terminals})
15: return mfinal, L
```

### F 补充讨论

轻量先验 vs. 训练式优化器。转移矩阵由简单的频率计数构建，不经梯度训练。当已有执行历史、而针对具体任务的训练又很昂贵时，这一设计尤其有用：矩阵可解释，随新工作流完成而增量更新，并且在没有历史转移可用时平缓退化。矩阵接口还可以支持学习式补全方法，例如矩阵分解或神经补全，而无需改动外围的编排流水线。

嵌入匹配 vs. TF-IDF。句向量能够捕捉关键词重叠之外的语义关系，例如“regulatory audit”（监管审计）与“compliance assessment”（合规评估）之间的关联；同时由于智能体嵌入是预先计算并缓存的，成本依然很低。匹配模块是抽象的，未来系统可以把当前编码器替换为领域专用嵌入或交叉编码器重排序模型。

矩阵稀疏性。在 35 个智能体的网格上用约 65 条自举工作流构建的转移矩阵，约有 20% 的非零元素。这种稀疏性是可以接受的，因为矩阵只用作软性引导；即使矩阵没有相关历史，工作流构建仍会保留硬性依赖。随着更多工作流被执行，矩阵密度会自然增长；而为新建智能体预测出的 LLM 链接能立即提供近似引导，后续再加以细化。
