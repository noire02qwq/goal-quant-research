## 摘要

LLM 智能体可以把自然语言的金融研究请求变成可执行、可回测的策略，但一次"成功"的运行仍可能实现了错误的规则、使用了决策时不可得的信息，或掩盖了修复与候选选择如何改变了策略。由于这些失败可能贯穿开发过程的始终，仅凭最终代码和绩效指标，既不足以证明策略忠实于原始请求，也不足以证明开发过程本身有效。因此我们在轨迹层面处理金融策略开发的可靠性问题：系统必须控制中间产物如何转化为下游状态，并保留足以支撑最终结论的证据。

我们提出 QuantHarness，一个两层智能体 harness：面向金融的 Workflow 负责组织规范、数据锚定、构建、测试与评审，Harness Core 则强制执行各阶段的信息、动作与提交边界。我们还提出 FinRelBench，一个从执行成功、需求满足和运行时证据三方面评估策略开发可靠性的基准。QuantHarness 取得最高的 Task Success，为 90.72%，对比系统为 74.23%–84.54%。受控压力测试表明其边界能遏制针对性的违规，而结构化的运行记录改善了证据检索，并在所评测的协议下支持决策回放。

**关键词**：LLM 智能体、agent harness、量化金融、轨迹治理、智能体可靠性

## 1 引言

近年来基于 LLM 的系统已经能把量化策略开发从一句自然语言研究请求推进到"已实现并完成回测"的策略 [9, 29]。然而，执行成功本身并不能证明所得策略忠实于原始请求。生成的代码可能实现了与所请求不同的交易规则 [7]，可能使用决策时不可得的信息，或引入时间错位 [11]。问题也可能在初版实现产出之后才出现：一次修复可能通过改动交易规则本身来消除执行错误；依据回测结果的反复选择，可能把评估变成对历史结果的搜索 [2, 19]。由于这些问题可能出现在不同阶段，最终代码和绩效指标未必能暴露它们的来源，也未必能揭示是哪些决策让它们得以存留。

我们把一次策略开发执行称为一个 run（运行）。从研究请求到最终结论的有序路径，就是该运行的开发轨迹（development trajectory）。我们因此在这条轨迹上考察可靠性：所请求的策略是否被忠实实现，以及开发过程是否有足以支撑其最终结论的证据。

已有工作从两个方向切入这个问题的一部分。金融智能体与基准支撑交易决策、因子发现、可执行研究与策略评估 [4, 7, 9, 18, 21, 29]；通用 agent-harness 研究则考察上下文、工具、持久状态与运行时控制如何塑造智能体行为 [12, 16, 24]。这两条线索共同引出一个问题：LLM 智能体如何可靠地把一个金融策略请求走完规范、数据锚定、实现、测试与最终验收的全过程。

我们提出 QuantHarness，一个治理这条轨迹的两层系统。面向金融的 Workflow 组织从"明确陈述预期策略"到实现与测试、再到最终结论的推进过程；Harness Core 通过控制每个阶段可用的信息与动作、并决定哪些输出可以更新下游所用的运行状态，来中介这一推进。在这些控制之下，运行要么以一个被冻结（frozen）的策略结束，要么在未获验收时终止。QuantHarness 还保存一份结构化运行记录，把运行的最终结论与其支撑产物、生命周期决策联系起来。

我们在 FinRelBench 上评估轨迹可靠性，这是一个包含 97 个显式规则型任务的基准。评估考察端到端 Task Success、边界执行、运行后的审计与回放。结果显示：QuantHarness 在对比系统中取得最高的 Task Success，在压力测试中遏制了针对性违规，并通过结构化运行记录支持更有效的证据检索与决策回放。可靠的开发是解读金融结果的基础，但金融研究系统也应支撑具有经济意义的策略产出。因此我们用 FinResearchSuite 作为对 QuantHarness 实用价值的辅助评估，结果见附录 E。我们的贡献如下：

- 我们把可靠的金融策略开发框定为轨迹治理问题，并区分轨迹可靠性与金融质量。
- 我们提出 QuantHarness，一个把面向金融的 Workflow 与 Harness Core 耦合起来的两层系统，用以治理工作流执行并保存有产物支撑的运行记录。
- 我们构建 FinRelBench——一个含 97 个任务、带有受控评估协议的策略开发可靠性基准，并用其任务评估端到端 Task Success、边界执行、运行后审计与回放。

## 2 相关工作

### 2.1 面向量化金融的 LLM 智能体

近期基于 LLM 的金融智能体工作横跨面向市场的决策支持与可执行的量化研究。面向决策的系统通过记忆、反思、角色协作等机制组织市场信息 [21, 26–28]，而 FinRobot [23] 一类平台则支撑范围更广的分析任务。在可执行研究方面，Qlib [25] 与 FinRL-Meta [10] 提供可复用的数据与市场仿真基础设施；R&D-Agent-Quant [9] 把结构化规范与实现、回测、迭代反馈以及留存的研究产物结合起来；FactorMAD [4] 则用智能体辩论来做可解释的 alpha 因子发现。随着这些系统把研究过程的越来越多环节自动化，可靠性关切也从"所得策略的绩效"扩展到"开发过程中积累的决策与证据"。仅有成功的执行和金融结果，并不能证明一个请求被恰当地解读、被锚定在数据上，并被推进到一个有依据的结论。QuantHarness 正是回应这一更广的需求：在整个开发轨迹上提供任务忠实度、过程控制与支撑证据。

### 2.2 金融智能体的评估

近期针对金融 LLM 系统的评估工作，既覆盖宽泛的金融能力，也覆盖可执行研究。FinBen [22] 展示了这种广度，涵盖金融语言任务、预测、风险管理与交易。更专门的评估针对量化研究的产出：AlphaForgeBench [29] 通过标准化回测评估生成的因子与策略，BacktestBench [18] 把自动化回测输出与参考答案作比较。在代码层面，QuantCode-Bench [7] 与 AlphaQT-Bench [11] 评估与任务描述的对齐度、时间因果性、功能正确性、结构合规性等属性。这些基准合在一起，评估的是金融能力与研究产出的质量；但仅凭产出层面的评估，无法确定任务约束在整个开发过程中是否被遵守。因此我们用 FinRelBench 评估：所请求的策略是否被忠实实现，其要求的行为是否在执行中得到展现。我们还考察智能体是如何到达那个结果的，追问开发是否尊重了任务约束、是否留下了足够的后续审计证据。

### 2.3 Agent Harness 与运行时治理

在单个模型的能力之外，近期 LLM 智能体研究还考察其外围的 harness：也就是组织上下文、工具访问、状态与工作流执行的支撑性执行环境。AutoGen [20]、SWE-agent [24]、OpenHands [17]、AIOS [12] 等框架对这些能力给出了不同的组合方式。近期研究也考察如何表示与改进 harness 本身：Natural-Language Agent Harnesses [15] 把控制策略表达为可编辑的文档，经由共享运行时执行，带有显式的交接、状态更新与验证门；Meta-Harness [8] 通过检查历史候选、评估分数与执行轨迹来优化 harness 代码。与这些 harness 设计工作并行，AgentSpec [16] 在智能体执行期间强制执行可配置规则。这些方法共同提供了组织、改进与约束智能体行为的机制。但对金融策略开发而言，这些机制必须落脚在交易需求与市场数据约束之上——挑战在于让这些需求穿过构建、测试与验收，同时保留支撑每个结论所需的证据。QuantHarness 正是在完整开发轨迹上考察这一问题。

## 3 QuantHarness

### 3.1 系统总览

把一个自然语言请求变成可运行的金融策略，既需要显式的开发过程，也需要对"中间结果如何被使用"的控制。QuantHarness 通过两个相互作用的层来治理开发轨迹：面向智能体的 Workflow 组织策略开发，Harness Core 治理其执行并保存由此产生的运行记录。图 1 总结了两层如何互动。下面的小节依次介绍 Workflow 与 Harness Core。

### 3.2 面向金融的 Workflow

在 QuantHarness 中，Workflow 覆盖"从澄清请求到产出并测试一个可运行策略实现"的全过程。本小节余下部分依次介绍这些阶段。

**把所请求的策略显式化。** 自然语言的策略请求往往留下实现所需的信息空白。如果模型只在写代码时才填补这些空缺，它的假设就会在未被明确陈述的情况下进入实现，后续阶段也就无法拿代码与"对预期策略的显式描述"作对照。QuantHarness 因此先记录它对请求的解读，包括任何假设与未决信息。由此得到的结构化描述就是 task contract（任务契约）。Workflow 再用这份契约产出 strategy specification（策略规范）。task contract 记录系统从请求中理解到了什么，strategy specification 则陈述最终实现必须满足的交易规则与约束；它是把策略与可用数据连接起来、并将其落地为代码的共同参照。此后策略含义的任何改动，都必须先反映到这份规范里。

**把策略需求锚定到可用数据与输出格式上。** 策略规范指明了交易规则需要哪些数据，但并不能确定现有数据集里是否存在兼容的数据源与字段。把这项检查推迟到代码生成阶段，可能导致实现引用不存在的字段、或使用频率不兼容的数据。因此 QuantHarness 在实现之前先检查可用数据，而不是假定每个需要的输入都存在。data binding（数据绑定）把每条需求映射到已确认的数据源、字段与频率；无法解析的需求保持显式，而不是被绑定到猜测出来的输入。仅有数据绑定还不足以开展测试，因为回测器还必须知道如何解读策略的决策。output protocol（输出协议）规定这些决策以资产分数还是交易订单的形式表示，并定义回测器期望的字段。数据绑定与输出协议合在一起，定义了策略如何接收数据、如何传达决策，而无需改动交易规则本身。

**构建可运行的策略实现。** 前面的阶段确定了策略需求、数据输入与输出协议，但尚未规定产生交易决策的计算过程。如果这一过程只在代码生成或模型训练时才被确定，那么定义它的选择就会隐含在最终实现里。QuantHarness 因此在构建开始前，就把这些选择显式写进一份 implementation plan（实现计划）。该计划说明绑定后的输入将如何在策略规范与输出协议之下转化为交易决策。QuantHarness 通过两条受支持的路径之一来实现这份计划：规则型策略实现为遵循既定计算的代码；模型型策略走另一条独立的构建路径。为把模型构建约束在可测试的接口内，当前路径仅限于 QuantHarness 预置的机器学习与深度学习模板库。系统先用绑定的输入构造训练数据，再拟合一个由所选模板实例化的模型；拟合后的模型按声明的输出格式产生策略分数。无论规则型还是模型型，由此得到的策略实现都成为下一阶段考察的候选。

**按既定需求测试候选。** 实现计划指导构建，但产出的候选仍可能不满足此前确定的结构、数据或执行需求。QuantHarness 因此让完成的候选先通过这些需求的检验，才能继续。测试阶段包含两个必需步骤：（1）validation（验证）与（2）backtesting（回测）。验证先检查候选是否结构完整、与执行环境兼容，再检查它是否使用了声明的输入、并以规定的形式给出交易决策。结果（包括任何未通过的检查）列入验证报告。只有通过验证的候选才进入回测。回测把候选应用于数据绑定指定的市场数据，并按声明的输出协议把交易决策交给回测器。生成的回测报告指出回测执行是否成功、交易决策能否被回测器处理；执行成功时报告还包含由此得到的财务绩效指标。这些财务数值不能凌驾于验证与执行检查之上——候选必须两项检查都通过才能继续。

**可选的策略优化。** 通过验证与回测，说明候选可以利用绑定的输入与声明的输出协议执行。此时 QuantHarness 支持一次可选的、预算受限的探索，看看在不改动任务需求、数据绑定与输出协议的前提下，其金融质量能否提升。在这个循环内，候选变体必须先通过验证，才能在优化期上回测并按预设目标比较；被选中的候选随后在独立的最终期上评估一次。该结果不回传给循环，其金融数值用于质量分析，而不是决定工程验收。之后候选连同相应的验证与回测报告进入 Judge 评审。完整的优化协议见附录 D.4。

**候选评审与 Workflow 决断。** 候选的开发与测试完成后，Workflow 必须决定该候选是否可被接受、还是需要进一步处理。QuantHarness 把这项评审交给 Judge，由其综合候选与 Workflow 中先前产生的产物与报告进行判断。评审导向三条去向：recovery（恢复）、termination（终止）或 freezing（冻结）。当 Judge 识别出可修复的问题时，其报告会指明需要回访的较早阶段；recovery 把运行送回该阶段，之后受影响的下游阶段在固定的尝试预算内重跑。如果问题无法解决或预算耗尽，运行就在没有被接受策略的情况下终止。如果现有证据支持验收，freezing 则生成一个冻结的策略产物，保存实现及其被接受的依据。Harness Core 会先检查支撑 Judge 建议的证据，才允许相应改动生效。

### 3.3 Harness Core：运行时中介与治理

Workflow 把策略开发组织成各个阶段，但仅有阶段顺序，并不能控制每个阶段如何运作、其结果如何影响后续阶段。QuantHarness 因此引入 Harness Core——一个在 Workflow 各阶段之间做运行时中介的控制层。information boundary（信息边界）决定哪些既有运行信息被提供给某阶段；单独的 action boundary（动作边界）限制该阶段可调用的外部能力；一旦某阶段产出结果，commitment boundary（提交边界）决定后续阶段能否依赖它。在这三条边界之上，Harness Core 保存解释"运行如何推进"所需的产物与生命周期决策。

**提供阶段专属上下文。** 每个 Workflow 阶段都需要为其当前任务量身定制的信息。完整历史把当前产物、已被取代的候选、早期失败的证据以及控制/审计元数据混在一起；这些材料的相关性随阶段变化，若把完整历史全盘交给智能体，就等于让它自己判断哪些信息仍然有效。Harness Core 转而为每个面向智能体的阶段构造一张独特的 Runtime Card（运行时卡片）。其智能体可见部分写明阶段目标、所需产物与适用约束，以及该时点上相关的任务信息与反馈；控制与审计信息则仅 Harness Core 可见。这种阶段专属的选择，给了智能体一个界定清晰的上下文，而无需它去解读整段运行历史。

**中介工具与外部影响。** 并非每种外部能力都适合每个 Workflow 阶段。不受限的访问可能让某个阶段触发本属于工作流其他环节的操作，或在所需输入尚不存在时就行动。QuantHarness 通过把每项智能体可访问的能力表示为由 Harness Core 中介的工具来执行动作边界。工具注册表为每个工具提供稳定的名字与声明的输入结构；对每个阶段，Harness Core 只暴露其当前任务允许的已注册工具。对这些工具的调用会按声明的输入结构被检查，并经 Harness Core 路由到相应能力。因此工具访问由 Harness Core 强制执行，而不是留给提示词指令。

**授权并提交生命周期变更。** Workflow 的某个阶段可以建议"接下来该做什么"。若允许这条建议直接改变运行，就可能在必需的产物与证据被检查之前推进 Workflow。QuantHarness 把"阶段的提议"与"Harness Core 执行的授权和状态更新"分开。运行的生命周期，是它从创建到最终结果在各 Workflow 阶段间的推进。在提议的转移改变这一生命周期之前，Harness Core 通过 lifecycle hook（生命周期钩子）拦截它；随后 guard（守卫）检查该路径是否被允许、目标阶段所需的产物与证据是否齐备，然后批准或否决该提议，且不改动运行本身。获批后，运行时通过更新当前阶段、并让输出对下游可用，来提交这次转移。

**保存运行证据与产物。** 最终的策略实现及其回测结果，并不能解释一次运行是如何到达其结论的。QuantHarness 因此为每次运行维护一个 Artifact Store（产物库）。运行期间，该库保存提供给各智能体阶段的 Runtime Card、工具调用结果、生命周期决策，以及各阶段产出的结果（包括后来未通过检查的输出）。当 Workflow 冻结某个候选时，产物库把最终实现与支撑其被接受的中间产物和决策关联起来；若没有候选被接受，产物库则保存显示运行"在何处、为何结束"的证据。运行后的分析可以查看这些材料，但不能修改它们，也不能把新的测量回流给 Workflow。Artifact Store 由此把最终结论与其"如何产生"的中间证据一并保存下来。

## 4 FinRelBench

### 4.1 基准目标

可靠的金融策略开发，要求智能体在需求解读、数据准备、策略实现、运行时验证与最终验收的全过程中保持用户的需求。一个策略即使数据处理或交易逻辑偏离了这些需求，也可能运行成功并给出漂亮的回测结果。因此，评估这种可靠性需要这样的任务：把显式的策略需求与可验证的实现及执行证据连接起来。为满足这一需要，我们构建了 FinRelBench（Financial Strategy Development Reliability Benchmark，金融策略开发可靠性基准），用来评估智能体是否把陈述的需求转化为正确的数据处理、策略实现与可观测的运行时行为。

FinRelBench 在三个互补的层面上评估这种转化：可执行性（数据管道与策略是否运行成功）、需求满足（实现是否符合所述的数据与交易需求）、运行时证据（执行记录是否展现了所需行为）。这三个层面共同支撑对任务完成度的端到端评估。同一批任务也为边界控制实验以及审计与回放研究提供共同的工作负载，后者考察开发过程中错误如何被控制、结果如何被追溯与复现。

### 4.2 基准构成

FinRelBench 由 97 个显式规定、规则型的策略开发任务构成，设定在 A 股股票场景：其中 80 个任务选自并改编自含 400 个任务的 QuantCode-Bench [7]，另有 17 个由我们自行设计。我们挑选的源任务，其核心交易逻辑能在只做多的股票交易条件下、利用可用市场数据表达为可验证的需求；凡是界定性需求依赖卖空、衍生品或不可得外部数据的任务，一律排除。改编在保留核心交易逻辑的同时，把股票池、市场数据与执行时点对齐到 A 股交易规则，包括 T+1 交收。

这 80 个改编任务覆盖趋势与动量、突破、均值回归、波动与流动性条件及其组合，包括依赖持仓状态或日历排程的规则。按 QuantCode-Bench 原始难度标签，这 80 个任务包含 41 个简单、29 个中等、10 个困难案例。我们自行设计的 17 个任务检验数据调整与时点对齐、股票资格与组合约束、现金回退、执行时点。合起来，这些任务检验智能体是否既保留了指定的交易逻辑，也保留了正确实现它所需的数据与执行需求。

合并后的套件包含 64 个日频打分任务（50 个改编、14 个原创）与 33 个分钟订单任务（30 个改编、3 个原创）。日频打分任务为股票打分以做截面排序与组合构建，检验智能体是否正确实现历史窗口、排序规则与组合约束；分钟订单任务产出带时间戳的买卖指令，检验 bar 聚合、决策窗口、下单延迟与持仓状态转换。这两类输出对"策略需求如何转化为数据处理与实际交易行为"提供了互补的检查。任务示例见附录 A。

FinRelBench 针对显式的策略需求评估可靠性。可靠的开发是解读金融结果的基础，但金融研究的实际使用还需要"策略产出具有经济意义"的证据。为了在主要评估之外补充实用金融价值的证据，我们提出 FinResearchSuite（Financial Strategy Development Research Suite，金融策略开发研究套件）。这个辅助套件含 22 个任务：12 个开放式规则研究任务、5 个指定模型开发任务、5 个开放式模型研究任务。它评估研究完成度以及所得策略的收益与风险，以考察 QuantHarness 这种受治理的开发过程能否支撑有经济意义的策略研究。因此财务绩效只作为研究实用性的辅助检查，不进入 FinRelBench 的可靠性评分。任务定义与结果见附录 D 和 E。

### 4.3 评估协议

每个 FinRelBench 案例都是一个自包含的评估包，分为智能体可见部分与仅评估者可见部分。智能体可见部分是公开任务查询、市场快照、数据与提交文档；仅评估者可见部分是交易执行设置与任务专属评分细则（rubric）。公开任务查询陈述任务目标与公开约束；市场快照提供带版本的只读市场数据；数据与提交文档描述表结构、列定义、时间覆盖与访问路径，说明如何取数与提交结果。交易执行设置规定测试期、交易执行规则与交易成本。任务专属评分细则定义用于评估实现及其执行结果的需求。由于不同的实现都可能正确完成同一请求，这些需求被表达为可检查的判据：数据判据检查所请求的证券与字段是否被使用、指定计算是否有足够的历史观测、准备好的数据是否真的被消费；策略判据检查所请求的信号计算、选股与交易排程。标为 must 的判据必须全部满足才算最低正确性；支撑性的 should 判据允许部分满足，给实现留出一定弹性。判据描述预期的数据处理与策略行为，forbidden conditions（禁止条件）则指出"无论满足了其他哪些需求都会使结果无效"的行为。例如，一个策略可能实现了所请求的交易规则，却用未来价格生成了更早的信号；一经确认的禁止行为即导致任务失败，即便实现通过了执行检查、满足了其他判据。

确定性的机械检查判断智能体的代码能否构造出任务完成所需的数据、并执行所需策略。各系统通过公共接口提交代码、数据构造与策略执行命令，以及保存的数据与输出；评估者在固定的市场与执行条件下运行这些命令。Data Pipeline Success 要求数据集被构造、保存并被策略消费；Strategy Run Success 要求策略完成执行并产出其声明的输出。

策略可能在使用错误数据或错误交易规则的情况下运行成功，因此外部评审组（panel）用评分细则检查实现是否满足任务要求。评审组查看匿名化代码、已准备数据集的摘要、执行记录与输出；对每条判据，分别评估需求是否被满足、执行证据是否展现了相应行为。运行时支撑要求既有实际执行路径上的代码，也有来自运行或其输出的对应证据。独立评估者对同一份评分细则的两种等价措辞分别打分；可能影响结果的分歧，由一位看不到先前判断的仲裁者（arbiter）复核证据后裁决。

这些评估共同决定 Task Success：两项机械检查都必须通过；每个语义维度必须满足全部 must 判据、至少 75% 的 should 判据（向上取整），且没有已确认的禁止条件、也没有经独立确认的致命缺陷。此外，每条派生自显式公开需求的判据都必须被满足并有运行时证据支撑，包括标为 should 的判据。

除两个机械指标外，我们还分别报告数据与策略两个维度上的 Requirement Satisfaction（需求满足度）与 Runtime-Evidence Coverage（运行时证据覆盖率），共六项诊断指标。这些基于判据的指标分别度量"被判为满足"与"有执行证据支撑"的比例，must 与 should 判据等权。第 5.2 节说明任务级结果与判据级判断如何聚合为所报告的比较；附录 A 提供详细的评分细则、证据规则与算例。

## 5 实验

### 5.1 实验设置

我们的评估旨在建立三种互补的可靠性证据。首先检验 QuantHarness 作为完整系统，能否构建出使用所需数据、并实现所请求行为的可执行策略；接着考察 Harness Core 的各个边界如何影响可靠完成与违规遏制；最后评估结构化运行记录是否支持运行后审计与决策回放。FinResearchSuite 则另行评估开放式规则研究与模型研究的完成度与财务实用性。

在策略构建与研究方面，我们把 QuantHarness 与 Codex CLI [13]、OpenHands [17]、SWE-agent [24]、Aider [5] 作比较。所有策略生成调用均使用 GPT-5.5 [14]。在每个任务内，这些系统收到相同的公开请求、冻结的市场数据与文档，同时保留其原生的智能体循环、工具与恢复策略。

为比较内部工作流各不相同的系统，FinRelBench 用一组共同材料评估任务完成度：每个系统提交其代码、准备数据与运行策略的命令、以及保存的数据与输出。这些材料使评估者能够施加第 4.3 节定义的机械与语义检查，而无需各系统复现 QuantHarness 的工作流阶段或内部记录格式。在每次比较内，一个确定性的 A 股回测器使用共享的信号时点、交易成本与交易约束。软件版本、资源限制、数据窗口与执行参数见附录 F 与 D.2。

在 FinRelBench 的语义评估中，Claude Opus 4.6 [1] 与 Gemini 3.1 Pro [6] 在两套等价的评分措辞下独立检查匿名化证据；DeepSeek V4 Pro [3] 对可能改变结果的分歧做盲审裁决。这些外部评估不为后续开发尝试提供反馈。附录 A 详述评审组流程，附录 B 记录所报告比较中体现的实现与证据收集配置。

### 5.2 策略开发可靠性

一个策略可能执行成功，却使用了不合适的数据、实现了不同的交易规则，或留下未经验证的必需行为。我们在全部 97 个 FinRelBench 任务上评估这一可靠性缺口，追问每个系统是否把一个显式请求经由数据准备与策略实现推进到可验证的最终结果。Task Success 是首要度量：在同一任务内，两项机械检查与最低语义门都必须通过，且每条显式公开需求都必须被满足并有运行时证据支撑（定义见第 4.3 节）。

Task Success 与两个机械指标是全部 97 个计划任务上的通过率。Requirement Satisfaction 与 Runtime-Evidence Coverage 度量每个任务、每个维度内"被满足判据"与"有执行证据支撑判据"的比例；这些比例在任务间取平均，每个任务等权，无论其评分细则含多少条判据。已完成的诊断评估即使 Task Success 为零也保留其分数，从而显示那些"在整体失败的任务里仍被满足的需求"。未完成的评估与确认失败在附录 B 中区分。

表 1 显示：产出可运行策略比"完成全部所需行为验证的任务"更常见。QuantHarness 取得最高的 Task Success，为 90.72%，对比系统为 74.23%–84.54%。各系统中 Strategy Run Success 均高于 Task Success。Aider 说明了这一差距：其策略在 94.85% 的任务上执行成功，但 Task Success 只有 79.38%；其平均 Strategy Requirement Satisfaction 达 99.09%，而 Strategy Runtime-Evidence Coverage 为 92.64%。这些结果表明，成功的执行与高平均需求满足可以与"运行时验证不完整"并存——可靠完成要求执行、需求、证据三类条件在每个任务内同时成立。

QuantHarness 更一致地满足需求、提供运行时证据，在构建与执行中遇到的失败也更少。OpenHands 的 Data Pipeline Success 与 Strategy Run Success 最低，分别为 86.60% 与 84.54%；附录 B 记录了 13 次生成或数据管道失败，支持"构建是其主要瓶颈"的判断。Codex CLI 的 Strategy Requirement Satisfaction（97.50%）与 Strategy Runtime-Evidence Coverage（91.11%）之间存在差距，说明其证据完整度低于实现层面评估所暗示的水平。SWE-agent 同样有 93.81% 的 Strategy Run Success，但 Task Success 只有 84.54%；案例级拆解识别出五个"机械上已完成、但需求未满足或不可验证"的任务，以及四个"缺少运行时证据"的任务。对 Aider，同一拆解记录了十个"机械完成但需求未满足或不可验证"的任务，这解释了为何其高的平均判据分数并不意味着单个任务内需求被完整满足。这些差异与 QuantHarness 的 Workflow 相一致：strategy specification 让请求显式化，data grounding 在实现前检查输入，validation 与 review 把候选验收与支撑产物绑定在一起。

两个 QuantHarness 案例说明"需求未满足"与"缺少运行时证据"的差别。在行业感知多因子任务中，当行业标签不可得时，允许不做行业约束的选股，前提是报告这一局限；其实现做了回退，却漏掉了所要求的报告，留下一条显式需求未被满足。在相对强度任务中，当没有股票通过流动性与趋势过滤时，策略实施现金回退。两个策略都通过了验证与执行，但一个漏掉了必需的报告，另一个则留下一个条件行为未经验证。更多细节见附录 A 与 B。

### 5.3 Harness 边界消融与压力测试

完整系统的比较显示了 QuantHarness 的整体可靠性，但没有显示这些可靠性来自 Harness Core 的哪些部分。因此我们考察 Harness 如何为每个阶段挑选信息、如何控制工具使用与运行变更。对每项测试，我们比较"目标边界开启"的系统与其消融配置，同时固定任务、共享输入与其余边界设置。我们在一个固定的 30 个 FinRelBench 任务子集上报告配对结果，该子集在实验前选定，覆盖多样的策略规则以及日频打分与分钟订单两类输出。

在常规运行中，Information Boundary 控制提供给 Agent 的历史；Action boundary 限制其工具并在执行前检查调用。对 Information 消融，两个变体取自同一份源运行历史、并获得相同的输入长度预算：边界开启时，Agent 收到仍然适用的需求与实现决策；边界被削弱时，Agent 收到一个按时间排序的切片，必须自己判断哪些信息仍然有效。Action 开启时，Agent 只看到该阶段需要的工具，调用会被检查；消融后，Agent 看到更多工具、收不到指导、面对的检查也更少。表 2 A 组显示：Information Boundary 开启时，25/30 的初版实现执行成功并满足公开需求，消融后为 23/30；Action 边界开启时，30/30 的 Workflow 全部正确完成，消融后为 23/30，其中失败包括无效数据绑定与空输出。这些结果共同表明：阶段适配的信息、以及协调一致的工具指导与执行检查，有助于智能体保住任务需求、把开发推进到可执行策略。

## 6 局限与未来工作

以 GPT-5.5 作为共享生成骨干，有助于把系统级差异与"模型选择带来的波动"区分开。这一共同设置支撑了受控比较，但结论仍只针对单一生成模型。要覆盖更广的模型需要大量额外资源，因为每个任务都涉及一条包含多级生成与评估的完整开发轨迹。把研究扩展到其他模型家族与能力层级，将有助于判断所观察到的可靠性增益是否可泛化，并厘清"可靠完成"与"推理成本"之间的权衡。

FinRelBench 目前通过日频打分与分钟订单接口，在只做多的 A 股环境中评估显式规定的规则型任务。这些任务在共享的市场协议下，把策略需求连接到可验证的数据处理与执行行为。把评估扩展到其他市场、资产类别与更开放的研究任务，将在不同的数据约定与交易约束下检验开发可靠性；补充更多历史区间会进一步拓宽该评估所覆盖的条件。

对 Harness Core 的评估聚焦于单条开发轨迹之内的治理。在已保存的运行记录之上，一个进一步的方向是跨任务、跨运行的受治理经验复用。一个记忆模块可以让后续运行复用已验证的数据绑定、重复出现的失败模式与成功的修复流程，由 Harness Core 中介记忆的写入与检索；取回的经验会继续与其来源证据关联，并在使用前检查与当前任务及市场情境的兼容性。对这一扩展的评估，将考察经验复用在保持可追溯性、保持"开发与留出评估相分离"的前提下，能否提升 Task Success 与效率。

## 7 结论

本文提出 QuantHarness，一个治理 LLM 驱动量化策略开发轨迹的两层 harness。其面向金融的 Workflow 组织策略的构建与评估，Harness Core 则通过 Information、Action、Commitment 三条边界中介信息交接、工具动作与生命周期提交。有产物支撑的运行记录把每个最终结论与其产生的证据和决策关联起来；FinRelBench 从可执行性、需求满足与运行时证据三方面评估策略开发可靠性。实验显示：FinRelBench 上的可靠完成度得到提升，针对性的工作流违规得到遏制，结构化来源信息带来了更强的证据找回与决策回放能力。这些结果共同暴露了一道鸿沟——"产出一个可运行的策略"与"证明所请求的策略是经由可检查的过程忠实开发出来的"之间，并非一回事。QuantHarness 把"可靠性优先"的观点付诸操作：策略开发通过任务忠实度、过程控制与支撑证据来评估，为更严谨的金融智能体研究提供了一个系统层的基础。

### A.2 评分细则构建与可靠性终点

为评估某个实现是否完成了公开请求，我们使用任务专属的评分细则：一份结构化评估规范，把请求与"正确实现所需的有效性条件"映射为判据与取消资格的条件。对任务 𝑖，我们写作 R𝑖 = (C𝑖𝑑, C𝑖𝑠, F𝑖𝑑, F𝑖𝑠)，其中 𝑑 与 𝑠 分别表示数据维度与策略维度，C 含判据，F 含预定义的禁止条件。数据判据关乎证券与时间戳身份、必需输入、时间覆盖及其实际使用；策略判据关乎信号、组合、时点与执行。禁止条件标识无效行为，例如使用决策时不可得的信息。

对每个任务，我们把公开请求分解为可独立评估的数据义务与策略义务。当复合指令的各组成部分可以被单独满足或违反时，就将其拆开——例如交易成本与滑点被作为两条独立判据评估。条件式义务同时保留触发条件与其所需响应，从而在分解中保住所请求行为的含义。每条判据都有一个标识符，可追溯到某条显式公开需求，或追溯到一个必要的语义前提——即"正确实现该任务所需的有效性条件"。每增加一条前提，都要记录说明其必要性的理由，例如"需要足够的历史观测才能计算所请求的移动平均"。

为反映每条判据对所请求策略及其输入有效性的重要程度，我们赋予任务专属的 must 或 should 级别。Must 判据刻画那些对任务的界定性数据或交易语义而言不可或缺的需求，必须全部成立才算最低语义验收；Should 则刻画细化实现的支撑性需求，在这道最低门上允许部分满足。这一区分确立了最低验收标准，却不改变公开请求中陈述的需求。对每个维度 𝑘 ∈ {𝑑, 𝑠}，C𝑖𝑘 被划分为互不相交的 must 判据集 M𝑖𝑘 与 should 判据集 H𝑖𝑘。这些级别决定了下文形式化的最低语义门。每个维度至少含一条 must 判据，故 |C𝑖𝑘| > 0；若 H𝑖𝑘 为空，则 should 满足条件自动成立。

为检验"仅改措辞时判断是否稳定"，每条判据都有两个语义等价的表述。它们改写同一个原子需求，而不改变"评什么、何时适用、所需行为、数值约束"。举例说，"组合最多持有 20 只证券"与"组合中持有的证券数量不超过 20"表达同一约束：判据标识符、must/should 级别与 20 只的上限都不变。为检查评分细则的完整性与来源可追溯性，结构校验会验证任务覆盖、标识符与链接、以及源引文与公开请求的逐字一致。两条表述共用一个判据标识符与级别，自动检查则核对二者的数值一致性。源引文即便在判据措辞改变时也保持逐字不变。这些检查确立的是结构与数值上的一致性，本身并不等于语义等价。评分细则的定义在评估前冻结；附录 A.4 描述这两套措辞在评估流程中如何使用。

为识别哪些判据直接编码了任务 𝑖 公开请求中显式陈述的需求，我们定义 E𝑖 ⊆ C𝑖𝑑 ∪ C𝑖𝑠 为所有这类数据与策略判据的子集。E𝑖 中纳入哪些判据，在评分细则构建时、任何系统输出被评估之前就已确定。E𝑖 中每条判据都链接到公开请求的一段逐字引文。同一条判据在评分细则的两种等价形式中保留同一标识符，使其判断可以在两套措辞间对齐。仅作为必要语义前提而加入的判据不计入 E𝑖，但仍留在 C𝑖𝑑 或 C𝑖𝑠 中参与语义评估。例如，当公开请求显式要求复权价时，对应的输入判据属于 E𝑖；而仅作为有效性前提引入的"证券与时间戳身份一般性检查"则不属于。E𝑖 的成员身份标识判据在完整判据集中的来源，must/should 级别则指明它在最低语义门中的角色。成员身份在细则构建时固定，不随观察到的运行结果而变。对应显式条件需求的判据，即便运行中未观察到触发条件，也仍留在 E𝑖 中。为完整满足公开请求，Task Success 要求 E𝑖 中每条判据既被满足、又有运行时证据支撑，形式化如下。

对 C𝑖𝑑 ∪ C𝑖𝑠 中的每条判据，我们记录两项评估：semantic status（语义状态）判断需求是否达成；evidence strength（证据强度）把"相关行为有运行时支撑"与"仅有代码或声明"区分开。单个评审者把语义状态标为 Satisfied（证据支持其达成）、Not Satisfied（证据显示矛盾或遗漏）或 Not Verifiable（证据不足或含糊）。证据强度记录该判据可得的实现支撑，标签为 Operationalized、Code Only、Declared Only 与 Not Verifiable。Operationalized 要求实际启动路径上有可执行代码，且有相关行为的执行或产物证据；Code Only 指可见的实现但缺少对应的运行时见证；Declared Only 指注释或元数据中无支撑的声称，或与执行无关的设置；Not Verifiable 表示缺乏站得住脚的实现证据。

数据与策略评估把缺陷归到相应的语义维度，避免对同一个缺失输入重复施加语义惩罚。数据不足本身并不使"在代码中正确表达的策略逻辑"失效，尽管它可能限制运行时证据。对一条显式要求观察到端到端行为的策略判据而言，仅有代码层面的正确性不足以确立"满足"。

外部评审组按附录 A.4 的流程综合这些个体判断。未能解决的语义状态分歧记为 Disagreed，这是评审组层面的结果，而非某个评审者的判断。对一个固定的被评系统及其在任务 𝑖 上的运行，令 𝑠𝑖𝑐 = 1 表示判据 𝑐 的最终状态为 Satisfied，𝑒𝑖𝑐 = 1 表示其证据强度为 Operationalized 且最终状态不是 Disagreed，其余情况取零。以下运行级定义中一律省略系统索引。这两个指示量捕捉不同性质：一条错误的规则可能被明显地执行，而一条正确的条件分支可能缺少运行时证据。

在套用语义门之前，我们先检查每个维度是否具备评估所需的最低材料。当收集到的证据记录到至少一个数据集产物存在时，数据维度可评审；当证据含有非空、可读的策略或数据集构建源码时，策略维度可评审。可评审只意味着可以做语义评估，并不确立执行成功或需求满足。对可评审的评估，维度 𝑘 的最低语义门为

$$G_i^k = \Big(\prod_{c \in M_i^k} s_i^c\Big)\cdot \mathbf{1}\Big[\sum_{c \in H_i^k} s_i^c \ge 0.75\,|H_i^k|\Big]\cdot (1 - v_i^k) \tag{1}$$

其中 1[·] 在括号内条件成立时为 1，否则为 0。为覆盖所列条目之外"会使任务失效的缺陷"，我们定义 unlisted fatal defect（未列明致命缺陷）：当前维度中一条有直接证据、未被任何所列判据或禁止条件覆盖、但即便所有所列条目都通过也会使任务实现无效的缺陷。此类缺陷需经附录 A.4 的盲审流程确认。标志位 𝑣𝑖𝑘 在 F𝑖𝑘 中某条禁止条件被确认、或经该流程确认存在未列明致命缺陷时为 1，否则为 0。禁止条件按存在、不存在或不可验证三种方式评估。因此这道门要求：全部 must 判据、至少 75%（向上取整）的 should 判据、且没有已确认的取消资格缺陷。若维度 𝑘 不可评审，令 𝐺𝑖𝑘 = 0。

通过最低语义门本身并不等于完整满足公开请求。因此 Task Success 还要求两道门都通过、数据管道与策略都执行成功，且 E𝑖 中每条判据都被满足并有运行时证据支撑。Data Pipeline Success 要求数据集被构造、保存并被策略消费；Strategy Run Success 要求策略完成执行并产出其声明的输出。令 𝑃𝑖 = 1 表示两项执行检查都通过，否则为 0，则

$$TS_i = P_i\, G_i^d\, G_i^s\, \mathbf{1}\big[s_i^c = e_i^c = 1 \ \text{for all}\ c \in E_i\big] \tag{2}$$

因此每条显式需求都必须被满足并被落实（operationalized），即便其细则级别是 should。

Task Success 给出一个二值的总体结果。为描述需求满足与运行时证据覆盖（包括那些未取得 Task Success 的运行），我们在每个任务、每个维度内分别聚合此前定义的 𝑠𝑖𝑐 与 𝑒𝑖𝑐。这两个比例即 Requirement Satisfaction（RS）与 Runtime-Evidence Coverage（REC）：

$$RS_i^k = \frac{\sum_{c \in C_i^k} s_i^c}{|C_i^k|}, \qquad REC_i^k = \frac{\sum_{c \in C_i^k} e_i^c}{|C_i^k|} \tag{3}$$

RS 与 REC 度量判据满足与运行时证据覆盖的程度，其打分方式区别于最低语义门与执行检查。尽管 must 与 should 判据在那道门中角色不同，在这两个比例中每条判据等权。同理，通过某项执行检查并不确立"每条需求都有运行时证据"：例如零行输出可以通过启动检查，却让某条条件需求没有运行时证据。附录 A.6 说明这些任务级取值如何跨任务聚合，以及系统失败与未完成评估如何处理。

### A.3 从公开请求到证据与判定

以下例子把附录 A.2 的同一套评分细则定义应用于两个形成对照的 QuantHarness 运行：第一个运行中，一条条件需求在语义上已满足但缺少运行时见证；第二个运行中，需求满足与运行时支撑都是完整的。把每个公开请求沿数据证据、策略证据一路追到最终判定，就能看出为何"通过了两项执行检查与最低语义门"的运行仍可能在 Task Success 上不同。

**A.3.1 日频相对强度轮动。** 第一个运行说明"实现一条条件规则"与"提供其执行证据"的区别。其公开请求是：

> Build a long-only relative strength rotation strategy across a small eligible equity universe. Rank names by recent relative performance, hold the strongest names, rebalance weekly or monthly, and stay in cash when no name passes liquidity and trend filters.

（在一小批合格股票池上构建只做多的相对强度轮动策略：按近期相对表现排序，持有最强的标的，按周或按月再平衡，当没有标的通过流动性与趋势过滤时保持现金。）

为评估数据是否支持所请求的排序与过滤，评分细则检查证券身份、可比的价格历史，以及流动性与趋势输入。持久化的日频数据集含 500 只证券、90 个交易日期，共 44,936 行，且没有重复的实体–时间对。其画像显示价格与动量输入对齐，并含策略消费的流动性与趋势特征。据此，已裁定的评审组把三条数据判据（包括共用的证券身份判据）全部标为 Satisfied/Operationalized，即每条都有 𝑠𝑖𝑐 = 𝑒𝑖𝑐 = 1，按式 (3) 得 RS𝑑𝑖 = REC𝑑𝑖 = 3/3 = 100%。

输入确定后，策略细则检查排序（S01）、选出最强标的（S02）、现金回退（S03）与按周或按月再平衡（S04）。这四条都直接来自公开请求，因而属于 E𝑖。对 S01、S02、S04，被执行的策略把近期动量度量合成相对强度分数、选取排名最高的合格标的，并把信号排在每周最后一个交易日。复现的输出含所选标的的正分数，抽样的信号日期相隔一周。评审组因此把这三条标为 Satisfied/Operationalized，𝑠𝑖𝑐 = 𝑒𝑖𝑐 = 1。

S03 值得细看：它的实现有支撑，但其条件行为缺少运行时见证。在可执行代码中，合格性同时要求流动性与趋势过滤；若无标的通过，该分支就不为该日期产出任何分数。实际执行配置在分数缺失时不保留此前持仓。这些代码与配置事实支持现金回退规则，但不能确立该条件确实被触发过。所提供的运行证据没有指出任何一个"没有标的同时通过两项过滤"的日期。已裁定的评审组因此把 S03 记为 Satisfied/Code Only：𝑠𝑖,S03 = 1 但 𝑒𝑖,S03 = 0。于是四条策略判据全部满足、其中三条有运行时支撑，得 RS𝑠𝑖 = 4/4 = 100%、REC𝑠𝑖 = 3/4 = 75%。

对最终任务判定，执行检查补充了这些判据级判断：数据集已构造、保存并被消费，策略以声明的分数输出完成，故 𝑃𝑖 = 1。两个语义维度都可评审，全部 must 与 should 判据均满足，评审组把预定义禁止条件记为不存在、且没有已确认的未列明致命缺陷。于是两道最低语义门都通过：𝐺𝑖𝑑 = 𝐺𝑖𝑠 = 1。尽管如此，S03 属于 E𝑖 且缺少运行时证据，故式 (2) 给出 TS𝑖 = 0。在这个例子里，把"最低语义验收"与"完整任务成功"分开的，是缺失的运行时见证，而不是错误的现金规则。

**A.3.2 日频复权价均线交叉。** 第二个运行给出互补的情形：所请求的行为既被实现、也有运行时证据支撑。其公开请求是：

> Implement a daily moving-average crossover strategy using adjusted close prices. Compute 20-day and 60-day moving averages. Generate positive scores when the short average is above the long average, rebalance on the next trading session, hold at most 20 names, equal weight positions, and include transaction costs and slippage.

（用复权收盘价实现日频均线交叉策略：计算 20 日与 60 日移动平均；当短期均线高于长期均线时给出正分数；在下一交易日再平衡；最多持有 20 只、等权配置；并计入交易成本与滑点。）

这里的数据评估检查每只证券是否具备复权价输入、以及是否有足够的时间序列历史来计算所请求的移动平均。持久化数据集保留了单只证券与带日期的观测，每只 80–90 条观测。实现从绑定的收盘价列与复权因子列推导复权收盘价；全窗口滚动计算要求在产出信号前有足够观测。数据集画像与复现输出支持这些输入与所需历史的使用，已裁定的评审组因此把三条数据判据全部标为 Satisfied/Operationalized，每条 𝑠𝑖𝑐 = 𝑒𝑖𝑐 = 1，按式 (3) 得 RS𝑑𝑖 = REC𝑑𝑖 = 3/3 = 100%。

用这些输入，被执行的策略计算所请求的 20 日与 60 日复权收盘均线（S01），且仅当短期均线高于长期均线时给出正分数（S02）；复现的输出记录了由此产生的选择。代码把每个信号日期的选择上限设为 20 只，复现输出遵守该上限（S04）。

对最终选择，实际执行配置规定了滞后一个交易日（S03）与等权组合构建（S05）。带日期的订单与成交支持下一交易日执行，订单的等权目标则支撑加权规则。费用扣减与滑点调整后的成交价，为交易成本（S06）与滑点（S07）提供了运行时证据。全部七条策略判据都直接编码公开需求，属于 E𝑖。在这一"实现 + 执行"的综合证据上，评审组把七条策略判据全部标为 Satisfied/Operationalized，每条 𝑠𝑖𝑐 = 𝑒𝑖𝑐 = 1，故 RS𝑠𝑖 = REC𝑠𝑖 = 7/7 = 100%。

对最终任务判定，执行检查同样补充了判据级判断：数据集的构造、持久化与消费均成功，随后策略以声明的分数输出完成，得 𝑃𝑖 = 1。两个语义维度都可评审，全部 must 与 should 判据均满足，评审组把预定义禁止条件记为不存在、且无已确认的未列明致命缺陷，因此 𝐺𝑖𝑑 = 𝐺𝑖𝑠 = 1。与第一个运行不同，这里每条显式需求既有满足状态、也有落实证据。全部条件成立，式 (2) 给出 TS𝑖 = 1。

两个例子合起来区分了成功执行、语义满足与完整运行时证据：前两者本身并不确立第三者。两个运行都通过了执行检查与最低语义门；它们不同的 Task Success 判定，反映的是"在同一条评估规则下，每条显式需求是否都有运行时见证"。下一小节介绍产生这些判据级判断的外部评审组，以及它如何化解分歧。

### A.4 外部评审组的裁定与校准

上面所示的判据级判断由一个外部基准评审组产生，它独立于内部 Workflow 的 Judge。内部 Judge 在开发期间建议接受或恢复；外部评审组则评估提交上来的证据，其判断不回流到后续候选开发中。

评审组使用附录 A.2 描述、并在评估前冻结的两套等价评分措辞，以检验判断在等价表述下的稳定性。在每套措辞下，Claude Opus 4.6（claude-opus-4-6）与 Gemini 3.1 Pro（gemini-3.1-pro-preview）独立评估同一批匿名化证据。它们返回判据级的语义状态、证据强度与证据定位符，而不是一个总体的通过或分数。

当这些独立判断在"与最低语义验收或公开请求完整达成相关的决策"上出现分歧时，DeepSeek V4 Pro（deepseek-v4-pro）做针对性仲裁。在同一套措辞内，重叠的触发点涉及：must 判据是否满足；在最低验收仍可能达成的前提下，已满足的 should 判据数量是否达到固定阈值；显式需求集 E𝑖 中某条判据的语义状态或证据强度；以及某条预定义禁止条件是否存在。未被送交仲裁的判据保留一致的语义状态，否则状态记为 Disagreed。两种情况下，都保留两个证据强度标签中较弱的那个。

在这一"套内"聚合之后，同一位仲裁者处理两套结果之间残留的差异。当某条判据在两套措辞下语义状态与证据强度都相同时，保留该标签，包括双方同为 Disagreed 的情况。两个仲裁阶段中，仲裁者都在看不到先前结论的情况下裁决原始证据。未列明致命缺陷（定义见附录 A.2）还额外需要盲审确认：它是在相关维度上独立的缺陷、未被所列判据或禁止条件覆盖。随后，最终标签与执行检查按该附录中的固定公式确定可靠性终点；最终状态为 Disagreed 的判据在 RS 与 REC 中都计零分。

为检查这套评审流程是否按预期识别已达成的需求与缺陷，我们使用带有已知预期判断的受控案例。这里的"校准"指与这些预期标签核对。17 个匿名静态 fixture 是预先构造、固定下来的证据包，含公开请求、代码片段、数据集与输出画像、执行记录，预期判断另行给出。四个正对照给出预期能满足需求的实现，覆盖日频交叉、开盘区间突破、改编的日频动量与改编的日内突破。十三个负对照分三组引入缺陷：数据充分性与身份（历史不足、观测身份错误、实体塌缩、时间戳不可用、未复权价格、日内频率错误）；策略逻辑与时点（规则反转、在区间形成期间入场、差一格的滞后、遗漏所要求的入场前通道收缩条件）；执行约束（同日执行、违反 T+1、零执行延迟）。

例如，"历史不足"这个 fixture 为一个 60 个交易日的需求只提供 30 条观测。长窗口均线无法定义，而提供的执行记录报告"正常终止、输出为空"。这检验评审组是否把缺陷归因于数据覆盖不足。在整个 fixture 集上，最终评审组检查要求与预期的 must 状态一致、must 判据的预期证据强度一致、禁止条件与未列明致命缺陷的判定一致，并在有规定处检查"所有显式需求是否都被满足且被落实"。保存的报告记录了 17 个 fixture 上这些预定义核心检查的成功完成，should 标签的比较另行报告。

为使这些检查可追溯到被评配置，每份验证报告记录协议、评分细则、judge 配置、输出 schema、指令与 fixture 包的哈希。附录 B 用评审组一致性与对基准提交的仲裁统计，补充这些受控检查。下一小节描述被评系统的基准运行证据如何被收集与组织起来供这套评审使用。

### A.5 证据收集

所有被评系统遵循同一套中立的提交规则：声明的数据构造与策略执行命令、持久化的数据集与输出、实际启动路径上的代码、以及捕获的执行证据。这些要求并不强制其他系统输出 QuantHarness 的阶段名或内部契约。

评估者把这些材料组织成匿名化的结构化证据包，连同任务需求与评分细则一并提供给评审组。数据集画像、观测到的文件访问、被执行的输出与代码引用都带有证据标签与定位符，使判据级判断能指向具体的代码或记录。当订单、成交、费用与持仓是从既有原生运行导出时，导出协议用代码与产物哈希、调用设置、回测元数据把这些记录与其来源执行关联起来。这种关联保持它们"作为原始执行证据"的身份：导出或链接这些记录并不构成一次独立回放，本身也不能确立某条策略需求被满足。自报字段提供辅助上下文，而非实际执行材料的替代品。"所报告的声称"与"被观测的证据"之间的这一区分，对每个系统同样适用。

证据收集设施一旦中断，评估会停留在未完成状态，而不是确认策略失败。附录 A.6 说明已完成与未完成的任务评估如何进入聚合指标。

### A.6 聚合与缺失结果

系统级结果把附录 A.2 的任务级终点在每个系统的全部 97 个计划案例上聚合。Data Pipeline Success、Strategy Run Success 与 Task Success 各自是"通过相应检查的任务数 ÷ 97"。Requirement Satisfaction（RS）与 Runtime-Evidence Coverage（REC）使用式 3 定义的任务级比例，数据与策略维度分别计算。每个系统级取值是"对应任务取值之和 ÷ 97"，不可得的取值按下文处理。这是不加权的任务宏平均：评分细则更长的案例不会获得更大权重。must 与 should 判据在单个案例内诊断权重相等，这不改变它们在最低语义门中的角色。举例说，在同一维度内，一个四判据案例的完全覆盖，与另一个案例八条判据中覆盖四条，得到的两案例均值是 75%，而不是把判据池化后的 8/12。

进入外部语义评估的资格要求：生成成功、提交有效、且执行检查记录没有设施错误；它并不要求任一机械检查通过。这一运行级资格检查不同于附录 A.2 中维度级的可评审条件（后者关乎评估可得的最低证据）。已完成且合格的语义评估，即使 Task Success 为零也保留其测得的 RS 与 REC。一种"完成的系统失败"会阻断语义评估（如生成失败或无效提交），它对这些诊断的贡献是零，而不是把任务从分母中移除。

有资格不等于完成：当证据收集或必需的评审组复核尚未结束时，外部评估就是未完成的。这类任务不给 Task Success 分、对 RS 与 REC 贡献零，但其观测到的 Data Pipeline Success 与 Strategy Run Success 结果被保留。它们仍留在所有计划分母中，并与"确认的策略失败"分开报告，因此"评估缺失"不会被解读为"策略错误"的证据。附录 B 报告相应计数与任务分组结果。

### B.2 端到端可靠性在何处失守

表 6 把上述比较中的非成功分解为互斥的类别。未完成评估先被分离出来；其余每个非成功按以下顺序归入第一个适用的类别：生成或数据管道失败、策略执行失败、需求未满足或不可验证、缺少运行时证据。每个任务只计一次，即便它同时满足多个失败条件。相比之下，单独报告的 Data Pipeline Success 与 Strategy Run Success 可能对同一任务同时记为失败，因此其失败计数可以重叠。

### B.3 代表性案例

下面的例子把上述结果类别连接到公开需求、实现与支撑证据上，说明"完整的需求达成"、"已执行的规则缺陷"与"缺失的报告路径"。附录 A.3 相对强度轮动示例中的现金回退规则，则补充说明一条被正确实现的条件规则如何仍可能没有运行时证据。

**案例 1：完整成功——复权价均线交叉。**
系统：QuantHarness ｜ 任务：generic_explicit_ma_crossover
请求规定 20 与 60 个交易日的复权收盘均线、短期均线高于长期均线时给正分数、下一交易日再平衡、最多 20 只等权持仓，并计入交易成本与滑点。QuantHarness 实现了这些需求，证据把实际的价格列与复权因子列连接到提交策略中的计算——只要能可复现地构造，复权收盘价不必预先作为单独输入列存储。最终评审组把三条数据判据与七条策略判据全部标为 Satisfied/Operationalized，两项机械门均通过，得到 Task Success。

**案例 2：可运行但不正确——EMA 趋势中的 ATR 回撤。**
系统：Codex CLI ｜ 任务：qcb_daily_atr_pullback_in_ema_trend
请求要求用非正分数表示未激活或退出状态。被执行的实现维护一个 active 标志，在入场时置位、出场时清除；然而它额外要求"正的 ATR 归一化回撤"才给出正分数，使激活状态也可能拿到零分数。完整输出画像含 54,161 行 active，却只有 54,021 个正分数，留下 140 行 active 但零分数。跨措辞仲裁者依据实现中的这额外条件与完整输出计数，把 S06 判为 Not Satisfied/Operationalized。执行证据由此确立了规则违反，任务在通过两项机械检查的情况下仍然失败。

**案例 3：缺少必需的回退报告。**
系统：QuantHarness ｜ 任务：generic_industry_aware_multifactor
公开请求只允许在记录了"行业元数据不可得"的前提下使用不受行业约束的回退。回退函数返回所选标的与一个行业元数据可用性标志；调用方收到了该标志，却没有把它传播到持久化输出或局限性报告中。现有运行含有行业元数据，未满足的需求关乎"所允许的回退缺少报告路径"。尽管两项机械检查都通过，最终 S03 判定为 Not Satisfied/Code Only，Task Success 无法达成。

## 附录 C 边界测试、可审计性与回放

实验把三个问题分开：运行时边界如何影响常规开发、它们是否遏制了指定的无效事件、以及由此产生的记录是否支撑证据检索与决策回放。

### C.1 案例选择与共享实验条件

常规运行消融与受控压力测试使用同一个固定的 30 案例子集（FinRelBench）：20 个日频打分任务与 10 个日内订单任务。案例在这些实验之前从公开任务文本中选出，以覆盖不同的策略规则与实现要求。按所赋的实现复杂度，该子集含 8 个基础、14 个中级与 8 个高级任务，反映规则组合、状态维护与时序依赖上的差异。覆盖范围横跨均线、动量、状态过滤、多因子规则、突破以及日内状态与时点约束，使边界测试既能考察简单规则，也能考察条件相互作用的策略。

在每个边界实验中，Full 保留目标边界，Off 施加其协议定义的消融。配对条件共享任务、作为该实验源检查点的已保存工作流状态、规范数据绑定、市场配置与非目标边界设置。已保存的源产物与干预检查用于验证配对条件确实共享这些输入。

回测门使用由 2025-12-31 的中证 100 成分股快照定义的 100 只股票池，回测期为 2026-01-05–2026-05-29。策略生成请求使用 GPT-5.5，temperature 为 0.0。以下各节为每项实验规定阶段专属的干预、终点与分析单位。

### C.2 常规运行的边界消融

在上述配对任务上，常规运行消融考察 Information 与 Action 边界在没有注入违规时如何支撑开发。

**Information。** 该消融检验"把先前信息组织成开发交接件"如何影响代码生成。共享检查点位于任务理解、规划与数据绑定智能体的提议及工具证据之后。Full 收到已解析的字段契约（指明可用输入字段及其从数据源到代码的映射），连同实现计划与精简的开发上下文；Off 则按时间顺序呈现智能体可用的更早工作流记录，包括 task contract、specification、规划蓝图、原始绑定提议、工具证据、Runtime Card 与公开执行接口，但没有提供给 Full 的那份组织化上下文。两种条件取自同样的早期记录。

对每个案例，Full 与 Off 的代码生成请求在"指令文本与消息体的总字符数上限"上相同。该上限依据 Full 参考请求确定，后者从已冻结 Full 运行的保存产物中重建。为守住这一上限，Off 用一条固定规则，从时间历史的开头与结尾各保留近乎相等的部分。这样，比较就在共同的输入长度限制下改变了信息的选择与组织。

该干预只改变呈现给代码生成模型的上下文，任务需求与下游评估设置保持不变。具体而言，下游的规范绑定、字段契约、实现计划、量化输入要求与协议决策都相同。全部 30 对都通过了已记录的 task contract、数据绑定与操控有效性检查。

我们把初版候选与最终 Workflow 结果分开评估。Initial implementation success（初版实现成功）要求同一任务上"机械执行"与"公开义务符合性"同时成立：机械执行要求首次验证与回测检查通过且无需策略修复，回测还必须确认预期的输出协议与可操作的策略输出（即回测窗口内可用于交易的信号或订单）；一次对 Full/Off 条件盲化的 GPT-5.5 评估，依据预定义公开需求与已记录的执行语义评判初版源码，公开义务符合性要求所有被评估的需求都得到满足。修复后的源码在该评估中不替换初版候选。Terminal completion（最终完成）另行要求验证、回测、Judge 批准以及候选身份一致的授权冻结。

**Action。** Full 暴露阶段适配的工具、提供相应指导，并在调用时检查授权；Off 暴露更大的已注册工具集、移除相应指导、并弱化针对性检查。该消融同时改变"阶段范围内的工具暴露、指导与调用检查"。

Admissible Workflow completion（合规 Workflow 完成）要求上述最终完成检查，加上对已保存的规划、数据绑定与实现记录的预定义检查。这些检查验证预期的输出协议，要求信号规则、持仓规则、风险规则与数据选择条目达到预定义的最少数量，并用预定义的词面匹配检查这些记录中是否含所需的任务概念。例如，均线交叉任务要求至少两条信号规则条目，持仓规则、风险规则与数据选择各至少一条，并且术语要覆盖两条均线、其 20 与 60 日窗口、下一交易日执行与等权配置。这些检查评估的是记录结构与任务概念覆盖，而不是 FinRelBench 所评估的完整需求级语义。

我们另行跟踪未授权行为，因为一次运行可能在没有违反授权规则的情况下未能完成。若记录显示"已完成的未授权工具调用"、"被绕过的生命周期授权检查"，或"必需检查未通过、或冻结产物无法与其记录哈希核对"的冻结，就把该运行计为观察到未授权行为。

表 8：30 个配对任务上的常规运行边界诊断，把首版候选的执行与语义同最终完成分开。

| 边界 | 终点 | Full | Off |
|---|---|---|---|
| Information | 初版机械执行 | 29/30 | 30/30 |
| Information | 公开义务符合性 | 26/30 | 23/30 |
| Information | 初版实现成功 | 25/30 | 23/30 |
| Information | 最终完成 | 30/30 | 30/30 |
| Action | 合规 Workflow 完成 | 30/30 | 23/30 |
| Action | 观察到的未授权行为 | 0/30 | 0/30 |

对 Information，表 8 显示 Full 下 25/30 的初版实现成功、Off 下 23/30，而两种条件的最终完成都达 30/30。即便两种条件都完成了 Workflow，最初的需求符合性差异依然可见——最终完成并不会在最终候选上重新评估全部公开义务。对 Action，合规 Workflow 完成在 Full 下为 30/30、Off 下为 23/30。两种条件在这些常规运行中都未表现出未授权行为，而常规运行本就不必然触发边界的拒绝条件。下面的压力测试提供明确的机会来行使拒绝。

### C.3 受控边界压力测试

正文表 2 B 组报告了聚合的压力测试结果。表 9 汇总相应的干预与证据判据。Information 与 Action 让智能体自行选择应对方式，并不指示它采取违规选项；Commitment 则在批准之后注入一次外部候选替换来测试授权。三者都只在"可观察证据确认目标边界违规确已发生"时才计为逃逸。这些测试评估的是对指定违规的遏制，而不是一般性的对抗安全。

表 9：压力协议。计数区分暴露、智能体激活与已验证逃逸。

| 边界 | 起始条件与干预 | 证据与分母 |
|---|---|---|
| Information | 一份修订交接件含已接受、已被取代与已被否决的决策。Full 收到当前已接受的版本；Off 收到原始版本与治理事件，但没有显式的"当前版本答案"。 | 执行证据必须显示使用了过时或被否决的值。Full 0/30、Off 11/30 的案例使用了无效信息。 |

**Information 权威性。** 该测试考察当修订历史同时包含已被取代与被否决的版本时，代码生成是否使用当前已接受的信息。每个版本把一个数据集及其所需字段链接到一个派生特征与执行步骤。Full 收到当前已接受的组合；Off 在保留正确版本的同时，也保留已被取代与被否决的版本及其接受、验证与回滚事件，但没有"已解析的当前版本答案"。公开任务与数据需求保持不变。无效信息终点要求有"使用过时或被否决值"的执行证据，例如对其字段的访问记录。这十一次逃逸计的是经验证的采用，与其他首轮失败分开统计。这一对照评估的正是修订交接处对权威信息的选择。

**Action 的激活与副作用。** 智能体可以在临时绑定尚未获得实质性复核与批准之前请求数据集构建。立即构建利用一个临时机会，与待决复核并行准备数据；等待批准要多加一个合成调度周期，但仍允许任务完成。绑定可能被修订，使早期工作作废；该场景既不给出修订概率，也不给出推荐选择。智能体最多有四轮，每个模型请求 600 秒超时。它在 22 个案例中请求提前构建、在其余 8 个中等待（后者不触发守卫）。每个提前构建请求及其参数在 Full 与 Off 之间共享，使用同一个真实的数据集构建工具、放在不同的运行目录里。调用时强制在 Full 下拦下这些未授权调用；Off 允许其执行，由此产生的文件确认了未授权构建确实发生。全部任务的逃逸率为 0/30 对 22/30；在 22 个已激活请求的条件下为 0/22 对 22/22。另有两个独立的授权调用对照，都通过了 Full 的强制；这些机制检查与 30 个智能体选择分开报告。

**Commitment 身份。** 该测试关心从 Judge 批准到冻结的转移：候选可能在评审之后被改动，使记录在案的批准关联到更早的版本。我们检验 Commitment 边界能否阻止被改动的候选在那份更早的批准之下被冻结。Full 与 Off 共享同一份已记录的 Judge 批准，以及一枚记录"已批准候选及其支撑产物路径与内容哈希"的 commitment seal（提交印章）。用案例标识符与预指定种子做固定哈希分配，选出 14 个替换案例，不基于任务内容或结果；其余 16 个保持不变。在每个暴露的配对中，同一段固定注释在批准与用印之后被追加到策略源码中，而不要求 Judge 批准一个新候选。这一确定性干预不需要新的策略生成调用。该改动保持可执行行为不变、但改变了字节身份，从而把"对被评审那份产物本身的授权"隔离出来。逃逸的判据是：被冻结源码与被改动的活动源码一致、且与用印中记录的已批准身份不同。无支撑的冻结在 Full 下为 0/30、Off 下为 14/30，即被改动案例中的 0/14 对 14/14。两种条件下 16 个未改动对照全部正常提交。下一小节从这些"干净、被遏制、已逃逸"的结果中定义一个审计语料。

### C.4 审计语料与证据视图

上面的 Commitment 压力测试问的是系统能否阻止被改动的候选在更早的批准之下被冻结。接下来我们考察：已保存的记录能否让审计者找回所需证据，以理解开发过程中发生了什么、最终的授权结果是如何产生的。

每份审计记录把一个任务的已保存开发历史链接到该压力测试中"Judge 之后的一个分支"。语料含来自同样 30 个任务的 44 份记录：16 份是批准后候选未变并被冻结的（clean，干净）；14 份是批准后的替换被阻止冻结的（contained，被遏制）；14 份是替换在更早批准之下被冻结的（escaped，已逃逸）。按预指定的替换分配，未被改动的任务贡献其 Full 分支，被替换的任务同时贡献其 Full（contained）与 Off（escaped）分支。选择不依赖审计或回放结果。

审计比较把每份已记录的过程与结果固定，只改变审计者可得的证据。每份记录通过三种证据视图呈现——organized（组织化）、flat（平铺）与 final-only（仅最终）——它们规定可得的产物与组织信息，共得到 132 次"记录–视图"审计。

对每份记录，organized 与 flat 视图在共同的 240,000 字符产物内容预算下，保留相同的可见产物内容、哈希与顺序。organized 视图额外提供描述性文件路径与元数据、相关产物之间的链接，以及按证据角色组织的索引。一个角色指明所寻找的证据类型，例如验证报告或已批准的源代码。flat 用编号的条目标识符替换描述性路径、移除显式结构，其底层文件内容仍可搜索、可读。这些可见路径或条目标识符充当访问产物的定位符。final-only 视图只暴露最终候选与最终摘要产物，省略中间过程与治理证据。

审计者被要求定位每条所请求的证据、返回其定位符与可见内容哈希；它还要报告关于"首个过程失败（如有）"、Judge 提议、授权与用印状态、以及已批准/活动/被冻结候选身份的发现。审计者使用 GPT-5.5，temperature 为 0.0，每次"记录–视图"审计最多 12 次证据工具调用。所有视图都支持列出、按内容搜索与按定位符阅读；只有 organized 视图支持按证据角色批量查询，在一次预算内的调用中返回多个所请求角色的定位符与哈希。访问仅限于被分配的视图，没有预分配的结果类别标签，也不能访问原始运行目录。因此 organized–flat 的比较在该调用预算下评估"结构化证据组织 + 其检索接口"；与 final-only 的比较则额外考察证据留存。

为比较各视图支撑证据找回的程度，我们报告 Exact audit evidence（精确审计证据），即审计者准确找回的必需审计角色比例。只有当返回的产物定位符正确、且哈希与其可见内容匹配时，该角色才算准确找回。对每份记录，分数是"准确找回的必需角色数 ÷ 该源记录所要求的审计角色数"；所报告的取值是该视图下全部 44 份记录上这些比例的不加权均值。

对这一指标，每份记录都要求 12 个证据角色：process trace、Runtime Card、验证报告、回测报告、Judge 报告、Judge 提议、commitment seal、用印验证结果、治理事件、运行指标、已接受代码、活动代码。当源记录含被冻结候选时，被冻结哈希构成第 13 个必需角色；不含它的遏制记录不要求该角色。源记录所要求的任何角色，在三种视图中都保持要求，即便某视图并不暴露它。找回这些审计角色本身并不确立"记录在案的结果可被复现"。审计者还会搜索额外输入，包括任务规格、数据绑定与执行配置，以支撑下文所述的验证、回测与 Commitment 重建。

### C.5 回放输入、执行与重建

回放用取回的证据检查两个关联的结果：对已批准候选的验证与回测，以及对送呈 Commitment 的候选的授权。验收组件需要十个角色：task contract、策略规格、蓝图与实现计划描述任务与设计；数据绑定、字段契约、实现元数据与已接受代码标识候选及其数据约束；验证与回测配置规定执行。在解析定位符并核验哈希之后，运行器在一个全新运行目录中恢复这些输入，重跑验证，若通过则用单独配置的冻结市场数据快照执行配置好的回测；随后把候选代码、数据绑定与字段契约的内容哈希与源记录中的比对。该比较还覆盖验证结果、回测状态与输出协议。

Commitment 组件则重建"提交时刻活动候选"的授权结果。它解析活动代码、已保存的 Judge 提议、commitment seal、用印验证、治理事件、运行指标，以及（当存在被冻结候选时的）被冻结哈希；它重新计算活动代码的身份并与用印比对，同时对用印所覆盖的支撑产物使用已记录的验证证据。该重建在已记录的强制条件下检查授权与最终候选身份。已保存的 Judge 提议是输入；Judge 评审本身不重跑。

每个组件只有在输入包完整时才能进行：其全部必需产物都必须能通过取回的定位符获得，且可见内容哈希匹配。回放输入接口接受描述性路径或编号的条目标识符，并在同一规范工作区中恢复所需输入。所有视图使用同样的完整性与执行检查。

只有当两个组件都与源记录指定的结果及候选身份相符时，回放才算通过验证。这包括：clean 记录重现正常的授权与冻结、contained 记录得到"未授权且未冻结"、escaped 记录在 Off 下出现"无支撑的冻结"。验证关心的是这些执行与授权结果及产物身份；它不要求交易输出逐字节相同，也不要求财务指标一致。

### D.3 完成度与财务指标

只有产出最终期回测的任务才计为完成。对每个系统，completion 以全部计划任务为分母：开放式规则研究 12 个，每个模型组 5 个。规则组进一步分为十个日频打分任务与两个日内订单任务，两类输出的完成度分别报告。

财务摘要覆盖日频规则任务与两个模型组；日内订单任务只通过完成计数报告。对每个系统，财务指标按"每个已完成任务"计算，并在相应组内以任务等权平均。没有最终期回测的任务留在完成度分母中，但被排除在财务均值之外，而不是被记为零收益。一个没有任何完成任务的组没有财务估计值。因此财务均值与完成计数一起报告，以显示有多少任务为其做出了贡献。

日频规则研究报告年化收益、Sharpe 比率、最大回撤与换手率；模型结果报告总收益、Sharpe 比率、最大回撤与下文定义的泛化差距。日频规则任务的年化收益不与模型任务的总收益合并。模型结果中的正收益计数，报告有多少已完成任务在最终期取得严格为正的总收益，分母为已完成任务数。

对每次回测，令 𝑇 为已记录的日频观测数，𝑉𝑡 为观测 𝑡 时的账户总权益，𝑡 = 1, …, 𝑇 按时间排序。总收益为 𝑉𝑇 /𝑉1 − 1，年化收益为 (𝑉𝑇 /𝑉1 )^(252/𝑇) − 1，按每年 252 个交易日计。

为计算波动率与 Sharpe 比率，我们用日收益 𝑟1 = 0、𝑟𝑡 = 𝑉𝑡 /𝑉𝑡−1 − 1（𝑡 = 2, …, 𝑇）。年化波动率是这 𝑇 个日收益的总体标准差乘以 252。共享回测器把 Sharpe 算作"年化收益 ÷ 该波动率"，不减无风险收益；波动率为零时 Sharpe 记为零。

最大回撤度量已记录权益序列中最大的"峰到谷"损失：在已记录观测上取 𝑉𝑡 /max1≤𝑢≤𝑡 𝑉𝑢 − 1 的最小值，其中 𝑢 索引到 𝑡（含 𝑡），故分母是截至该点的最高权益。它以非正收益报告，越接近零表示峰谷损失越小。交易活跃度用换手率（turnover）衡量：已执行买卖的货币总额（两者都计为正）除以评估期内的平均账户权益；以累计倍数报告，而非日率或年化率。

对模型任务，generalization gap（泛化差距）比较被选候选在最终评估中的总收益与它在优化期的总收益。令 𝑅final 与 𝑅optimization 分别表示这两个收益，则差距为

$$\Delta R = R_{\text{final}} - R_{\text{optimization}}.$$

对给定任务，负差距表示最终期总收益低于优化期；正差距表示更高。对每个系统，这些任务级差距在每个模型组的已完成任务上等权平均，以百分点报告。该差距比较的是两个期间的收益，不度量其他市场期间或状态下的表现。

### D.4 QuantHarness 的优化与候选选择

本小节详述 QuantHarness 在 FinResearchSuite 中如何为最终评估开发与选择候选。下面的优化与选择规则是 QuantHarness 专属的；共享评估协议见附录 D.2。

通过验证与回测，说明候选可以利用绑定的输入与声明的输出协议执行。此时 QuantHarness 支持一次可选的、预算受限的探索，考察在保持任务需求的前提下其金融质量能否提升；Workflow 不带这个循环也能完成。优化期间，任务需求、数据绑定与输出协议保持不变。Repair（修复）针对执行或接口错误；optimization（优化）探索对可执行候选的改进，两者预算不可互换。

**协议与候选提议。** 优化预算与财务质量目标在运行前固定。在 FinResearchSuite 中，QuantHarness 每个任务至多允许三次优化评估与一次最终提交。市场数据被划分为不重叠的优化期与最终评估期；候选开发期间，模型型策略在更早的训练期上拟合。

在该协议内，提议智能体收到允许的改动与评估设置、当前候选以及优化期反馈（而非最终期结果）。提议必须指明一项允许的改动，并与任务、数据绑定与输出协议保持一致。proposal guard（提议守卫）在开发前检查所请求的改动是否被允许；variant guard（变体守卫）再按提议的约束以及固定的任务与数据要求检查产出的候选。模型型变体还要产出验证与回测所需的训练与推理产物。每个变体必须先通过验证，才能在同一优化期上回测。

**预算记账与证据。** 为把探索保持在声明的预算内，Workflow 分别跟踪候选身份、提议迭代、优化评估、修复、最终提交与最终评估尝试。一本仅追加的预算账本记录评估的开始与完成、候选身份与提交状态。启动一次评估即消耗其相应额度，即便该尝试随后失败。

为识别重复候选，哈希从"定义策略及其实现的指定文件"计算（适用时含模型配置）。重复候选不会获得新的独立评估；它只有在"该结果来自同一候选在匹配的已记录执行协议下的一次已完成评估"时，才能复用已记录的结果。不完整或不兼容的缓存证据不能使候选具备入选资格。

**停止与选择。** 当配置的迭代、候选或评估预算耗尽，或已无可执行的改进、无可进一步受理的提议时，探索结束、Workflow 进入选择。拒绝一个新提议（例如因为它试图改动固定的数据环境）会挡住该提议，并可以在不使先前合格候选失效的情况下结束探索。

相比之下，运行级的协议违规——例如试图评估未注册的候选、或用另一个候选替换已注册的选择——会终止运行，且没有有效的最终提交。当协议仍然有效时，选择同时考虑初版候选及其修订版。入选资格要求适用的验证与回测检查通过，而不只是一个好看的财务数字。若没有剩余的合格候选，运行终止且无有效最终提交；否则，合格候选在固定目标下用优化期证据比较，被选候选的身份、排序及其最终提交记录被保留。

在 FinResearchSuite 中，QuantHarness 使用复合财务分数而非单看收益。对所报告运行中的合格候选，该分数把年化收益与 0.5 倍 Sharpe 比率相加，再减去 0.5 倍绝对最大回撤与 0.05 倍累计换手。收益与回撤以小数进入；指标约定见附录 D.3。规则任务打分对每次已执行成交加 0.01，上限 0.1；模型任务打分把该成交数奖励减半，并加上 0.05 倍成交率（已执行与请求股数之比，截断到 [0, 1]）；换手超过 2 时再罚 0.25。

规则研究候选按该分数在优化期上排序。模型候选则要求该窗口内四个按月子期（2025 年 9–12 月）的完整证据，且每个子期至少十条日频观测。其排序分数为"四个月度分数的中位数 − 四个分数总体标准差的一半 −（中位数与最差月度分数之差）的一半"。模型变体还必须在四个月度分数中至少三个上超过它所修订的候选，才能保持入选资格。选择取排名最高的合格候选；分数相同则保留候选的注册顺序。这些计算只使用优化期证据。

**最终评估与工程验收。** 选择之后，候选的设计被固定，在最终期上只评估一次。对 FinResearchSuite 中 QuantHarness 的模型任务，这次评估的准备包括在训练期与优化期上重新拟合被选模型、并为最终期生成预测，而不修订被选设计。最终尝试在执行前登记；失败并不授权重新选择或第二次最终尝试。最终财务结果保留用于质量分析，不回传优化、也不用于重新调参；其数值大小不决定工程验收。

随后候选连同相应的验证与回测报告进入 Judge 评审。Harness Core 会先检查支撑 Judge 所建议路径的证据，才允许其生效。正式的 Workflow 冻结发生在一次获授权的验收决定之后，并把候选连同其支撑产物一起保存；把候选固定下来做评估本身并不构成冻结。实验窗口与生成预算见附录 D.2。

### F.1 阶段职责与决策权限

Workflow 定义每个阶段的金融专属操作；Harness Core 控制某阶段收到哪些信息、可调用哪些工具，以及运行能否基于其输出改变状态。表 15 汇总各阶段的输入、允许的动作、必需证据与决策权限；下文段落解释三条边界如何贯穿这些阶段。可选的优化路径单独在附录 D.4 中详述。

**信息边界。** 对每个面向智能体的阶段，这条边界把"提供给模型的上下文"与"为治理和审计保留的信息"分开。Runtime Card 保存 agent_visible 与 harness_private 两类字段：前者含当前目标、任务意图、公开假设与反馈、约束、允许的工具与所需输出；后者记录上下文预算、策略备忘、哪些信息被排除在请求之外、以及指向源产物的引用。完整的卡片为审计保留；每个阶段的请求构造器用智能体可见字段组装模型消息。因此，信息边界是在"该阶段的请求被组装时"生效的，而不是靠把完整审计记录交给智能体。

**动作边界。** Runtime Card 中的允许工具清单，在"向智能体暴露工具"与"调用被触发"两处都被强制。工具定义及其执行处理器只注册一次，但只暴露该阶段被允许的工具。执行调用之前，运行时会再次检查权限；若调用被拒绝，运行时先记录所请求的工具、参数、允许工具清单与拒绝原因，再返回一个工具错误。附录 C.2 描述 Action 消融如何改变工具暴露、指导与强制方式。

**提交边界。** 产出候选文件或报告本身并不授权运行改变状态。受守卫的运行时检查"提议的转移是否被允许"以及"其所需证据是否齐备"。在候选评审处，Judge 建议接受、恢复或停止，它本身并不改变运行状态。当获授权的路径通向冻结时，freezer（冻结器）会先检查 Judge 验收、验证、回测与必需产物，然后才复制关键文件并记录其哈希。冻结成功后，记录运行完成的是运行时，而不是 freezer。

在启用用印强制（seal enforcement）的配置中，冻结还会检查候选与支撑证据是否仍与已批准版本一致。commitment seal 记录这些文件的路径与内容哈希；freezer 在提交前用该记录核对当前文件。财务绩效始终与这些工程前提分离。附录 C.2 与 C.3 的配对消融与受控干预评估这些边界。

### F.4 市场与回测协议

所有报告的财务结果都由一个确定性的 A 股评估器重新计算，而不是取自各系统自带的回测器。这使价格基准、交易成本、流动性限制与市场规则在每次比较内保持固定。

FinRelBench 快照使用 2025-12-31 的中证 500 成分股清单，日频覆盖 2025-01-02 至 2026-05-29，分钟覆盖 2026-04-29 至 2026-05-29。数据提供方为 Tushare；快照清单记录校验和，用以标识导出的清洗数据与量化数据文件。各任务在该覆盖范围内申请其所需的历史。评估窗口之前的日频历史为计算任务信号提供预热观测。当任务要求复权价时，评估既检查复权因子输入，也检查计算这些价格的代码。单独的边界测试使用冻结的 100 只中证 100 股票池，检查候选能否通过回测。FinResearchSuite 的时间窗口与中证 500 成分股快照见附录 D.2。

**F.4.1 信号时点、组合转换与执行约束。** 在收盘生成的日频分数不能在该收盘价成交；它们被转换为下一交易日的订单，执行价格取 09:30–10:00 的成交量加权均价。除非公开任务规定了别的构建规则，日频打分输出构成等权、只做多、总敞口不超过 100% 的组合。

日内订单输出保留其声明的股数、名义金额或权重。执行在"信号时间之后至少一分钟的第一个可用分钟 bar"上进行，价格基准按任务所述。两条时点规则都防止在产生信号的那个 bar 上成交，且对同一案例内的各系统同等适用。实际成交仍受下列账户与市场约束限制。

每个账户起始资金 CNY 1,000,000。评估器收取 3 个基点的券商佣金（最低 CNY 5）、卖出 5 个基点的印花税、买卖各 0.1 个基点的过户费。实验默认滑点为 5 个基点；过滤型反转案例有预指定的 8 个基点覆盖值。

除交易成本外，成交还受流动性、可用现金与市场规则约束：每个订单在其执行窗口或分钟 bar 内至多消耗市场成交量的 10%；账户禁止现金为负，买入的股票在下一交易日之前不得卖出（T+1）；同时强制停牌、每日涨跌幅限制与 100 股整数倍的买入，但允许零股余量的完整清仓。

案例专属的回看、组合与执行约束在同一任务内对各系统固定。这些设置定义共同的评估条件；只有当它们被写进公开请求时，才进入需求忠实度评估。
