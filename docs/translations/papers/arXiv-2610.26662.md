## 摘要

LLM 交易 agent 几乎全部在回测和自治基准测试框架（benchmark harness）中被评估。部署中的动作不可逆，由此引出一个不同的问题：谁来验证 agent 的动作，每个验证者在结构上能够捕获哪类失败？我们报告 AllPath——一个部署在实盘模拟经纪账户（paper-brokerage account）上的个人 LLM 交易 agent。系统用确定性规则引擎监控持仓，每晚复盘当天，并提出对其自身交易策略的修订。

验证被拆分为三层。代码验证那些绝不能依赖判断的部分：确定性闸门强制执行风险限额，并阻止任何未通过完整性检查的策略修订。agent 在固定边界内自我验证：其夜间复盘设有迭代上限，且没有任何可以实际执行动作的工具。人类验证判断，通过展示每个提议当前状态的审批界面。

我们还在实盘系统上比较了两种针对 agent 自我修订的验证策略：前两周半，每一次自我修订都由人工把关；随后五周，反思提出的修订在通过同样的代码闸门后自动应用，而操作者的聊天通道全程保持人工把关。每一层都捕获了不同类型的失败。代码闸门没有拒绝任何提议，其作用在于保持修订的一致性。人工否决了两个通过全部代码检查的提议，两者都源于对市场的分歧；后来还移除了 agent 自行添加的 19 条规则中的 11 条，中位滞后为八天。最具启发性的生产事故——例如策略被悄悄置于无人监控状态——通过了所有闸门；由操作者手工发现，而每次的修复都是一个让该状态可见的接口改动。我们贡献了分层架构、两种运行模式的实盘记录，以及生产事故分类学；这些在回测中都无法观察到。

## 1 引言

LLM agent 如今已能在回测和模拟市场中熟练交易 [24, 25, 28, 30]，近来一波实时市场基准 [1, 5, 16, 27] 向它们推送真实行情数据。几乎所有这类工作都把 agent 当作一个不受约束的决策函数来评估：输出即动作，运行结束时，什么也没有发生。

生产环境要宽容得多。在工业级电商搜索中我们发现，一个能在离线条件下提升排序质量的 LLM 无法原样上线服务：延迟和稳定性要求先把它蒸馏成更小、更可预测的模型再部署 [15, 26]。这些约束是关于「服务」的。一个已部署的交易 agent 继承它们，又加上自己的两条：一笔错误下达的订单是不可逆的成交，而不是质量下降的排序；而一个会自行修订交易规则的 agent，可能在任何人查看之前就把一次糟糕的判断复利放大。

本文在一个持续运行的系统上研究这个验证问题。AllPath¹ 是一个个人 LLM 交易 agent，自 2026 年 8 月起持续运行在实盘模拟经纪账户上。它通过确定性规则引擎监控持仓，与操作者对话，维护一套受治理的股票、策略与提炼教训的记忆（§3），每晚复盘当天并提出对其策略的修订。没有任何单一验证者能覆盖这一切。一笔订单是否超过风险上限是算术问题，属于代码；一个止损是否过紧是判断问题，属于人。agent 的夜间自我复盘介于两者之间：只有当 agent 不能依据自己的结论采取行动时，它才有用。§4 把系统中的每一个动作分配给这三类验证者之一。

¹ 代码：https://github.com/dukesky/allpath-trading-agent ；部署公开日志（模拟账户）：https://trading.all-path.com/trading/journal

我们还利用这次部署比较了两种针对 agent 自我修订的验证策略。系统用一个配置开关同时支持两者：反思提出的修订可以等待人工批准，也可以在通过代码闸门后自行生效。我们把第一种策略跑了两周半，期间操作者批准了四个提议、否决了两个；随后切换到第二种跑了五周，以一个回撤断路器兜底：56 次修订被应用，闸门一次也没有拒绝。两种策略下，操作者的聊天通道都保持人工把关；通过该通道，操作者后来移除了 agent 自行添加的 19 条规则中的 11 条。

本文有三项贡献。第一是一个带有实际生产运行时间的分层验证架构：按提议者、验证者和闸门机制对自我修订交易 agent 中的每一类动作做分解（表 1），并给出让每一层真正承重的设计规则。第二是关于自我修订的两种运行模式的实盘记录：来自人工把关期与自治期的运行证据，包括人工否决了闸门判定无懈可击的提议的那两个案例（§5）。第三是生产事故分类学：来自这次部署及其构建过程的二十起事故，没有一起能在回测中观察到，每一起都被归纳为一条设计规则（§6）。

全文的评估方式都是运行层面的：提议流、闸门触发、决策延迟、事故。据我们所知，此前没有已发表的工作在同一个实盘 agent 上同时报告人工把关与自治两种运行方式；§2 给出这一说法的依据，§7 说明其边界。

## 2 相关工作

**LLM 交易 agent。** 一条快速成长的研究路线为 LLM agent 配备记忆、工具和多智能体结构用于交易：分层记忆与角色设计（TradingGPT、FinMem）[11, 28]，多模态工具增强 agent（FinAgent）[30]，辩论式多智能体框架（TradingAgents）[24]，开放 agent 平台（FinRobot）[25]，以及模拟市场（StockAgent）[29]；两篇综述梳理了这一领域 [3, 22]。这批文献以回测或模拟为中心，agent 的输出是不受约束的最终动作。更新的一波实时市场基准（StockBench、LiveTradeBench、Agent Market Arena、AI-Trader）[1, 5, 16, 27] 推送实时数据，但让 agent 完全自治地运行，其中几个把「无人干预」当作设计目标而非待研究的变量。我们的问题在别处：一个已部署 agent 的动作是如何被验证的。

**没有利害的自我改进。** Reflexion、Self-Refine 和 Voyager 确立了 agent 通过批评和修订自身行为来改进 [13, 17, 20]，如今的自我演化 agent 综述已经能列出整个设计空间 [6, 9]。在这些设定下，一次糟糕的自我修订只代价一次重试；近期工作开始追问当代价更高时会发生什么 [12]。我们的反思循环是这一家族中刻意保守的一员：它对未来行为唯一的杠杆，是一个经过把关、可审计的修订提议，其授权与生命周期字段由代码冻结（§4.1）。

**Agent 监督与治理。** 可扩展监督方案（辩论、放大）[2, 10] 面向超出人类直接评估能力的系统验证；一个互补的风险分析追问层层叠加的安全机制何时会同时失效 [4]。更贴近实践的有：运行时强制 DSL（AgentSpec）[21]、守护 agent（GuardAgent）[23]、自主级别分类学 [8]、以及接口介导的监督（Magentic-UI；regulable-UI 模式）[7, 14]——它们各自提出了我们所部署栈中的一层。据我们所知，还没有任何一个被组合进同一个具有实质性动作的已部署系统，也没有任何一个在同一实盘 agent 上同时报告人工把关与自治运行。

**交易系统安全。** 我们的确定性层继承自前 LLM 时代的市场实践：交易所级熔断 [18] 与美国证监会要求券商侧盘前风险控制的市场准入规则 [19]。贡献不在于这些机制本身，而在于它们在 agent 循环中的位置：agent 无法与之讨价还价的限额、一个通过降级自治而非中断交易来发挥作用的回撤断路器，以及架在 agent 自我修改通道上的完整性闸门——这是前 LLM 时代的风险控制从未需要考虑的界面。

## 3 AllPath 系统

AllPath 是一个个人 LLM 交易 agent：一个确定性规则引擎监控持仓，一个聊天 agent 与操作者交谈，一个夜间反思会话复盘当天并提出修订，而每一个提议与它的执行之间都隔着同一个审批队列。它是一个单操作者的生产系统，而不是基准测试框架：它按实盘市场价格持仓、发送通知给操作者（错误会让操作者付出时间代价）。图 1 展示了架构。图中叠加的验证机制（详见 §4）位于每一个动作可能变得不可逆的边界上。

图 1：AllPath 架构。每一条从提议到不可逆动作的路径都至少穿过一个验证层；颜色标记验证者类别（蓝：确定性代码闸门；橙：受强制边界的 agent；绿：人类判断）。实线蓝色箭头是完全自治的路径；绿色箭头经过操作者。虚线断路器在回撤过大时把自治修订路径降级回人工确认。（原文第 3 页）

### 3.1 策略即带版本的文件

一个策略是一个人类可读的文件，包含四部分：thesis（为什么持有这个头寸）、rules（针对价格与指标的带类型入场、出场、止损条件）、授权级别（authorization）和状态（status）。这个文件是唯一事实来源（source of truth）。每次变更都会产生版本，快照进入一张只追加的历史表，并逐字渲染给人（web UI）和 agent（会话上下文）两端。授权按规则后果设置：notify 通知人类，confirm 把订单排入待批准队列，auto 在风险限额内执行，hard 标记该规则为机械执行、agent 无自由裁量权。状态控制监控：sentinel 只监控 active 策略。图 2 展示了仓库随附的示例文件。

图 2：一个策略文件（仓库随附的示例，已缩略）。thesis 与 rules 是修订可以改变的部分；authorization 与 status 对自我修订冻结（§4.1）。（原文第 4 页）

```yaml
id: example
name: NVDA long-term hold - AI infrastructure play
status: draft
version: 2
authorization: confirm ***
thesis: 'Bullish on NVDA''s leadership in AI chips
  and data center hardware. 18-24 month horizon.
  [...] Invalidation: AI chip demand deterioration,
  significant market share loss to competitors, or
  datacenter revenue growth <15% for two
  consecutive quarters.'
position:
  ticker: NVDA
  target_weight: '0.2'
  max_weight: '0.25'
rules:
- id: initial-entry
  type: soft
  condition: position_weight == 0 and price < 205
  action: buy $8000
  state: armed
- id: stop-loss
  type: hard
  condition: price < 170
  action: sell all
  state: armed
- id: take-profit-1
  type: soft
  condition: pnl_pct > 40
  action: sell 30%
  state: armed
[...]
```

### 3.2 Sentinel：确定性看门人

一个调度守护进程在交易时段内按固定间隔（数据窗口内为 15 到 60 分钟）用实盘行情评估每条活跃策略的规则。规则评估是纯代码，模型不在回路中。当一条规则触发时，其后果按授权执行：auto+hard 直接通过风险闸门执行，confirm 规则则把一个带有完整快照（触发价、规则文本、意图）的待处理订单排入队列等待人工批准。一次性规则状态防止重复触发；已触发的触发器必须手工重新布防。同一个守护进程还运行夜间流水线——组合摘要、记忆归并与反思会话（§3.4），每一步都靠持久化的日期标记实现崩溃可恢复。规则也可以通过同一闸门下达只做多的期权订单；按语法，这类订单只对 auto+hard 规则开放，因此期权界面完全是自治的。

### 3.3 Agent 会话：聊天与复盘

聊天 agent 是操作者在 web 或 Telegram 上的对话接口。它拥有用于市场数据、组合、日志、策略文件和记忆搜索的读取工具，以及一个很短的动作工具列表：提议订单（进入与 sentinel 订单相同的待处理队列）、提议策略修订、受防护的记忆写入。它不能直接下单，不能编辑策略文件，也不能批准任何东西，包括自己的提议。复盘 agent 用重新生成的上下文（§4.3）渲染待处理条目，并记录人类的批准或拒绝决定；批准也可以通过通知中的一次性令牌链接完成（§4.1）。

### 3.4 Reflection：有界的夜间自我修订

收盘后，一个独立的反思会话复盘当天。它接收一份代码生成的简报（按执行价的成交、规则状态变化、持仓变动、待处理队列状态、完整策略文本、近期报告摘要），在迭代上限内用只读工具调查，并写出一份结构化报告。它对未来行为唯一的杠杆是 propose_strategy_revision，可以改变策略的 thesis 和 rules，但绝不改变其 authorization 或 status（§4.1）。在人工把关模式下，这类提议与任何其他提议一样在队列中等待。在自治模式（§5）下，来自反思的提议通过同样的机械闸门后立即生效，并以组合回撤熔断器作为模式级兜底：若权益回撤超过配置阈值，auto-apply 降级为 confirm，并保持降级状态直到有人工复位。

### 3.5 记忆

agent 的记忆是一组人类可读的 markdown 文件，分四个整理层级：跨账户共享的操作者画像、按策略的笔记、按股票的笔记、以及提炼出的教训。每一层的大小预算只有几 KB，这迫使系统做归并而非堆积。agent 恰好只有一条写入路径：一个受防护的工具，它做入口级编辑、拒绝注入式内容，并把每次变更的 diff 记入日志；操作者可以直接读写同一批文件。一张只追加的观察日志在整理层级之外记录日常事件。夜间归并把观察日志蒸馏进各层，且归并标记只在成功摘要的日期之后推进，因此崩溃后会重新归并而不是跳过。在数据冻结时，模拟账户持有 141 条教训、37 条股票笔记和 36 条策略笔记，全部由 agent 在这些约束下写成。附录 B 展示了一条教训条目和一份反思报告节选。

### 3.6 部署形态

生产运行在单台消费级机器上，位于无公网端口的私有网络之后，由进程监督器在失败时重启。操作者通过令牌认证的 web UI（仪表盘、策略、待审批、可回放反思记录的报告、日志）和一个用于通知、聊天与批准链接的 Telegram 频道访问它。系统用同一个 agent 和同一条流水线运行两个账户。模拟账户通过经纪商的模拟交易 API 交易，操作者按它采取行动，它的错误会消耗操作者的时间。图 1 展示了架构，图中叠加的验证机制（详见 §4）位于每一个动作可能变得不可逆的边界上。

**模型。** 数据窗口内每个 agent 会话都通过一个 API 网关运行 Claude 家族模型：反思与记忆归并用 Claude Opus 5，聊天用 Claude Sonnet 5，sentinel 的分析层用 Claude Haiku 4.5。模型名是配置而非代码；验证栈不依赖于由哪个模型提出提议。

**产物。** 系统开源。² 每个交易日收盘后，夜间流水线把模拟账户的摘要、交易和反思成文发布到一个公开日志页³，该页面自 2026 年 8 月 31 日起持续运行，覆盖 §6 所报告数据窗口的大部分。本文的计数来自系统内部账本，账本还保存操作者的策略文件、并不公开；公开日志是读者可以据以核对的日级记录。

## 4 验证栈

系统的设计前提是：对于动作不可逆的 agent，没有任何单一验证者是充分的。我们按「每个验证者在结构上能捕获哪类失败」来分解验证，并为每一类动作在该分解中给出明确的一行（表 1）。由此得到三类验证者。

表 1：系统中每一类动作，按提议者、验证者与闸门机制分解。（原文第 6 页）

| 动作 | 由谁提议 | 由谁验证 | 闸门机制 |
|---|---|---|---|
| 股票订单（confirm 授权） | Sentinel 规则或 chat agent | 代码，然后人 | 风险闸门限额 → 待处理队列 → 人工批准（web/链接），一次性令牌 |
| 股票订单（auto 授权、hard 规则） | Sentinel 规则 | 仅代码 | 风险闸门限额；一次性规则状态；回撤断路器作为模式级兜底 |
| 期权买入订单 | Sentinel 规则（按语法仅 auto+hard） | 仅代码 | 权利金 + 敞口限额；到期安全扫描；断路器 |
| 期权平仓 | Sentinel 规则 / 到期扫描 | 仅代码 | 从不因价值被阻断（降低风险）；仅受每日笔数限制 |
| 策略修订（人工把关模式） | Reflection 或 chat agent | 代码，然后人 | 提出时解析 + id/版本/冻结检查；应用时逐字节陈旧性 + 复查；陈旧 chat 草稿被 superseded 顶替；人读取重新生成的 diff |
| 策略修订（自治模式） | Reflection | 仅代码 | 相同的机械闸门，自动应用；范围限于反思来源的行；断路器兜底 |
| 策略生命周期（激活/暂停） | 仅人 | 人，带代码护栏 | 两步确认；原子写入 + 版本快照；已触发器重新布防警告 |
| 记忆写入 | 任何 agent 会话 | 代码（注入防护） | 受防护的工具路径；外部内容围栏；分层文件 |
| 通知 / 报告 | 系统 | 代码 | 永不抛出契约；按通道隔离；失败从不阻塞流水线 |
| 交易参数（限额、模型、密钥） | 仅人 | 人 | 仅设置页 / env 文件；agent 永不可写；paper-vs-real 标志不可网页编辑 |

### 4.1 代码验证绝不能依赖判断的部分

确定性闸门是唯一不可能被说服的验证者。我们把它们放在失败明确且机械的位置上。

- **风险闸门。** 每一笔订单都要通过一个确定性闸门，无论它由用户在聊天中提出、由 sentinel 规则触发，还是（对期权而言）被自治地选中。闸门强制执行单笔订单价值限额、每日交易笔数限额，以及对期权买入的权利金限额和期权总敞口相对权益的限额。闸门是代码，agent 无法与之讨价还价。平掉期权头寸从不会被价值限额阻断：平仓降低风险，而一个能把操作者困在头寸里的闸门本身就是危险源。

- **修订完整性闸门。** 策略修订是 agent 修改自身交易规则的唯一路径，只有三项检查全部通过才会被应用：(i) 当前文件与计算该提议所依据的基准逐字节一致；其间任何微小变更都会使提议作废，而不是被静默覆盖。(ii) 提议的版本严格递增，从而保持审计轨迹顺序的真实性。(iii) 只允许提议改动 thesis 和 rules。授权（谁可以行动）与状态（策略是否在运行）被冻结：自我修订可以收紧止损，但绝不能把自己提升为自治交易，或静默关闭监控。任何检查失败的提议都退回待处理队列。其失败模式是「什么都没发生」，绝不是「发生了某种微妙的不同」。

- **陈旧草稿的顶替。** 如果某个策略已有一条较早的 chat 草稿仍在待处理，此时又收到一条更新的、来自 chat 的修订，旧行会被重新标记为 superseded，其处理被加上时间戳，其批准令牌随之失效。通知中过期的批准链接无法再应用过期草稿，审计轨迹记录这次顶替。

- **幂等与至多一次语义。** 夜间流水线靠持久化标记实现崩溃可恢复：一个报告日期只能被产出一次，记忆归并标记只在成功摘要之后推进。来自远端频道的入站聊天消息在处理之前先推进偏移量，因此回合中途崩溃至多丢失一条可见消息，绝不会重放一个不可见的重复消息——后者可能重复提议一笔订单。

- **一次性批准凭据。** 链接批准令牌按次审批、只以哈希存储、24 小时过期、首次使用即作废（包括执行失败时）。一次泄露的通知至多暴露一个本已可见的决定，绝不会暴露一个会话。

### 4.2 Agent 自我验证，但仅在强制边界内

夜间反思会话用 agent 的完整只读工具集复盘当天，并写出结构化报告。它作为自我验证的价值来自那些边界。

- **没有动作工具。** 反思注册表包含市场、组合与日志读取器、受防护的记忆写入和 propose_strategy_revision。它没有下单、没有批准、也没有文件写入。测试通过把反思工具集与动作注册表做 diff 来钉死这一排除。

- **有界搜索。** 一个会话至多有 𝑁 次工具迭代（默认 12 次），包括报告解析失败时允许的一次纠正性回合。早期草稿曾在纠正回合中悄悄把预算翻倍，被评审发现；上限现在是会话的属性，而不再是回合的属性。

- **围栏化的确定性简报。** 会话以一份代码生成的简报开场（按真实执行价的成交、规则状态变化、持仓当日变动、待处理队列状态、完整策略文本）。每个块都包裹在外部内容围栏中，使工具返回的文本不会被误当作指令。agent 从事实出发，把预算花在调查上。

- **可审计的记录。** 每个会话是一段独立的对话，其每一次工具调用都可以从 Reports 页回放。无法被审计的自我验证与凭空编造无异。记录让人类抽查 agent 的勤勉程度，也是 §6 中会话账目的基础。

### 4.3 人类验证判断——前提是接口如实呈现

人类是判断类决策唯一的验证者：这个止损是否过紧，这个论点是否仍然可信。系统的义务是让这种验证真实发生，而我们的若干事故（§6）恰恰是这一义务的失守。

- **重新生成而非存储的 diff。** 待处理修订的 diff 在渲染时针对当前文件重新计算，当文件已变动时给出显式的「基准已陈旧」警告。人类看到的是「此刻批准意味着什么」，而不是 agent 提出提议时所看到的。已处理的修订渲染其冻结的历史 diff，并如实标注。

- **审批卡片上的决策级上下文。** 附录 B 的表 5 列出卡片的每一个字段。每张卡片显示触发时价格、带当日方向着色的实时价格、自触发以来的偏差、按名义金额估算的股数，以及一行市场状态（「market closed: fills at next open」）。这些正是人类一眼看出一笔不再合理的订单所需要的事实。

- **准确的标签。** 提交时间与成交时间在所有地方（日志、仪表盘、agent 自己的系统提示、长期记忆事件）都是不同标签的不同列；此前发生过一次事故：一个以成交时间面目出现的提交时间戳让操作者误解了 17 小时。「Fill pending」只在轮询窗口内被声明；超出窗口后系统会说「status unconfirmed」。

- **让沉默可见。** 状态被排除在监控之外的策略，在每个界面上都佩戴一个常驻的「not monitored」徽章。这个徽章源自部署中最具启发性的事故：全部四条在运行的策略在 draft 状态下停留数日、止损从未布防，而每个页面都照常渲染它们。sentinel 的心跳行（「last tick 𝑁 m ago」或「monitoring paused: market closed」）如今会说明是否有人在看着，而此前这个问题的答案取决于省略。

### 4.4 验证构建者本身

上述栈本身是在对抗性评审下构建的。每一次变更都要经过一个被要求执行攻击场景的独立评审者才能发布。在合并前，该评审捕获了一次静默回退的 Critical（一个陈旧的同级提议，其批准会撤销一次已生效的止损收紧）和一系列 Important（一个授权翻转漏洞、修订应用器中的路径穿越、已删除策略的复活）。我们把它列为一条范围主张的证据：其中若干漏洞只有真正执行失败才能发现，没有一个会在回测框架中浮现。

## 5 两种运行模式下的自我修订

我们按设计在同一实盘部署上以两种验证模式运行自我修订通道：两周半由人工把关每一次自我提出的变更，随后五周只留机械闸门。本节描述这一循环以及两种模式各自的运行形态，§6 报告数字。

### 5.1 修订循环

一个修订提议——无论来自夜间反思会话还是操作者的聊天 agent——在提出时即被校验：必须能解析、指向一个已存在的策略、版本严格递增、且不触碰 authorization 和 status。随后它连同其计算所依据的基准文件快照进入待处理队列。在应用时，完整性闸门再次运行，这次针对线上文件：逐字节陈旧性、版本单调性、字段冻结（§4.1）。两种模式的差别只在于这两个检查点之间由谁扣动扳机。

### 5.2 模式 A：人工把关（8 月 11–27 日）

每一个提议都要等操作者。此窗口内共有六个来自反思的提议，四个被批准、两个被拒绝，而机械闸门对两个被拒提议均无异议。两者形态相同：在一轮价格上涨使「只回调入场」的阶梯变得够不着之后，agent 提议增加一个贴近现价的买入批次（其中一例还上调了持仓权重上限），书面理由把这次加仓框定为支撑位回踩而非动量追涨。操作者两次都拒绝了，理由在提议中无处可见：一个先验信念——半导体是周期性的，正在发生的上涨只是周期内的摆动而非持久的重估，而面对够不着的阶梯，正确做法是等周期再次光顾。

¹ 该分歧正好定位了人工把关的独特贡献。操作者的回忆记录于 2026-09-12；拒绝本身在评审账本中有时间戳。

agent 的论证内部自洽、机械合规，否决来自一个 agent 并不持有的世界观。人类层之下的任何闸门都没有被设计来裁决两个自洽论点之间的分歧。

本窗口的标志性案例是部署中的第一次自我修订。反思会话在审计一份新转录的 NVDA 策略时发现，其加仓阶梯用百分比表达持仓权重上限（position_weight < 12），而策略的目标权重是小数（0.2）。上限因此恒真，阶梯的风险限制形同虚设。提议的修复把单位归一（< 0.16、< 0.2），并在 thesis 中写明这一约定。它还移除了动量加仓规则，依据是当天的成交：一次突破加仓把平均成本抬高 2.4%，却让回调阶梯更够不着。操作者按原样批准了。这正是循环按设计运转：一个影响重大的 bug——其类型回测根本看不到，因为该文件从未被执行过——由有界自我复盘发现，并经由人工闸门修复。

### 5.3 模式 B：自治（8 月 27 日晚–10 月 2 日）

一个配置开关界定了这次变更。自 8 月 27 日晚起，通过机械闸门的反思来源提议立即生效，回路中不再有人。操作者的聊天通道全程保留人工把关，因此两条验证路径在同一账户、同一市场下并行运行。自 9 月 14 日起，影子账户在同一开关下运行它自己的夜间反思。

在这一模式下，反思通道自动应用了 56 次修订，模拟账户 32 次、影子账户 24 次，每次都在提出后约两分钟内完成。完整性闸门一次也没有拒绝。人工把关的聊天通道在同样的几周里处理了 57 个提议：53 个批准、1 个拒绝、3 个因 superseded 而被顶替。顶替闸门在 9 月 8 日触发，三条陈旧 chat 草稿被重新标记而非静默替换（§4.1）。

### 5.4 模式级兜底

自治以一个回撤熔断器为条件。若账户权益从其跟踪峰值下跌超过配置比例，auto-apply 降级为 confirm：队列和闸门继续运行，但人回到回路中。触发状态会一直保持直到人工复位，且不会自动重新布防。该断路器在整个模式期间处于布防状态但从未触发，因此这个兜底属于设计的一部分，却没有被事件检验过。

### 5.5 如何解读这组对比

两种模式是先后相继的，其间市场发生了变化。可用的对比有两个：反思通道上模式 A 对模式 B，以及模式 B 内部自治的反思通道对人工把关的聊天通道。§6 对两者做量化，§7 说明它们不能证明什么。

我们把这解读为监督在时间上移动，而非消失。反思通道上的闸门撤掉之后，人类并没有停止审阅 agent 的规则变更；审阅发生在事后，大约一周后，通过另一条通道。完整性闸门不可能介入，因为这些规则每一条都是形态良好的。移除并不证明该规则是错的（操作者可能因其他原因重构一个策略），所以我们报告计数和滞后，而不下判词。

## 6 运行实证

### 6.1 修订流水线的量化

图 3 按日期、来源和结果展示数据窗口内的每一次策略修订。截至 10 月 2 日，系统共处理 119 个修订提议：模式 A 的六个反思提议（4 批准、2 否决），随后是模式 B 的 56 次自动应用的反思修订，以及并行的 57 个人工把关 chat 提议（53 批准、1 拒绝、3 作为 superseded 被顶替）。

图 3：数据窗口（8 月 11 日至 10 月 2 日，两个账户）内的每一次策略修订，按日期、来源和结果。模式 B 只自动应用反思来源的提议；chat 通道全程保持人工把关，从而给出一个模式内的对照。（原文第 6 页）

有两个运行层面的事实框定了这组对比。其一，人工验证有延迟。模式 A 的六个决定从提出到处理的中位时间为 8.8 小时，范围从 11 分钟到 80.7 小时，最长的一个横跨一个周末。一个由人工把关的夜间自我修订循环，实际上是一个次日上午的循环；这对 thesis 级别的修改可以接受，也是我们测试自治模式的动因之一。在模式 B 中，同类提议在约两分钟内生效。其二，窗口内每一次否决都来自人：模式 A 中对反思提议的两次，模式 B 中对 chat 提议的一次。到达机械闸门的东西，闸门一个也没有拒绝。观察到它们的贡献是完整性——顶替三份陈旧草稿、保持授权冻结——而不是过滤。各层捕获的是互不相交的失败类别，这正是设计前提。

订单通道更薄。共有 12 笔股票订单经过审批队列，8 月 10–18 日五笔、9 月 14–28 日七笔；操作者批准十一笔、拒绝一笔。其余全部订单流来自 auto+hard 规则，只经过代码层。因此本文的模式比较建立在修订通道上。

### 6.2 自治修订改变了什么，以及后来人类撤销了什么

56 次自动应用的修订涉及 20 个策略。每一次都重写了策略的 thesis；49 次还编辑了现有规则（67 处条件编辑、19 处动作编辑、12 处状态变更），16 次新增规则（共 19 条），6 次删除规则（共 11 条）。在卖出侧价格阈值的编辑中，方向并不一致：四次把止损移得更靠近市场，五次移得更远。因此自治通道在两个方向上都不是单向棘轮；它随价格移动重新锚定水平。

更能说明问题的是之后发生的事。agent 以自己名义添加的 19 条规则中，11 条后来被操作者通过人工把关的 chat 通道移除，中位滞后 8 天（范围 1 到 17 天）。最大的单一案例：8 月 31 日反思会话一次性给四个策略添加了 salvage-options 出场规则；9 月 8 日操作者把四个全部移除。另有一对 agent 添加的规则由后续反思会话自己移除。被修改过的条件从未被回退到先前的值。

### 6.5 Reflection 的可靠性与账目

窗口内全部 52 个夜间反思会话（模拟账户 37 个、影子账户 15 个）都完成并产出了可解析的报告。存储的记录每个会话 23 到 44 条消息（中位 35），可从 Reports 页回放。仍有一个账目缺口：按会话的 token 计量对 chat 和记忆层做了埋点，对 reflection 没有，因此我们报告会话规模与结果，而不是美元成本。

## 7 局限

**一个系统、一个操作者，而操作者是作者之一。** 这是一个单案例研究，我们分析其判断的人类验证者正是本文第一作者。§5 中的拒绝理由是自我报告的（与决策同时入账、事后解释）。每一个计数、diff 和时间戳都来自系统只追加的账本，但选择与解释出自我们。

**模拟盘交易。** 成交是真实市场的，但资本没有风险；操作者的利害是注意力与自尊，不是钱。财务压力下的人类闸门可能在两个方向上表现不同（更警觉，或更焦虑而越过闸门）。代码闸门对这种区别漠不关心；人类层的发现应被读作对该现象的下界估计，而非测量。我们不报告该账户的收益。本文没有任何主张依赖其符号，而一个 7.5 周的中等期限策略窗口在统计上无法支持任何方向的绩效主张。这正是评估必须是运行层面的原因。

**自然实验，而非实验。** 两种模式是先后相继的；8 月的上涨与 9 月的行情不同；提议构成随市场变化。模式 B 内部 chat 与反思通道的对比共享同一个市场，从而只对该对比的混淆因素形成约束；A 对 B 的对比则完整携带了这一混淆。因此我们只做存在性主张（「人工闸门否决了任何机械闸门都不可能否决的提议」「这些事故发生了，并在这里被捕获」），并报告描述性统计；我们不主张某一种模式可测量地更安全。

**规模与范围。** 一个 7.5 周的窗口、119 次修订、一个经纪商、一个模型家族、一种资产构成（美国股票加只做多的期权）。断路器从未触发，因此模式级兜底未被事件检验。只有 12 笔订单经过人类队列（§6），因此模式比较建立在修订通道上。

我们相信可泛化的是形态，而不是阈值：按失败类别对验证的分解（表 1）、对自我扩张自治的冻结、把准确的接口当作验证前提、以及表 3 中的事故类别。每一条都是具有不可逆动作的已部署 LLM agent 的属性，没有一条特定于这份代码库。

## 8 结论

我们追问谁来验证一个交易 agent，并以一个已部署系统的分解作答。代码验证绝不能依赖判断的部分；agent 只在强制边界内自我验证；人类验证判断，通过必须呈现系统真实状态的接口。让同一个实盘 agent 先后以人工把关、再以自治方式运行，显示出各层捕获互不相交的失败：代码闸门保持修订一致、一个也没有拒绝，而人类两次因对市场的看法否决提议。给我们教训最多的生产事故通过了所有闸门，由操作者手工发现；每一次修复都是一个让状态可见的接口。对动作不可逆的 agent 而言，验证不是你添加的一层，而是你设计的一份分解，而人类在其中的位置是判断——下方任何一层都无法替它吸收。
