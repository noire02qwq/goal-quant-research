## 摘要

随着计算机使用 agent（computer-use agent，CUA）走向跨越多个应用的长时程（long-horizon）工作流，未被察觉的错误会悄悄破坏持久状态，并在后续动作中引发连锁失败。可靠的错误检测与恢复因此成为构建鲁棒 CUA 的关键瓶颈。然而，现有基准主要关注端到端任务表现，对 agent 能否在执行中发现并恢复错误提供的洞察很有限。少数评估恢复能力的基准大多依赖人工注入的错误，而这类错误未必反映真实 agent 策略所诱发的失败类型或失败视界。这种错配既限制了评估的真实性，也阻碍了系统性的进展。

本文提出 CUA-Recovery——一个覆盖多个桌面应用的测试集与训练集。我们用 ReRail 构建该基准：ReRail 是在持久桌面环境中合成时程任务与轨迹的框架，它把 MyPCBench 的任务组装成带可执行 ground truth（基准真值）的长时程工作流，收集多个策略经验证器（verifier）确认的失败，并把它们变成经过验证的恢复轨迹。ReRail 产出 CUA-Recovery：包含一个人工核验的测试集，涵盖 100 个任务上的 2,250 个错误状态；以及一个训练集，涵盖 377 个任务上的 8.6K 条轨迹。

测试集上的评估显示，agent 既难认出继承来的错误，也难完成任务。在六个 agent 与六个接管深度上，Error Awareness Rate（EAR，错误感知率）最高只有 44.0%，Pass@3 最高只有 25.5%。在训练集上微调 Qwen3.5-35B-A3B 之后，它在留出的恢复状态上平均 EAR 从 19.9% 升到 35.2%，Rubric Score（评分表得分）从 5.0% 升到 16.1%；在 MyPCBench 与 Odysseys 上 Pass@3 分别提升 15.3 和 10.8 个百分点，说明这些训练轨迹既有助于恢复，也有助于从干净状态完成任务。代码见 https://github.com/xu-hu-2002/CUA-Recovery 。

## 1 引言

计算机使用 agent（CUA）通过截图、鼠标、键盘和命令行操作桌面应用，而如今它们面对的评估已是跨越多个应用、数百个步骤的工作流。OSWorld 2.0 把典型任务从大约 30 次工具调用提高到 300 次以上（Yuan et al., 2026），Agents' Last Exam 则收集了约 1,500 条专业工作流（Sun et al., 2026b）。在这两个基准上，最好的 agent 拿到的部分分数都远多于完整完成：OSWorld 2.0 上是 77.7% 对 44.3%，Agents' Last Exam 上是 59.3% 对 34.2%。也就是说，agent 通常能做完任务的大部分，只在少数几步上失败。

（注 1：公开排行榜，2026 年 9 月访问：https://snorkel.ai/leaderboard/os-world-2-0/ 与 https://snorkel.ai/leaderboard/agents-last-exam/ 。）

根源在于持久状态：早期的一个错误动作被写进文件、表格或数据库，后续步骤就在这个结果之上继续搭建。错误发生时几乎从不显形；它要到很多步之后才浮现，而造成它的那一步早已离开 agent 的上下文。图 1 展示了一个真实案例：Kimi-K3 在第 3 步没有打开订单历史，此后一直在这个错误上继续叠加，直到第 43 步 agent 虚报完成时错误才暴露。在这类任务中，agent 能否注意到并修复自己的错误，决定了它能否完成任务。

（原文位置：docs/papers/arXiv-2610.27645.pdf 第 2 页）

**图 1：案例研究——从一次真实的策略引发错误中恢复。** 用户要的是他常点的 Sweetgreen 订单。上排：Kimi-K3 没能注意到并恢复错误；下排：ReRail-35B-A3B 在根因步骤接管，检测到错误并从中恢复。译注（可还原的图内元素）：上排标 error horizon h=40，依次为 step 3 root cause action（本该打开 Orders 了解常点订单，却改用搜索）、step 13 built from the menu（从菜单而非订单历史拼装订单）、step 29 “usual” invented（凭空加了一碗并称其为「常点的」）、step 43 false completion（报告成功，但购物车并不是用户的常点订单）；下排标注「ReRail-35B-A3B 在第 3 步（d=0）接管，继承到根因步骤为止的历史并恢复」，依次为 step 5 opens the Orders page（找到四条过去的 Sweetgreen 订单）、step 6 scrolls to Sweetgreen orders、step 31 checks items in each order（逐单查看菜品；Kale Caesar 出现在过去一半订单中，即为常点项）、step 40 correct completion。

在训练一侧，恢复需要这样一条轨迹：它跟着一个错误从犯错走到修复——agent 犯下错误，错误在许多步里没被察觉，agent 之后找到并修复它。现有 CUA 训练集只覆盖了这个过程的一部分（表 1）。这些轨迹平均 3.8–39.3 步，很少跨越多个应用（有报告的至多 26.1%）。即便包含错误，错误也来自人类示范、合成注入或自我报告，而不是执行策略本身产生的失败。GUI-Reflection 是唯一带显式纠正的数据集，但每条纠正都紧跟在一个注入错误之后。CUA-Recovery-Train 用 60 步的轨迹（其中 67.5% 跨越多应用）填补这一空白：每条轨迹从一个策略引发的失败开始，保留其间带错误的历史，最后以验证器确认的恢复结束。

在评估一侧，长时程基准只给最终结果打分，无法说明 agent 是否在过程中发现并修复了自己的错误。现有数据集与基准同真实的长时程失败有三点不同。（1）覆盖面。多数数据集只含完美轨迹；含错误的那些取自人类示范错误、注入错误或自我报告的失败，且大多是无效点击一类的低层执行错误（Wang et al., 2025; Wu et al., 2025; Jung et al., 2026）。我们标注了 CUA-Recovery-Test 中六个 agent 的 619 次失败，发现真实错误主要出在决策上：规划与感知占根因的 57.3%，而 AgentNet 与 GUI-Reflection 的根因中执行错误分别占 84.3% 与 71.2%（图 3a）。

（2）视界。现有轨迹很短，错误在发生的那一步就可见；而我们标注的错误中有 78.1% 在根因之后三步以上才暴露，中位延迟 17 步（图 3b）。（3）界面。真实的计算机工作是混合的：agent 通过 GUI 检视视觉状态，通过命令行执行精确的批量操作，两者作用在同一份应用状态上。现有资源在两方面不足。其一，训练数据大多只有 GUI 动作（表 1），在其上训练的模型很少见到两种界面配合使用。其二，打分往往依赖截图，而前沿 agent 在有命令行时更偏爱命令行，产出的截图很少甚至没有。在 MyPCBench 上，一旦判分器同时读取终端输出、工具调用响应、GUI 动作日志和截图，GPT 5.5 就从官方报告的 45.1% Perfect Pass（Jang et al., 2026a）升到 85.0% Pass@3。因此，基于截图的打分低估了这类 agent，也无法在同等条件下比较交互方式不同的 agent。

这三点差距构成了我们工作的出发点。首先，我们提出 CUA-Recovery，一个面向长时程计算机使用中错误恢复的基准（图 2）。其测试集 CUA-Recovery-Test 含 100 个任务上的 2,250 个人工核验错误状态，取自六个 agent 的 619 次失败 rollout。对每个状态，agent 在根因之后 0 到 25 步处接管，并且不会被告知发生过错误。我们报告它是否注意到继承的错误（Error-Awareness Rate，EAR）、完成了任务的多大部分（Rubric Score），以及三次运行中是否至少有一次完成（Pass@3）。判分器同时读取终端输出、工具调用和截图，使通过 GUI 与命令行行动的 agent 被同等对待。其训练集 CUA-Recovery-Train 含 377 个任务上的 8.6K 条经验证的恢复轨迹。

其次，我们用 ReRail 构建 CUA-Recovery——一个从真实失败合成恢复数据的框架。ReRail 把每个种子任务转换成可执行的中间表示（intermediate representation，IR），其 gold lineage（真值血缘）固定了每一步的正确值；再把这些任务组装成共享持久状态上的长多应用工作流。gold lineage 免去了注入错误的必要。多个 agent 通过 GUI 与 CLI 执行工作流；ReRail 只保留任务验证器确认的失败，对照 gold lineage 定位每个根因，并在其后若干深度截断 rollout。这样每个错误状态都来自 agent 自己的决策，且接管深度可控。训练时，基座模型 Qwen3.5-35B-A3B 从每个截断点出发，在越来越具体的提示下继续。只有验证器确认该继续部分完成了任务才保留它，随后移除提示——于是模型学会在不被告知的情况下注意到并修复错误。

在 CUA-Recovery-Test 上，六个 agent 在所有接管深度的 Pass@3 至多 25.5%；而且干净启动（clean-start）的成功并不意味着会恢复：Kimi-K3 能从零解决 66.9% 的 MyPCBench 任务，却最多只能注意到自己失败中 18.5% 的错误。值得注意的是，在 CUA-Recovery-Train 上训练能缩小这一差距。ReRail-35B-A3B 的恢复优于其基座模型，在较早的接管深度上于 Kimi-K3 自己的失败超过 Kimi-K3 本身，并把干净启动 Pass@3 从 9.2% 提到 24.5%（MyPCBench）、从 24.1% 提到 34.9%（Odysseys）。

综上，我们的贡献是：

- **CUA-Recovery**：一个由真实策略引发的失败构建的评估与训练基准，面向长时程、有状态的计算机使用工作流，含 2,250 个人工核验的测试状态与 8.6K 条经验证的恢复训练轨迹。
- **ReRail**：一条流水线，把种子任务组装成带 gold lineage 的长工作流，并把验证器确认的 agent 失败转化为测试状态与经验证的恢复。
- **一项对照研究**：表明强劲的干净启动表现并不意味着可靠的恢复，而在 CUA-Recovery-Train 上微调同时改善恢复与干净启动表现。

## 2 相关工作

**面向鲁棒 CUA 的长时程基准。** CUA 基准测量 grounding（界面定位，Cheng et al., 2024; Li et al., 2025）、离线轨迹上的单步准确率（Zheng et al., 2024; Li et al., 2024; Lu et al., 2025c），以及真实环境中的端到端成功率（Bonatti et al., 2024; Xie et al., 2024; Rawles et al., 2025）。近期基准把时程拉长：MyPCBench（Jang et al., 2026a）在持久的多应用状态上构建带人设（persona）的工作流，OSWorld 2.0（Yuan et al., 2026）收集人类要花一小时以上才能完成的任务，Agents' Last Exam（Sun et al., 2026b）覆盖 55 个子领域的专业工作流。这些基准报告任务成功率与部分得分。

鲁棒性基准则施加外部设计的压力源，例如扰动与注入故障（Zhao et al., 2025; Yang et al., 2025b; Bai et al., 2026; Chen et al., 2025; Liu et al., 2026a; Sun et al., 2026a），或对抗性内容（Liao et al., 2025）；AgentErrorBench（Zhu et al., 2025）分析基于文本的 LLM agent 的失败。与我们最接近的是 Bu et al. (2026)，他们研究短时程 GUI 任务上策略引发错误的恢复；由于其数据未发布，我们与其报告的统计量作对比（图 3a）。CUA-Recovery 衡量的是 agent 在任务中途接管后能否发现并修复一个真实错误：其错误状态取自 agent 自己的长时程失败，接管点最深放在根因之后 25 步，已超出 agent 的视觉上下文。

**训练鲁棒 CUA 的数据。** CUA 在人类示范（Rawles et al., 2023; Deng et al., 2023; Wang et al., 2025）与合成轨迹（Xu et al., 2025; Pahuja et al., 2025; Trabucco et al., 2025; Gandhi & Neubig, 2025; Xie et al., 2025; Jung et al., 2026; He et al., 2025）上训练，并从反思数据与 critic 学习错误处理（Wu et al., 2025; Wanyan et al., 2025; Qin et al., 2025），在失败轨迹上自训练（Fu et al., 2025; Yuan et al., 2025），或使用在线 RL（Bai et al., 2024; Yang et al., 2025a; Lu et al., 2025b; Ye et al., 2025）。公开语料都很短：AgentNet 平均 18.8 步、多应用轨迹占 7.2%，ProCUA-SFT 平均 29.7 步、多应用占 26.1%，GUI-Reflection 平均 3.8 步，而且没有一个跨应用携带持久状态（表 1）。CUA-Recovery-Train 平均 60.0 步、多应用轨迹占 67.5%，并把多个策略的真实失败与验证器接受的恢复配成对。

## 3 问题形式化

**环境与任务。** 一个计算机使用任务被建模为部分可观测马尔可夫决策过程（POMDP）(S, A, O, T, Ω)。状态 s_i ∈ S 是第 i 步之后机器的完整持久状态：应用数据库、文件与用户界面。动作 a ∈ A 是 agent 发出的操作，包括点击、拖拽、滚动、输入、组合键等 GUI 操作以及 CLI 命令。每个 agent 用自己的原生语法发动作；harness（评测框架）把每个动作归一化成共享的可执行形式，因此一个 agent 的历史可以为另一个 agent 重放。

在第 i 步，agent 观察到截图 o_i = Ω(s_{i−1}) ∈ O，它只揭示状态的一部分；其动作把状态更新为 s_i = T(s_{i−1}, a_i)。在关闭自动更新、通知守护进程这类破坏可复现性的因素之后，我们把 T 视为确定性的——正因如此，一段已记录的动作前缀才能被重放到同一状态。一个任务是三元组 (l, s0, C)：自然语言指令 l ∈ L、初始快照 s0，以及由二值准则构成的评分表（rubric）C = {(c_j, w_j)}，j = 1…m，权重 w_j > 0。

**Rollout 与评估。** 在第 i 步，VLM 策略 π 采样 a_i ∼ π(· | l, o_i, H_{i−1})，其中 H_{i−1} = (o_1, a_1, …, o_{i−1}, a_{i−1}) 表示交互历史。当 agent 发出 terminate 或用尽步数预算 B 时回合结束，得到一条 rollout ξ = (o_1, a_1, …, o_T, a_T) 与最终环境状态 s_T。rollout 记录观测，因为状态只有部分可观；由于 T 是确定性的，任何状态 s_i 都可以从 s0 重放 a_1, …, a_i 重建。一个动作可能改动不可见的状态分量，其影响会持续并左右后续操作。于是一个错误动作可能潜伏很多步，直到被未来某次观测显式揭示。

与之相关，多数 agent 框架把上下文窗口限制为最近 K 张截图（我们的评估中 K = 20）。于是视觉证据可能从 agent 的上下文中脱落，而它对持久状态的影响依然生效。每条评估准则 c_j(l, ξ) ∈ {0, 1} 由 rollout、其关联截图与最终状态 s_T 共同判定，总体评分为 ρ(ξ) = Σ_j w_j c_j / Σ_j w_j。当且仅当所有准则都满足时我们称该 rollout 成功（V(ξ) = 1），否则失败。每项评估运行三次：三次 rollout 中任意一次成功则任务计为已解决（Pass@3），而 Rubric Score 取该 rollout 的得分。

**根因、接管深度与错误视界。** 在一次失败的 rollout 中，根因步骤 t_r 定义为 agent 没有撤销的最早动作——若无此动作，任务在 s_{t_r − 1} 处本仍可解。其错误类型 κ 依附录 C.3 的分类法给出。所有被识别的错误都源于 agent 自己的决策。接管深度 d 统计根因之后走过的步数。深度 d 处的错误状态是重放失败 rollout 前缀 ξ≤t_r+d 所到达的状态 s_{t_r+d}，前提是此前不相关的错误已被修复，使前缀中恰好只有一个根因（§4.1）。agent π′ 接管时拿到指令 l 和历史 H_{t_r+d} 作为自己的历史，我们用 V 与 ρ 给整条轨迹打分。对每次失败我们还标注错误视界（error horizon）h_e = t_e − t_r，其中 t_e 是错误在轨迹中首次变得显式的步骤；若轨迹在 t_e 之前结束，则 h_e 不可观测。我们记 c = t_r + d 为接管步骤，H_c 为截至第 c 步的交互历史。执行类错误在下一次观测即可见（h_e ≥ 1），而规划与感知类错误从 t_r 起就隐含在历史中，可能很晚才暴露。

## 4 CUA-Recovery 基准与 ReRail

在上述形式化之上，我们提出 CUA-Recovery——一个面向长时程计算机使用任务中错误检测与恢复的基准——以及构建它的流水线 ReRail。CUA-Recovery 针对第 1 节的三点差距：它的错误来自 agent 自己的策略而非注入（覆盖面），会沿依赖关系跨应用传播并隐藏许多步（视界），并且发生在 agent 同时通过 GUI 与 CLI 行动的持久桌面环境中（界面）。ReRail 把种子任务组装成较长的多应用工作流，从多个 agent 收集失败，并把它们转化为 CUA-Recovery-Test（2,250 个错误状态的人工核验测试集）与 CUA-Recovery-Train（8,577 条经验证的恢复轨迹的训练集）。图 2 总结了这条流水线。

### 4.1 用 ReRail 构建基准

ReRail 的关键思想是：每个任务都带一条 gold lineage，即每一步的正确值。这样，agent 自己的失败可以对照这条血缘被追溯，从而定位根因，也就无需注入错误。下面概述主要步骤；细节见附录 B。

**构造带依赖的任务。** 我们从 MyPCBench（Jang et al., 2026a）的任务出发。对每个任务，ReRail 创建一个可执行的中间表示，记录应用操作、这些操作读写的数据以及对其输出的检查。在一个全新的环境快照上运行这张图，就得到预期的中间值与最终状态。为了形成更长的工作流，我们把「第一个任务的输出可作为第二个任务输入」的两个任务连接起来：原本在指令中直接给出的值，现在必须通过先前的工作找到，于是产生一条错误可以沿之传播的依赖。得到的任务池含 477 条工作流，每条工作流的中位数是 3 个源任务、22 个图节点。

**检查生成的任务。** 我们执行每条工作流，得到其参考中间值与最终状态，然后把这些验证器冻结到该 gold lineage 上。接着扰动中间值并重跑工作流：若下游验证器失败，或最终输出、存储数据与 gold lineage 不一致，则该变异被捕获。我们保留至少捕获一半已执行变异的工作流，并在不同依赖长度上选取任务。

**构造错误状态与评估套件。** 我们把组合出的工作流划分成训练与测试任务，来自同一工作流的所有 rollout、接管状态与恢复轨迹都被分到同一侧。我们在这些工作流上运行六个 agent：GPT 5.5、Claude Opus 4.8、Kimi-K3、Qwen3.5-35B-A3B、EvoCUA-32B、OpenCUA-72B。对每条失败的 rollout，ReRail 把记录的执行与 gold lineage 对比，识别根因步骤 t_r、错误类型以及错误首次显露的步骤。为了让每个案例可控，专家会先修复 t_r 之前所有不相关的错误，使根因成为前缀中唯一的错误。随后 ReRail 把 rollout 重放到根因之后 d ∈ {0, 5, 10, 15, 20, 25} 的深度来创建接管状态，每次重放都必须复现原始 rollout 同一位置记录的状态。对测试套件，人工标注者核验根因、错误类型、错误视界、修复后的前缀与重放状态；这些标注支撑了感知指标以及按错误类型、错误视界的分析（附录 E）。

**生成训练套件。** 对训练侧的每个错误状态，基座模型 Qwen3.5-35B-A3B 在关于早期错误的引导下尝试完成任务。恢复生成从「指出出错步骤」的提示开始，若先前尝试失败，再补充冲突证据与受影响的数据。第一个被最终验证器接受的续写成为训练目标；当基座模型产生不了经验证的续写时改用教师模型。每条训练样本包含任务指令、错误历史与经验证的续写；提示不进入训练输入，以匹配评估所用的「不知情接管」设置。附录 F.4 描述提示调度与生成预算。

## 5 实验

我们用 CUA-Recovery 回答两个问题：(1) 现有 agent 能否从继承的错误中恢复（§5.2）；(2) CUA-Recovery-Train 能否教会恢复（§5.3）？

### 5.1 评估设置

**Agent、指标与协议。** 我们评估 GPT 5.5、Claude Opus 4.8、Kimi-K3、EvoCUA-32B、Qwen3.5-35B-A3B 与 OpenCUA-72B。各 agent 使用各自的 scaffold（执行骨架）；EvoCUA 与 OpenCUA 只用 GUI 动作，其余配置在支持时开放命令行工具（附录 F）。在自我接管（self-takeover）中，每个 agent 从自己失败产生的状态继续，拿到记录的历史且没有错误警告，最多可再走 100 步。Error-Awareness Rate（EAR）衡量 agent 是否明确承认继承来的工作有问题。Rubric Score（第 3 节定义）衡量任务的部分完成度，Pass@3 报告三次运行中至少一次的完整完成。把两者一起报告，可以区分「表达出来的感知」与「恢复结果」。

**干净启动评估。** 我们也让 agent 从 MyPCBench（Jang et al., 2026a）与 Odysseys（Jang et al., 2026b）的初始任务状态出发运行，任务数分别为 184 与 200。每次运行限 150 步、3,600 秒。MyPCBench 提供构建我们工作流所用的源任务，并在源环境中度量干净启动表现；Odysseys 包含训练环境之外的真实网页任务，用来度量恢复训练的效果能否迁移到不同的任务设置。

### 5.2 在 CUA-Recovery-Test 上的恢复基准测试

我们让六个 agent 各自在六个不同接管深度上接管自己失败的状态。表 2 报告 EAR、Rubric Score 与 Pass@3。这些结果给出以下四条发现。

**发现 1：现有 agent 很少能完全从自己的失败中恢复。** 在 CUA-Recovery-Test 上，完全恢复对全部六个 agent 都很困难。跨所有 agent 与接管深度，Pass@3 至多 25.5%（GPT 5.5 在 d = 20 达到，表 16）。Claude Opus 4.8 至多 7.7%，三个开源 agent 都不超过 6.4%。这些结果说明，即便较强的计算机使用 agent，一旦早期错误影响了工作流，也常常无法完成任务。

**发现 2：干净启动表现不能可靠预测错误感知。** Kimi-K3 从干净启动在 MyPCBench 上取得 66.9% Pass@3，却只能认出自己失败中 7.8–18.5% 的继承错误。相反，OpenCUA-72B 的干净启动 Pass@3 只有 5.1%，却认出 14.1–26.1% 的继承错误（表 3、表 2）。

**发现 3：认出错误很少带来恢复。** 跨六个 agent 的自我接管运行，EAR 至多 44.0%，除 Claude Opus 4.8 外所有 agent 都低于 33%（表 2）。接着我们按「是否认出继承错误」把每个 agent 的单次运行分组，计算每组内的验证器成功率。六个 agent 宏平均后，感知组的验证器通过率为 15.6%，未感知组为 12.2%（附录表 18）。多数运行即使认出错误之后仍然失败：agent 常能发现问题，却让受影响的状态原封不动，或没能修复全部后果。在未感知的运行中，agent 几乎总是从继承的状态继续，从不回头检查先前的工作。因此，感知与更高的恢复机会相关，但仅仅认出错误往往不够。

**发现 4：即使感知改善，更晚的接管依然困难。** 从 d = 20 到 d = 25，根因截图移出了 20 张截图的历史。在这一区间，GPT 5.5 的 EAR 从 16.2% 升到 21.0%，而 Pass@3 从 25.5% 落到 18.9%。Claude 的 EAR 也从 18.8% 升到 27.3%，Pass@3 却从 7.7% 落到 0.0%；Kimi-K3 的 Pass@3 从 23.1% 落到 9.1%。这说明更晚的接管点上存在一种权衡：错误在工作流中传播时，其影响在当前状态里变得更可见，问题反而更容易被注意到；然而一旦根因截图离开上下文窗口，agent 就必须从下游影响反推问题的成因，错误也就更难诊断和修复。这有助于解释为何 EAR 可以在 Pass@3 下滑的同时上升。

### 5.3 用 CUA-Recovery-Train 训练恢复能力及其泛化

上述结果表明，agent 在「注意到继承错误」和「修复其下游影响」上是两种不同的困难。接下来我们考察训练套件中那些经过验证的轨迹，能否支撑以标准监督目标进行的恢复导向微调。

**训练设置。** 我们在 CUA-Recovery-Train 的 8,577 条经验证恢复轨迹上微调 Qwen3.5-35B-A3B 一个 epoch，得到 ReRail-35B-A3B。给定任务指令 l、错误历史 H_c 与经验证的恢复 r⋆，我们最小化

```
L(θ) = −E_{(l, H_c, r⋆) ∼ Q} [log π_θ(r⋆ | l, H_c)]
```

其中 Q 是训练集。生成 r⋆ 所用的提示不包含在 H_c 中，因此模型收到的输入与评估时的「不知情」输入一致。

**发现 5：从 CUA-Recovery-Train 学到的恢复可以跨 agent 迁移。** 我们先在取自 Qwen3.5-35B-A3B 自己失败的状态上评估微调后的模型，使两个模型从同一批错误状态出发。微调在各接管深度上把 EAR 提高 13.4–16.5 个百分点、Rubric Score 提高 5.9–16.0 分（表 2）。在 d = 0，Pass@3 从 1.2% 升到 4.7%。在 d ≥ 20 上 EAR 与 Rubric Score 同样改善，尽管两个模型在这些深度都解不出任何任务。因此训练数据同时改进了错误识别与部分恢复，而更晚接管点上的完全恢复依然困难。我们还在 Kimi-K3 与 EvoCUA-32B 产生的失败上评估微调模型：在 d = 0，ReRail-35B-A3B 在 Kimi-K3 的失败状态上达到 16.6% Pass@3（Kimi-K3 为 11.6%），在 EvoCUA-32B 的状态上达到 12.7%（EvoCUA-32B 为 6.4%，图 13）。它对 Kimi-K3 的优势保持到 d = 10，对 EvoCUA-32B 的优势保持到 d = 15；更深处这些增益收窄或消失。结果说明学到的恢复行为可以跨失败来源迁移，且在较早的接管点增益最大。

## 6 结论

我们发现，现有计算机使用 agent 在长时程工作流中很少从自己的错误中恢复，而强劲的表现并不意味着可靠的恢复。现有数据与基准在三方面漏掉了这一场景：错误是注入的或低层的而非 agent 自己引发的；轨迹太短，错误来不及隐藏；评估只覆盖 GUI 动作并以截图打分。我们提出 CUA-Recovery——一个用 ReRail 基于 agent 自己的失败构建的基准，这些失败来自同时涉及 GUI 与 CLI 的长多应用工作流，并配有经人工核验的测试集与经验证的恢复训练轨迹。在 CUA-Recovery-Train 上微调能改善对继承错误的恢复以及干净启动表现，包括在未见过的环境中，这说明从真实失败学习是通往可靠计算机使用 agent 的一条可行路径。

## B ReRail 数据合成框架细节

本附录完整给出第 4.1 节的 ReRail 框架。当前的 MyPCBench 任务集虽提供真实的工作流，但大多任务相对较短，一个有能力的 agent 只需 20 到 45 步即可完成，而让错误得以隐藏的依赖结构通常不超过两个节点。要大规模研究隐藏错误，需要依赖链长、且 ground truth 可执行的任务——在任何 agent 运行之前，每个中间值、每个写入的单元格和最终状态就已确定，而这正是现有基准所缺的性质。因此我们通过组合已验证的源任务来合成任务，并且只有在组合被执行过、其验证器被证明能拒绝错误运行之后才接受它。本附录描述实际实现的流水线：从每个源任务抽取可执行的任务表示（§B.2）、带可执行闸门的组合搜索（§B.3）、验证器冻结与度量验证器覆盖率的变异测试（§B.4）、带世界与指令变体的视界受控选择（§B.5），以及发布集合的规模与视界（§B.6）。

### B.1 从工作流到训练与测试样本

算法 1 总结了 ReRail 如何用已验证的工作流构造两个划分。

```
Algorithm 1 ReRail: collecting failures and building recovery data
Require: validated task pool M with reference executions G(M) and frozen verifiers; source policies Π;
         base model π0; teacher πT; depths D = {0, 5, 10, 15, 20, 25}
Ensure: training recovery set Q and test-state set E
 1: Split M into training and test tasks
 2: Q, E ← ∅
 3: for task M ∈ M, instruction l for M, source policy π ∈ Π do
 4:     ξ ← ROLLOUT(π, l, M)
 5:     if the final verifier accepts ξ then continue
 6:     (tr, κ, te) ← ANALYZE FAILURE(ξ, G(M))
 7:     if the root cause is unresolved or type confidence is below 0.7 then continue
 8:     ξ ← REPAIR EARLIER MISTAKES(ξ, tr)
 9:     if prefix repair fails then continue
10:     for d ∈ D with c = tr + d ≤ |ξ| do
11:         if replay does not reproduce the recorded state then continue
12:         if M is a test task then
13:             Apply the test eligibility rules of Appendix C.1
14:             Obtain human checks of the labels and replayed state
15:             Add accepted state, history, and labels to E
16:         else
17:             r⋆ ← first verified continuation under the hint schedule of Appendix F.4
18:             if r⋆ ≠ ⊥ then add (l, Hc, r⋆) to Q, without the hint
19:         end if
20:     end for
21: end for
22: return DEDUP(Q), E
```

### B.2 从源任务到可执行任务 IR

**任务中间表示。** 一个任务被表示为一个冻结环境快照之上的有根 DAG M = (V, E)。每个节点 v ∈ V 记录它作用的应用，其操作从以下动作集合中选取：retrieve、resolve、filter、compare、aggregate、verify、decide、create、modify、delete、communicate、confirm。节点还定义它读取的表格单元格、它产生的值及其实现推导（例如只读 SQL 查询、对上游值的表达式、文件读取、行或文件创建）、它写入的单元格、其可逆性类别，以及一个节点验证器。一条边把值或状态从输出端口转移到输入端口；若某个输入端口没有边连入，该端口就取指令中指定的字面量或常量。整张图带一个最终状态验证器，其中显式列出等价的最终状态集合。该快照由 17 个应用数据库（含 201 张表）、一个同时刻画外键与推断关系的 schema 图，以及人设主目录中 48 份文档的清单构成。文件清单以单张虚拟表的形式暴露，使文件与数据库行可以当作同一类事实来处理。

**抽取与程序化校验。** 语言模型从指令、评分表、人设与 schema 中抽出 184 个 MyPCBench 源任务各自的 Task IR。结果由程序而非 LLM 判分器校验：静态检查确认 DAG 合法、每个单元格都能在 schema 图中落地、每个命名实体都存在于快照中。每个输入字面量要么出现在指令里，要么指人设自己的身份，以确保期望 agent 检索的事实不会被直接当作常量给出。

随后 gold IR 在快照的一份新副本上执行。解释器求值每条推导、执行声明的写入、把每条 SQL 查询实际读取的单元格与声明的读取集合比对，一旦遇到未声明的写入即中止。它还记录 gold lineage G(M)，包括每个产生的值、每个写入的单元格以及每个节点之后的状态摘要。最后，gold 值与源评分表中的 ground truth（如金额、日期、姓名）比对；相对日期变量按快照的参考时间展开。当评分表不含可比字面量时，则按其措辞与 gold 值的重合度判定。任何校验失败的任务都会把程序发现附加到提示后重新抽取，最多四轮。

我们最终从原始 MyPCBench 的 184 个任务中接受了 135 个（73.4%）：53 个按与评分表的字面一致接受，82 个按措辞接受。其余 49 个任务中，34 个因模型的推导或写入与实际 schema 不兼容而无法执行，8 个的评分表没有可比值，5 个的最终验证器会拒绝自己的 gold 运行，2 个与其评分表矛盾。被接受的 IR 中位数为 6 个节点。每个被接受的 IR 都随附其 gold lineage，它是后续一切的唯一事实来源。

### B.3 带可执行闸门的组合搜索

**带单元格证据的类型兼容。** 组合把一个已接受 IR 的输出端口 p_o 连到另一个 IR 取字面量值的输入端口 p_i。第二个任务指令中原本以常量给出的值，就必须通过执行第一个 IR 获得。

记 τ(p_o, p_i) ∈ {0, 0.4, 1} 为两个端口的类型兼容分：实体引用类型相同时为 1，共享 Integer 或 Text 之类的通用标量类型时为 0.4，否则为 0。对每个端口 p，记 col(p) 为与该端口关联的 schema 列。我们先从 IR 声明的读取中确定 col(p)；若声明的读取无法唯一定位列，则从 SQL 推导中恢复——对输出端口，col(p) 是标量查询中唯一被选中的列；对输入端口，它是与查询中对应 p 的参数相比较的那一列。若仍无法唯一定位，该端口不具备组合资格。

记 rel(p_o, p_i) 表示包含 col(p_o) 与 col(p_i) 的两张表在 schema 图中由至多两跳的键路径相连。兼容分为：

```
              ┌ 1,                                   col(p_o) = col(p_i),
σ(p_o, p_i) = ├ max(τ(p_o, p_i), 0.8),               τ(p_o, p_i) > 0 ∧ rel(p_o, p_i),
              └ τ(p_o, p_i),                          otherwise.                (1)
```

若 σ(p_o, p_i) ≥ 0.5，则称该端口对可容许，记作 p_o ⇝ p_i。因此，通用标量类型匹配的端口对只有在两端落在同一 schema 列上、或两列由键路径相连时才可容许——这条额外约束避免了仅凭类型的匹配。端口还必须基数匹配，且表示人设身份的字面量不能作为嫁接目标。在 135 个被接受的 IR 中，1,053 个输出端口与 109 个候选输入端口产生 143 条可容许边：51 条连接落在同一列上的端口，92 条连接由键路径支撑的类型兼容端口。

**算子与搜索。** 对每个种子 IR，我们考虑与已接受池中任意 IR 组合的 beam search。每一步中，搜索可以把任务 A 的输出传给任务 B 的字面量输入、添加同一操作模式的另一个实例、给比较或聚合节点再挂一个生产者、在值产生之后隔几个节点复用它，或用 A 中 decide 节点产生的布尔值守卫 B 中第一个改变状态的节点。每一步之后整张图被重新求值。

为避免命名冲突，每个节点标识符都以其父任务为前缀；每次组合的来源记录保存操作符、端口绑定与源任务。执行之前，每个候选必须通过一组静态检查：若图中超过 25% 是互不相连的独立分量（通常说明两个任务只是被并排放置而非有意义地结合），该图被拒绝；若从一个任务传到另一个任务的值对后续计算没有影响、落入目标视界范围（§B.5）的节点少于两个，或节点数少于 10 或多于 24，同样被拒绝。下界排除了短到无法有意义检验长时程推理的任务（§B.6），上界则把任务保持在现有 agent 力所能及的范围。

通过这些检查的候选在快照的新副本上执行：执行必须成功完成，最终验证器必须接受所得 gold 状态。beam 保留 16 个状态，最多允许三次嫁接，每个种子每轮不超过 48 次 gold 执行。由于每个世界都使用数据库的完整副本，每步之后重算所有数据库摘要代价很高；解释器改为缓存每个数据库的摘要，只在相应连接报告变化时重算，把一次 gold 执行的时间从 8.9 秒降到 0.1 秒，使可执行校验变得实际可行。

**组合后的评分表。** 对由源任务 T1, …, Tk 组合出的工作流，我们把各源任务的评分表条目合并成它的评分表。当组合用上游输出替换某个源任务输入时，我们用组合后的 gold lineage 更新相应的期望值与验证描述；每个保留的条目沿用其源任务的权重。得到的评分表既用于构造冻结的程序化验证器，也被 GPT 5.6-Terra 的 rubric 判分器逐条使用。

### B.4 验证器冻结与变异测试

**把验证器冻结到 gold。** 抽取过程中产生的验证器主要检查内部一致性而非正确性。在 135 个被接受的最终验证器中，122 个是导出谓词，76 个只引用运行期间算出的值。因此这样的验证器可能接受一个输出彼此一致但并不正确的运行。组合之后问题更严重，因为从接收任务继承来的验证器里可能仍带着原任务的字面量。

为防止这一点，我们在使用前把每个验证器锚定到 gold lineage。记 Sink(M) 为 M 的汇点（其输出不被任何其他节点消费），g_{u,x} 为节点 u 的输出 x 的 gold 值。设验证器谓词 φ 引用运行时值 val[u][x] 以及由这些值导出的 SQL 参数。我们通过把每个非汇点值的引用替换为其 gold 对应物来冻结该谓词：

```
φ̂(ξ; G(M)) = φ(ξ; val[u][x] ← g_{u,x}  对每个被引用的非汇点值 (u, x))        (2)
```

汇点值保持不变、取自被评估的运行，而用于推导期望结果的值固定为 gold lineage。所得谓词因此拿运行的最终输出对照一个 gold 落地的期望。对节点级验证器，被检查的节点视为汇点，其自身输出保持不冻结，而检查所依赖的值固定为 gold。

组合过程中还有一个小步骤：在固定从接收任务传下来的验证器之前，必须先把与插入点或后续阶段参考答案重合的字面量替换为参数；任何仍依赖这些被弃用字面量的候选最终条件直接丢弃。接着我们拼接两个源任务的最终验证器，执行组合后的 IR，得到其参考答案血缘；再用这条血缘按式 (2) 固定新参数。最后用新快照重跑固定后的 IR，只有通过这次校验的才真正进入基准数据集。

**变异测试。** 变异测试评估验证器发现不正确行为的效果。对每个目标值，框架按其类型从预定义库中选取合适的变异，常见变异包括交换表名或实体名、把日期平移一天或一周、缩放金额、省略费用、改动列表元素、翻转布尔值或使用过时文本。然后用变异后的值覆盖原值重跑 IR。节点 v 处的变异 µ 被认为已捕获，当且仅当任一下游验证器失败、冻结的最终验证器失败，或运行结果偏离 gold 标准——最后这项检查模拟人工判分器把模型输出与评分表对照。任务的拒绝率为：

```
R(M) = |{µ ∈ Mut(M) : caught(µ)}| / |Mut(M)|                              (3)
```

我们只在真正执行过的变异上汇总 R(M)，仅当 R(M) ≥ 0.5 才把任务保留在池中。第一个失败的节点验证器揭示该变异的动态潜伏视界，即从节点 v 到那个失败验证器的拓扑距离。只被最终验证器或 gold 偏离捕获的变异标记为 verifier-only，完全逃过检测的标记为 silent。在一次生成运行中，417 个候选上执行了 17,857 次变异，我们观测到 R 的中位数为 0.64（均值 0.67），327 个候选越过阈值。具体而言，下游节点验证器捕获 4,711 个变异，最终验证器捕获 823 个，汇点或写入偏离捕获 6,394 个，5,929 个保持 silent。省略冻结步骤与偏离检查会把 R 的中位数降到 0，417 个候选中只剩 3 个存活。

### B.5 视界分桶、选择与变体

**静态潜伏视界。** 为了量化一个错误在暴露之前能藏多深，我们在执行前的 IR 上计算静态潜伏视界 λ(v)。概念上，当节点 v 产生错误值时，它会污染自己触及的数据事实；视界 λ(v) 度量从 v 到第一个消费这些受污染事实的下游节点 u 在依赖图上的最短路径：

```
λ(v) = min{ dist(v, u) : u ≻ v, facts(u) ∩ cont(v) ≠ ∅ }                  (4)
```

若错误只被最终验证器捕获（即 verifier-only 错误），我们置 λ(v) = ∞；若没有任何下游组件检测到它（即 silent 错误），则留作未定义。我们把节点分成四类：1、2–3、≥ 4、verifier-only，并把每个任务归给其节点中最频繁出现的类别。桶 1 表示即时错误传播，错误在紧接的下一步就被抓住；更高的桶刻画更难的情形——错误跨越多个动作一直存活到执行结束。

**选择。** 为了构建平衡的基准，我们先按固定目标占比 α = (0.20, 0.35, 0.30, 0.15) 选择基础任务来填充四个视界桶，得到每桶配额 q_b = N·α_b。候选按一个综合分排序选取：该分数奖励更高的目标桶占比与跨应用边，同时惩罚落在 [5, 9] 之外的依赖深度。选择受两条约束：源任务限定在对照桶内；未填满的配额记为缺口，而不从其他桶回填。

**维度一：世界变体。** 选定基础任务后，我们把环境隐患作为第一个变化维度，包括身份别名、过时文档、标题相似的干扰事件以及失效的前置条件。为防止人为过度注入，我们先查询每个隐患在快照中的基线出现率，只有基线率非零才注入，并把注入后的比率封顶为基线的两倍。当某个节点的指令常量或输出命中隐患选择器时，环境播种器以人设补丁的方式施加该隐患。在我们的快照中，只有干扰事件满足这些条件（基线计数 19），身份别名与过时文档不满足注入条件。

**维度二：指令变体。** 指令实现构成第二个变化维度。对每个选定任务，模型从图摘要与公开上下文生成候选指令，但不泄露受限的「隐藏值」——即被排除在初始输入与先前种子之外的 gold 值。一条指令只有在包含全部所需输入字面量、又不泄露隐藏值时才被保留。彼此不同的有效指令在保留任务核心 gold 目标与验证器的前提下，给出相互独立的 rollout 起点。

## C CUA-Recovery 更多细节

### C.1 测试用例构建

测试任务运行在 MyPCBench 环境（Jang et al., 2026a）中——一个最多含 17 个应用的持久个人工作区。每个任务有一条指令、一个恢复初始状态的 setup 例程，以及第 4.1 节的冻结验证器。我们分四步把每条失败的 rollout 变成测试用例。

**归一化轨迹。** 六个 agent 使用不同的动作格式。我们把每一步存成一种共享的可执行格式，再转回接管 agent 的原生格式。

**前缀修复。** 每个测试用例恰好有一个根因。ReRail 修复根因步骤之前所有不相关的错误，标注者确认修复后的前缀没有其他错误。

**重放校验。** 我们恢复任务快照，重放修复后的前缀、根因动作及其之后的步骤。只有重放后的状态与记录的状态一致才保留该前缀；标注者还确认重放状态确实呈现了预期的错误。

**在六个深度接管。** 从一次经验证的失败，我们最多构建六个测试用例：每个都在根因步骤之后 d ∈ {0, 5, 10, 15, 20, 25} 步处停止重放，并把控制权交给被评估的 agent。若根因之后不足 d 步，或接管点落在错误变得显式的步骤之后，我们跳过该深度。这样六个深度上分别得到 602、443、373、328、273、231 个测试用例，合计 2,250 个。

### C.2 与现有训练语料的比较

图 3 把 CUA-Recovery-Test 中的错误与 AgentNet、GUI-Reflection 中的错误作比较。我们从每个语料各抽样 100 条轨迹，用附录 E 的协议标注其根因、错误类型与错误视界。表 1 也列出了 ProCUA-SFT。下面描述各语料如何收集错误。

**AgentNet。** AgentNet（Wang et al., 2025）在 Windows、macOS 与 Ubuntu 上有 22.6K 条人类示范。它保留人类的错误，并给每步加一条反思。其轨迹很短：平均 18.8 步（中位数 17），只有 7.2% 使用一个以上的应用。它的错误来自一个知道目标的人，因此大多是误点、打错字和选错菜单，属于我们的执行类。其错误视界至多一步，因为反思器只比较每步前后的截图。

**ProCUA-SFT。** ProCUA-SFT（Jung et al., 2026）有来自单一策略（Kimi-K2.5）的 93,566 条合成桌面轨迹。失败轨迹只带一个最终失败标签，没有任何一步标出错误发生的位置。前置条件检查在 rollout 之前剔除不可行的目标，因此规划错误按设计就很少。平均长度 29.7 步，但中位数只有 19，73.9% 的轨迹只用一个应用。

**GUI-Reflection。** GUI-Reflection（Wu et al., 2025）有 8,640 条带显式反思步骤的移动轨迹。其错误被注入成功轨迹，随后紧跟一次反思与修复。因此它的错误类型取决于注入模板，且每个错误都在发生的那一步变得显式。其轨迹平均 3.8 步，短于 CUA-Recovery-Test 中 17 步的错误视界中位数。

### F.4 恢复生成与监督训练

对结束于步骤 c 的错误前缀，我们用越来越细的提示生成续写。第一个提示 ℓ1 指出出错步骤；ℓ2 补充冲突的观测；ℓ3 还指出受影响的行。基座模型在每个层级最多有八次尝试；若都失败，教师模型用 ℓ3 有一次尝试。我们在第一个被固定最终验证器接受的续写处停止：

```
r⋆ = first { r ∈ (r1,1, …, r1,8, r2,1, …, r2,8, r3,1, …, r3,8, rT) : φ̂_final(ξ≤c ⊕ r) = 1 }   (5)
```

其中 r_{k,j} 由基座模型在任务 l、历史 H_c 与提示 ℓk 条件下生成，rT 由教师模型生成。没有经验证续写的前缀不贡献恢复目标。我们还会检查并删除 r⋆ 中来自提示的信息，以缓解提示对训练的影响。

### G.2 错误视界与恢复结果

证据时机与接管深度描述失败的不同部分。对根因在步骤 t_r 的失败，标注的错误视界为 h_e = t_e − t_r，其中 t_e 是错误在记录的 rollout 中首次变得显式的步骤；接管深度为 d = c − t_r，c 是另一个 agent 恢复执行的步骤。因此 h_e 描述证据沿原执行何时出现，而 d 决定被评估的 agent 继承了那段执行的多少。Sweetgreen 的例子 h_e = 40；在 d = 0 或 d = 25 接管，呈现的是同一底层失败的不同历史。

长错误视界可以把原因与可见后果分开。对 h_e > 20 的错误，根因之后超过 20 步的接管可能发生在错误于原 rollout 中变得显式之前；此时提供的截图历史可能已不含根因，而当前状态看上去仍与 agent 先前的决策相容。随着工作流继续，后续观测可能提供关于该错误的更多证据，而恢复还需要把证据与先前决策联系起来、检查它所影响的数据。这为第 5.2 节某些更晚接管深度上「EAR 更高而完成更低」的组合提供了一种解释。

每个深度选出失败集的不同部分。附录 C.1 的构造只保留位于标注证据步骤处或之前、且落在记录 rollout 内的接管点。对观测到 t_e 的失败，这些条件是 d ≤ h_e 且 t_r + d ≤ T，T 为 rollout 长度。合格状态数从 d = 0 的 602 降到 d = 25 的 231。因此更晚的深度聚焦于「持续得足够久以支撑接管、且显式证据出现得足够晚」的失败；这些深度上的分数描述的是这种延迟证据设置下的恢复。附录 F.5 的同状态比较在每个深度内比较恢复策略时固定了继承的状态。

证据延迟与失败时长需要分开来读。Sweetgreen 的失败在错误显式之前有很长的延迟；SprintBoard 的失败则是在有可见证据表明命令从未运行的情况下，仍包含一长串等待。两者都产生很长的错误历史，但要求不同的恢复行为：前者需要拿源数据核对一个更早的假设，后者需要重新考虑一个与当前屏幕冲突的解释。把标注的视界与轨迹、恢复分数一起读，有助于区分「找不到证据的困难」与「拿到证据后不知如何行动的困难」。
