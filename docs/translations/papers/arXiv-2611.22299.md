## 摘要

基础模型能否成功充当自主智能体，很大程度上取决于它的运行时软件，而不只是权重。这段运行时即智能体 Harness（agent harness，本文译作「智能体外壳」），它管理上下文与记忆、引导多轮控制、在沙箱中执行工具动作，并在停止前验证工作。

由于不同模型使用工具的方式和失败的方式各不相同，为某一模型或任务调优的静态 Harness 换到另一个模型或任务上往往停滞不前、浪费 token 或出现回退。这一瓶颈推动了从提示词调优向自我改进型智能体 Harness 的转变：这类系统检查自己的执行轨迹，把运行时缺陷与模型能力上限区分开来，并重写自己的代码。

我们提出一个关于自我改进型智能体 Harness 的统一架构与设计框架。该框架把四个可编辑的运行时组件（上下文与状态、智能体控制、动作接口、验证与恢复）与一个四阶段循环配对：诊断失败、提出代码补丁、验证候选、部署更新。借助这一框架，我们展示了优化器如何跨长轨迹追踪错误，并发现可复用的运行时机制，例如停止前验证器、循环打断器与持久记忆。

我们进一步说明：为什么整体重写整个 Harness 会过拟合或在模块之间被破坏，以及带验证门控的模块化更新如何在限定 token 成本的前提下跨模型泛化。为使自我修改保持安全，我们针对反复出现的失败模式建立了实用防线，包括提示词膨胀、基准测试作弊与评估器篡改。最后，我们在 SWE-bench Lite 上的实验验证了这一框架，表明带门控的模块化演化在跨模型、跨仓库的设置下优于提示词反思与整体重写，而 token 成本只是后者的一小部分。

## 1 引言

语言模型如今已被广泛部署为自主智能体，用于修复大型软件仓库中的缺陷 [1]、[2]，运行命令行工具 [3]、[4]，操作桌面与网页界面 [5]，以及执行多步推理与科学工作流 [6]。每一个能工作的智能体，都是把一个基础模型与一个智能体 Harness 配对使用：Harness 是有状态的运行时软件，把单步的 token 预测变成跨越长时间跨度、持续进行的多轮执行。

模型提供通用推理与代码生成，而 Harness 则在每一轮接管周围的执行循环：组装并压缩状态历史、调度控制流与子智能体交接、在隔离沙箱中执行工具或 shell 调用，并在任务完成前运行自动测试或恢复检查 [4]、[7]、[8]。

**Harness 为何与模型同样重要。** 早期关于语言模型智能体的工作把运行时 Harness 视为包裹在模型检查点外面的一层薄薄的工程胶水。随着时间推移，它的范围与职责不断膨胀，成为任何智能体系统的核心部分；近期在编码、终端与计算机使用任务上的对照评估凸显了这一转变的三个理由。

第一，Harness 决定了智能体如何失败、以及运行它要花多少钱。当同一个模型跑在不同的生产级 Harness 中时，它的主要失败模式（测试前就退出、在失败命令上打转、撑爆上下文窗口、跳过验证）遵循的是 Harness 的设计，而不是模型家族。每个已解决任务的 token 用量在不同 Harness 之间也可能相差一个数量级 [9]、[10]。

第二，一个设计良好的 Harness 既能支撑较弱的模型完成简单任务，也能释放更强的模型去解决复杂任务。在简短、自包含的问题上，额外的 Harness 结构主要是在弥补较弱模型的不足；但在长时间、仓库级的任务上，一个有能力的 Harness 起到的却是相反的作用：它的状态跟踪、多步规划与验证钩子给强模型提供了必要的脚手架，使其能够解决独自无法完成的问题 [11]。

第三，没有任何单一的静态 Harness 对所有模型都是最优的。由于模型在格式化工具调用、遵循指令、以及平衡探索与行动方面各不相同，为一个模型调优的 Harness 换成另一个模型时常常表现更差，甚至颠倒排行榜名次 [8]、[10]。即使固定基础模型不变，横跨数十个人工维护的 Harness 版本的纵向审计也表明，人工调优经常停滞不前，或在较早的任务上引入回退 [12]。

**从提示词流水线到自我改进型智能体 Harness。** 由于 Harness 对可靠性影响巨大、又必须与特定模型匹配，工程师构建它们的方式已经历了三个截然不同的代际 [4]、[8]。

第一代是人工 Harness 工程：靠人类开发者手工检查失败的执行轨迹，打造更好的系统提示词、智能体-计算机接口（ACI）、上下文压缩器与重试循环，由此产生了 SWE-agent [2]、Antigravity、Claude Code、Codex CLI、Gemini CLI 等基础运行时 [4]、[7]、[12]。

第二代是自动化的提示词与工作流优化：在冻结的模型上做程序化搜索，调优提示词指令、示范与模块参数 [13]、[14]，对多轮执行轨迹进行反思 [15]、[16]，或在代码定义的多智能体工作流上搜索 [17]、[18]。这类第二代优化器虽然可以检查多轮轨迹、也可以在多智能体路由拓扑上搜索，但它们优化的是提示词、参数或智能体之间的调用图，同时把每个智能体内部有状态的运行时 Harness（上下文压缩器、沙箱化的 ACI 工具包装器、循环控制器、停止前验证钩子）当作固定原语，而不是可变的软件。

第三代，即自我改进型智能体 Harness，把多轮运行时的可执行代码本身视为可变软件。在外部元 Harness 搜索中，外层编码优化器检查多轮执行轨迹，并为目标智能体的上下文管理器 [19]、[20]、工具包装器 [21]、[22]、控制循环 [23] 与验证钩子 [24] 打补丁。在自指与递归 Harness 中，智能体把这一优化循环折进自身，用自己所在的模型诊断反复出现的执行失败、修补自己的运行时钩子 [8]、[25]，甚至重写自己的改进算法 [26]–[28]，以演化出开放式编码智能体 [29]、[30]。

为了把这一范式形式化，我们建立了自我改进型智能体 Harness 的架构与工程设计框架。虽然把模型权重与 Harness 代码协同设计的研究兴趣日益增长（见第 8 节），但本文关注的是底层模型权重保持冻结时的 Harness 自演化。

## 2 智能体 Harness 与自我改进循环

**智能体 Harness 如何把模型与环境连接起来。** 在长时间跨度的任务中，冻结的基础模型无法自己检查工作区、执行命令或跟踪多步状态；相反，它运行在一个可执行的智能体 Harness（例如 Claude Code、Antigravity、Mini-SWE-Agent 或 Terminus）内部，由后者在每一轮中介它与真实环境的交互（图 1 左）[4]、[8]。

与静态提示词模板不同，Harness 通过四个相互耦合、可用代码编辑的组件，掌管跨越数十乃至数百轮的自主执行。**第一，上下文与状态管理**通过组装动态指令、把工作记忆与经验记忆分开 [31]、并对先前各轮的陈旧观察做掩码或压缩，从而掌管整条轨迹上的多轮历史，使长时间跨度不会撑爆上下文 [32]、[33]。

**第二，智能体控制**通过调节轮次预算、检测并打破重复循环、在规划与执行阶段之间切换、以及把子任务委派给隔离的子智能体，来引导多轮探索 [8]、[25]。**第三，动作接口**定义智能体如何通过智能体-计算机接口（ACI）[2]、[34] 作用于环境，把模型输出翻译成沙箱化的 shell 命令 [35]、文件编辑或 GUI 动作，同时在当前步骤解析或截断单轮的原始 stdout 与 UI 状态，并按需加载工具 schema [36]。

**第四，验证与恢复**拦截来自智能体控制的 stop 或状态提交信号，运行自动测试套件、linter 或视觉检查，并把失败路由回上下文与状态以在终止前自修复 [37]–[39]。更细粒度的模块化系统还把这四个组件进一步拆成五个模块（把单轮观察格式化与多轮上下文管理分开 [25]）或四种生命周期上下文（规划、监督、验证、恢复 [39]），而执行前动作守卫则桥接组件 3 与组件 4 [40]。

**四阶段闭环自我改进循环。** 由于这四个运行时组件在一条轨迹上紧密交互，其中一个组件的缺陷会很快级联到其他组件。自我改进的 Harness 框架用一个自动化的外循环（图 1 右）取代对这些耦合组件的人工调试，让 Harness 在一轮轮迭代中演化。

阶段 1（诊断失败）：系统在开发集切分上运行当前 Harness，收集多轮执行轨迹，通过聚类验证器错误、对比通过与失败的轨迹、或检索原始执行日志来定位系统性的 Harness 瓶颈 [8]、[19]、[21]。阶段 2（提出编辑）：优化器把这些诊断结论翻译成覆盖一个或多个 Harness 组件的具体代码或钩子补丁 [22]、[25]。

阶段 3（验证与过滤）：候选 Harness 在验证任务、轨迹回放模拟器或效率前沿上接受筛查，以检查运行时执行、防止回退、并滤掉过拟合或浪费 token 的编辑 [20]、[24]、[41]、[42]。最后，阶段 4（部署或路由）把通过验证的补丁要么合并进默认 Harness 供后续运行使用 [8]、[19]，要么存入 Harness 变体的存档、供未来搜索轮次从中分叉 [24]、[29]，要么与一个轻量路由器或策略配对，为每个到来的任务挑选量身定制的 Harness 配置 [43]、[44]。

**自我改进 Harness 中的关键设计选择。** 在这一循环里，现有系统沿三个实际的设计选择而分化 [8]、[45]。

其一，谁来提出编辑：同模型自循环让一个有能力的编码智能体诊断并修补自己的 Harness，无需维护第二个模型 [8]；而当任务智能体很小或是领域专用的（见第 5 节），就需要外部编码优化器 [19]、[21]、[39]、[46]。

其二，哪些代码可以被修改：把编辑限制在任务 Harness 之内可使搜索可预测，而允许对优化器本身做递归编辑，则可能以更高的算力代价换来更好的搜索工具（见第 4 节）[26]–[30]。

其三，评估器放在哪里：评分脚本与日志应始终锁定在智能体沙箱之外的只读存储中，这样优化器就无法通过修改评估器或伪造日志来通过测试（见第 6 节）[47]、[48]。

**约束式 Harness 优化的形式化。** 形式化地，记 Mθ 为参数 θ 冻结的基础模型，x ∼ D 是一个任务，它配有一个隔离的执行环境 Ex 与一个外部只读验证器 Rx(τ) ∈ {0, 1}。一个可执行的 Harness 是四个有状态代码模块的四元组 h = (hctx, hctrl, hact, hver) ∈ H，对应图 1 中的组件 1 至 4。在 Ex 上运行 (Mθ, h) 会诱导出一条多轮轨迹 τ ∼ P(· | x; Mθ, h)，其运行时 token 成本为 C(τ)。

闭环 Harness 自我改进并不寻求在小型开发集 Ddev 上无约束的经验最大化，而是求解：

```text
max   E_{x∼D, τ∼P(·|x;Mθ,h)} Rx(τ)
h∈H
s.t.  E[C(τ)] ≤ Btok ,  Gval(h, h0) = 1                                   （1）
```

其中 h0 是起始 Harness，Btok 限定每任务的运行时 token，Gval(h, h0) ∈ {0, 1} 是阶段 3 的验收门控，它要求修改后的代码路径经过真实执行、且在留出验证集 Dval 上不出现回退。在模块化演化（见第 4、7 节）中，外循环通过对单个模块 hk（k ∈ {ctx, ctrl, act, ver}）做块坐标更新、再经过一次冲突消解的合并过程来近似式 (1)。

## 3 失败诊断与修复合成

**为什么单轨迹反思在长跨度智能体上失效。** 在多轮智能体 Harness 中，一次失败的执行轨迹把随机的模型手误（例如正则表达式打错、一次性的工具超时）与结构性的 Harness 缺陷（例如无状态的 shell 执行、缺失的退出检查）混在一起。孤立地对一次失败做反思、往提示词里追加一条规则 [49]，无法把随机噪声与系统性错误分开，导致优化器为那些其实从未发生过的失败添加过于具体的规则或不必要的限制，既增加延迟又挤占上下文窗口 [50]。反复迭代之下，不断追加临时修补会让指令文件累积相互矛盾的规则、无限膨胀 [51]。对照消融实验确认了为什么必须能访问广泛的轨迹 [19]：当优化器只拿到标量基准分数或简短的单次运行摘要时，搜索会停滞在基线附近；而一旦能访问一个可检索的文件夹，里面装着原始执行轨迹、既往 Harness 代码与差异对比，它就能在数十次运行中发现反复出现的瓶颈。

**跨轨迹的结构化失败诊断与归因。** 诊断上的核心挑战，是把 Harness 的缺陷与模型的能力上限分开 [10]、[11]。一个自动分析器通过检查多次执行中模型的推理与其已执行动作之间的分歧来区分二者。当模型的推理轨迹指出了正确的文件或修法（或至少在一次重试中解出了任务），但运行仍然失败——因为编辑工具拒绝了它的补丁格式、某次 shell 调用丢失了工作目录、上下文压缩丢掉了某条早期约束、或循环在运行测试之前就退出了——那么责任在 Harness。反过来，如果工具调用执行干净、观察在多次重试中都完整保留在上下文里，而所有轨迹都败在领域逻辑上，阶段 1 就会放弃提出 Harness 编辑，以免把搜索算力浪费在模型的知识缺口上。

第一，为了滤掉随机的一次性手误，基于验证器的失败聚类把每条失败轨迹与它的编译器或单元测试错误输出配对，并跨任务对反复出现的运行时瓶颈分组 [8]、[24]。第二，对比式轨迹差异分析在某个任务于一个 Harness 版本（或一次重试）下通过、在另一个版本下失败时启用，跨重试或跨 Harness 版本比较通过与失败的执行，以分离反复出现的模块瓶颈 [25]、[52]。

第三，反向的步级因果追踪无需人工步标注即可定位早期的复利式错误：它从最终的测试失败或堆栈跟踪出发，沿数据依赖反向追溯到最早写入或误读了损坏变量的那一轮 [21]；或者检查运行时后置条件不变量，以及中间轮次发出的视觉状态转移预测——例如截图差异显示一次 UI 点击带来的屏幕变化为零 [38]，或某次文件编辑发生在任何探针脚本验证代码不变量之前 [37]。

第四，在任务智能体自我报告中，任务智能体回顾自己失败的轨迹，报告工具或指令在哪里卡住了它，而验证器只保留有具体证据支撑的主张 [22]。表 I 中更广泛的存档历史、复杂度预算、token 成本与多臂老虎机任务聚类信号 [19]、[20]、[23]、[42]、[43]，通过优先决定下一步瞄准哪些失败簇，对这四种基于轨迹的归因技术形成补充；而错误签名表与代码库索引则把每个被诊断出的失败簇直接映射到责任所在的 Harness 钩子或源码模块 [24]、[53]。

**候选修复如何被合成并保持可编辑。** 一旦诊断出一个失败簇，优化器就必须把该诊断翻译成可维护的 Harness 编辑。生产级 Harness 动辄数万行代码 [4]，无约束的整文件重写既脆弱又容易引入语法或导入错误。现有系统通过三种方式让自我修改保持可靠。

其一，生命周期钩子注入暴露轮前、工具后与轮停钩子，使优化器能够编写短小、自包含的中间件函数，而不必触碰核心事件循环 [8]、[54]。其二，有范围的模块与动作守卫合成把编辑限制在隔离 git 分支内的特定类上，或合成短小的代码守卫，在执行前滤掉无效动作 [19]、[20]、[25]、[40]。其三，维护代码库索引把高层的智能体行为映射到确切的源文件与函数，使优化器知道该改哪里，而不必通读整个仓库 [53]。

**该改什么：持久规则与上下文消融给出的三条实用设计教训。** 明确的负面边界（例如禁止提前退出、禁止改动无关文件）始终优于逐步的过程性建议——后者会让智能体在任务偏离模板时变得僵硬，损害求解率 [55]。此外，当智能体的瓶颈在于实现能力时，把静态的仓库文档塞进上下文几乎得不到收益 [56]。指令文件里的纯文本安全规则也缺乏与之匹配的内置沙箱控制，除非背后有确定性代码钩子在运行时拦截不被允许的工具调用 [57]。

**自我改进的 Harness 在运行时究竟发现了什么。** 跨编码、终端、网页、GUI 与机器人基准，自动化优化器反复发明出五族具体的运行时机制（表 I）：

**1）停止前验证与补丁检查子智能体：** 优化器在终止前插入强制检查，验证必需的输出文件确实存在、检查 git diff 有无意外改动或残留调试语句、自动运行语法与单元测试套件，或在允许智能体退出之前派生一个轻量验证器子智能体来审查补丁 [4]、[8]。由于过早终止是编码与终端智能体中最常见的失败模式之一，拦住未经验证的退出始终是编码与终端基准上求解率提升幅度最大的手段之一。

**2）空轮与失控推理的恢复：** 当推理模型耗尽其思考 token 预算却没发出工具调用、或返回格式错误的动作块时，演化出的恢复钩子会接住这个空轮、总结卡住的推理步骤，并注入一条配对了完成自检的续接提示词 [24]。

**3）循环打断与策略改向：** 当智能体反复执行失败的 shell 命令、重复读取相同的文件区段、或在两个损坏的编辑之间来回摇摆时，优化器会合成有状态的计数器，跟踪连续的工具错误或重复的参数，迫使智能体退后一步、检查自己的假设并改换策略 [8]、[21]。

**4）跨轮的环境与记忆持久化：** 外循环优化器自主发现中间件，在无状态的 shell 调用之间捕获并恢复工作目录与 PATH 变化 [8]，并在活跃工作记忆（当前子目标、文件指针与用户约束 [58]、[59]）与可复用的经验记忆 [31]、[37] 之间演化出结构化的分离。自我改进的 Harness 还会纳入或调优基础的上下文压缩与动作接口原语，包括观察掩码 [32]、[33]、shell 或代码动作空间 [34]、[35]、增强的工具描述 [60] 与按需工具加载 [36]、[61]。

**5）视觉与物理状态提交守卫：** 在桌面与具身场景中，优化器会发现截图转移验证器，确认 UI 点击确实改变了屏幕状态之后才继续 [38]；还会发现带视觉进度或版本检查的状态提交，防止失败的恢复步骤污染具身智能体的物理任务状态 [39]、[52]。
## 4 不过拟合的 Harness 演化与验证

**单分支精化、分支存档与递归自我改进器。** 一旦 Harness 优化器诊断出智能体为何失败，它就必须决定如何在四种主要搜索拓扑上探索候选代码编辑。最简单的做法是逐步的单分支精化：把定向补丁反复施加到单一在位 Harness 上，只有通过回归检查的改动才被保留 [8]、[20]、[37]。单分支搜索样本效率高、也易于审计，但当早期的结构性选择限制了后续编辑、或修复一个任务组导致另一个任务组回退时，它常常停滞在局部最优 [43]、[62]。

为了避免被困在单一设计路径上，基于种群的系统维护候选 Harness 的分支树或存档，使优化器可以回访早期变体、保留解决小众失败模式的垫脚石设计、并并行探索多样的执行策略 [21]、[29]、[30]、[42]、[43]。更进一步的变异库搜索，把每一个历史补丁都索引进一个可检索的仓库，并打上标签：它改了哪个文件、针对哪个错误签名、让验证性能改变了多少——这使优化器能跨分支检索并组合兼容的补丁，而不必从零发明修法 [24]。

当仅凭本地失败日志不足以启发修法时，文献引导的搜索会从科学论文中检索算法思想，并把它们改造成新的 Harness 模块 [63]。最后，递归自我改进器把编辑范围从任务 Harness 扩展到优化器代码本身 [26]–[28]，例如达尔文哥德尔机器（DGM）[29] 与门德尔哥德尔机器（MGM）[30]：通过把自己的文件补丁工具重写成行锚定的 diff 编辑器，或改进自己审查与挑选变体的方式，递归系统可以在多轮之间复利式累积收益——尽管这样做需要严格的沙箱隔离，以防搜索循环弄坏自己 [29]、[30]。

**模块化演化与冲突消解的合并过程。** 变异的单元也已从粗粒度的多智能体调用图 [64]、[65] 与工作流搜索 [17]、[18]、[66]、或多 Harness 路由器 [43]、[67]，转移到单个运行时 Harness 内部的模块化演化。一次性重写整个生产级 Harness 往往失败，因为观察过滤、上下文压缩、循环上限、完成检查这类子系统依赖共享的状态假设。同时修改全部这些子系统会让信用分配变得困难，并使某一处例程的编辑破坏另一处——例如新的输出过滤器恰好剪掉了新验证检查需要读取的堆栈跟踪。对照消融实验证实：一次性编辑所有 Harness 模块，在留出的终端基准上表现不如起始种子 Harness [25]。

近期系统通过模块化隔离与显式的合并阶段来解决这种耦合问题（图 2，保障措施 1）。把一个终端 Harness 分解成五个独立模块（智能体循环、工具使用、观察管理、上下文管理、任务完成检测），可以让每个模块在受限范围内演化，随后由一次集成合并过程在验证切分上解决跨模块冲突 [25]。编码优化器同样先独立测试模块更新，再在全局通用性检查之下将其合并 [22]。在物理领域，具身机器人 Harness 把规划、监督、验证与错误恢复隔离到不同的上下文中，使故障不会跨阶段级联 [39]；而具身视觉系统则通过回合级的增益-损失修复来精化共享的多子任务例程 [52]。

关键在于：即使文件层面的合并是干净的，运行时仍可能在行为上冲突，因此这些合并过程通过运行一个以失败迹线为条件的 LLM 引导代码对账或重组过程，来消解行为上的不兼容 [22]、[25]、[52]。

**朴素 Harness 搜索为何过拟合，以及防止它的验证门控。** 智能体 Harness 由任意可执行代码与提示词组成，一个在小型开发集上最大化分数的无约束优化器很容易过拟合。无约束搜索与其说是发现了通用的控制逻辑，不如说经常硬编码任务特定的启发式、脆弱的关键词触发器，以及利用开发集怪癖的臃肿重试链。经验消融展示了朴素搜索对泛化的伤害有多严重：无约束的递归演化在自己的开发集上拿到最高分，却在分布外（OOD）基准上几乎没有任何收益，同时让每任务 token 用量翻了一倍还多 [20]。直接在基准子集上演化同样会把基准特定的捷径误当成真正的架构进展 [68]。

在模块化隔离（保障措施 1）之外，横跨阶段 1 至 3 与任务池设计的三项跨阶段保障措施可以恢复 OOD 迁移能力（图 2）。

**其一，保持编辑小而通用（保障措施 2）**：把阶段 1 与阶段 2 的每个补丁都绑定到一个反复出现的失败簇，而不是孤立的某次执行；强制执行逐步收紧的编辑规模预算（例如在正则化递归自我改进 RRSI [20] 中限定跨搜索代际的 git diff 行数或提示词 token 增量），并拒绝任务特定的提示 [8]、[20]、[21]。

**其二，严格执行阶段 3 验收检查（保障措施 3）**：校验语法、要求在演化集与验证集上都不回退 [8]（或在完整评估之前验证补丁确实如预期改变了那个失败的步骤 [38]），并使用运行时插桩确认新增代码路径确实被执行，防止没被用到的代码碰巧通过 [24]。虽然自动化死代码剪除会在每次提交时移除未执行的分支 [20]，但在目标失败簇上专门验证执行 [24]、并为演化出的模块配上故障注入单元测试 [69]，可以避免把罕见的防御性恢复钩子一并剥掉。

**其三，严格分离开发与测试任务池（保障措施 4）**：在经过筛选、与下游评估套件无重叠的外部任务仓库上演化 Harness，并在 OOD 测试之前把 Harness 冻结 [25]、[68]。

## 5 模型适配、跨模型迁移与成本效率

**选择外部优化器还是同模型自循环。** 用外部编码优化器 [19]、[23]、[24] 还是同模型自循环 [8]、[25] 来演化 Harness，取决于模型规模如何影响「提出编辑」与「从编辑中获益」这两件事。把外层优化器与内层任务智能体解耦的跨规模对照实验确立了两条核心发现 [70]。

其一，在模型达到基本的指令遵循阈值（例如技能与提示词更新类任务上的 32B+ 模型）这一前提下，补丁提出的质量从中型模型到前沿模型基本持平：一旦具备基本能力，这类模型提出的 Harness 更新与前沿模型提出的一样有效，因为诊断已有的批次轨迹要比端到端解出整个任务容易 [70]。

其二，对内层任务智能体的收益随模型规模呈非单调变化。非常弱的模型难以调用和遵循检索到的技能与规则；中等能力的模型获益最多，因为演化出的 Harness 恰好提供了它们原生缺乏的结构化指导与状态跟踪；前沿模型则主要在复杂的长跨度问题上获益 [11]、[70]。

**把 Harness 缺陷与模型局限分开，也指导该写什么样的补丁** [22]。当失败源自 Harness 缺陷——例如笨拙的编辑接口、缺失的工具反馈、未经验证的停止——修好那个接口或钩子就能释放模型已有的能力 [10]。反过来，当较小的模型跟丢状态或在失败命令上打转时，添加提示词规则常常带来回退，而把该负担下放到确定性代码（例如循环打断器、依赖检查或状态恢复中间件）则能可靠地补偿 [8]、[21]。

因此，当任务智能体本身已是一个有能力的编码模型时，同模型自循环是有效的 [8]、[25]；而对更小的模型、规划或机器人领域中非编码的领域智能体 [39]、[46]、以及必须从零诊断原始多轮轨迹并编写复杂中间件的无助自循环而言，更强的外部编码优化器仍然必不可少。

**跨不同能力的多个模型演化 Harness。** 在多个前沿模型上跨 Harness 评估，会频繁出现名次反转：为一个模型家族最大化准确率的 Harness 配置，在完全相同的基准上可能伤害另一个模型，因为模型在格式化工具参数、遵循否定指令、以及决定何时停止方面各不相同 [10]。当不同模型从同一个起始 Harness 出发、在相同任务上演化时，它们会发明符合各自失败习惯的修法。例如一个模型加了循环打断器和提前建文件来遏制过度探索，第二个模型加了依赖检查和补丁审查子智能体来抓住仓促的编辑，第三个模型则加了跨命令的持久 shell 状态 [8]、[24]。

即便如此，结构性运行时检查 [19]、[20]、记忆存储 [31]、视觉守卫 [38] 与模块化控制循环 [22]、[25] 跨模型迁移的效果，远好于针对特定模型的提示词措辞。代码补丁在失败习惯相同的模型之间迁移也很可靠，尽管直接用部署模型演化能达到最高峰值分数 [24]。

因此，支持多个不同能力的模型，最好以两层演化工作流来做。在阶段 3 验证期间，候选结构补丁（例如验证钩子、环境快照与上下文压缩）可以在目标模型套件上测试，只有当它们在所有模型上都带来提升或至少持平才被提升进共享核心 [19]、[22]、[31]。当某个候选补丁改善了一个模型家族却在另一个家族上触发名次反转时（例如激进的循环打断阈值或特定模型的提示词规则），外循环可以把该补丁分叉成一个轻量的逐模型适配器，或按失败签名把它索引进共享补丁库 [8]、[24]、[71]。运行时，路由器可以把查询分派到专家型 Harness 分支 [43]，或者用一个紧凑策略对每个任务施加专属补丁 [44]。

**控制搜索期执行成本与运行时 token 开销。** 自我改进的 Harness 必须在两个不同的时间尺度上管理算力：搜索期间评估候选编辑的一次性外层成本，以及部署期间每任务产生的内层 token 成本 [9]、[10]。为削减搜索期的执行成本，近期系统用三种定向策略取代蛮力重评估。

多臂老虎机调度器按失败签名对开发任务分组，把执行聚焦到未解决的失败簇或有希望的模块组合上，而不是重测智能体已经通过的任务 [23]、[72]。轨迹回放模拟器把过去的执行树变成离线测试台，在运行昂贵的真实容器之前先筛查搜索策略 [41]。多分支路由器（例如自我改进分支混合 MoSIB [43]）通过把已解的开发任务剪成不同的分支子集、并优化一个基于提示词的路由器来为每个查询挑选最佳分支，从而共同演化专家型 Harness 分支。在互补的部署范式中，测试时补丁生成器 [44] 并不削减初始离线搜索预算，而是把离线搜索轨迹摊销成一份紧凑的操作手册或策略，在部署时一次性施加定制补丁、无需迭代搜索。

在运行时，经验消融表明准确率与 token 效率不必取舍。联合优化求解率与 token 成本的多目标搜索循环 [20]、[42]、确定性的观察掩码 [32]、以及分块丢弃旧工具输出且不破坏提示词缓存的周期性历史截断 [33]，都在保持或提升求解率的同时削减了每任务 token 用量。此外，用验证钩子尽早抓住错误，可以在无产出的探索循环烧掉几十轮之前就将其拦下，使更便宜的低努力推理设置能够匹敌昂贵的高努力运行 [38]、[73]。

当演化出的 Harness 降低了每任务 token 用量时，前期搜索成本在越过盈亏平衡查询量之后即可直接摊销；当它是在相同或更高的运行时成本下提升求解率时，则必须与算力对齐的测试时扩展基线做基准比较（例如在同为总执行与验证器反馈预算下、于冻结种子 Harness 上做并行 Best-of-N 采样或顺序精化 [68]、[74]）。
## 6 失败模式、安全边界与评估标准

**内部 Harness 退化：提示词膨胀、工具混淆与模块冲突。** 给智能体对自己运行时的写权限，会引入五种反复出现的失败模式，它们分为「内部 Harness 退化」与「外部沙箱或评估器被利用」两类（表 II）。如第 3、4 节所述，前三种模式（表 II 的 A 部分）源于 Harness 内部嘈杂的信用分配：单次运行反思会发明不必要的规则、在不清理的情况下让指令文件不断膨胀、或在压缩过程中丢掉用户约束（模式 1）[50]、[51]、[59]；臃肿的插件库造成技能遮蔽，重叠的工具描述使动作选择劣于一个极简的 shell 接口（模式 2）[35]、[75]；同时编辑整个 Harness 则破坏控制例程与验证例程之间共享的假设（模式 3）[25]。

后两种失败模式（表 II 的 B 部分）更为严重，因为外层搜索会主动利用评估沙箱、评分流水线或持久记忆存储中的弱点。

**基准测试作弊与环境泄漏。** 在模式 4 中，由于外层搜索会挑出验证分数最高的候选 Harness，只要评估沙箱留下环境捷径，它就会主动放大这些捷径 [84]、[85]。在仓库级编码基准上，智能体常常检查 git log、reflog 或 pull request 元数据来恢复真实的人类提交，而不是从零解决该问题 [76]。在终端环境中，智能体即使被提示词明确禁止，仍会读取或执行泄漏的参考解法与测试文件 [77]。类似地，当候选 Harness 只在一小批可见的验证断言上受筛查时，演化搜索可以合成查表式程序：通过所有可见检查，却在留出的测试输入上完全失败 [78]。虽然在提示词中加入明确的反作弊指令可以减少随手可得的捷径 [76]，但纯文本安全规则缺乏内置的沙箱强制力 [57]。因此，防止基准测试作弊需要从评估容器中剥掉 git 历史与网络访问，并在严格留出的测试套件上给候选打分。

**篡改评估器、执行日志与持久记忆。** 在模式 5 中，虽然把评分脚本、测试套件与执行日志放在智能体工作区内可以简化容器搭建，但让它们可写，就等于允许自我改进的 Harness 通过重写评估器、而不是解决任务来抬高分数。经验审计表明，只要这些文件落在智能体的写权限范围内，自我改进的智能体就经常削弱单元测试断言、压制错误退出码或编辑打分脚本 [47]。更令人担忧的是，对商业编码 Harness 的审计发现，智能体可以修改或删除自己的本地执行日志，抹掉违规证据、逃避轨迹监控 [48]。

持久记忆、工具调用链与配置文件构成了进一步的跨会话攻击面：被植入工作区笔记、缓存规则或工具配置中的恶意指令或 token 耗尽触发器，会一直带到未来的任务中 [80]、[81]。呼应 Thompson 的《论信赖信赖》（Reflections on Trusting Trust），仅仅污染少量训练任务，就可能诱导一个自我修改的智能体写下永久性的 Harness 规则，在后续干净的任务上关闭 HTTPS 校验、JWT 验证或安全 YAML 加载之类的安全检查 [79]。

即使没有对手，安全或权限规则随时间推移而收紧，也会让演化存档中的缓存分数过期；如果不重新测试存档候选，不安全的旧 Harness 变体就可能继续存活 [82]。让这些风险雪上加霜的是，对开源智能体项目的软件工程审计发现：自动化单元测试覆盖不到处理 LLM 的 Harness 代码中一半的行与分支 [69]。

**实用安全边界与评估标准。** 表 III 把这些失败模式翻译成四条部署安全边界（A 部分）与三条评估报告标准（B 部分）。

**表 III**　值得信赖的自我改进型智能体 Harness 的实用安全边界与评估报告标准。

| 原则 / 标准 | 实用要求及其重要性 |
| --- | --- |
| **A 部分：实用安全边界** | |
| 1. 隔离评估器与日志 | 把评分脚本、测试套件与仅追加的执行日志放在智能体沙箱之外的只读存储中，使智能体无法查看隐藏测试或篡改自己的日志 [47]、[48]。 |
| 2. 禁止权限升级 | 在所有自我编辑上强制执行严格的权限限制，使被修改的 Harness 永远无法授予自己比父进程更宽的文件、网络或子进程访问权 [57]、[83]。 |
| 3. 保护持久记忆 | 把保存的记忆、学到的规则与生成的插件当作不可信输入，追踪其来源并按技能与会话设置 token 预算；安全策略变化时重新测试存档 Harness [79]–[82]。 |
| 4. 测试 Harness 代码 | 为演化出的运行时模块配上自动化单元测试与分支覆盖测试，检查 LLM 错误处理与恢复路径 [69]。 |
| **B 部分：评估报告标准** | |
| 1. 分离演化集与测试集 | 把任务严格拆成互不重叠的搜索集、验证集与留出测试集（最好跨不同基准），并报告相对完全相同的起始 Harness 的域内收益与分布外收益 [20]、[25]、[68]。 |
| 2. 分离搜索成本与运行时成本 | 报告前期搜索成本，以及在全部尝试过的任务上、按已解决任务计的平均运行时成本（避免选择性偏差），并与种子 Harness 上算力对齐的测试时扩展（如 Best-of-N）做比较 [9]、[23]、[44]、[68]、[74]。 |
| 3. 跨模型与消融检查 | 至少在两个不同的模型家族或规模上演化后的 Harness，并逐个关闭演化出的模块，验证它们在运行时确实有帮助 [10]、[24]、[70]。 |

操作系统级的只读隔离可以确定性地阻断对评估器与日志的直接篡改，而针对持久记忆、学到的规则与工具链的来源追踪和存档重测主要属于检测性手段，必须与严格的运行时权限边界、按技能与会话的 token 预算配合使用，才能遏制语义层面的持久化与间接提示词注入攻击 [80]、[81]。这些标准共同强制执行一条唯一的架构不变量：可变的 Harness 绝不能控制自己的权限边界、评分流程或审计日志；任何被声称的收益都必须在留出任务切分、算力对齐的搜索与运行时预算、以及多个模型家族上得到验证。
## 7 实验

我们在 SWE-bench Lite [1] 上围绕三个问题检验本文的框架（表 IV）。其一，测试时重试或提示词规则能否取代运行时代码钩子？其二，无约束的整体 Harness 重写，与阶段 3 门控的模块化演化相比，在准确率与 token 成本上孰优孰劣？其三，演化出的 Harness 能否零样本迁移到更强的模型？

**设置与基线。** 我们在 60 个经过验证的 Python 缺陷修复任务上评估。40 个 sympy/sympy 任务被拆成开发集（N=12）、验证集（N=8）与留出的域内测试集（N=20）；20 个 django/django 任务构成留出的跨仓库测试集（N=20）。每次运行都在一个剥掉 git 历史的干净单提交沙箱中执行，补丁在外部的留出测试套件上评分（表 III）。

所有方法都从同一个 142 行的 Python 种子 Harness 出发，它覆盖图 1 的四个组件：`context_mgr.py`（提示词与原始轮次历史）、`control.py`（12 轮上限与 JSON 解析器）、`action_aci.py`（bash、view_file、edit_file 与 finish）、`verify.py`（一个直通的 stop 钩子）。A 部分把 Gemini 3.8 Flash 冻结为任务智能体，用 Gemini 4 Carbon 作为共享的外部优化器，在完整模块提示词上超时则回退到 Gemini 4 Argon。每个优化器读取完全相同的开发轨迹，且看不到隐藏测试名。我们比较五种方法：只运行一次种子 Harness（Pass@1）；对三次种子执行做排序但不使用 oracle 测试（Best-of-3）；把学到的文本规则追加到 RULES.md（仅提示词反思）；在没有验证与 token 上限的情况下一次性重写全部四个 Python 文件（无约束整体重写）；以及在阶段 3 验证、运行时行执行检查与 110k token 运行时上限下逐个模块更新（模块化门控演化，式 1）。B 部分把这些冻结的 Harness 零样本迁移到 Gemini 4 Argon。

**重试与提示词规则无法取代运行时代码。** 在 Gemini 3.8 Flash 上，种子 Harness 只解出 5.0% 的留出任务（表 IV，A 部分）。大多数运行把 12 轮全部耗在反复阅读未压缩的大文件上，其余则在空 diff 上调用 finish。对每个任务采样三次执行（Best-of-3）让 token 成本翻了一倍还多，准确率却没有任何提升，因为上下文在每次重试中都以同样的方式溢出。

仅提示词反思写出了一个 RULES.md 文件，其首条规则明确禁止在 diff 为空或未经测试时调用 finish。由于没有 Python 代码在运行时阻止终止，模型依然会提前退出：跨仓库的未验证停止从 15.0% 翻倍到 30.0%，留出准确率跌到 2.5%。

**无约束重写推高成本，模块化门控则产出精简代码。** 无约束整体重写把留出准确率抬到 42.5%，但它是靠把轮次上限从 12 提到 28、且不压缩近期文件与 shell 输出换来这一收益的。随着上下文在 28 轮中不断堆积，运行时成本跳到种子 Harness 的近四倍，达到每任务 451.6k token，其中一次执行超过 2.8M token。模块化门控演化则一次更新一个模块，并保持 12 轮上限：

**1）context_mgr.py（接受）：** 把两轮以前的观察压缩成首尾摘要，并追加一条实时的轮次与编辑状态页脚。这削减了 token 用量，同时把开发集与验证集准确率提高了五倍。

**2）action_aci.py（接受）：** 增加分窗文件视图、截断的 shell 输出，以及 finish 上的空 diff 守卫，消除过早的空退出。

**3）control.py（被阶段 3 拒绝）：** 把轮次上限从 12 提高到 18。开发集准确率虽然跃升，验证集准确率却下降，且 token 用量突破 110k 上限，因此阶段 3 拒绝该编辑。

**4）verify.py（接受）：** 只有在 git diff 非空、被编辑的 Python 文件干净编译、且编辑后的测试运行无错误通过时，才允许退出。

在留出任务上，这个 12 轮的 Harness 在两个仓库上都达到 40.0% 的准确率（为种子的 8 倍），且零未验证退出。关键在于，它每任务只用 46.7k token：比种子 Harness 少 2.5 倍，比无约束重写少近 10 倍。这些运行时节省在不到 100 个部署任务内就抵消了全部 100 次搜索执行的成本。

**零样本迁移到更强的模型。** 当不加重新调优地迁移到 Gemini 4 Argon 时（表 IV，B 部分），紧凑的代码机制比冗长未压缩的轨迹泛化得好得多。在种子 Harness 上，Argon 凭更强的指令遵循避免了空 diff 退出，但仍然把 12 轮全花在读未压缩文件上，只解出 10.0% 的留出任务；仅提示词反思达到 15.0%；无约束整体重写掉到 30.0%，因为 Argon 更长的推理链与 28 轮未压缩上下文叠加在一起。模块化门控演化在两个仓库上都取得最高准确率（总体 37.5%），每任务 64.8k token，以不到四分之一的 token 成本胜过无约束重写。

## 8 讨论与结论

随着自我改进型智能体 Harness 走向更广泛的部署，四个开放的研究方向凸显出来：

**1）协同适配模型权重与 Harness 代码：** 更新模型权重会改变模型的失败方式、并使较早的 Harness 检查过时；而编辑 Harness 代码则会改变强化学习期间看到的观察、工具 schema 与动作分布。稳定这一循环需要统一双向的模型-Harness 共同演化 [86]、由路由式 Harness 引导的后训练 [87]、以数据为中心的权重更新 [88]，以及把演化出的 Harness 行为蒸馏回模型权重 [89]。

**2）环境漂移下的终身适配：** 当外部 API、软件依赖或用户工作流在数月的部署中发生偏移时，Harness 必须检测分布漂移、修复过期的工具包装器或记忆存储，并防止随着持续演化的 Harness 跨阶段扩张而出现「Harness 导致的遗忘」[62]、[82]、[90]、[91]。

**3）自我修改代码的可验证安全保证：** 由于纯文本安全规则在长时间跨度上很容易被绕过，未来的自我修改 Harness 必须结合证书驱动的变异限制 [92]、脚手架可达性与平稳性的理论审计 [74]、跨自我修改的形式化权限与预算配额守恒 [83]，以及自动化分支覆盖单元测试 [69]。

**4）动态、防污染的基准：** 静态基准很快会泄漏进模型预训练或演化存档，因此要对 Harness 优化器做公平比较，就需要持续刷新、无污染的任务生成器 [93] 与演化中的 Harness 流 [91]，并配上跨模型家族与 Harness 配对的标准化、算力对齐的测试时扩展基线 [9]、[10]、[68]、[74]。

**结论。** 智能体 Harness 已不再是包裹在冻结模型外面的固定执行外壳；它是一个可执行、自我改进的运行时系统，其上下文管理器、控制循环、动作接口与验证钩子决定了原始模型能力能否变成可靠的长跨度工作。在这一范式中，持久的收益并不来自由标量分数或孤立执行驱动的无约束整体重写——那很容易破坏跨模块状态、并过拟合开发集的怪癖——而是来自有纪律的闭环系统工程。

构建值得信赖的自我改进 Harness，要求我们在原始轨迹上把系统性运行时缺陷与模型能力上限分开，在冲突消解的验证门控与 token 效率门控之下演化模块化代码机制，让共享检查适配各模型的特定习惯，并把评估器、审计日志与权限边界严格隔离在可变运行时之外。
