## 摘要

智能体进化遵循一个简单的循环：提议者（proposer）写出候选工件（提示词、技能、记忆），选择机制则接受得分更高的那些。这个循环颇有前景，但实践者面临一个谜题：不同论文之间方法互有胜负，而且进化在某些任务上常常无法启动。我们将这一谜题追溯到分辨率假设（Resolution Hypothesis）：智能体进化之所以停滞，并非因为方法无法提出更好的工件，而是因为带噪声的评估无法可靠地识别它们。

在七种进化方法、六个模型上（超过 1,000 万次 LLM 调用），我们发现在使用评估分数的两个层面上，该假设都得到支持。在候选层面（选择工件），确实存在有帮助的候选工件，但选择机制在把它们与有害工件区分开这一点上并不比随机更好，于是误差逐轮累积。在方法层面（对方法排序），典型的几个百分点的边际差异，小于同一方法两次独立运行之间的差异，因此已发表的排名往往靠运气。

这些发现合起来表明：智能体进化常常受制于「可靠地识别改进」这一瓶颈。这要求我们转变开发与评估自我改进智能体的方式——从设计越来越多的候选改进系统，转向让真正的改进变得可检测、可累积。

## 1 引言

智能体进化通过打磨持久化的外部工件——提示词、技能、记忆乃至完整的智能体 harness——来改进冻结的 LLM 智能体。它通常遵循图 1b 所示的循环：提议者写出候选工件，在任务集上评估由此得到的智能体，选择机制接受得分更高的候选工件。这一族进化方法在多个基准与模型上展现了前景 [24, 27, 37]，使「系统持续改进自身工作流」这一前景越来越可信。

然而图景远未尘埃落定。研究常常得出相互冲突的结论：同样的方法在不同基准上在有效与无效之间翻转，其排名在不同论文之间互换位置。在 Terminal-Bench [22] 及其他编码智能体基准上，进化方法被反复报告为停滞 [7, 17, 29]；而在其他基准上，每种新方法都声称超越前作 [18, 24, 31, 43]。进化是否有帮助，取决于具体设定，其方式尚无法被学界预测。

这种不稳定侵蚀了学术界与产业界对这一方向的信心，并且奖励了那些恰好在评估时更幸运的方法。然而不可靠的评估影响的不只是进化方法的报告排名。在候选层面，同一种评估决定哪些工件被带入下一轮。结果，进化方法本身就变得不可靠。

我们认为，这种评估建立在一个未经检验的前提之上：其分数能够识别进化所带来的改进。我们发现，该前提在使用分数的两个层面上都不成立。在方法层面，论文中区分方法的边际差异，小于同一方法两次独立运行之间的差异：在 Terminal-Bench 上，当前的通行做法（附录 D.3）只有 33% 的时候能在四种文本工件方法中识别出真正最好的那一个，仅略高于随机猜测（第 4 节）。在候选层面，选择器在两个候选工件中挑出更好的那个的概率只有大约一半，不比掷硬币更好（第 5.2 节）。由于每一轮都接受碰巧得分最高的工件，分数上升了，但工件并没有变好（第 5.3 节）。

这两处失败都可以追溯到同一个约束，我们将其表述为一个假设。

> **分辨率假设。** 智能体进化的瓶颈在于识别哪些工件带来改进，而不在于提出它们。

为什么识别改进如此困难？因为模型权重是冻结的，一个工件只能通过改变模型在推理时的行为来发挥作用，而智能体每次尝试任务时 LLM 轨迹本身也在变化。因此，把真正的行为改变与评估噪声分开是困难的。我们把一条评估流水线的分辨率定义为它能可靠地与噪声区分开的最小真实改进。一旦真实改进低于这一分辨率，候选选择就退化为随机，进化过程中几乎累积不下什么改进（图 1a）。提议决定了可供选择的改进有多大；分辨率则决定了一个改进可以小到什么程度仍能被可靠识别。

我们在远大于当前实践的规模上检验这一假设。以往工作通常依赖单次进化运行（附录 D.3），而我们对每个方法在每个模型与基准上运行 8 次，并对每个产生的工件评估最多 16 次，合计 1,030 次独立进化运行和超过 210 万条测试轨迹。

总体而言，本研究覆盖七个智能体进化方法、六个模型与四个智能体基准，外加九个我们重新审视其已报告增益的其他基准；据我们所知，这是迄今规模最大的智能体进化可复现性研究。我们的发现如下：

- 方法层面（第 4 节）。典型的方法边际差异小于单次运行所能识别的幅度。历史上报告过的大幅增益是我们假设最清晰的例证：在那些基准上，进化通过利用评估捷径成功——这类捷径几乎同时提升几乎所有任务，产生大到足以超过评估分辨率的增益，而一旦评估被修复，进化就停滞（第 4.2 节）。
- 候选层面（第 5 节）。我们从该假设导出三条预测，全部在 Terminal-Bench 上的实验中得到支持：
  - P1 候选池中确实包含能真正提升任务性能的工件：提议不是瓶颈（第 5.1 节）。
  - P2 常见的选择机制——无论基于执行分数还是 LLM 判断——在识别两个候选工件中更好的那个时，表现接近随机（第 5.2 节）。
  - P3 每轮的选择误差跨轮累积，造成同一方法两次独立运行之间的巨大差异，并因此翻转排名（第 5.3 节）。

最后，我们探索了在候选与方法两个层面应对低评估分辨率的实用方法，从方差更小的行为检查，到对提议者与选择器的分别评估（第 6 节）。

总而言之，这些发现提示了一种看待智能体进化的新视角。提议者决定有哪些改进可供选择，而评估分辨率决定哪些改进能够被保留和累积。当分辨率不足时，真正的改进淹没在噪声中，而巨大的、易于检测的变化即使利用了评估捷径也能主导进化过程。进展要么需要扩大被提出的改进，要么需要让更小的改进被可靠地检测到。更广泛地说，开发更高分辨率的反馈，可能与开发更强大的进化算法同等重要。

## 2 相关工作

智能体进化方法共享一个「提议—评估—选择」循环，但在进化的对象上有所不同：提示词 [2]、技能 [24, 37]、记忆 [27, 43] 或可执行代码 [18, 42]。若干分析记录了这一范式的脆弱性，例如对运行间方差与任务顺序的敏感性 [39]、依赖稀疏反馈的增益 [19]，以及技能引发的失败或失控累积造成的污染 [7, 17, 29]。这些发现指向带噪声的选择是一种共同的失败模式，并与最优臂识别 [12]、不确定性感知的强化学习评估 [1] 以及 PACE 的错误接受分析 [30] 相联系。我们的工作把这一机制分离出来：我们把评估噪声与运行间方差分开，并用受控的候选池独立检验提议质量与选择可靠性。附录 A 给出完整讨论。

## 3 方差分解与实验设置

为了判断基准分数能否识别改进，我们首先需要一个形式化模型，把进化算法的随机性与评估工具的噪声分开。本节定义方差分解并概述我们的实验。

### 3.1 分数方差的两个来源

考虑在一个基准上评估的某种进化方法。记工件 A 为该方法产生的持久化外部状态（一个提示词、一个技能库、一个记忆手册或一个智能体 harness）。对工件 A 评估一次得到观测分数 Ŷ(A)。我们把工件 A 的真实质量定义为 Y(A) = E[Ŷ | A]，即重复评估下的期望分数。单次观测分数可分解为 Ŷ(A) = Y(A) + ϵ，其中 ϵ 是零均值的评估噪声（E[ϵ | A] = 0）。在独立的进化运行之间，产生的工件各不相同；记 τ² = Var(Y(A)) 表示真实质量的运行间方差。由全方差公式，观测分数的方差分解为：

```
Var(Ŷ) = E_A[ Var(Ŷ | A) ] + Var_A[ E[Ŷ | A] ]        (1)
          └────── σ² ──────┘   └────── τ² ───────┘
```

（译注：原文此处公式排版无法完整提取，按符号说明重建。）

第一项 σ² 是对每个工件内部的评估噪声取平均；第二项 τ² 衡量工件质量本身在各次运行之间的变化。标准做法常常报告单次运行、评估一次的结果（表 8），把两个来源混为一谈。要识别真实改进，必须分别界定每个来源。关键在于，分辨率取决于问题：识别单个固定工件相对参照的增益只受 σ² 限制，而识别两种方法之间的差异受 (τ² + σ²) 限制，因为方法的每次运行都会抽到一个新的工件。

### 3.2 实验

我们研究两个家族的七种进化方法。四种文本工件方法进化提供给智能体的文本：提示词（GEPA [2]）、技能（SkillOpt-Lite [31]、Trace2Skill [24]）与记忆手册（ReasoningBank [27]）。三种 harness 方法进化智能体的脚手架（HarnessLens [36]、Meta-Harness [15]、AHE [18]）。我们使用六个智能体模型：GPT-5.4 nano [25]、GPT-5.6 Luna 与 Terra [26]、DeepSeek-V4-Flash [6]、Kimi-K3 [13] 与 GLM-5.2 [9, 41]。模型覆盖随成本而定：较便宜的实验使用全部六个模型，较昂贵的实验只用其中一个子集。实验分为四组：

- 方差测量（第 4.1 节）。在 ALFWorld [32]、SpreadsheetBench [20]、OfficeQA [5] 与 Terminal-Bench v2.1 [22] 上运行全部七种方法，每种都反复进化与评估以估计 τ 和 σ。

- 增益审计（第 4.2 节）。十二个基准上已报告的最大增益——上面前三个加上九个来自各方法原论文的基准——在已发布与修复后的评估下重新检验；其中四个基准上，我们还在修复后的评估下重新进化这些方法。

- 候选池（第 5.1 与 5.2 节）。不失一般性，我们使用基于文本的技能来单独检验提议质量与选择可靠性，构建两个各含 n=100 个技能、分别针对各自问题的候选池（附录 F.1）：提议池（Proposal Pool，第 5.1 节）在 10 个 Terminal-Bench v2.1 训练任务上生成、在 10 个不相交的测试任务上评估（每对 16 次 rollout），以测量样本外的提议增益；选择池（Selection Pool，第 5.2 节）汇集来自 Terminal-Bench 与 DeepSWE 轨迹的候选，覆盖 11 个按难度分层的 Terminal-Bench 任务（每对 8 到 15 次 rollout），用于对选择规则与轨迹裁判进行基准测试。

- 轨迹重评估（第 5.3 节）。Terminal-Bench 上八次 SkillOpt-Lite 与八次 GEPA 进化运行的每个中间工件，每个任务重评估八次。

## 4 方法层面的分辨率

两个方差分量都测量之后，我们就可以检验标准评估实践能否识别这些论文所报告的方法差异。

### 4.1 单次报告无法对方法排序

对每种方法、每个模型与每个基准，我们独立运行进化 8 次（文本工件方法在 GPT-5.4 nano 上运行 16 次），并对每个产生的工件在留出的测试集上评估 16 次（Terminal-Bench 与 harness 方法为 8 次）。未进化的基线也以相同次数评估。我们把给定模型与基准上的某种方法或未进化基线称为一个配置（configuration）；这些实验合计 150 个配置、1,030 次独立进化运行和超过 210 万条测试轨迹。我们从同一工件重复评估之间的差异估计 σ，从不同运行产生的工件均值之间的差异估计 τ（附录 B.2）。

大多数方法差异都在单次运行的标准差之下。评估噪声的标准差 σ 在 SpreadsheetBench、OfficeQA 与 ALFWorld 上为 1.0 到 3.7 个百分点（pp），在 Terminal-Bench 上达到 4.5 pp，而运行间标准差 τ 从 0 到 12.3 pp。合计起来，一种只进化一次、评估一次的方法，其分数的标准差典型值为 1.7 到 4.1 pp（取每个基准各配置的中位数；每个配置的数值见表 6）。大多数方法差异都小于这一幅度：在同一模型与基准上超过 60% 的配置对中，其全运行均值之差低于单次运行比较的一个标准差（图 2a）。该结果逐方法成立：对每种方法，其比较中有 53% 到 79% 低于单次运行的一个标准差（附录 D.1）。

已报告的边际差异落在同一区间内。在九篇智能体进化论文主表中的 171 个基准–模型结果上，所提方法领先其最强竞争对手的幅度中位数为 3.4 pp，四分位距为 1.2 到 6.6 pp。这些结果无一报告方差估计，只有 6 个对超过一次进化运行取了平均。附录 D.3 列出所调查的结果。

**识别这样的边际需要很多次运行。** 在 80% 检验效能、α = 0.05 下识别真实边际 ∆，每种方法需要

```
N ≥ 2 · ( (z₁₋α/₂ + z₁₋β) / ∆ )² · (τ² + σ²)            (2)
```

次独立运行。（译注：原文此处公式排版无法完整提取，按符号说明重建。）按已报告的中位边际 3.4 pp 计算，这意味着在 SpreadsheetBench 上约需 5 次运行、OfficeQA 上 10 次、ALFWorld 上 19 次、Terminal-Bench 上 23 次（在下四分位边际下 Terminal-Bench 需 181 次）（图 2b）。单次运行无法对真实差异如此之小的方法排序：一张每种方法只跑一次的结果表，在 SpreadsheetBench、OfficeQA 与 ALFWorld 上只有 51% 到 73% 的时候能从四种文本工件方法中选中最好的那个，在评估噪声最大的 Terminal-Bench 上只有 33%；随机猜测是 25%。附录 D.2 给出完整分布与排名模拟。

### 4.2 大幅报告的增益来自评估捷径

第 4.1 节表明，典型的方法差异太小，当前评估无法识别。然而有些基准显示出 10 到 40 pp 的增益，远高于单次运行的分辨率——无论在原论文还是我们自己的运行中都是如此，例如 SpreadsheetBench 与 LiveMathematicianBench（附录 E.1）。这说明进化终究能找到大的改进。分辨率假设恰好预言了这种模式：只有当真实改进超过分辨率时，进化才能累积改进。评估捷径可以产生这样的改进：一种行为若能在基准的大多数任务上同时被评估奖励，就会产生大到即使带噪声的评估也能识别的增益。我们用两项测试审计十二个基准上已报告的最大增益（涉及三个模型）来检验这一预测（设计见附录 E）。

**一句话复现了增益。** 进化工件包含大量指令，因此巨大的增益可能来自许多改进，也可能只来自一个。为此，我们逐条指令审计随 GEPA 与 SkillOpt-Lite 发布的工件以及我们自己进化的工件（由一个 LLM 智能体标出候选指令，我们逐条手工核对），并把那条看起来最应为增益负责的规则单独追加到未进化的基线上。这一句话几乎达到了完整进化的效果（图 3a）：在 27 个已报告增益超过 3 pp 的模型–基准对上，它中位数恢复了 90% 的增益。这条规则通常利用了评估捷径：它适配了只认可一种答案格式的评分器，或适配了随某方法发布、偏离官方评估的基准版本（表 9）。附录 E.2 讨论例外情况。

**修复评估后增益消失。** 我们随后修复每处允许捷径的评估——恢复官方评估，或按含义而非表面形式给答案打分——并对同样的工件重新打分。增益中位数从 17.6 pp 降到 0.8 pp（图 3b），在若干基准上，修复后的基线几乎没有留下任何余量。在修复后的评估下重新运行文本工件方法并不能让增益回来（附录 E.3）。

这一对照支持我们的论点：当一个工件带来大到超过分辨率的改进时进化成功，而当只剩下细小的、任务特定的改进时进化失败。由此引出两个问题：这样的小改进究竟存在吗？如果存在，为什么选择机制没能接受它们？

## 5 候选层面的分辨率

一次进化运行内的进展取决于两个条件：提议必须提供真实的改进，选择必须识别出它们。我们在冻结的候选池上考察这两个条件（第 5.1 与 5.2 节），然后追踪选择误差在各轮之间的表现（第 5.3 节）。

### 5.1 有帮助的工件确实存在

**检验 P1。** 为了在选择机制过滤掉候选之前观察提议者产出什么，我们构建了提议池：由基于 SkillOpt-Lite 的提议者离线生成的 n=100 个候选技能，素材来自 10 个 Terminal-Bench v2.1 训练任务上的轨迹，并在 10 个不相交的测试任务上评估，每个技能–任务对 16 次独立 rollout（共 16,000 次 rollout；协议见附录 F.1）。

**更多候选带来真实增益。** 如果提议者写出 K 个候选技能，我们为每个任务保留最强的那个，任务性能会随 K 增长而真正提升吗？图 4a 中的实线追踪这一量，记作 Quality@K，定义为随机抽取的 K 个技能中最好者的期望成功率。在 2 小时执行预算下（蓝色实线），允许多步解决方案跑完，Quality@K 从 K=1 时的 49.2% 稳步攀升到 K=100 时的 61.8%。在 Terminal-Bench 更短的原始超时下（深灰实线），总体成功率起点更低（K=1 时 39.7%，因为慢轨迹被截断），但 Quality@K 仍升到 K=100 时的 51.6%。

由于对 K 个带噪声的分数取最大值即使在 100 个技能完全相同时也会使曲线上翘，图 4a 中每条实线都配有一条等质量虚线零假设——即当 100 个候选共享同一真实成功率并经过同一经验贝叶斯估计器时产生的曲线（附录 F.2）。实线与虚线之间的垂直间隙把真实的技能差异从抽样运气中分离出来。在两种超时制度下，观测曲线都在 K=5 时明显高于其虚线零假设，并在 K=100 时保持 +3.3 到 +3.4 pp 的领先（中间超时截断见附录 F.1）。因此生成更多候选确实会带来真正更强的技能，其增益与第 4.2 节修复后的方法边际相当。

**可共享的工件存在。** 虽然 Quality@K 允许每个任务挑选自己的最佳技能，单个技能也能同时提升全部 10 个测试任务的表现。对每个候选的全部 160 次测试取平均后，提议池中的单个技能跨度超过 15 个百分点：在 2 小时预算下，最强的共享技能（artifact-063）达到 57.5%，而池均值为 49.2%（+8.3 pp），最弱的技能为 41.9%；在原始超时下也有类似的 +8.4 pp 领先（48.1% 对 39.7%）。附录 I.1 考察我们候选池中有代表性的共享技能与任务特定技能，以展示这些改进在实践中是什么样子。

这样的候选池与「LLM 无法提出有效工件」的说法不一致。既然仅靠提议无法解释进化为何停滞，我们在第 5.2 节单独隔离选择环节。

### 5.2 选择无法识别它们

**检验 P2。** 由于候选池中包含有帮助的技能（第 5.1 节）而进化却未能累积它们，我们接下来单独考察选择步骤。我们构建了选择池：从 Terminal-Bench 与 DeepSWE 轨迹生成的 n=100 个技能，在跨五个难度级别的 11 个 Terminal-Bench 任务上评估（附录 F.1）。每个选择器只观察第一次 rollout（原生 SkillOpt-Lite 与 GEPA 选择观察两次），而真实技能质量在其余留出的 rollout 上测量（附录 F.3）。我们检验标准选择器挑选到更好技能的频率是否高于随机。

**在现实预算下，选择接近随机。** 基于执行分数的贪心接受/拒绝若有效，应当能以高可靠度接受改进、拒绝退化。表 1 与下文的秩相关在全部三个指标上都给出相反的结果。在两两比较中，基于执行的选择只有 49.7% 的时候偏好更好的工件，与随机选择达到的 50% 在统计上无法区分。退化工件占池的 30.5%，却占被接受候选的 62.1%，因此选择机制并未滤除退化；很宽的区间让人无法确定它是否比随机接受更差。单次执行分数与工件后验质量之间的秩相关为 0.054，基本为零。SkillOpt-Lite 与 GEPA 的原生父代选择算子（对每个工件观察两次 rollout 而非一次）达到 48.6% 的两两准确率。本研究中每一个基于执行的选择器在统计上都与随机选择无法区分。

**更多候选对任何选择器都没有帮助。** 图 4b 绘制了候选预算 K 从 1 增到 100 时所选技能相对基线的增益，在 11 个任务上取平均（各任务曲线见附录 F.4）。随着更好的技能进入样本，选择预言机（顶部的紫色曲线）随 K 稳步上升，而每个实用选择器都几乎持平在随机选择基线（灰色虚线）附近。即使检查完全部 100 个候选，也没有任何选择器恢复到预言机在 K < 5 个候选内就达到的质量。

**基于模型的裁判无法恢复识别。** 基于模型的裁判是恢复识别的自然候选，因为它们读取完整轨迹而非单一终态结果 [43, 45]。因此人们或许期望它们能把有帮助的工件与有害的工件区分开。表 1 表明这种额外证据并无帮助。没有哪个裁判表现出可靠的两两准确率。这可能是因为裁判能力有限，而其阅读噪声又独立于评估噪声；两者因此相互累积而非抵消，给评估过程引入了额外噪声。

这一失败在如此不同的选择器之间保持一致，支持了 P2：在现实预算下，标准选择机制无法识别有帮助的工件。附录 F.3 考察重复验证是否有帮助。

### 5.3 噪声跨轮累积

**检验 P3。** 第 5.2 节表明单个选择步骤的判别力处于随机水平。一次进化运行每一轮都会应用这样的步骤，因此相关的量是逐轮误差在多轮上的累积效应。

**环路内增益反映的是对噪声的利用。** 接近随机的选择意味着，一次运行在自己的验证分数中记录的大部分增益——它的环路内增益——应当在仔细重评估后消失。重评估正是如此。我们在同一 Terminal-Bench 验证集上独立重评估八次 SkillOpt-Lite 与八次 GEPA 进化运行产生的每个工件，对每个工件–任务对做八次 rollout（进化时为一次；协议见附录 G）。环路内增益在进化过程中涨到 6.9 到 9.0 pp，而重评估后的增益保持在 +0.4 到 −3.2 pp 之间（图 5）。其机制来自接受规则：该规则把候选的噪声分数与当前工件的噪声分数相比，因而一轮又一轮地接受来自噪声分布上尾的幸运抽样 [3, 30]。环路内分数在这一过程中改善；智能体能力没有。

**运行间方差随轮次增长。** 逐轮的选择误差也把独立运行推开。所有运行都从同一个工件出发，因此 τ₀² = 0，而每一轮带噪声的选择都是工件空间中无引导随机游走的一步。到最后一轮，校正后的运行间方差 τ̂t² 在方法–模型组之间达到 4.2 到 24.5 平方 pp（图 6；估计细节见附录 G）。同一方法的独立运行之间的差异，如今与文献中区分方法的边际一样大——这正是第 4 节记录的不稳定性。这些结果支持 P3：逐轮的选择误差跨轮累积，产生方法间排名不稳定性背后的运行间方差。

总之，让单个选择步骤无法识别改进的那个方差，正是跨轮累积后破坏方法间排名的同一个方差。

## 6 迈向更好的评估分辨率

由于低评估分辨率既限制候选选择（第 5 节）也限制方法比较（第 4 节），我们考察两种检测终端通过/失败分数所错过的改进的实用方法：候选层面更细粒度的行为检查，以及方法层面对提议者与选择器的分别评估。

**候选层面：更细粒度的反馈。** 终端通过/失败奖励可能掩盖特定智能体行为中的改进。一个有前景的方向是用中间行为的程序化检查来补充它们，例如对验证命令的未被掩盖的失败诊断，或智能体在编辑文件后是否运行测试。这类检查本身并不能修复选择，因为触发更多中间检查的工件未必解决更多任务。但它们是廉价的诊断：在初步分析（附录 H）中，未被掩盖的诊断检查率表现出比终端通过/失败判定低 13 倍到 57 倍的评估噪声（表 13），而且编辑后验证率能暴露终端判定所看不到的行为转变。

**方法层面：分组件评估。** 不要只通过嘈杂的端到端分数比较进化方法，我们主张分别评估它们的组件。对提议者，Quality@K 曲线衡量 K 个提议中最好候选的质量（第 5.1 节）；对选择器，所选工件质量曲线衡量随预算增长从固定候选池中恢复出的质量（第 5.2 节）。这些诊断不能取代端到端评估，但它们把一个低于分辨率的比较拆成两个超过分辨率的比较，从而揭示停滞究竟在提议还是在选择——即便方法层面的边际低于单次运行的分辨率。在报告层面，把评估噪声（σ̂）与运行间方差（τ̂）连同点分数一起发表，可以让读者直接判断所声称的边际是否超过评估的分辨率。

## 7 结论

我们提出一个假设：智能体进化的瓶颈不在于提出有帮助的工件，而在于识别它们。我们在使用评估分数的两个层面上都给出了证据：区分已发表方法的边际与单次运行的波动相当，因此单次运行的排名主要由噪声决定；有帮助的候选工件确实存在，但选择机制识别它们并不比随机更好，而这些误差累积成运行间方差。已报告的最大增益从反面印证了这一限制——它们利用评估捷径，一旦评估被修复就消失。

作为未来研究的一个有前景的方向，我们建议让评估具备分辨率感知：噪声更小的中间过程指标、面向提议者与选择器的分组件诊断，以及让读者能判断所声称的边际是否超过分辨率的方差报告。

## 局限

- **仅限冻结权重。** 我们研究的是模型权重保持冻结、进化只作用于外部状态（提示词、记忆、技能、harness）的智能体进化。通过强化学习更新模型权重的方法运行在不同的梯度动力学之下，可能面临不同的分辨率约束。

- **候选池范围。** 候选层面的证据只在 Terminal-Bench v2.1 上评估：第 5.1 节的提议池在 10 个不相交的测试任务上评估由 10 个 Terminal-Bench 训练任务提出的 n=100 个技能，第 5.2 节的选择池在 11 个任务上评估由 Terminal-Bench 与 DeepSWE 轨迹提出的 n=100 个技能，第 5.3 节的轨迹重评估覆盖两种方法与两个模型。结论是否适用于更大的池、不同的生成策略或其他基准领域，仍是开放问题。

- **模型强度与分辨率。** 我们的网格包含截至写作时最强的可用模型 Kimi-K3。我们不能排除未来显著更强的模型会表现出更低的评估噪声、从而具备更好的分辨率。在我们的网格中，评估噪声主要在强模型的成功率接近上限时缩小，例如 ALFWorld（附录 D.1），那里也几乎不剩余量（附录 E.4）；而在余量很大的 Terminal-Bench 上，三个模型的中位数都保持在 3.5 到 4.0 pp。

- **网格覆盖。** 七种方法、六个模型与四个智能体基准构成了一次广泛但不完备的调查。作用于根本不同工件表示的方法，或任务结构差异很大的基准，可能表现出不同的方差特征。

- **超越智能体工件。** 程序进化（program evolution）进化的是求解任务的程序并对它做确定性打分，而不是智能体的提示词、记忆、技能或 harness 代码；它在 GPU kernel 优化 [4]、ARC-AGI-2 [23] 与 Atari 策略搜索 [14] 等领域已显示出稳步累积的增益。这一范式通过廉价的确定性代码并行重评估与更易得的程序–环境诊断，在结构上降低了评估噪声。我们的分析覆盖当前一代的文本工件与 harness 进化方法。因此，分辨率是否同样约束程序进化，是一个我们的框架可以处理、但我们的实验没有回答的开放问题。

## 附录 A 扩展相关工作

**进化持久化工件的方法。** 近来在不更新模型权重的前提下改进冻结 LLM 智能体的努力，沿两个维度组织：进化循环的宏观结构，以及被进化的对象。在结构维度上，方法包括对单个技能的顺序精化 [37]；对提示词种群或智能体档案的基于集合的进化 [2, 42]；以及基于记忆与手册的进化 [27, 40, 43]。在对象维度上，方法进化不可执行的文本工件，包括从轨迹中提炼的技能 [24]，或可执行的代码工件，包括工具与 harness 组件 [18, 42]。尽管结构多样，所有这类方法共享同一个循环：提议者产生候选工件，评估者给由此得到的智能体打分，选择器接受得分更高的候选。我们的分析适用于这一共享循环，我们识别出的约束跨表示成立。

**关于进化为何失败的分析。** 另一条平行的工作线索记录了进化智能体的脆弱性与其基准的不可靠性。Ye et al. [39] 识别出对运行方差与任务顺序的敏感性；Wang et al. [34] 强调匹配预算的基线与留出评估；Liu et al. [19] 发现跨进化轮次的稀疏、依赖反馈的增益。SkillsBench 测量人工整理技能在各种任务上的效果 [17]，后续分析则考察技能引发的失败 [7] 与失控技能累积造成的污染 [29]。SEAGym 与持续学习评估进一步把中间增益与迁移、退化和持续改进区分开 [33, 44]。

**选择的统计可靠性。** 带噪声的候选选择与最优臂识别 [12] 以及模型选择准则的过拟合 [3] 有关。不确定性感知的评估在深度强化学习中也已确立 [1]。PACE 直接研究重复带噪声比较下的错误接受，并提出一个随时有效的接受检验 [30]。我们的研究把评估噪声与跨进化运行的变化分开，并用候选池分别考察提议质量与选择可靠性。

## 附录 B 方差分解

### B.1 方差分解的推导

一个进化实验是一个两阶段抽样过程。第一阶段，一次进化运行产生工件 A，它从由方法随机性诱导的工件分布中抽出。第二阶段，对该工件进行评估，产生观测分数 Ŷ，其在给定 A 下的条件分布反映智能体执行的随机性，真实质量为 Y(A) = E[Ŷ | A]。

记 Ŷ = g(A, U)，其中 U 收集所有评估侧的随机性（实例抽样、解码随机性、环境随机性），且与 A 独立。由全方差公式（式 1）：

```
Var(Ŷ) = E_A[ Var(Ŷ | A) ] + Var_A[ E(Ŷ | A) ]        (3)
          └────── σ² ──────┘   └────── τ² ───────┘
```

（译注：原文此处公式排版无法完整提取，按符号说明重建。）

第一项 σ² 是「评估一个固定工件」的方差在各工件上的平均：即评估噪声的方差。第二项 τ² 是所产生工件的真实质量 Y(A) 在各进化运行之间的方差：即运行间方差。该分解是精确且穷尽的：观测分数的任何波动，要么来自对同一工件的不同评估，要么来自抽到了不同的工件。

### B.2 两个方差分量的估计量

对每个配置（方法、基准与模型），我们独立运行进化 R 次，并在测试集上对每个产生的工件评估 M 次，得到观测分数 Ŷ_rj，r = 1, …, R，j = 1, …, M。

**评估噪声。** 对固定工件 A_r，评估噪声的方差 Var(Ŷ | A_r) 用样本方差估计：

```
s_r² = 1/(M−1) · Σ_{j=1}^{M} ( Ŷ_rj − Ȳ_r )²            (4)
```

其中 Ȳ_r = (1/M) Σ_j Ŷ_rj 是其 M 次评估的均值，评估噪声分量由工件内方差的平均估计，σ̂² = (1/R) Σ_r s_r²；我们报告 σ̂ = (σ̂²)^{1/2}。（译注：原文此处公式排版无法完整提取，按符号说明重建。）

**运行间方差。** 工件均值 Ȳ_r 的方差为 τ² + σ²/M，其中 τ² = Var_A[E(Ŷ | A)]。随机效应方差分析的矩估计量去掉每个均值中残留的评估噪声：

```
τ̂² = 1/(R−1) · Σ_r ( Ȳ_r − Ȳ_·· )²  −  σ̂²/M            (5)
```

（译注：原文此处公式排版无法完整提取，按符号说明重建。）

σ̂² 与 τ̂² 都是无偏的。τ̂² 为负意味着工件均值之间的差异不比仅由评估噪声造成的差异更大；此时我们报告 τ̂ = 0，这发生在 117 个方法配置中的 9 个上。

**每个配置的设计。** 每个方法配置有 R = 8 次独立进化运行（文本工件方法在 GPT-5.4 nano 上为 R = 16）。一个配置的每个工件都以相同次数评估：SpreadsheetBench、OfficeQA 与 ALFWorld 上的文本工件方法为 M = 16，Terminal-Bench 与 harness 方法为 M = 8（后者的单条轨迹贵得多）。估计量在每个配置内部计算，因此上述无偏性在所有基准上都成立；较小的 M 只会让 σ̂ 与 τ̂ 的不确定性变宽。式 2 中所需运行数公式依赖 τ² + σ²，即单次运行评估一次的方差，因此不受 M 取值的影响。

### D.2 方法级比较所需重复次数

在置信度 1 − α、效能 1 − β 下识别两种方法之间差距 ∆ 所需的完整进化重复次数，由第 3 节的两个方差分量导出。两种方法各运行 N 次、每个工件评估 M 次时，所报告差异的方差为 2(τ² + σ²/M)/N，因此

```
N ≈ 2 (z₁₋α/₂ + z₁₋β)² (τ² + σ²/M) / ∆²                 (6)
```

表 7 用 α = 0.05、1 − β = 0.8、M = 1，并代入每个基准各配置的单次运行方差中位数，以及文献所报告边际的四分位数（附录 D.3）来实例化该式。重评估只压缩 σ²，而在四个基准中的三个上它是较大的分量：若每个工件多评估几次，中位边际将分别需要约 1、5、9 与 3 次运行，而不是 5、10、19 与 23 次，因此降低评估噪声直接降低识别边际的成本。

**单次运行的排名一致性。** 第 4.1 节还报告了单次运行正确排列四种文本工件方法的频率。对每个模型与基准，我们为每种方法均匀随机地抽一次进化运行和其工件的一次评估，按这些分数给方法排序，并把结果与它们在所有运行与评估上的均值排序比较。在每个模型与基准上抽样 20,000 次后，我们记录排名第一的方法与完整排名同均值一致的频率，并在模型上取平均。排名第一的方法在 SpreadsheetBench、OfficeQA、ALFWorld 与 Terminal-Bench 上分别有 67%、51%、73% 与 33% 的时候一致，完整排名分别有 33%、29%、24% 与 8% 的时候一致；对四种方法的随机排名，猜中第一名为 25%，完整排序为 1/24 ≈ 4%。

**如何读这些图。** 在图 3 中，每个点是一个模型–基准对，横轴是随方法发布之评估下的增益；QA 基准（†）为 OfficeQA、HotpotQA、SearchQA 与 DocVQA，数学基准（‡）为 AIME 2025、LiveMathematicianBench 与 LiveBench-Math。未发现捷径的基准没有修复后结果，只出现在面板 (a) 中，IFBench 除外——它也没有单规则结果。图 8 把图 3 展开为每个模型与基准一根柱子，表 11 给出两图背后的分数。在评估允许捷径之处，所报告的增益（灰色）与单规则基线（黑色刻度）相当，而在修复后评估下缩到接近零（绿色）。点线标出修复后的余量，即一百减去修复后基线：在若干基准上，所报告的增益超过这一余量，因此它不可能反映基准想要测量的能力上的增益。单规则测试并不能复现每一个增益；下文讨论例外。

**不来自捷径的增益。** 在 HoVer 上，其增益来自多跳检索策略，一句话只恢复了 GPT-5.4 nano 与 GPT-5.6 Luna 增益的 43% 与 41%。对 DeepSeek-V4-Flash，单条检索规则——点名那些页面仍缺失的实体——恢复了 91%，因此对这个模型而言，检索改进本身一句话就能装下。在 HotpotQA 上，5 到 8 pp 的增益在修复后仍然保留；它同样来自更好的检索（附录 E.4）。

**模型不遵守的规则。** 更常见的情况是增益确实来自捷径，但模型并不按一句话行事。在 DeepSeek-V4-Flash 的 ALFWorld 上，该规则只恢复 30% 的增益，因为模型不遵守该搜索流程，而更长的进化工件确实改变了它的行为。在 LiveMathematicianBench 上，有了该规则，模型在该选项正确的 4%、54% 与 27% 的题目上选择「更强结果」选项，而在使用进化技能时分别为 67%、86% 与 92%，因此该规则恢复 0% 到 51% 的增益，而修复后的增益对两者都保持在接近零。该技能与规则有四处不同：它给出理由，即具体选项「几乎总是被故意弱化表述」；除非能论证某个具体选项是精确的，否则它把「更强结果」选项设为默认；它列出该选项出现时的措辞；它在最终答案之前重复该指令。因此，进化不仅优化走哪条捷径，还优化如何陈述它，使模型真的去走。

**打分与进化工件不同的规则。** 在 GPT-5.6 Luna 的 AIME 2025 上，该规则得分高于进化工件（69.3 对 51.0）：两者都适配了只认可裸整数的解析器，但该规则去掉了更多解析器读不出的答案。在 SearchQA 上，该规则恢复 45% 到 78% 的增益，但在语义打分下，它使 GPT-5.4 nano 相对未进化的基线降低 2.0 pp：语义打分认可「George Calvert（第一代巴尔的摩勋爵）」这类留有余地的答案，而被要求只写最短片段的模型有时留下了错误的部分。

**没有单规则结果的基准。** IFBench 既无单规则结果也无修复后结果，原因有二。其已发布评估用代码检查每条指令，而只针对模型原始回答、更严格地给相同输出打分，会让增益变大而不是变小，因此我们没有发现可修复的捷径，也没有哪条评估要求是单条规则能陈述的。其增益本身也小，为 2.7 到 3.8 pp，与第 4.1 节测得的单次运行标准差相当，因此单条规则恢复的那部分增益无法解读。我们在图中保留 IFBench，作为「增益不来自捷径时剩下多少小改进」的例子。LiveBench-Math 没有单规则结果，因为其增益太小：在已发布评估下为 0.9、1.3 与 3.9 pp，只有最后一个的 95% 置信区间排除零，因此单条规则恢复的比例无法解读。

### E.3 在修复后评估下重新进化

**对已发布工件重新打分，** 留下了一个问题：如果从一开始就用修复后的评估，进化是否能找到自己的增益。因此我们重新运行进化，把修复后的评估用于训练反馈、验证与测试（表 12）。在 OfficeQA 与 SpreadsheetBench 上，重新进化的文本工件方法相对修复后基线最多增益 1.9 pp，例外是 SpreadsheetBench 上 DeepSeek-V4-Flash 的 SkillOpt-Lite（+5.8 pp），其工件避开了重算引擎不支持的电子表格函数。在这两个基准上，我们只用 DeepSeek-V4-Flash 与 GPT-5.6 Luna 重新进化 GEPA 与 SkillOpt-Lite，这已经表明已发布评估下的大增益不会回来。在 LiveMathematicianBench 上，泄露的选项只能在进化过程中被平衡，使其出现时有一半的时候正确（附录 E.5）；这把捷径减半而非消除。在完整的平衡测试集上，DeepSeek-V4-Flash 用 GEPA 增益 5.2 pp、用 SkillOpt-Lite 增益 3.8 pp，但这些增益完全来自包含该选项的题目，在不含该选项的题目上没有任何配置显著改善。HotpotQA 是例外：在两种评估下 GEPA 都改进了三个模型的检索（附录 E.4）。

### E.4 修复后的余量

修复评估也显示了一个基准给进化留下多少空间。我们没有审计的 Terminal-Bench 按其已发布评估纳入。

**不再测量其目标的基准。** 有两个基准，不具备其想要测试的能力也能拿到分数。

- **SearchQA：闭卷知识而非检索。** 该基准本意是测试根据检索到的搜索片段作答，但没有这些片段模型同样答得好。在语义打分下，移除所有片段把 GPT-5.4 nano 的分数从 84.2 改到 81.9、DeepSeek-V4-Flash 从 89.4 改到 90.2、GPT-5.6 Luna 从 89.8 改到 90.7。片段只在 1,400 道题中的 126 道上有帮助，这些题的片段来自题库网站且同时包含线索与答案。其余错误对模型说明不了什么：在 100 个残余错误中（由 LLM 归因并抽查核对），36 个源于错误或含糊的金标准答案，例如丢失了类别的 Jeopardy 线索，或者其实是可接受的答案。该基准甚至无法区分 DeepSeek-V4-Flash 与 GPT-5.6 Luna（−0.4 pp，95% CI [−1.5, 0.8]），已发布的技能最多增加 1.6 pp。
- **LiveMathematicianBench：某个选项永远正确。** 该基准把近期 arXiv 论文中的定理变成五选一题目，要求选出可证明的最强陈述。有些题目包含选项「其余选项中有一个是正确的，但可以证明一个更强的结果」。在已发布划分的 177 道题中，该选项出现在 85 道里，且在全部 85 道中都是正确答案；它出现在 106 道测试题中的 46 道。例如，有一道测试题出自定理：每个流可行、循环 5-边连通的三次带符号图都有一个处处非零的 6-流。定理本身不在选项中：一个选项把结论弱化为 Z6-流，两个把它强化为循环 4-边连通或 5-流，一个去掉流可行性，而正确答案是「更强结果」选项。一个总是选该选项的模型不读数学就能把全部 46 道此类测试题答对，而已发布技能的全部增益就来自这些题目。在不含该选项的 60 道测试题上，基线为 50–61，但没有任何工件在这些题上有改进；60 道题的置信区间约为 ±5 pp。

**余量很小。** 在若干基准上，一旦答案被正确打分，基线或基线加一句话已经接近满分，进化没什么可赚的了。

- **DocVQA。** 语义打分下基线达到 88–94，已发布的技能没有增加任何东西。

- **AIME 2025。** DeepSeek-V4-Flash 不经进化就解出 96.5% 的尝试。三个模型的修复后增益都在 2.5 pp 以内，与 30 题测试集的置信区间相当。

- **PUPA。** 进化工件在 DeepSeek-V4-Flash 与 GPT-5.6 Luna 上达到 96–97，基线加一句话也达到同一水平。

- **ALFWorld，仅对强模型。** Gemini-3.7-flash 是主网格之外的额外模型，起点为 96.3，我们四种文本工件方法中最好的达到 97.0。在 SkillOpt-Lite 论文 [31] 中，SkillOpt-Lite 与其最强竞争者在 GPT-5.4-mini、GPT-5.4 与 GPT-5.5 上都得 100.0，因此该基准对这些模型已无法再对方法排序。

**有余量但识别不出增益。** 在另一些基准上还剩很大空间，但进化得到的增益很小，或评估根本识别不出来。

- **Terminal-Bench。** 它留下的空间最大，对 DeepSeek-V4-Flash 为 28 pp、对 GPT-5.6 Luna 为 46 pp，然而最好的方法只增益 1.0 与 3.6 pp，低于单次运行的标准差（第 4.1 节）。

- **OfficeQA。** 在其官方评估下留下 35–39 pp，但已发布工件与重新进化的文本工件方法都没有增益，重新进化的 harness 方法最多增益 3.7 pp（表 12）。

- **LiveBench-Math。** 修复后留下 11–17 pp，然而修复后增益只有 0.2 到 1.3 pp。

- **IFBench。** 其 2.7–3.8 pp 的增益与其评估噪声同量级（附录 E.2）。

**有真实增益的余量。** 有三个基准保住了修复没有消除的增益，而且每一处都能说出来源。在 HotpotQA 上，GEPA 在语义打分下保住 5.5–7.6 pp，重新进化把增益追溯到检索：支持文章的召回率提高约 10 pp。在 SpreadsheetBench 上，5.7–6.7 pp 在 LibreOffice 重算后存活，但保住增益的重新进化工件是靠适配重算引擎做到的——写值并避开不支持的函数。在 HoVer 上，8–13 pp 的增益来自检索策略。这些就是第 5 节所考察的那类细小而具体的改进。

### E.5 审计的适用范围

审计检验已报告的最大增益是否需要不止一条规则；它并不表明进化工件中不含其他有价值的东西。由于我们是在检查工件之后写出每条规则的，该测试表明一条规则足以复现某个增益，而不表明该增益需要这条规则；而 HoVer 表明，当增益分散在若干策略上时该测试会失败。随 GEPA 发布的工件是为 GPT-4.1-mini 进化的，因此它们在我们模型上的增益小于原论文中的增益；因此我们在同一模型上比较已发布评估下的增益、单规则结果与修复后增益。最后，修复可能不完整。为了在 LiveMathematicianBench 上重新进化，我们平衡泄露的选项：在它正确的题目数量同样多的题目里，我们用它的文本替换一个错误选项，使其出现时只有一半的时候正确。一半仍然多于模型答对这些题的概率（DeepSeek-V4-Flash 约 34%），因此选择该选项仍然有利可图，而平衡只使其收益减半。因此我们只在不含该选项的题目上给能力打分。

### F.1.1 提示词与技能撰写协议

为了从训练轨迹生成 n=100 个互不相同的离线候选技能而不引入外部选择循环，提议者启动并行研究子智能体，检查训练语料中的失败机制，并用小型本地探针验证候选修复。下面是用于合成提议池中 n=100 个独立技能的研究与技能撰写提示词。

**研究与技能撰写指引**

你的目标是调查 workspace/.skillopt/corpus/ 中的训练语料，揭示任务成功与失败背后的具体机制，验证它们，并把它们转化为一百个完整、独立、可执行的技能，写入 workspace/artifacts/001/SKILL.md 到 workspace/artifacts/100/SKILL.md（各自附带 report.md），并以 workspace/report.md 中一份可审计的证据报告作为支撑。

没有固定的阅读配额、编辑上限或僵化的输出模板。只要证据支持，就在 workspace/ 中尽可能多地阅读、搜索、写脚本并运行小型可执行探针。

**1. 到哪里找：找到「错误承诺的时刻」**

因为训练池中的任务结果是不平衡的，不要简单地按任务名给失败运行分组。既要研究有失败的任务（把同一任务上的失败运行与通过运行对比，看清越过早期安装或启动崩溃之后的完整工作流），也要研究只通过或只失败的任务（提取通过的运行如何诊断并从中途障碍中恢复；若不存在通过的运行，就在 workspace/ 中使用本地探针）。重点盯住智能体锁死到有缺陷路径上的关键决策点：

- 状态与交付物生命周期：检查智能体是否在做安全备份之前就原地改动原始输入；是否把整个预算花在临时实验上、却没有在目标路径维护一个有效的可交付成果；是否在最终清理时意外撤销了可用状态并停掉了必需的服务。

- 未经验证的引用与循环自检：智能体常常相信一个有缺陷的自我测试——甚至更糟，修改一个正确的实现去迎合不准确的参照。检查智能体是否未先验证某个库辅助函数或参照脚本的隐含行为是否符合任务契约，就把它当作神谕；或者写了一个只是复用生成器自身假设与偏移量的检查器。

- 没有小探针就贸然扩容：检查智能体在哪里先跑昂贵的全规模运行，而不是先用一次微型运行验证接口、输出结构，以及运行时、内存或输出规模如何增长。

- 停在表面增益上：在优化或重建任务中，检查智能体在哪里满足于相对朴素基线或粗略近似的初步改进就停下，对照成功的运行如何使用具体诊断（性能剖析、执行计划、结构化解析器或定量残差）来定位并消除剩余瓶颈。

**2. 证据纪律：验证机制，不要只讲故事**

一次失败的运行和一个貌似合理的故事并不能确立因果，而通过运行自己的解释或代码注释只是一个假设。

- 检查中段日志（警惕输出截断）：你环境中的长命令输出会在中间被截断。绝不要假设一份宽泛的 dump 展示了完整轨迹。在把失败归因于下游可见性或配置之前，检查记录的中段，确认上游步骤（如编译、链接或安装）是否真的成功。

- 精确断言要算数：同一任务的重复运行不是相互独立的任务，同一个测试函数失败也不意味着以同样的原因失败。检查每次运行的实际验证器输出，以区分早期的格式或缺文件失败与下游的数值或行为失败。

- 用小探针验证技术性断言：通过运行中的智能体有时依赖侥幸的近似，或陈述不准确的公式、字节布局或 API 规则。在把某个具体数学公式、二进制或数据库记录格式、解析器行为或库规则写进技能之前，先在 workspace/ 中用小型可执行探针或对照本地文档验证它。

**3. 撰写 skill.md：具体行动，与训练字面量脱钩**

高层原则是给你（提议者）的研究视角，不是给求解者的成品指令。同时，过度拟合某一个训练问题表面细节的技能，会在相邻任务上无法触发。

- 剥离训练实例字面量，保留技术深度：绝不要把训练专属的文件名、JSON 字段名、样本 ID 或狭窄的单任务公式留在 skill.md 中作为触发条件或示例。把触发条件拓宽到一般技术场景（例如「损坏的数据库或文件恢复」而非只有「截断的文件」；「结构化序列或协议组装」而非某个具体的拼接公式），同时让具体的诊断命令、字节与格式规则、验证配方保持尖锐。
- 把原则变成决策点检查：为你写的每条工作流，给求解者一份完整、可执行的手册：
  1. 它何时触发、以及首先要保护或建立什么（例如，第一次接触工具之前先完整备份目录；用极小预算检查 schema 与内存增长；先保存一个初始可编译的基线交付物）。
  2. 如何校准参照检查：教求解者在信任任何第三方参照 API 作为神谕之前，先用一个极小的 2–3 元素手工核对输入验证它，并用独立解析器与端到端模拟验证结构化与复合输出（不要复用构建器的索引偏移量，也不要为了猜评分器行为而丢掉必需的协议前缀）。
  3. 如何诊断下一个瓶颈：给出具体的诊断回路（检查执行计划与性能剖析、在重算之前缩小候选集、用定量残差驱动重建，以及从全新客户端检查多组件服务链）。

**4. 输出与诚实的边界**

全部训练证据以只读方式挂载在 workspace/.skillopt/corpus/（可选辅助工具见 corpus/README.md）。用 workspace/ 放你自己的脚本、笔记与可执行探针。不要检索外部基准解答或测试集材料。

- 恰好保存一百个完整独立的技能到上述工件路径，每个都不含训练任务名、样本 ID 与任务本地的字面常量。
- 在 workspace/report.md 中保存一份简洁、可审计的报告，追踪从「你读了什么 → 你用探针验证了什么 → 你把什么写进技能 → 还剩哪些反例或开放缺口」的链条，并引用确切的消息 ID、行范围与验证器断言。

### F.2 Quality@K 的后验估计

每个工件的逐任务质量是一个潜在成功概率，通过少量二值评估被观测到（附录 F.1）。原始成功计数的噪声太大，无法可靠地给单个工件排序，因此我们用经验贝叶斯层级模型做正则化，并定义两个互补的估计量。

**层级模型。** 记 n 为池大小，s_i 与 n_i 为工件 i 在给定任务上的成功次数与总评估次数，θ_i ∈ [0, 1] 为其潜在成功概率。全部 n 个工件共享任务特定的 Beta 先验 θ_i ∼ Beta(a, b)，其均值 µ = a/(a+b) 与集中度 κ = a+b 由合并结果的跨工件矩方法估计。在我们的主估计器中，κ 限制在 [0.25, κmax]，κmax = 100（已是每技能 rollout 预算 m=16 的 6 倍以上）：只要跨工件样本方差不超过纯二项抽样噪声，κ̂ 就饱和在 κmax，而不是确定性地坍缩为零宽度的点质量。对任何有限的 κ，每个工件的后验为 θ_i | s_i, n_i ∼ Beta(a+s_i, b+n_i−s_i)，后验均值 θ̄_i = (a+s_i)/(a+b+n_i)。我们在观测池与模拟的等质量零假设池上以完全相同的方式评估这个 κmax = 100 的矩估计器，并在下文检验 κmax ∈ {30, 100, 300, ∞} 的敏感性。

**后验预言机。** Quality@K 问的是：如果从池中均匀抽取 K 个工件，最好的那个有多好？记 I_K 为 n 个工件（不含基线）上均匀随机的大小为 K 的子集。后验预言机在整个后验上对这一量积分：

```
Quality@K_Oracle = 100 · E_{θ|D} [ E_{I_K} [ max_{i∈I_K} θ_i ] ]   (7)
```

（译注：原文此处公式排版无法完整提取，按符号说明重建。）

我们用 8,000 次后验抽样近似外层期望（每个零假设数据集内部每次模拟 256 次抽样）。在每次抽样内，内层期望是精确的：把 n 个抽到的质量按升序排序后，排名为 r 的工件以 C(r−1, K−1)/C(n, K) 的权重贡献（r ≥ K）。曲线给出抽样均值；阴影表示在拟合超参数条件下逐点的 95% 可信区间。（译注：原文此处二项系数排版无法完整提取，按上下文符号说明重建。）

**对 κmax 的敏感性。** 图 11 在 κmax ∈ {30, 100, 300, ∞} 上检验提议池 2 小时 Quality@K 曲线的敏感性。像 κmax = 30 这样过紧的上界，即使等质量零假设没有表现出任何过度离散，也会迫使先验显著离散，把 2 小时匹配零假设在 K=100 处抬到 64.28%，使 +2.20 pp 的超出量落在重叠区间之内。在 κmax = 100 时，2 小时曲线达到 61.77% 对 58.36% 的零假设（+3.41 pp，从 K ≥ 4 起清晰分离），把 κmax 进一步放宽到 300 或 ∞ 会平滑地把超出量扩大到 +4.75 pp（K ≥ 3）与 +6.42 pp（K ≥ 2）。重要的是，κmax = 100 处的有限正则化避免了 κmax = ∞ 下出现的一种微妙的点质量退化：在样本方差恰好低于二项下限的近似同质任务上（如 dna-assembly 或 mailman），κmax = ∞ 会把观测先验坍缩成 δµ（一条平曲线），而大约一半的纯二项零假设模拟恰好抽到正的有限样本过度离散与有限的 κ̂，在逐任务视图中把模拟零假设均值略微推到坍缩的观测曲线之上。把 κmax 限制在 100 使类零假设任务保持在其匹配零假设区间中心，同时每个 κmax ≥ 100 都确认同一个「余量为正」的结论。

**等质量零假设。** 即使所有工件一样好，两个估计器也会随 K 上升，因为在更多候选中挑最幸运的那个会得到更高的期望分数。为校准这一统计选择效应，我们对每个任务运行 1,000 次零假设模拟：全部 n 个候选按任务级合并通过率独立同分布生成，并在每个模拟池上重新拟合同一个估计器（先验拟合与后验 Quality@K）。每个估计器有自己的零假设曲线（图 4a、9 与 11 中的虚线）。零假设区间描述的是等质量数据集之间模拟变异的中央 95%，而非后验不确定性。

**适用范围。** Quality@K 刻画的是 n=100 个候选的有限池，而非理论上的任务最优；跨任务平均允许每个任务选择不同的技能。对选择池（第 5.2 节），质量真值使用与每个选择器所观察 rollout 独立的留出 rollout 参照（附录 F.3）。

### F.3 选择算子与评估指标

**独立参照协议。** 每个选择器只看到每个工件的第一次 rollout（表 1 中原生 SkillOpt-Lite 与 GEPA 行看到前两次）。工件质量对照由选择器未观察到的其余 rollout 构成的留出参照评估；基线参照同样排除其前两次 rollout。这一分离确保用于评估选择器的质量真值与它们可得的信息无关。工件质量后验按附录 F.2 所述拟合到这一留出证据上。所有选择器共享同一批后验抽样，因此所选质量在同一抽样下从不大于预言机，且所有方法在 K=1 处重合。

**原生父代选择消融。** SkillOpt-Lite 与 GEPA 行（表 1 中标 †）把各自方法的接受/拒绝逻辑应用于前两次 rollout 结果。SkillOpt-Lite 只有在两次 rollout 均值严格改进时才替换当前工件；GEPA 应用其前沿剪枝例程，并按存活频率的比例采样父代。这些行使用与其他选择器相同的留出质量参照。

**轨迹裁判。** DeepSeek-V4-Flash 在 Terminal-Bench 子集的 1,111 个工件–任务对（含基线）上担任裁判模型。每次调用收到任务描述、初始技能上下文以及第一次 rollout 的求解器轨迹，不带结果标签。逐点打分为每对产生一个分数（1,111 次调用）。两两打分对 1,100 个固定对按两种呈现顺序各评估一次（2,200 次调用）。LLM 裁判（ACE）条件沿用 ACE Reflector 的无真值模板（错误识别、根因、纠正方法，以及有益、有害、中性标签），并加上一个显式成功概率分数。不使用任何 ACE 训练循环或验证器反馈。

**报告指标。** 两两准确率：选择器所选工件具有更高潜在质量的后验概率，平局均匀打破。错误接受：在被接受的基线替换中，质量低于基线的后验比例。改进与退化率：所选工件质量超过或低于基线的后验概率。Spearman 相关在任务内计算；选择器分数恒定的任务被排除。

**更高分辨率的选择能让进化变好吗？** 我们的结果引出一个自然的问题：如果我们在进化的每个选择步骤上通过平均多次验证 rollout 来降低评估噪声，进化会累积更大的增益吗？为直接检验这一点，我们运行 SkillOpt-Lite 最多八轮、共 16 次独立进化运行，对每个候选平均 16 次验证 rollout 而非一次（并用每任务 32 次独立测试 rollout 评估最终工件）。平均 16 次验证 rollout 把各运行的平均最终测试分数从 61.4% 提到 64.4%，把最好进化工件的测试分数从 64.8% 提到 72.7%。检查轨迹可以说明原因：在单次 rollout 验证下，一个普通候选偶尔靠运气抽到异常高的验证分数（例如 80%）并成为在位者；后续候选无法超过这个被抬高的阈值，使进化在四轮内停滞。平均 16 次 rollout 抑制了这些假峰，使被接受的更新反映真实改进，让最好的进化工件随着更多运行的启动而持续改进。与此同时，16 倍 rollout 的验证在计算上非常昂贵，并且一旦发现强力在位者就让贪心接受更保守，这促使人们转向第 6 节探索的更廉价、更细粒度的行为诊断。

### I.1 候选池中的可共享工件

第 5.1 节表明，即使单个技能被跨任务共享，候选技能之间也有实质差异。为说明有效的共享技能与任务特定技能在实践中是什么样子，本附录印出选择池（附录 F.1）中的三个具体技能：seed-027 与 seed-099，在全部 11 个 Terminal-Bench v2.1 任务上并列最佳平均增益（比基线 +11.4 pp），以及 seed-058——它在 mteb-retrieve 的每次 rollout 上都拿到满分，但全局共享时几乎不增加什么。

#### I.1.1 工件 seed-027（最佳平均增益，+11.4 pp）

**软件工程技能**

- 改代码之前先读任务与相关源码。

- 在实现所要求的公共 API 的同时保持既有行为。

- 在受影响的模块之间做出协调一致的实现。

- 用有针对性的测试验证正常行为与边界情况。

- 把提示词中每条精确的校验、解析、错误、导出与格式规则都当作显式断言。

- 运行相关的既有测试并处理回归。

**智能体陷阱：** 用惯用的库名、约定俗成的类名或泛化的「合理」签名，去替换任务中明确点名的那个确切导出符号、函数签名、返回结构或错误信息字符串。

**触发条件：** 提示词给出一个逐字的公共标识符（类、函数、入口点）或一段字面的错误与状态文本，隐藏的调用方或断言会去匹配它，而智能体却发明了一个带库风格的替代品，例如生成出来的 servicer 类名。

**具体纠正：** 编码之前，从任务中提取每一个逐字标识符、签名、空值与零值返回规则、错误片段；在公共界面与错误路径上导出并引用那些确切字符串，并加一条有针对性的检查，断言每个被点名的符号与信息都以完全相同的拼写存在。

**微型验证：** 对一个导出 Mean(xs []int) (float64, error)、且空切片必须返回 (0, nil) 的规范，暴露的应当恰好是 Mean（而不是 computeMean），返回文档所写的 (0, nil) 而非 (-1, err)，然后用一次空输入调用确认。

**智能体陷阱：** 手工即兴编写分词或嵌入调用（自定义分隔符、切换 special-token 标志，或把同一个泛化的任务与提示词名同时用于查询和语料），而不是交给指定的模型或包及其文档化的编码约定。

**触发条件：** 一个数据任务点名了某个特定的分词器、嵌入模型或包，并要求一个由该模型自身编码行为导出的精确数值计数或排名。

**具体纠正：** 只通过指定的包或入口点加载模型，让它既分词又编码每一个输入；当封装层区分查询与段落、或暴露 special-token 与 clip 参数时，按侧显式设置这些参数而不是传一个默认值，并把计数或排名再算一遍以确认稳定。

**微型验证：** 在指定分词器的文档默认值下，用 "\n" 与 " " 连接的两个短字符串应当分词出相同的总长度；断言改变分隔符或查询与段落提示词标志会改变结果，然后保留文档默认值，使最终数字与评分器一致。

#### I.1.2 工件 seed-099（并列最佳，+11.4 pp）

**软件工程技能**

- 改代码之前先读任务与相关源码。

- 在实现所要求的公共 API 的同时保持既有行为。

- 在受影响的模块之间做出协调一致的实现。

- 用有针对性的测试验证正常行为与边界情况。

- 把提示词中每条精确的校验、解析、错误、导出与格式规则都当作显式断言。

**智能体陷阱：** 假设第三方文本流水线（分词计数、嵌入相似度排名、检索到的文档）产出的精确、机器核对的数值结果与输入文本的组装方式无关，于是用任意分隔符连接源字段，或用同一个默认提示词设置同时编码查询与参照集合。

**触发条件：** 一个脚本必须输出一个由文本送入编码器导出的确切数字，而它通过拼接若干源字段来构造这段文本，或者它对一个探针查询和一个文档语料只调用一次编码。

**具体纠正：** 精确复现源数据形态：用语料中相同的边界字符连接字段（换行而非空格，可能让计数差一个或更多），当编码器封装层具备指令感知时，对探针用查询提示词类型调用一次、对文档用段落提示词类型调用一次，使每一侧都收到它真正的指令前缀。

**微型验证：** 不要求 len(encode("a\nb")) 等于 len(encode("a b"))，同一段文本在查询提示词下与段落提示词下的嵌入也不同，因此选错角色可能把另一篇文档挤到第 5 名。

**智能体陷阱：** 重命名或重新包装提示词中明确点名的确切公共符号（类、函数或变量），换成一个更符合惯用法、更具描述性的名字，假定检查器会调用智能体自己选择定义的任何东西。

**触发条件：** 任务文本以固定措辞点名一个可导入的入口点，例如「在一个叫 X 的类中」「暴露 BeginRepl(args, version)」，或一个具名 API 变量，而智能体却交付了一个不同名字的实现。

**具体纠正：** 把提示词点名的符号按原样（确切的名字与签名）声明为一个薄的导出垫片，把真实工作委托给内部辅助函数；把任何重命名都当作破坏契约，因为被评分的 harness 导入并调用的是字面名字，不是转述。

**微型验证：** 若规范要求 class Server，harness 做的就是 from module import Server；一个以 Servicer 之类名字交付的类不会被该导入触及，即使手工运行正确也会失败。

#### I.1.3 工件 seed-058（mteb-retrieve 上最佳）

**软件工程技能**

- 改代码之前先读任务与相关源码。

- 在实现所要求的公共 API 的同时保持既有行为。

- 在受影响的模块之间做出协调一致的实现。

- 用有针对性的测试验证正常行为与边界情况。

- 把提示词中每条精确的校验、解析、错误、导出与格式规则都当作显式断言。

**智能体陷阱：** 在把文本送入外部 AI 库的子词分词器或检索编码器时，智能体猜了组装后的文本形态（用空格或什么都不加来连接相关字段）、猜了 special-token 标志，也猜了按角色的提示词，而不是去读文档化的契约。

**触发条件：** 某个计数或检索结果对确切文本如何组装、以及套用哪个提示词敏感：用空格还是换行连接两个文本字段、一个猜出来的 special-token 设置，或在任务感知编码器会区分查询与文档时用同一提示词编码两者，都可能移动计数或改变哪篇文档排第 N。

**具体纠正：** 编码之前查源码或包的文档，确认确切的文本格式与提示词角色。用文档规定的分隔符连接独立文本字段（BPE 分词器会把前导空格并入后一个子词，因此换行可避免跨字段合并），并有意识地设置分词器的 special-token 标志。对检索编码器，用查询提示词编码查询、用段落提示词编码文档（例如 prompt_type 或 role 参数），绝不对两者共用一个默认值。

**微型验证：** 对 BPE 分词器，"a" + " " + "b" 的分词数与 "a" + "\n" + "b" 不同；用查询提示词与段落提示词分别嵌入查询，会改变哪篇文档的余弦相似度排第 N。

**智能体陷阱：** 智能体把所要求的行为实现在一个符合惯用命名的类、函数或注册表键之后，而不是任务所声明的确切公共标识符与签名，于是代码在它自己的测试下能构建能运行，检查器却根本走不到它。

**触发条件：** 一个隐藏的检查器导入或实例化某个文档化的标识符（服务类名、包函数、模块注册表键），或以给定签名调用某个文档化的公共入口点；任何名字不同或签名不同的变体对它都不可见，即使该变体在孤立情形下行为正确。

**具体纠正：** 写代码之前，列出提示词点名的确切公共标识符——类名、函数名、完整参数列表与返回类型、注册表键——并精确地命名这些工件；保持既有公共入口点与签名不变，在它们周围新增内部实现，而不是重命名可触达的界面。

**微型验证：** from module import ExactName 只有当该类或函数字面上就叫 ExactName 时才会解析成功；一个继承了预期类型的 NearbyName 类，不会被查找 ExactName 的导入方找到。
